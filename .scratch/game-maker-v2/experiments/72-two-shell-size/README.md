## 回答的两件事（票 72 Q3 = (a) 逐字要的）

### ① 今天无头 Chrome 里 `canNine` 的实际值 = **`false`（Canvas 回退）**

两个壳**自己报了那句话**（`scene.ts` 与 `td/scene.ts` 各一处，条件是 `s9 && !canNine`）：

```text
[warning] hud.panel: 这个渲染器不支持九宫格（Phaser 的 nineslice 仅 WebGL）—— 面板退回普通拉伸   ← 横版
[warning] hud.panel: 这个渲染器不支持九宫格（Canvas 回退）—— 面板退回普通拉伸                 ← 塔防
```

⚠️ **`getContext` 请求过的类型列表不是判据** —— 实测是 `["webgl","experimental-webgl","2d"]`：
Phaser 的设备探测会**试探** webgl，与最终选哪个渲染器无关。权威信号是外壳自己那句话
（外加：全部绘制都走了 2D 上下文）。

### ② 塔防 `hud.start` 的**实际渲染宽度 = 44.5**，而它声明的是 **28**

方法：探针在**外壳之前**注入钩子，记下每一次 `CanvasRenderingContext2D.drawImage`
的**目标 canvas · 变换矩阵 · 源矩形 · 局部目标矩形**。Phaser 的 Canvas 渲染器是
`ctx.translate(...)` + `ctx.scale(...)` 落位、再在 `(0,0)` 画 —— 所以**渲染尺寸 = 局部宽 × scaleX**。

```text
[at(0,0)   scale(5, 1.1538)] src (0,0) 96×26  ⇒ 画出来 482.50×30.58   ← hud.panel：声明 480×30 **作数**（对照）
[at(300,4) scale(1, 1)     ] src (0,26) 44×22 ⇒ 画出来 44.50×22.50   ← hud.buttons[0]（声明 44 == 包 44）
[at(348,4) scale(1, 1)     ] src (0,26) 44×22 ⇒ 画出来 44.50×22.50   ← hud.buttons[1]
[at(396,4) scale(1, 1)     ] src (0,26) 44×22 ⇒ 画出来 44.50×22.50   ← hud.buttons[2]
[at(444,4) scale(1, 1)     ] src (0,26) 44×22 ⇒ 画出来 44.50×22.50   ← ⚠️ **hud.start：声明 28×22**
```

⇒ ⭐ **同一个资产 `ui-btn`、同一张图集、同一帧里，四格的画法完全一样** ——
`hud.start` 的 `scale(1,1)` 说明**没有任何拉伸**，它画的是**包里的原生 44×22**，
而配置声明的是 **28×22**。从 `x=444` 起画到 `488.5`，而**视口只有 480 宽** ⇒ 右边缘出屏。

⚠️ **对照组是同一帧里的 `hud.panel`**：`scale(5, 1.1538)` 正是 `setDisplaySize(480, 30)`
打在 96×26 上的结果（480/96 = 5 · 30/26 = 1.153846…）⇒ **塔防那条拉伸路本身是好的**，
有问题的是 `hud.buttons` / `hud.start` 走的那条（`img()`）。

### ③ 顺带量到的横版那一格（同一次跑）

```text
[at(8,262) scale(1,1)] atlas 72×44 src (0,0) 72×32 ⇒ 画出来 72.00×32.00   ← 横版 hud.panel
```

`hud-lost-slots` 声明 **72×32**、包里也是 **72×32** ⇒ 画出来正好一致
⇒ **横版那条「画原生像素」的路今天一处也看不出错**（潜伏，不是活的）。

## ⚠️ 探针自己的两条坑（照实记，免得下一个人重踩）

1. **`--virtual-time-budget` 下 rAF 跑几帧是飘的** —— 同一个页面，一跑记到 **605** 条
   `drawImage`，另一跑只有 **2** 条（一帧都没渲染）。⇒ 探针改成**持续快照、取最富的一帧**
   并最多重试 6 次。⚠️ **重试是为了拿到「一帧真渲染」，不是「重试到绿」。**
2. **`drawImage` 的 9 参形式是 `(img, sx, sy, sw, sh, dx, dy, dw, dh)`** —— 第一版把
   `sx/sy` 与 `dx/dy` 写反了，读数看着像「所有精灵都画在 (0,0)」。⚠️ 而且**去重键必须带上
   变换矩阵**，否则四个按钮塌成一条。

## 施工之后（2026-10-15 · 票 72 的两处已落地）

按裁定改了两处：横版 `scene.ts` 普通 image 那一支补 `setDisplaySize(p.w, p.h)` ·
塔防 `img()` 真图那一支补 `setDisplaySize(w, h)`。重跑本探针 ⇒

```text
[at(444,4) scale(0.6364, 1)] src (0,26) 44×22 ⇒ 画出来 28.32×22.50   ← hud.start：**28 作数了**
                                                       （多出的 0.32 是像素对齐的半像素外扩 × 0.6364）
```

`node diff-before-after.mjs` —— **塔防 605 → 605 条，只变了那一行**：

```text
前 605 条 · 后 605 条 · 消失 1 · 新增 1
  消失： 图集 96×48 src(0,26) 44×22 · at(444,4) scale(1,1)      ⇒ 画出来 44.50×22.50
  新增： 图集 96×48 src(0,26) 44×22 · at(444,4) scale(0.6364,1) ⇒ 画出来 28.32×22.50
```

⇒ ⭐ **`img()` 那一句对其余四个调用者（砖 · 核心 · 插槽 · 场地）是空操作，这是量出来的、不是预期的**
—— 605 条里没有第二条动过。横版那一侧 `hud.panel` 前后都是 `scale(1,1) ⇒ 72.00×32.00`（同样的空操作），
`消失 0`；另两条「新增」是**另一帧里实体位置不同**造成的采样噪声，不是行为变化。

`zoom-td-start.png` 是施工后重拍的：`开波` 那一格现在**收在 472**（= 444 + 28），
右边是面板底色，**不再被画布边缘裁掉**。
