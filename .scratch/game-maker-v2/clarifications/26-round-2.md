## 0.1 · 第 1 轮裁定之后新量到的两条事实

**① 理解层本来就通吃 N 张 —— 拦住它的只有一行 throw。**

```ts
// packages/vision/src/analyze-reference.ts:168-178
function imageBlocks(refs: StyleReference[], cwd: string): Record<string, unknown>[] {
  return refs.map((r) => { … });        // ← 本来就是 N 张通吃
}
// :242   content: [...imageBlocks(styleReferences, cwd), { type: "text", text: visionPrompt(…) }]
// :154   if (r.data.length === 0) throw …（空图，第一阶段恰好要 1 张）
// :155   if (r.data.length > 1)    throw …（**唯一**拦住 N 张的地方）
```

⇒ **要多图进理解层，删掉的正是那一个 `> 1` 的 throw** —— 装图、喂模型、收结果那条路**本来就写好了**。

**② 生图层恰好一个风格槽，喂的是原图 —— 下游今天就已经「只认第一张」。**

```ts
// packages/assets/src/pack.ts:592   const styleReference = recipe.referenceImage …（世界风格图）
// packages/assets/src/pack.ts:445   …(masterStyleRef ? { styleReference: masterStyleRef } : {})
// packages/assets/src/pack.ts:663   …(styleReference ? { styleReference } : {}), …(reference ? { reference } : {})
//   ⇒ 母版那一发与**每一个**资产那一发，都拿到同一张风格图
// packages/assets/src/ops.ts:232-241  const src = …refs[0]!.path      ← 复制成 reference.png 的是**第 1 张**
// packages/pipeline/src/create-game.ts:246  styleIdOf(input.styleReferences[0]!.path)   ← style-id 也只取第 1 张
```
而那个槽位的语义是**写死**的（`image-gen.ts:63` · `:305-307`）：Gemini 的提示词里
「附件第 1 张是风格参考图 / 附件第 `${styleReference ? 2 : 1}` 张是照画的角色」是**三目写死的**。

⇒ **一句话**：**理解层已经准备好了，生图层只有一个槽。**

❓ **Q1** - **融合发生在哪一层？**（票面 §2 那一问，也是本票的承重墙）

今天那张风格图**干两件事**：① 被**理解层读**，作者那份 `style.palette` + 风格描述；
② **原图**被塞进**每一次生图调用**（母版 + 每个资产）。

- **(甲) 融合在理解层 · 下游永远只看到一张**
  N 张全进 `analyze-reference` 那**一次**调用（§0.1① 说那条路本来就通吃），产出**一份** `style`。
  下游那张「风格图」有两种给法：
  - **甲① 下游仍然拿原图**：从 N 张里**取第 1 张**当锚图 —— ⚠️ 那正是**今天代码的行为**（`ops.ts:232` / `create-game.ts:246` 都取 `[0]`），
    ⇒ **实现 = 删掉那一个 throw**，下游**一个字不改**。
  - **甲② 下游不再拿原图**：`styleReference` 那个槽只带 palette / 描述文本 ⇒ 动的是 `pack` 那条路。
  - **打架了怎么办**：由那**一次**调用自己消化（第 3 轮再定「要不要另立规则」）。
- **(乙) N 张都进生图**：生图调用带 N 张附件。
  ⇒ 单槽要变 N 槽；**每个协议各改各的**（Gemini 的三目编号要泛化；OpenAI 的 multipart 本来就是通用的；
  ⚠️ **DashScope 今天在「有参考图」时就已经出局**（`ops.ts:1116-1126` 预检拒）—— 所以它**不新增加**一个出局者，
  只是把「一张」变成「N 张」；**minimax 没有客户端**）。
- **(丙) 并置**：理解层融合**一份**（甲），**并且**原图最多 K 张也进生图（乙）。⇒ 两套机制的代价都要付。

➡️ **推荐 甲①**。理由三条：
1. **它几乎是零改动** —— §0.1 那两条加起来就是「删一个 throw，下游不动」；
2. **融合只发生在一处**（一次调用），而 (乙) 是**每条协议各解一次**冲突（而且解不了）；
3. 它把「谁说了算」变成一个**问不出来的问题**（下游只有一份产物）—— 而那正是 (A) 语义下**对的**形状。

⚠️ **甲① 的代价，说清楚**：下游仍然只带**第 1 张原图**，⇒ **融合只发生在 palette 与描述那一层，像素层没有融合**
（第 2、3 张图对最终画面**没有直接影响**）。你要「像素层融合」，就得走 (乙)/(丙)。

⚠️ **另有一支我没列进上面**：**(丁) 融合不进本票** —— 第一阶段维持 N>1 就拒，本票只把**契约与边界**说清。
若你选它，请顺带说一句「第 3 轮还要不要问」。

❓ **Q2** - **那条待办、和将来那张施工票 —— 住哪？**

你在第 1 轮的 Q3 裁定里说「本轮只形成待办」。待办需要一个**落点**，而这里有两条**不同**的路：

- **(i) 决定**（`role` 的去留 · 融合在哪一层 · 仲裁规则 —— 即本票的 `## Answer`）：**在范围内**。
  它改的是**链上那份契约**（`VisualWorldSpec.styleReferences`），而契约是链上的东西。✅ 留本图。
- **(ii) 实现**（改 `>1` 那个 throw / 提检查到调用方 / 带 N 张进生图）：⚠️ **这才是要认真看的一处。**
  本图的**终点**是「一条命令跑完整条链，并在 fixture 上**真跑通一次**」，而终点的入口写的是
  **`--style <风格参考图>`**（**单数**）；`maxItems === 1` **就足以跑通终点**。
  ⇒ **多图实现不在通往终点的任何一步上。**

- **(a) 在本图开一张施工票**（挂成本图子票，等实现时做）。
- **(b) 进本图的 `## Out of scope`** —— 一行说清「多图实现越过终点」，并在**票 26 的 Answer 里留指针**。
  ⇒ 与本图已有的先例同款：**塔防进新链** · **`visual-memory` 包** · **`Material DNA`** · **打分体系**
  —— 都是「穿过终点的活，从这里毕业、不在这里做」。
- **(c) 先不定**，等 `role` 与融合都裁完再说。

➡️ **推荐 (b)** —— 理由：本图终点要的是**一条能跑通的链**，不是**一条功能齐全的链**；
把多图的实现挂在终点**之外**，与「塔防不进新链」用的是同一条界线。
⚠️ 而那句「R18 写着『实现延后**并开票**（见票 26）』」**不冲突** —— 票 26 就是这张票，
它出的是**决定**；决定之后的实现**住到别处去**，正是你这轮 Q2 裁定说的「另开施工票」。
⚠️ 若你选 (a)，请说一句要不要**同时**在票里写「它挡不挡终点」（挡的话，本图就必须先做它）。
