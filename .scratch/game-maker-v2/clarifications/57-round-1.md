## 一、根问题

### ❓ Q1 — 它到底有没有一个**点得出来的落点**？

票 45 的 Q2 裁定原话是「前者**有明确的潜在生产场景**，不能仅凭当前零生产者就删除」。
⚠️ **但那个场景在票 45 里从没被点名** —— 本票就是来点它的。

我把**仓库里能落的位**逐一扫了，候选只有五个，**没有一个站得住**：

| | 候选落点 | 今天是什么样 |
|---|---|---|
| **L1** | `source.kind: "import"` 的 `ref` 指进仓库 | ⚠️ **已经在跑** —— `fixtures/recipes/*.json` 里就有一条 `"ref": "../reference/test.png"`（= `fixtures/reference/test.png`，**仓库内置**），而它**诚实地标着 `imported`** |
| **L2** | 新开一个 `source.kind: "fixture"` | `ImportSource` **已经收一个路径**；再开一个同形的 kind = **一个形状两种名字**。而 `AssetSource` 的判别式自己写着它回答的是「**创作态是哪一种**」（`recipe.ts:40`）——「这图是仓库里的还是人这次给的」**不是创作态** |
| **L3** | `AssetRecipe.authoring[]`（票 04 的母版） | **结构上够不着**：母版**不进交付包**（票 04 Q1/Q2 就是为这个做的独立数组）⇒ 它**永远不会**有一个 `origin` |
| **L4** | 不经配方的包装配 | 那种包的身份来自**它自己的 manifest**，`pack` 不再是写入侧 ⇒ **不产生**新的 `fixture` |
| **L5** | 母版那条路（`ImageSource.reference` → `player-master.png`） | 母版**是**仓库内置件，但它住在 `authoring`（L3）⇒ 交付的那几帧是 `image` ⇒ `generated` |

- **(a) 留 —— 因为你能点出 L1–L5 之外的落点**（请把它写在裁定表第 3 列）。
- **(b) 删**（`AssetOrigin.fixture` + 随它派生不出来的 `PackMode.fixture`，`assetpack/v3 → v4`）。
- **(c) 别的**（例如「留字面但宣布它保留、等一个生产者」—— ⚠️ 那就是票 26 / 票 45 拒过的那种**零消费者字段**）。

➡️ **推荐 (b) 删**。理由：票 45 那句「有明确的潜在生产场景」**今天没有承载物** ——
唯一的活案例（L1）**已经在跑、而且标得对**（`imported` 本来就是「人这次给的位图」，配方本身就是那次人工交接）。
⚠️ 而 **Q1 是根**：**你若点得出落点，(a) 立刻盖过推荐**，那 Q2/Q4 才需要答；
点不出，Q3/Q5 才需要答。⚠️ 删的同时，我建议把「**仓库内置件作为资产来源**」这条路
写进地图的 `Not yet specified` —— 这样下一次扫「零生产者」扫到的是**理由**，不是**一个空档**。

### ❓ Q2 — 若落点在 `source.kind` 那一侧：本票与 `recipe.ts` 怎么分工？

（**只在 Q1 选 (a) 且落点属于 L2 时**才需要答。）

- **(a) 不开新 kind**：把区分做成 `import` 那一支的**一条规则**（例：`ref` 解析后落在仓库内 ⇒ `fixture`），
  分工是「**`recipe.ts` 管形状，`pack` 管来源判定**」。
- **(b) 开新 kind**：`AssetSource` 从三变体变四变体 —— ⚠️ 代价是**每一个消费者**（`pack` / `auditAssetSpec` /
  atlas / coverage / manifest / `recipe-tool`）都得认识它，而它**与 `import` 同形**。
- **(c) 别的。**

➡️ **推荐 (a)**。理由：`AssetSource` 的判别式回答的是**创作态**，「仓库内置 vs 人这次给」不是创作态
（见 Q1 表 L2）；新开 kind 是**给同一个形状起第二个名字**，正是这个仓库反复记的那条病。

### ❓ Q5 — `PackMode.fixture` 跟不跟着动？（**两叉都答**）

`derivePackMode` 把二者**绑在一起**（`if (allOf("fixture")) return "fixture"`）。
票面问的是：**动一处不动另一处，那条「两头对账」的 `superRefine`（`:280`）会不会立刻自相矛盾？**

✅ **实测答案：不会立刻矛盾**。那条 `superRefine` 只做一件事 —— **比字符串**
（`m.provenance.mode !== derivePackMode(...)`）。删掉 `AssetOrigin.fixture` 而留 `PackMode.fixture`，
`derivePackMode` **再也返回不出** `"fixture"` ⇒ 那**不是矛盾，是一条谁也走不到的岔路**。
⚠️ 而 `mode` 与 `origin` **不是同一种东西**：`mode` **有真读者** —— `verify` / `inspect` 都印它
（`ops.ts:1474` · `:1571` · `:1673` 逐字 `来源：${m.provenance.mode}`），
所以这里要删的是**那一档值**，不是那个字段。

- **(a) 两边一起动**（`origin.fixture` 与 `mode.fixture` 一起走）。
- **(b) 只动 `origin`，`mode` 留着** —— 代价是 `derivePackMode` 里那一行变成**死分支**，
  且没有任何判据会告诉你（它安静地永远不触发）。

➡️ **推荐 (a)**。理由：留一个**派生不出来**的值，等于留一条**永远绿的判据** ——
而这个仓库的尺子是「**一条从没被执行过的规矩等于没有**」（票 45 落地时逐字写过这句）。
