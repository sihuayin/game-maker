## 0.1 · 病根一句话：**两层之间的一段缝**

| 层 | 今天的样子 |
|---|---|
| **设计层** | 有一条「id **跨桶**唯一」的判据（`game-design.ts:255-264`），但它**只遍历四个桶** `enemies / npcs / interactables / resources`。⚠️ `player` 是个**独立的 `strictObject`**（`:147`），**压根没进那个 `seen` 表**。 |
| **下游** | 要它唯一，而且是**三层绑死的**（见 §0.2）。 |

```ts
// 设计层（game-design.ts:255-264）—— 判据自己的理由写在报错文案里
const seen = new Map<string, string>();
for (const bucket of ["enemies", "npcs", "interactables", "resources"] as const)
  v[bucket].forEach((item, i) => {
    const first = seen.get(item.id);
    if (first !== undefined)
      issue([bucket, i, "id"], `\`${where}.id\` 与 \`${first}\` 重复 —— 同一个 id 落在两个桶里，
        设计层就**说不出它是什么**（意图层按 \`type\` 只认一个桶）`);
    else seen.set(item.id, where);
  });
// ⚠️ player 不在这个循环里 —— 它上面第 147 行是个独立的 strictObject
```

**而下游有三处都假定 id 唯一 / 一对一**：

1. **DNA 契约自己**（`character-dna.ts:164-166`）：`角色 id 重复："${c.id}" —— characterId 会变得含糊（它靠 id 命中）`
2. **集合等值闸**（`build-character-dna.ts:63-70 / 101-117`）：`player` + `enemies[]` + `npcs[]` 装进**同一个集合**，
   要求与 `characters[].id` **恰好相等**
3. **一条一对一链**（`character-dna.ts:74-79`）：`GameDesignSpec.player.id` = `character-dna[].id` = `AssetSpec.characterId`

⇒ 设计层放行 ⇒ DNA 那一发**必然**吐出两条同 id ⇒ **必然**撞 ①②。

## 0.2 · 量到的：**两份设计 · 两次真跑 · 同一个形状**

```
第五跑（2026-10-10b）                    第七跑（2026-10-11a · 段 A）
  player.id = scavenger                    player.id = scavenger
  enemies   = ['enemy']                    enemies[0]       = 'enemies'
  npcs      = ['scavenger']  ← 同 id       npcs[0]          = 'scavenger'  ← 同 id
  interactables = ['chest','bench',…]      interactables[0] = 'chest'
  resources     = ['resource','supply']    resources[0]     = 'resources'
⇒ 重复 = ['scavenger']（闸一声没响）      ⇒ 重复 = ['scavenger']（闸一声没响）
```

**两次死在同一个位置**：`characters[2].id` / `"scavenger"`。错误逐字：

> 重采样 3 次都没有拿到一份过契约的 `CharacterDNA`（最后一次：`schema`）。
> 最后一次的病因：**工具入参不过契约：`characters[2].id: 角色 id 重复："scavenger"`**
> —— `characterId` 会变得含糊（它靠 id 命中）

**探针 ⑥（拿第五跑那份输入重放 6 次）**：`过闸 ok 0 · bad 6`，**逐发 ids 都是 `['scavenger','enemy','scavenger']`**
⇒ ⚠️ **模型从不自行合并那两条** ⇒ **任何次数的重采样都是纯烧文本**。这就是「确定性的失败证据」。

⚠️ **两处更正**（我第一次报这条时写错了，留在这里免得你按错信息答）：
① 「9/9」是错的，**探针是 6/6**；② 撞的不是「`characters[2]` 与设计层的 `player` 同名」，
而是 **`characters[2].id` 与 `characters[0].id`**（都在 DNA 的 `characters[]` **里面**）。

⚠️ **两次的 NPC 都是设计层自己补出来的**（第七跑那条写着「**玩家控制的拾荒者本人**，无对话，
仅作为被操控的角色存在于场景中」）—— 按票 10 的 R2-Q1，**设计多出意图是合法的**（意图 ⊆ 设计），
它只是补了一个「玩家自己」。⇒ **这是个「合法的设计」撞上一条没写全的判据**，不是模型乱来。

❓ **Q1** - **`player` 当初没进那条判据，是「故意」还是「漏了」？**（⚠️ **本问不给推荐**）

这是**设计意图**，只有你能答。两边我量到的证据都摆出来：

**支持「故意」的证据**：

- 票 10 的票面字面就是「id 跨**桶**唯一」，而 `player` **不是桶** ——
  `vocabulary.ts:108` 的 `ENTITY_BUCKETS` 只有四个值（enemy / npc / interactable / resource），
  而 `player` **在意图层根本不是一种实体类型**（`IntentEntityType` 里没有它）。
  ⇒ 字面上，`player` 确实**不在**那条规矩的作用域里。
- **判据自己的理由文字**写着「意图层按 `type` 只认一个桶」——
  而 `player` **从来不参与那个 `type` 映射**。⇒ 这条判据要防的那件事，在 player 身上**不适用**。
- 「player 与 NPC 是两种东西」本身是个**说得通**的设计立场（一个是操控对象，一个是场景角色）。

**支持「漏了」的证据**：

- **下游不这么看**。`build-character-dna.ts:63-70` 把 `player`、`enemies[]`、`npcs[]`
  **装进同一个集合**，`:101-117` 要求它**恰好等于** `characters[].id`；
  `character-dna.ts:74-79` 又把它钉成一条**一对一链**（`player.id` = `dna[].id` = `characterId`）。
  ⇒ **在下游眼里，player 与 npc 确实是同一种东西：一个角色实体。**
- 既然如此，设计层那句理由（「**说不出它是什么**」）在 player 身上**同样成立** ——
  `player.id === npcs[0].id` 时，下游说不出「这条 DNA 是玩家还是那个 NPC」。**只是没人查。**

⇒ **你的答案决定了 Q2 选哪一支**（下面每一支都标了它对应 Q1 的哪种回答）。
**若你也拿不准，可以答「按 Q2 里我勾的那支倒推」** —— 那等于把 Q1 的定义权交给选定的方案。

---

❓ **Q2** - **三条路选哪条？**（票面原本写的就是「三选一，或组合」）

1. **在设计层拒**：把 `player.id` 并进那条唯一性判据（`seen` 里**先放 `player`**）。
   - ✅ **最早、而且免费**：`compile-design` 是**文本步**，在任何生图之前。
   - ✅ **形式是现成的**：票 10 已经定过「拒绝是一条结论」（退出码 4 · 走 `rejections` · **不重采样**）。
   - ⚠️ 后果：人看到的是「**设计不合格**」（设计层拒），而不是「模型吐错了」。
   - **⇒ 与 Q1 答「漏了」最配。**
2. **在 DNA 那一层改**：承认「player 与某个 npc 可以同名」，把「每个角色实体恰好一条」那条规矩松开
   （或让 DNA 的 id **带上来源桶**，例如 `player:scavenger` / `npc:scavenger`）。
   - ⚠️ **代价**：`characterId` 靠 id 命中（`character-dna.ts:164` 那句报错就是说这件事），
     **「含糊」是真的含糊**；而 id 带桶名会**改掉那条一对一链**（票 04 Q3 立的），
     等于**动三个契约的引用族** —— 按本仓库的规矩，那要**另开票**。
   - **⇒ 与 Q1 答「故意」最配（player 与 NPC 本来就是两种东西）。**
3. **两处都动**（设计层拒 + DNA 层把**文案**说清）。
   - 注意：这里说的「DNA 层动」只是**改那句话/加注释**，**不改引用族** —— 与第 2 支不是一回事。

➡️ **我的推荐（与 Q1 绑定，请连着看）**：

- **若 Q1 = 「漏了」⇒ 选 1**。理由一句话：**缝在哪一层，就在哪一层堵** ——
  这个洞的成因是**设计层放行了一份下游必然拒绝的设计**，堵在下游等于让每一次都先烧一通重采样。
  而且**免费**（文本步）、**形式现成**（票 10 的拒绝路径）。
- **若 Q1 = 「故意」⇒ 选 2**，但**必须另开票**（它动引用族）。
  ⚠️ 并且要接受一个后果：**「同一个 id 出现在两个桶里」从此是合法的**，
  那条一对一链要重新定义成什么，得**一起定**。
- **若你想要最小改动 + 不动引用族**：**1 + 3 的文案部分**（设计层拒；DNA 那句报错改得更好懂）。
  这也是**我若必须挑一个**会挑的 —— ⚠️ **但 Q1 没答之前，这句话不算数。**

❓ **Q3** - **「桶名被当成 id」算不算同一个病？**（本轮新看出的一条）

第七跑那份设计里还有：`enemies[0].id = "enemies"`、`resources[0].id = "resources"` ——
**桶名被当成了 id**。⚠️ 这一跑**没撞**（因为桶名彼此不同、且没有哪个桶叫 `player`），
但**同一个成因**（模型把「这个东西是什么」当成了「它叫什么」）。

- **A. 同一个病，本票一起收**（在设计层的判据里顺带说清「桶名不是 id」）。
- **B. 不是同一个病，另记一条**（它的判据是另一句话：id 应当**描述这一个**，不是**描述这一类**）。
- **C. 先不管**，记在票里留个尾巴。

➡️ **推荐 B** —— 判据要说的不是同一句话（A 会让一条判据管两件事，本仓库栽过）。
但**这一条我拿不准**，你若看得更清就直接覆盖。
