## 二、这一轮要你裁的

### ❓ Q1 — 容器里存**哪一份**：模型原话，还是过完 Zod 的那份

- **(a)** 只让**失败分支**多回一个 `raw`；成功那一支继续用 `value`（= `parsed.value`）
- **(b)** **两个分支都回 `raw`**，容器**一律**存 `raw`

➡️ **推荐 (b)**。今天 (a) 与 (b) **结果相同**（那个 schema 不改写），所以这不是为了今天——
是为了**将来**：一旦有人在契约里加一个 `.default()`，选 (a) 就会得到
「**R12 那一发存的是被改写过的、schema 那一发存的是原话**」这种**同一份容器里两种口径**，
而且**看不出来**。(b) 是一条规矩：**容器存的一律是模型写下的那几个字节。**

⚠️ 反方（请一并考虑）：(a) 的改动面更小，只碰失败分支。

---

### ❓ Q2 — R12 那一发的 `detail` **留不留**（它与 `rejections[]` 是同一份事实的两种形式）

- **(a)** 留 —— 每一发都有 `detail`，读者不用按 `outcome` 分支
- **(b)** 不留 —— 只留 `rejections[]`，避免同一份事实落两处

➡️ **推荐 (a)**。⚠️ 仓库里已有同型先例，而且写明了**哪一份权威**：
`master-ratio.ts` 同时存 `requestedRatio` / `returnedRatio`（「**给人读的**」）与
`match`（「**零容差判定的权威值**」）—— 一条规矩：**权威那一份负责判，方便那一份负责读**。
本容器同理：**`rejections[]` 权威，`detail` 是一行人话**。

---

### ❓ Q3 — 容器要不要带**每发的 token 数**

事实：账那一格今天是**调用级**的（`ms` / `usage` 各一格；逐发的只有 `failures` 那个数组）
⇒ **逐发 token 今天任何地方都没有**。

- **(a)** **不带** —— 容器装的是「模型写了什么」，token 是**账**的事（第一轮 Q7 已裁不动账）
- **(b)** 带

➡️ **推荐 (a)**。诊断要用的是**内容**；而「这一发是不是被截断了」容器里已经有了
（`outcome: "truncated"`）。⚠️ 若你要 (b)，那就等于**新建一处逐发花费记账**，
而它正是第一轮 Q7 明确不动的那件事。

---

### ❓ Q4 — 失败时要不要在**提示里点名**这个文件

- **(a)** **不点名** —— CLI / MCP 今天已经有 `failureSiteNote` 指向失败**目录**，读者 `ls` 就看得到
  （`ledger.json` / `master-ratios.json` 也从来没有被点名过）
- **(b)** 在错误消息里加一句「原始入参落在 `…/design-attempts.json`」

➡️ **推荐 (a)**。失败现场的**通行做法**是「目录即索引」；点名一个文件会让下一个诊断产物
**也得点名**，每一份都往错误文字里塞一行。

---

### ❓ Q5 — 要不要顺手给**外壳**开一个读它的口（`inspect` / MCP）

- **(a)** **不开** —— 本票只保证「**现场里有、且读得回来**」；票 23 要的诊断是**人去看现场**
- **(b)** 开

➡️ **推荐 (a)**。⚠️ (b) 会把本票变成一条**新的产品面**（要定输出格式、要定退出码、
要和 `inspect` 现有的几个 section 对齐），而票 23 的验收读点（「`player.id` 被改成了什么」）
**读一个 JSON 文件就够了**。真需要产品面时，另开票。
