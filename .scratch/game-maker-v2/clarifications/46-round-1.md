⇒ **「一份违反自己契约的包落在盘上、并被当作成功产物交付」今天可以复现**，走的就是生产函数本身。

（这不缩小本票范围 —— 只说明「已确证的那条」确实被堵住了。）

### 2. ⚠️ **提交边界已经存在，而且很干净**

```text
pack.ts:1143  manifest.files = walk(packDir)                    // checksum 取自真字节
pack.ts:1147  fs.writeFileSync(packDir/manifest.json, jstr(...)) // 写进工作目录 .building-<pid>-<N>/
pack.ts:1150  auditAssetSpec(...)                                // ⚠️ 不是 schema 校验、不抛
pack.ts:1158  fs.renameSync(packDir, finalDir)                   // ← 提交成 pack/v<N>/
```

`:1147` 与 `:1158` 之间**没有任何 schema 校验**。而 `jstr` = `JSON.stringify(o, null, 2) + "\n"` ——
**验内存那个对象**与**验写出去的那份字节**不是一件事（`undefined` 会被丢掉、`NaN` 变 `null`）。

### 3. 失败现场与出口的现成机制

- `buildAssetPack` 已经是 `try { buildInto } catch { keepFailureSite(...); carryOnError(e, {failureDir}); throw e }`
  （`pack.ts:290-301`）⇒ **「抛」就会自动留现场**，不需要新约定。
- `keepFailureSite`（`pack.ts:248-288`）**只改名不删**，落 `failed-<ts>/`，**不占版本号**，且同一份配方**只留最近一次**。
- 出口表在 `packages/contracts/src/command.ts:45`：`{ok:0, failure:1, usage:2, upstream:3, invalid:4}`；
  `CommandError("invalid")` ⇒ **4**（票 29 与 `compileRuntime` 同款）。
- ⚠️ **票面说「各档语义边界写在 `docs/v2/01-contracts.md`」—— 今天不成立**：那份文档里**没有**退出码那一节。

### 4. `verify` 比 `parseAssetPack` 宽

`verifyPack`（`ops.ts:1402`）= schema **＋** checksum 对账 **＋** 未声明文件 **＋** ledger/ratios。
**但**在 `:1147` 那一刻，后面那几项**结构性成立**：`files[]` 就是 `:1143` 从真目录走出来的、
checksum 取自刚写下去的字节 ⇒ 在生产者这一侧，它们**测不出东西**。

## 二、这一轮要你裁的

### ❓ Q1 — 验在**哪个点**、验**哪一份**

- **(a)** 验内存里那个 `manifest` 对象 —— `writeFileSync` **之前**
- **(b)** 写进工作目录**之后**、`renameSync` **之前** —— 验**真字节**（`JSON.parse(readFileSync(...))`）
- **(c)** 提交进 `pack/v<N>/` **之后**再验

➡️ **推荐 (b)**。它是唯一一个「**① 验的是真正要交出去的那份字节**（能抓住序列化本身的失真）
∧ **② 非法产物永远没机会变成一份包**」的点 —— `renameSync` 这一步之后，`pack/v<N>/` 就是**交付物**了，
在那里才发现，正是票 44 证据④点名的「**先交出去、再说它不合格**」。⚠️ 定位：**验在 `buildAssetPack` 里面**
（不是 `packAssets` 的入口）—— 因为**入口那两道闸恰恰就是这次漏掉它的原因**，验在入口等于没验。

### ❓ Q2 — 失败时**留不留现场**，怎么与票 14「不落盘」并置

票 14 裁定过「业务校验不过 ⇒ 抛、**且不落盘**」（理由：坏配置比没配置更坏）；
票 15 又定了「失败现场**只改名不删**」。两者看起来顶牛：

- **(a)** **复用现有机制** —— 抛在 `buildAssetPack` 的 try 里 ⇒ 工作目录改名成 `failed-<ts>/`
  （**违约的那份 manifest 在里面可看**），而 `pack/v<N>/` **根本不出现**。不新增任何约定。
- **(b)** 不保留 —— 直接把工作目录删掉
- **(c)** 另加一套现场约定

➡️ **推荐 (a)**。⚠️ 两句「不落盘」**说的不是同一件事**：票 14 要禁的是**一份会被当成产物的盘**，
而 `failed-<ts>/` **不是产物**（它不占版本号、`verify`/`inspect` 不会误认、`ls` 里一眼认得出是哪一次）。
⇒ 「**不许交付**」与「**留住现场**」在这里不冲突，**冲突只出现在「现场该叫什么名字」这一层**，而那层已经有答案了。

### ❓ Q3 — 用哪个**错误出口**

- **(a)** `CommandError("invalid")` —— 退 **4**，**不重采样**（确定性失败，票 14 的第二档）
- **(b)** 别的

➡️ **推荐 (a)**。它是**确定性**的（manifest 由已验证的输入算出来），不是「模型没生成好」
⇒ 按票 14 那条线，**不许重采样**，否则又把确定性错误伪装成模型抽签。⚠️ 报错**必须点名到字段**
（`parseAssetPack` 回的 `errors[]` 本身就带路径串，如 `assets[0].layers: 层名重复："far"`）。

### ❓ Q4 — 验**什么**

- **(a)** **只 manifest schema**（`parseAssetPack`）
- **(b)** **整包** = 复用 `verifyPack` 的全套（schema ＋ checksum ＋ 未声明文件 ＋ ledger）

➡️ **推荐 (a)**，理由不是「省事」而是**「(b) 在那一刻测不出东西」**：`files[]` 与 checksum 都是
`:1143` 从真目录现走出来的（**同一份字节数的两遍**），未声明文件在「按目录走」的模型下**不可能存在**
⇒ 加进来是**一条永远绿的空判据**。⚠️ 反过来说：**这恰好说明自校验与 `verify` 不是两把尺子** ——
`verify` 管的是**跨进程 / 跨时间**（包在盘上躺过之后），自校验管的是**离开进程之前**，**同一套 schema，问了两次**。

### ❓ Q5 — 判据落在哪（票面第 4 问）

- **(a)** **拿探针 A 那条真路径**驱动 `buildAssetPack`：断言 ① **抛** ② 报错点名到字段
  ③ **`pack/v<N>/` 没被创建** ④ **现场里有那份违约 manifest**；再加一条**阴性**（好包照常提交、一字不变）。
  **不需要测试缝** —— 那条路本来就通。
- **(b)** 抽一个校验函数单独测（**不碰生产路径**）

➡️ **推荐 (a)**。⚠️ 这正是票面点名的陷阱：`pack.test.ts` 那三处回环是**测试自己**调 `parseAssetPack`，
验的是「测试预言的那个形状对不对」，**不是「生产路径会不会拦住」** —— (b) 是同一个病的另一种写法。

### ❓ Q6 — 层名重复这条，要不要**顺手在契约层堵**（= 花钱之前就拒）

探针 A 量到的是：**一条规矩只住在一半**（交付侧有、创作侧没有），于是它一路走到**花完钱之后**才被
（本票要加的）自校验接住。两条路不是一回事：

- **(a)** **本票只做接线**（自校验兜底）。契约收紧**另开一票**（按票面自己那句：撞 R6 走 R17）
- **(b)** 本票**同时**收紧 `BackgroundSpec.layers`（或 `recipe.ts` 的 superRefine）的唯一性
- **(c)** **只堵契约、不做自校验**

➡️ **推荐 (a)**。三条理由：① 票面**已经预答**了（「必须收紧契约才能自校验」才走 R17，而我们**不需要**收紧 ——
接线本身就跑得通）② 两件事**解决的问题不同**：契约堵的是**这一条**、且在**花钱之前**；
自校验兜的是**任何一条**、但**在花钱之后** —— 后者**换不掉**前者，前者也**替不了**后者
③ 混在一起会让判据分不清「是哪道闸拒的」。⚠️ **但 (b) 的道理是真的**（R12：能免费拒的就别花完钱再拒），
所以我在 §三 里把它记成一张**待开的票**，你说开我就开。
