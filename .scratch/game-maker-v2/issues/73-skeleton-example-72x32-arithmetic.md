## 1 · 立案现场

**骨架**（`packages/assets/src/ops.ts:636`，`gameConfigExample` 里那一格）：

```ts
panel: { asset: "<ui 面板资源的 id>", at: { x: 8, y: 262 }, size: { w: 72, h: 32 } },
```

**规则 8**（同一份提示词，`packages/assets/src/ops.ts:817`）逐字：

> ⚠️ **`hud` 的坐标是屏幕空间（≤ 480×270），不是世界空间。**
> 世界可以宽 1440，但屏幕只有 480 宽 —— HUD 写到 x > **408** 就跑出屏幕了，直接拒。

（模板里逐字是 `${vp.w - 72}` ⇒ 480 − 72 = **408**：那个 **72 就是骨架里那件面板的宽**，
被写进了**一条讲所有 HUD 的规矩**的算术里。）

**那个数是谁家的**（⑦ 量到的）：`fixtures/packs/last-train/v2` 的 `hud-lost-slots` = **72×32**，与骨架**逐字节相同**；
而第十二跑那一包的 `hud-bar-backdrop` = **32×16** ⇒ **同一个骨架，换一个包，这个数就是另一件东西的尺寸**。

**而同一份提示词里还印着真实尺寸**：`resourceBrief`（`ops.ts:643`）**每一件资源都把真实尺寸写给它看**（`32×16px`）
⇒ ⭐ **提示词内部自相矛盾**：清单说 `32×16`，骨架与规则说 `72`。
（票 40 那条「**示例错了，模型就会错**」的同族；而这里更窄：**示例对某一个包是对的**。）

## 2 · ⚠️ 两件必须替这一票说清的事（读出来的）

**① 骨架那一格本身是合规的 —— 不要把它记成「骨架自己会被拒」。**
面板的锚点是**左下角**（`{x:0, y:1}`），盒子**从 `at` 往上长**（票 48）⇒
(8, 262) + 72×32 的盒子是 `(8, 230, 72, 32)`，`y + h = 262 ≤ 270` ⇒ **没有出界**
（`contracts/src/game-config.ts:423-425` 的 `inWorld`，而 `hud.panel` 那一次在 `:430`）。
⚠️ 本 session 一开始**误以为它出界**（262 + 32 = 294 > 270）—— 那是**按左上角读**才会有的结论，
而 `at` 是**锚点落在的那个点**（同一份文件 `:408-420` 的 `boxOf` 注释，`:415` 逐字：「而它的盒子是**从 `at` 往上长**的 —— 不是从 `at` 往下」）。**记这一笔是为了防下一个人重犯。**

**② 规则 8 的那个门槛，只在「模型的面板宽正好是 72」时才等价于那条尺子。**
真正会响的那把尺子是 `inWorld`（`game-config.ts:423-430`），它量的是
`boxOf(config.hud.panel.at, config.hud.panel.size, …)` ⇒ **用的是模型自己声明的那个宽**
⇒ 规则 8 把门槛写成 408，对**更宽**的面板**过松**（声明 120 宽时真门槛是 360，写到 400 会被拒，而规则当时说没事）、
对**更窄**的 HUD 件**过严**。⇒ **它给的是一个「对所有 HUD 都成立」的错觉。**
⚠️ 而这条算式**全仓只有一处**（本 session 按 `- 72` / `− 72` 全仓 grep：只有 `ops.ts:817`）
—— 塔防那一份提示词（`tdConfigPrompt`）**今天没有**同款算术 ⇒ 这一票是**横版那一份提示词内部**的事。

⚠️ 顺带记一笔（**它可能比这一票更大，但不在本票射程**）：`gameConfigExample` 的注释（`ops.ts:610-615`）逐字写着
「⚠️ **它必须是能过 schema 的** —— 导出它是为了让测试能直接断言这件事」，
而那条断言是 `packages/assets/tests/compile-runtime.test.ts:56` —— 它**只管骨架能过 schema**，
**不管骨架里的数与提示词里的算术同不同源**。要不要补一条（见 Q2）由本票裁。

## 3 · 要裁什么

- **Q1 · 这个数怎么处置**
  - **(a) 骨架与规则都改成「与包无关」的形状**：规则 8 不再写死一个常数，改成用**声明的宽**表述
    （「`x + 你声明的宽 > 480` 就拒」）；骨架里那一格换成一个**包无关**的数（或明说「这个数只是示例、照清单里的真实尺寸写」）。
    ⚠️ **硬约束**：骨架**必须继续能过 `parseGameConfig`**（那是 `compile-runtime.test.ts:56` 的既有断言）
    ⇒ 骨架里**不能出现空位数字**，这一支要找一个既自洽又合法的写法。
  - **(b) 骨架保留，只把规则 8 的算术改成不写死 72。**
  - **(c) 两者都改。**
  - **(d) 不登记**（记为已知的示例口味）。
  - **(e) 别的。**
- **Q2 · 要不要一条判据看着「示例与规则同源」？**
  现成的先例是 `:56` 那条断言（骨架 ⇒ 过 schema），而它管不到「数与算术同源」这件事
  ⇒ 要不要在**同一份测试文件**里加一条（例如：提示词里出现的尺寸常数与骨架里那一格对得上）？
  ⚠️ **加断言 = 施工**，本票只裁「要不要」。
- **Q3 · 验证边界**：免费能证到哪（骨架、规则、清单都在**同一份提示词**里，可以逐字对；
  「模型会不会照 72 写」免费证不了）· 真跑归**票 23**。
