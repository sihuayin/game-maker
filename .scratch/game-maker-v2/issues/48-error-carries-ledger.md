## Question

### 病：票 46 那个二分缺了第三格

`game-creation-v1` 票 46 `## Answer` §5 原文：

> **不是上游失败的错误**（比如某个普通 `Error`）**不带账** —— 那种是**代码的 bug**，
> 而不是「钱花了包没出来」；给它们套一个 `CommandError` 只会把栈弄丢。

⚠️ 那个二分是「**上游失败** / **代码 bug**」，而实测（[票 36](36-failure-ledger.md) §2）量出了**第三类**
——「**判断失败，但钱已经花完了**」：

- **花钱之后**的判断**全部**抛普通 `Error`（**11 处**）：
  `pack.ts:427 / 554 / 568 / 610 / 735 / 797 / 810 / 830 / 895 / 940 / 1005`；
- ⚠️ 而**花钱之前**还有**三处**（`pack.ts:371 / 377 / 383`）**也**抛普通 `Error` ——
  文件里**点名**叫它们「**免费拦停**：三件『调用方/清单的错』，**全部在第一笔钱之前**」（`pack.ts:368`）
  ⇒ **票 46 §5 那个二分的第二格（代码 bug / 调用方的 bug）在本文件里本来就有主**，
  缺的**只有第三格**；⇒ 它给的判据不是「抛的是哪个类」，而是**抛点在花钱之前还是之后**
  （这也正是下面第 3 问「一刀切还是分格」该照着答的靶子）；
- **机制**（为什么第三类会丢账）：`ops.ts:1228-1231` 只在 `GenerationError` / `ImageGenerationError` / `CommandError` 三种情况下
  把 `carried = { ledger, failureDir }` 包进 `CommandError`，**其余走 `throw e`** ⇒
  **账与失败现场指针一起丢**；
- ⇒ 2026-10-09 那次真跑（**9 张已付费的图**）死在**其中一个**判断上，而：
  - CLI / MCP 那一屏里「**已经花掉的**」**一个字都没有**
    （实证：pack 段失败的 run JSON 只有 `['command','error','exitCode']`，而**理解段**失败的带 `ledger`）；
  - **失败现场的路径也没报出来** —— 现场本身在磁盘上（票 36 之后**里面还有账**），但人得自己去 `find`。

⚠️ 而它**不是**票 46 §5 说的那种「代码的 bug」—— 它是「**图生成完了、钱付了，然后判据说这批图不行**」。
那个二分里**没有它的格子**。

### 今天的状态（票 36 之后）

- **包内账**在失败时**已经活着**（票 36：`…/failed-<ts>/ledger.json`）—— 但**要先找到现场才读得到**；
- 跟着异常走的那一份（票 46 的地基）**仍在** `ops.ts:1187` 那个数组里、也仍在被 `carried` 组装

### 这一票要答的

1. **手续**：这是**变更票**。票 46 那份 `Answer` 要不要**连带**加一条**带日期的注**
   （本仓库的先例是就地加注、不改原文 —— 票 02 / 票 43 / 票 44 都这么做）？
2. **机制**：账怎么搭上去？两条路，**各自把代价说清**：
   - **(a) 挂在原 error 上**（`Object.assign(e, carried)`）+ 两个壳改成**按能力读**
     （`e.ledger !== undefined` 而不是 `e instanceof CommandError`）。
     ⇒ **栈不丢** —— 票 46 §5 那第二条理由（「只会把栈弄丢」）被正面解决；
     代价是动**三处读者**（`cli.ts:594` · `cli.ts:597` · `server.ts:331`）。

     ⇒ 读者**一处都不用动**，且**退出码零变化**（裸 `Error` 今天的落点就是 `EXIT.failure` = 1，
     与 `CommandError("failure")` 同码 —— `command.ts:60`）；
     代价是**栈与错误类的身份丢了**（正是票 46 §5 担心的那件事）。
3. **一刀切还是分格**：那 **11 处**抛点之外还有 **3 处**（`371 / 377 / 383`），

   实测它们**一分钱都没花**（注释：免费拦停）。⇒ 于是问题收窄成一个**可判别的靶子**：
   要不要给「**判断失败**」（= 抛在**花钱之后**）一个**可判别的信号**
   （例如一个 `JudgementError` 子类），而不是让兜底去**猜**？

   「**失败即止**」保证没发出去的不入账）⇒ 也许**不需要新类**，需要的只是**把这条已有的尺子说出来**。

> **核心原则（人给的）**：**是否携带账本，取决于失败时是否已经产生实际花费**；携带账本

### 1. 新规则的完整字面（Q1 点名要落在这里的）

> **失败时带不带账，看的是「失败时有没有已经发生的花费」，不是「抛的是哪个类」。**
>
> - **已经花掉的那几笔**跟着异常走 —— 挂在**原异常**上、**原样抛出**（栈 / 错误类 / `cause` 链一样不丢）。
> - **一分钱没花的**（真·代码 bug / 调用方的错）**原样抛出**，**不包装、不凭空附加账**。
> - **失败现场指针与账是并列的两项信息**，各自可缺；**缺一项不许连累另一项**。
> - ⚠️ **「已有花费」以账本记录为操作判据** —— 不宣称账本能证明所有外部费用最终都已结算。
>   **账本为空时，不应仅凭抛出位置或错误文本就把它归为判断失败。**
> - ⚠️ **同一个抛点在不同包形状下可以是两类**：全 `import` / 全 drawlist 的包在那些行上
>   一分钱没花 ⇒ 它**就是**第二格，**原样抛出**。这是**正确行为**，不是漏判（Q3 的裁定原话）。
>
> 依此，`game-creation-v1` 票 46 §5 第二条的**判据**被替换（**不是**被推翻：它反对的「套
> `CommandError` 会丢栈」那半条**仍然成立**，而且是本票选实现路线的**唯一理由**）。

### 2. 三类失败语义（执行约束 1）

| 类 | 判据 | 行为 | 退出码 |
|---|---|---|---|
| **上游调用失败** | `GenerationError` / `ImageGenerationError` | **沿用现有**：重包成 `CommandError("upstream", …, carried)`（`ops.ts:1250`）| 3 |
| **判断失败且已有花费** | `ledger.length > 0` | **保留原始异常**，把 `ledger` + 可用的 `failureDir` **挂上去**再抛 | 1（`Error` 的落点）|
| **真正的代码错误且没有花费** | `carried` 是空的 | **原样抛出**，不包装、不附加 | 1 |

⚠️ 第三行是票 46 §5 那个二分**要保住的第二格** —— 本票把它**原样保住**，而保住它靠的
**不是**一个白名单，是 `carried` 组装时的 `...(ledger.length > 0 ? { ledger } : {})`：**没花就什么都没挂**。

### 3. 判别为什么用 `ledger.length > 0`，而不是新开一个类（Q3）

票面的原假设是「给判断失败一个**可判别的信号**（如 `JudgementError` 子类）」。**实测把它否掉了**：

- 那 **11 处**抛点 **不是一个类** —— 只有 **4 处（734 / 796 / 809 / 829）必然在花钱之后**，
  **7 处随包形状变**，而 **567 必然在花钱之前**。⇒ 按行号贴类标签，**会在那些行上说谎**。
  ⚠️ **行号更正（施工后的当前值）**：`pack.ts:426 / 553 / 567 / 609 / 734 / 796 / 809 / 829 / 894 / 939 / 1004`
  （票面那组 `427 / 554 / 568 / …` 是**施工前**量的，施工动过一行 ⇒ 整体 **−1**；
  花钱之前那三处同理：票面 `371 / 377 / 383` ⇒ 现值 **`370 / 376 / 382`**）。
- ⇒ 判据**只能是动态的**，而它**已经存在**：`ledger.length > 0`（`ops.ts:1239` 的组装处，
  用的是 `ops.ts:1225` 那个数组）。「这笔账非空」与「钱花过了」在**「发出即记」**之下是同一件事
  —— [票 47「并行生成资源」](../../game-creation-v1/issues/47-parallel-generation.md) §4 的「**失败即止**」
  保证**没发出去的不入账**。
- ⇒ 本票做的**只是把这条已有的尺子说出来**，一个新类都没有加。

### 4. 账与失败现场是两项独立信息（执行约束 2）

- `ledger` 由 `ops.ts` 在 `carried` 组装时挂上（`ops.ts:1239 / 1259`）；
- `failureDir` **本来就已经**由 `pack.ts:298` 挂在原异常上（`create-game.ts:337` 同款）——
  丢它的是**读者那一侧**：三处 `instanceof CommandError` 把它当不存在。
- ⇒ 读者改成**按能力读**：`ledgerOfError` / `failureDirOfError`（`command.ts:105 / 111`），
  两个壳各自 `if (kept)` / `if (spent)` **分别**渲染 ⇒ **缺一项不吞另一项**。
- **可扩展性边界**：`carryOnError`（`command.ts:96`）只走 `Object.assign` 那一条路**并且**
  用 `try` 包住 —— 冻过的异常**挂不上就挂不上**（现场在磁盘上另有一份，票 36 已保证），
  但**绝不**因此替换 / 包装 / 吞掉**原异常**。⚠️ 本仓库的异常**没有一个**被 `freeze` 过，
  这条边界是**防着未来**的，由 `packages/contracts/tests/carried-error.test.ts` 钉住。
- **只加不改**（逐键）：`if (!(k in e))` —— 下层挂的比上层更接近现场，**不覆盖**；
  而被让位的那一项**不连累**另一项（同名测试里有一条专钉这个）。
