## Answer

**结论：账在失败时也落盘了。而这一票最要紧的一行，是**票面 Q2 那句前提被量出来是假的。**
`pack.ts` 里**根本没有 `spentCall` 那条链**，每一笔生图**在发出前就记了**（「发出即记」，记在闸门**里面**）
⇒ **内存里那份账一直是全的**，缺的是**唯一那一次 `writeFileSync`**。
全套 **1237/1237** 绿 · `pnpm check` 绿 · 新增 **2 条**测试。

### 1. 票面 Q2（那件「第一件事」）：前提是假的

票面问：「`spentCall` 那条链今天记了没有？还是说**调用发生了、记账那一行没跑到**？」

**答案是「两者都不是」** ——
- `pack.ts` 里**没有 `spentCall` 这条链**（那是 `ops.ts` / `game-design/*` / `vision/*` 的写法）；
- 生图这笔账走**发出即记**：`pack.ts:665-668` 在闸门**里面**、在真正调用**之前** `opts.ledger?.push(rec)`，
  返回后 `Object.assign(rec, …)`（`pack.ts:688-695`）把事实补齐 ⇒ **内存里那份账一直到抛出那一刻都是全的**；
- 缺的是**唯一那一次 `fs.writeFileSync`**（票面写的 `pack.ts:880`）。
- ⚠️ 而且 `opts.ledger` 的**最后一次 push 就是 `pack.ts:668`**（母版那笔更早在 `:442`）⇒ 数组**冻结**，
  **账在生图段一结束就已经完整** —— 这正是 Q1 那处提前写能「写一次就够」的原因。

### 2. 现场实测（票面那两处行号都过期了）

- 抛点**不是一个、是 11 个**：`pack.ts:427 / 554 / 568 / 610 / 735 / 797 / 810 / 830 / 895 / 940 / 1005`。
  第三跑只是撞上了**其中一个**（票面的 `617` → 补注的 `656` 都不对）。
- ⚠️ 而**花钱之前**还有**三处**也抛普通 `Error`（`pack.ts:371 / 377 / 383`）—— 它们**不是漏网的**：
  文件里**点名**叫它们「**免费拦停**：三件『调用方/清单的错』，**全部在第一笔钱之前**」（`pack.ts:368`），
  而 DNA 那处是**故意**提到开跑前一次算完的（`pack.ts:391-398`，原话「放在第一笔调用之后，
  一个写错的 id 就要等到钱花出去才被发现」）⇒ **票 46 §5 那个二分的第二格（代码 bug / 调用方的 bug）
  在这份文件里本来就有明确归属，而且注解就是「免费」二字**。真正缺的只有第三格：
  **判据抛在花钱之后**。⇒ 派生票的切法因此**有据可依、不靠猜**（见 §7）。
- `run/v1/ledger.json` 里只有 **5** 条理解调用（`analyze-reference` / `analyze-intent` / `compile-design` /
  `character-dna` / `plan-assets`）—— **没有 `pack`、没有任何 `step:"image"`**（= Q4 那个事实，实测无误）。
- **理解段**失败的 run JSON 带 `ledger`；**pack 段**失败的（`run-2026-10-10c.json`）只有
  `['command','error','exitCode']` —— 因为 `ops.ts:1228-1231` 只把 `GenerationError` /
  `ImageGenerationError` / `CommandError` 包成带 `carried` 的 `CommandError`，**普通 `Error` 走 `throw e` ⇒
  账与现场指针一起丢**（= 派生票的由来，见 §7）。

### 3. 施工（Q1 / Q2）

**`packages/assets/src/pack.ts`** —— 账**构造器只此一份、写两次**（两处不可能漂移）：

- **第一处（新）**：`allSettled` 之后、**任何判断抛点之前**（紧挨 `firstFailure` 那条）。
  构造器 `ledgerDocNow()` 定义在此，两处共用 ⇒ `calls` / `byStep` 两处**完全相同**。
- **第二处（原有，保留）**：`pack` 末尾。它是成功路径的**权威终值** —— 只多算了 `run.wallClockMs`
  的尾段（图集 / 落盘 / 穷举 / 对账）⇒ **成功路径的产物一个字节都没变**（Q1 那条约束）。
- ⚠️ 原注释「包内这份**只在成功时才写**，而失败时根本走不到这里」**已作废**，就地改写（带日期）。
- ⚠️ 另外两处**点名过 `ledger.json`** 的注释也就地更正（`pack.ts:471-481` 母版逐张那处、
  `pack.ts:499-504` 汇总那处）：`ledger.json` **已经离开「末尾才写」那一组**，今天仍是
  `manifest.json` / `coverage.json`。

**「半截 / 完整」不靠字段、靠位置（Q2）** —— 契约**一个字没改**：`Ledger` 仍是 `.strict()`，
没有 `complete` / `finishedAt`。两种读法的分工写进了那处注释：

> `pack/v<N>/ledger.json` = 包交出去了；`…/failed-<ts>/ledger.json` = 没交出去。
> ⚠️ 位置答的是「**包交出去了没有**」，**不是**「这笔记账全了没有」—— 末尾那三个点
> （动态 `import` / `auditAssetSpec` / `mkdirSync`+`renameSync`）在账写完之后**仍能抛**，
> 那时**钱已花光、账已记全**，账是对的而包没交出去 —— 而那几处**一分钱都不花**。

**测试（新增 2 条 · `packages/assets/tests/pack.test.ts`）**：

- 「第 2 个资源挂 ⇒ **失败现场里有账**」：`failed-<ts>/ledger.json` 在、**过 `parseLedger`**、
  两条都在（回来那条有 `ms`；挂掉那条 `ms` **缺席** —— 不编一个数）、`byStep.image = {calls:2, attempts:2}`、
  且**不占版本号**（它仍是失败现场不是包）。
- 「成功路径**一个字不变**」：账仍在包里、仍在 `files[]` 里（= 仍被 checksum 覆盖）——
  若有人把末尾那处挪到 `walk` 之后，这条会红。

### 4. ⚠️ 一处**施工时才知道的边界**（我加的，人可以推翻）

**账是失败现场的「附件」，不是「现场本身」。** 第一处那笔写**不是无条件**的：

```ts
if (ledgerDoc && hasAnyFile(packDir)) fs.writeFileSync(path.join(packDir, "ledger.json"), jstr(ledgerDoc));
```

- 起因：无条件写会**顶掉 v1 票 01** 那条「**一笔都没成功 ⇒ 不留空现场**」——
  `packages/assets/tests/ops.test.ts:48-53` 当场红了（那个例子里唯一的调用撞死端口、一个字节都没落盘，
  而账一写，树就「有东西」了，`keepFailureSite` 于是留下一份只含 `ledger.json` 的现场）。
- 判据用的就是 `keepFailureSite` 自己那个谓词 `hasAnyFile`（`pack.ts:267-271`）⇒
  **票 01 的「有东西才留」原样保住**，且「有没有现场」仍然取决于**这一次真花掉过什么**，
  而不是取决于**我们写不写账**。
- ⚠️ 它**不削弱本票**：真花掉钱的情形（生成图 / 母版 / drawlist 落过盘）树里**必然**有东西 ——
  第三跑那 9 张已付费的图正是如此。「一笔都没成、一个字节都没落」时那一笔仍跟着异常走（票 46）。
- ⚠️ **人若裁定「账本身就该让现场存在」**，就把这个条件去掉 —— 但那是**改 v1 票 01 的观测行为**，
  按 R17 的同一套手续，该另开一张票。

### 6. 两本账谁在失败时活着（Q4）

**各在各家，不搬**：

- **理解段**的花费 → `run/v<N>/ledger.json`（`create-game.ts:313`，**已经有**）；
- **pack 段**的花费 → `failed-<ts>/ledger.json`（本票修的）或 `pack/v<N>/ledger.json`（成功时）；
- **接起来的是那枚指针** —— 异常上的 `failureDir`（v1 票 01 已有）。⚠️ 而它在**普通 `Error` 上会被丢**
  （`ops.ts:1231`），这正是派生票要补的第三格。
- ⚠️ 本票**没有**给 `runBuild` 加 catch、**没有**碰正式 run 目录、**没有**动 `abandonRun` 的失败现场策略
  （那是 v1 票 01 的地盘）。
- ⚠️ 记一条**已知**（不解决、只记下）：`run/v<N>/ledger.json` 在 build 段失败时**顶着正式版本号躺在正式位置**，
  而 `RunLedger` 是 `.strict()`、**没有字段**说它没跑完。今天能看出「没跑完」的是**间接**信号
  （`game-config.json` / `qa-report.json` 不在）。

### 7. 派生的票（Q5）

**新增一条依赖**：`game-creation-v1` 的**票 46「失败也要报账」** Answer §5 原文：

> **不是上游失败的错误**（比如某个普通 `Error`）**不带账** —— 那种是**代码的 bug**，
> 而不是「钱花了包没出来」；给它们套一个 `CommandError` 只会把栈弄丢。

⚠️ 而 §2 量到的 11 处判断抛的**都不是代码的 bug** —— 它们是「图生成完了、钱付了，
然后判据说这批图不行」（第三跑撞上的那条 0 像素哨兵正是其一）。
⚠️ 而 §2 新补的那条让这份二分**更好切**：第二格（**代码 bug / 调用方的 bug**）在 `pack.ts` 里
**已经有主**（`371 / 377 / 383` 三处，注解就写着「**免费拦停 … 全部在第一笔钱之前**」）
⇒ 缺的**只有第三格**，且它的判据不是「抛的是哪个类」，而是**抛点在花钱之前还是之后**。
⇒ 票 46 那个二分（**上游失败 / 代码 bug**）**缺了第三格：「判断失败，但钱已经花完了」**。
本票**只记录依赖、不碰 `ops.ts` 的异常传播行为** —— 那张变更票见
[48-判断失败也要报账](48-error-carries-ledger.md)。
