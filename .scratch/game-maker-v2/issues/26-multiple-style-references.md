## Question

Q19 的裁决是两半：

- **契约层进**：`styleReferences: { path, role }[]` —— 理由是「一图一角色」是个合理方向
  （`image A: palette` · `image B: character` · `image C: environment`），
  而且 `01-contracts.md` §2 与 `00-overview.md` §1（"Style Reference Image**(s)**"）本来就是复数。
- **第一阶段 `maxItems === 1`**：N 张图的**权重融合、冲突解决、谁说了算**，
  **没有任何实测**。不许在这一阶段实现。

这一票要答的就是被推迟的那件事。

### 1. `role` 是一个**封闭枚举**还是一段自由文本

Q19 给的例子是 `global` / `character` / `environment` / `palette`。
- 若是**封闭枚举**：每个 role 必须有**明确的优先级**（两张图都说自己是 palette 怎么办？）。
- 若是自由文本：那它**进不了任何判据**（R3），只能当提示词素材。

⚠️ 按 **R7 的门**：说不出「谁读它」的 role 不进契约。

### 2. 参考图与 `VisualWorldSpec` 的关系

今天（R15）：原图**只存引用**（路径），二进制不进 JSON。
多图之后要答：那张图**各自**参与生图调用吗？
⚠️ 生图那条路的既有实况（别重新量）：Gemini 把 `[styleReference, reference]` 按序内联、
prompt 里注明「附件第 N 张」（`image-gen.ts:299-312`）；OpenAI 有输入图时走 `/images/edits`
（`:460,469-474`）；**DashScope 接不了本地文件**（需公网 URL），**minimax 没有客户端**。
⇒ 多图会让「这个协议撑不撑得住」变成一个**每协议各不相同**的问题。

### 3. 冲突怎么判、要不要判

两张图互相打架时（一张冷调、一张暖调）：
- **(a) 不判**：全喂给生图模型，让它自己合 —— ⚠️ 那就是**不可复现**。
- **(b) 判**：按 role 定优先级 —— 那 `role` 必须是封闭枚举（见 §1）。
- **(c) 拒绝**：检测到冲突就**当场拒绝**（判据）。

⚠️ (a) 与 R6「换色板 → 创作态一字不变」那条**可复现**的性质直接冲突。

### 4. 第一阶段不许做的事（写在这里免得被顺手做掉）

**不许**做：权重融合 · 图与图之间的相似度 · 「哪张图更权威」的自动裁决。
第一阶段 `maxItems === 1`，多给了一张**就拒绝**（退出码 2），并**明说**这条限制。

### 一 · 语义

**1.** 多参考图是**同一个游戏世界的多个来源**，核心问题是**融合**与**冲突**。
**不采用**「一图定色 / 一图定角色 / 一图定环境」的分工模型 —— 没有材料证明那些角色都有明确的消费者。

### 二 · 融合落在哪一层

**2.** N 张图**共同进入一次** `analyze-reference` 调用，产出**一份** `style`
（`style.palette` + `styleBrief` 的四项 `identity` / `shapeLanguage` / `material` / `constraints`）。
⚠️ 实现落点：今天拦住 N 张的**只有 `vision/src/analyze-reference.ts:155` 那一个 `> 1` 的 throw** ——
`imageBlocks`（`:168-178`）本来就是 `refs.map` 通吃。

**3.** **生图协议的参考图槽位不扩展**：生图（母版 + 每个资产）**仍只带第 1 张原图**作为 `styleReference`
（`pack.ts:592` / `:445` / `:663` · `master.ts:189`）。
⇒ Gemini 那两处**写死**的附件编号（`image-gen.ts:305-307`）、OpenAI 的 `[styleReference, reference]`（`:469`）、
DashScope 的预检拒（`ops.ts:1116-1126`）、minimax 无客户端（`ops.ts:1046-1051`）—— **一条都不用动**。

**4.** **第 1 张＝锚图**：它的**像素进入生图调用**；第 2..N 张**只**参与那一次 `analyze-reference`，
**共同影响融合后的 `palette` 与 `styleBrief`**。
⇒ 下游 `ops.ts:232`（→ `reference.png`）与 `create-game.ts:246`（style-id）取的 `[0]`
**从此是规定的语义，不再是静默行为**。

### 三 · 冲突

**5.** **不判**。本项目**不规定**冲突裁决规则：生图模型**每次自行处理**两侧输入
（融合出来的文字描述与 `palette` · 第 1 张原图的像素）之间的潜在冲突。三条限定（人裁）：

- 「模型自行处理」是对**现有行为**的**描述**，**不是**一条要求模型执行的**判据**，**也不承诺**色彩一致；
- **不引入**冲突阈值 · 自动拒绝 · 额外检测 · 重生成逻辑；
- 两侧输入的**来源不同**（文字＝融合所得 · 像素＝第 1 张），是甲① **已接受**的设计代价。

### 四 · 契约

**6.** **移除 `role`** ⇒ 契约目标回归 `styleReferences: { path }[]`（即 **R15 的字面**）。
理由：它**零读者** —— 融合那一次调用**看不到它**（`analyze-reference.ts:42` 把 `styleReferences`
整块 omit 出模型面向的 schema）· 提示词**不写它**（`prompts.ts:24` 明说模型答不出）·
两个真实调用方都**硬编码** `"global"`（`cli.ts:466` · `mcp/src/server.ts:263`）· **无判据无测试**。
⇒ **必填 + 零读者** 与 **R7**（说不出「谁读它」的字段不进契约）正面冲突。

**7.** **本票不直接改契约、不改 R18 决策表** ⇒ **另开票**处理 R18 的字面变更（按 **R17**）：
[票 43「R18 变更票：移除 `role`」](43-r18-amendment.md)。

### 五 · 入口

**8.** **`--style` 可重复，参数顺序就是数组顺序**（第 1 个是**锚图**）；
MCP 的 `stylePath: string` → `stylePaths: string[]`。
⚠️ 现状：`--style` **给两次是 usage 错**（`cli.ts:88-90`，而那条文案自己写着「见票 26」）。
⚠️ **本轮只是确定未来实现的入口设计** —— 第 9 条不变。

### 六 · 边界与落点
