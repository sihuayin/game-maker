# 参考图候选（票 04 的原型）

```bash
node generate.mjs    # 造三张候选图 → out/ref-{A,B,C}.png
node extract_preview.mjs   # 对三张各真跑一次 StyleSpec 提取（要上游）
node preview.mjs     # 拼成自包含的 prototype.html
open prototype.html  # ← → 切换
```

**这是一次性的原型，不是产品代码。** 三个候选是同一个世界（黄昏的山间列车小站）的
三种**结构不同**的构图 —— 这样人比较的是构图，不是题材。

| | 构图 |
|---|---|
| A | 正交侧视单景：一条地平线，天空/山/站台/轨道四段横切 |
| B | 等距俯视：斜穿的地面 + 等距盒子建筑 + 树 |
| C | 分层剖面：天空 / 候车室内景 / 站台 三条横向带，各带一套光照 |

## 为什么用 Node 自绘

票 04 问了「用什么造（Node + Canvas / 手写 SVG / HTML + Playwright 截图）」。
答案是第四种：**Node + 仓库自己的 `RasterImage`/`encodePNG`**（`draw.mjs` 建在 `packages/assets` 上）。
理由：零第三方依赖、与管线**同一个 PNG 编码器**、不需要浏览器。
代价：没有现成的绘图 API，`draw.mjs` 里那 50 行原语得自己写。

## 🔴 造这张图时撞到的一件大事：**上游会重编码图片，精确读色不可能**

票 04 原本要求「这张图要能**真正考验** StyleSpec 提取（色板…都得有话说）」。
于是我们把色板**刻意做小**：18 色，而且**每个像素都恰好是其中之一**。
结果（`out/extractions.json`）：

| 变体 | 图上真实色数 | 模型报的色数 | **精确命中** | 报出的色覆盖了多少像素 |
|---|---|---|---|---|
| A | 16 | 8 | **0** | **0.0%** |
| B | 16 | 9 | **0** | **0.0%** |
| C | 16 | 8 | **0** | **0.0%** |

于是一个决定性测试（`probe_reencode.mjs`）：送一张 **64×64 纯单色**图，问它是什么颜色 ——

```
  送 #4a6076  →  答 #5f6a76   ΔRGB=23.3
  送 #d9a441  →  答 #d2a53c   ΔRGB= 8.7
  送 #6b4a33  →  答 #8e7c68   ΔRGB=80.8
  送 #e6e2d6  →  答 #f2efe9   ΔRGB=26.0
  送 #2e3b4e  →  答 #595d66   ΔRGB=59.8
```

**五次零精确。** 纯色图都读不准 ⇒ **「读不准」与参考图的色数、质量、格式都无关**，
是上游在模型看到之前就把图**重编码**过了（暗色被整体抬亮，像是色彩空间/伽马转换的痕迹）。

**这条推翻了票 15 的一个推论。** 票 15 说「参考图有 122,240 色，所以没有精确色板可提取」——
看起来像是**那张图**的问题；现在知道**换一张干净的图也一样**。
「提取精确色板」不是一个**有风险**的目标，是一个**不可能**的目标。

**后果**：`StyleSpec.palette` 永远只是近似。这不是缺陷 —— 契约本来就只要求
「颜色 ∈ 色板」（相对于 StyleSpec），从不要求色板等于参考图。但**别再拿「色板准不准」
去评价一张参考图的好坏**，那是评价错了对象。详见票 39。
