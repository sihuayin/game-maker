## `measure-import.mjs` —— 导入位图的入口体检（2026-09-25 加）

在把一张图塞进配方之前先量它值不值得进包。**改色率不管用**：实测它在 8 色板上恒定
100%（879 种网格色 → 8 色，没有一格能不换色），区分不出好坏。能区分的是两个量，
且它们在 32×48 与 64×96 上几乎不变（8.5% / 8.8%），所以可以横向比不同图：

| | 含义 |
|---|---|
| **平均色误差** | 量化把每个像素平均推远了多远（0~441 的欧氏距离） |
| **色板覆盖** | 8 色用上了几色；只用到 3 色的资源在那个世界里会显得突兀 |

2026-09-25 的基线（`fixtures/import/wan-player-1024.png`，halt-dusk 8 色板，32×48）：

```
非透明格 1017 · 改色率 100.0%（饱和值，无信息）
平均色误差 37.6 / 441（8.5%）· 最大 112.2
色板覆盖 8/8 · #5a6a8a×25% #1c1c28×18% #6b4a3a×17% #4a5a7a×16% #3a3f5c×15% ...
```

它还诊断两个会**静默毁掉构图**的东西：

- **极淡 alpha 孤点**。旧判据 `alpha != 0` 会把一颗 alpha=1 的像素算作墨，包围盒被撑满画布 ——
  实测角色在 32×48 里从占满缩到 **19×42（原大的 59%×88%）**，而那个像素在二值化后根本不会出现。
  已按「只认过得了二值化的像素」修正（`trimToInk` 的 `floor`），见 `import.ts` 的注释。
- **长宽比**。管线会把角色外接矩形**强制拉伸**到 `spec.size` 两个方向独立缩放 ——
  源 0.529 → 目标 0.667 就是横向拉伸 26%。提示词里的长宽比要求必须按这个数写。

## 实测结果

```
清单 → 真包：77.7s · 8 个资源 · 28 个文件 · 1182.7 KiB
manifest 过 schema ✅ · 对账（spec ↔ 产物）0 问题
provenance.mode = mixed · coverage = {exact:4, composited:3, quantized:1, unbound:0}
```

**14 帧的玩家是同一个角色** —— 头、帽、躯干、胸口那块 CRT 屏在全部帧里一致，只有四肢在变。
这就是把「一个 asset 的全部帧放一次调用」写死进实现换来的东西。

## 视觉抽查抓到的（`reviewPack()`）

抽查本身也暴露了一个结构化校验查不出的真问题：

> 房间场景（左下角）的墙面和部分道具使用了带有平滑渐变或较高对比度阴影的色块，
> 并非全部依赖像素抖动；橙色海报与暖黄色发光的面积占比明显超过规格里的 15% 上限；
> 房间场景是带有正立面透视的封闭空间，并非严格的正交投影。

**那正是人工导入的那张背景** —— 它被量化到 9 色，但量化不会把一张照片变成像素画。
「颜色 ∈ 色板」是构造成立的，而「看起来属于同一个视觉世界」不是。
这条是这轮抽查最有价值的产出。
