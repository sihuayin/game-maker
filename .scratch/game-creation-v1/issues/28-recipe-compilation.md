## Question

1. **清单文件的形状**：它是 `AssetManifest`（[票 24](24-asset-pack-contract.md)，
   产物的自描述）的**输入版**吗？两者字段有多少重叠、要不要共用一套类型、
   怎么区分「需要什么」与「实际做出了什么」（票 20 已定：Spec 与 Artifact 是两层，
   要在契约注释里写死）。若共用，一个文件既是输入又是输出会不会混淆？
2. **「由需求推导」这条路的输入**：只有需求文本，还是同时要参考图和 StyleSpec？
   逻辑顺序上 StyleSpec 先于资源清单（风格约束会影响「该造哪些资源」吗 ——
   还是反过来，资源清单先于 StyleSpec？两者其实**互相约束**：
   「我要一头牛」和「这个世界是灰绿+奶油+橙」是同时被满足的）。
3. **推导出来的清单要不要人确认**：R7 说两条路同构，那「推导」的产物就是一份清单文件 ——
   人是可以先看一眼再改的。要不要设计成**两阶段**（先出清单、人/agent 过目、再生成）？
   这是一个产品形态决策，不只是技术决策。
4. **幂等与增量**：同一段需求推导两次，清单应该一样吗？不一样的话，
   「人给清单」这条路的确定性优势就被稀释了 —— 因为包内容会随推导波动。
5. **清单里的依赖**：票 05 定「`dependencies` 只用于**生成顺序**，不用于组合」。
   推导时要不要自动填依赖（造「骑马的牛仔」自动推出「马」和「牛仔」）？

## Answer

**结论：清单 = `{spec, source}` 两层的 `asset-recipe/v1`，与资源包自描述不共用类型。
真跑了一次「需求 → 清单」的推导：14.8 秒、一次通过 schema、8 个资源。
144 条测试全绿。**

### 0. 五问的裁决

| 问题 | 裁决 |
|---|---|
| ① 清单的形状 | **嵌套 `{spec, source}`** —— 清单**不是** manifest 的输入版，两者不共用类型也不互相扩展 |
| ② 推导的输入 | **需求文本 + 已存在的 StyleSpec 文件**。参考图**不进 prompt** |
| ③ 两阶段 | **是** —— 先出清单、人过目、再生成 |
| ④ 幂等 | 不承诺「两次推导逐字节相同」，但承诺「**清单一落盘就不再变**」 |
| ⑤ 依赖 | **自动填，但只进清单、只用于生成顺序**；且引用的 id 必须在清单里 |

### 1. 清单的形状：两层，而且两层在文件里就分得开

```jsonc
{
  "format": "asset-recipe/v1",
  "id": "shift-change-assets",
  "styleRef": "authoring/stylespec.json",
  "assets": [
    { "spec": { /* 票 27 的四类 AssetSpec —— **纯意图，不含任何路径** */ },
      "source": { "kind": "generate" } },                       // 让管线画
    { "spec": { /* … */ },
      "source": { "kind": "import", "ref": "fixtures/…",        // 或人给的位图（票 23 的两种形态）
                  "sheet": { /* 网格 + 逐格命名 + 动画分组 */ },
                  "background": { "tolerance": 30 } } }
  ]
}
```

**为什么不共用类型**：票 20 已定 Spec 与 Artifact 是两层，而「一个文件既是输入又是输出」正是
最容易混淆的那种设计。清单说「要做什么」（意图 + 帧从哪来），manifest 说「做出了什么」
（文件、checksum、图集）。有一条测试专门守着这个边界：**拿一份 manifest 形状的对象当清单喂进去会被拒**。

**`source` 只有两种**：`generate`（不写任何路径 —— 路径是产物，由管线自己产、自己记进 manifest）
或 `import`。而 `import` 的**目标尺寸不写在 source 里** —— 它就是 `spec.size`。
清单只说「从哪来」，「要多大」是规格的事；分开才不会出现两份互相矛盾的尺寸。

### 2. 推导的输入：需求文本 + StyleSpec

两者**互相约束**（「我要一头牛」与「这个世界是灰绿+奶油+橙」是同时被满足的），所以必须同时给。
逻辑顺序是 **StyleSpec 先、清单后** —— R11 已经定了 StyleSpec 是人在会话里看图产出的文件，
它必然已经存在。

**参考图不进 prompt。** R11 定了那条通道的产物就是 StyleSpec，管线只消费文件。
实测这不影响推导的可用性：StyleSpec 的 `material` / `shapeLanguage` 词汇**明确出现在**模型给的资源描述里
（"worn painted metal"、"rust streaks"、"hard-edged"、"rounded corners only on handheld props"）。

### 3. 两阶段：是

R7 已经定了「清单先落盘成文件」，两阶段几乎是它的直接推论。更实际的理由：
**清单是最后一个能廉价改主意的地方** —— 过了它就是几分钟的生成，而错误只会表现在产物上。
[票 30](30-cli-and-mcp-surface.md) 的操作集合里因此要多一个「只推导清单」。

### 4. 幂等：不承诺可复现，承诺**冻结**

LLM 推导做不到逐字节幂等，硬求它只会得到一个假的承诺。所以规矩和资源包一样：

- 推导是一次性动作，产物是**文件**；文件之后就是唯一真相；
- 再推导产出**新文件**，**绝不覆盖**（与 `v<N>` 同一条规矩）；
- 于是「人给清单」那条路的确定性优势**完整保留** —— 因为下游只认文件。

### 5. 依赖：只用于生成顺序

票 05 定了「依赖只用于生成顺序，不用于组合」，这条在清单里落成**可校验的规则**：
`dependencies` 引用的 id 必须是清单里已声明的、且不能自引用（跨出清单的依赖无处兑现）。
**实际推导出的清单一处都没用它** —— 这是对的：那份需求里没有真正的顺序约束。

### 7. 🔴 两次推导暴露的两件事

**① 模型的默认动作是「把角色的每个动作拆成一个资源」，而这正好打掉了帧间一致性。**
第 1 次它产出 `player-idle` / `player-run` / `player-jump` **三个资源**，还用 `dependencies`
把后两个挂到第一个上 —— 像是在用「生成顺序」补「它们属于同一个东西」，而票 05 明说依赖
**只用于生成顺序**。[票 22](../animated-player/README.md) 实测过：多状态**必须一次调用生成**
才能保证是同一个角色；拆成三个资源就是三次独立调用，正是那个失败模式。

把这条写成 prompt 规则之后，第 2 次自己就收成了一个资源、三个动画。
**这条规则现在是清单契约的一部分含义** —— 写进了 `asset-recipe/v1` 的推导 prompt。

**② 锚点是推导里最不可靠的字段。** 两次跑同一段需求：

| 资源 | 第 1 次 | 第 2 次 |
|---|---|---|
| 货箱 | (0.5, **1**) | (0.5, **0.72**) |
| 漏电地板 | (0.5, **1**) | (0.5, **0.8**) |
| 罐头 | (0.5, **1**) | (0.5, **0.5**) |
| 地砖 / 背景 / 招牌 | (0,0) / (0,0) / (0.5,0.5) | 同左（**稳定**） |

理由很直接：**推导发生在产物之前，模型看不到画**，只能猜「脚底在画布上的比例」。
而票 26 裁定锚点必须被**声明**、不能从 ink 包围盒自动推。
两条合起来说明：**锚点在两阶段流程里是人该重点看的那一栏** —— 这正是 §3 的理由之一。
