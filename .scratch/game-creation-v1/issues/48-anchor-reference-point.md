## Question

`Entity.at` 与 `player.at` 是「**资源锚点的落点**」还是「**盒子的左上角**」？
契约里**没有写明**，而[票 41](41-game-config-landing.md) 落地的 `auditGameConfig`
**在同一个函数里用了两种读法**：

| 用处 | 现在怎么读 | 代码 |
|---|---|---|
| 越界检查 | **左上角** | `inWorld(where, e.at, s.w, s.h)` → `at.x + w > W` |
| 台阶高度 | **底边** | `step = groundY - e.at.y` |
| 出生点卡在 solid 里 | **左上角**（注释自称是近似） | `inside()` |

### 方向其实已经定了 —— 由**包**定的

`fixtures/packs/last-train/v2/` 里每个资源每帧的 `anchor`：

| 资源 | anchor | 读法 |
|---|---|---|
| `player-traveler` | `{x:.5, y:.95}` | **脚** |
| 世界里的道具（行李堆 / 雨棚台阶 / 皮箱 / 车厢 / 信号灯） | `{x:.5, y:1}` | **底边中心** |
| `hud-lost-slots` | `{x:0, y:1}` | **左下角** |
| `hud-pip` | `{x:0, y:0}` | 左上角 |

⇒ **`at` 是「锚点落在哪」**，盒子由「锚点 + 尺寸」推出来。

旁证：票 09 那句「锚点落在这一点上（角色的**脚**在这里）」在锚点语义下
**不是特例，而是通则的一个例子** —— 玩家因此不需要任何特殊处理。
[票 44](44-implement-runtime-shell.md) 的外壳已经**整体**建在这个方向上（纯层的 `boxAt()` 是唯一算盒子的地方）。

### 现在的读法会**拒掉合法的 config**

一个底边锚点、站在地面线上的东西（世界里的绝大多数），正确写法是 `at.y = 地面 y`；
而越界检查算的是 `at.y + h` —— **凭空多出一个 `h`**。
于是「世界高 270、地面线 250、东西高 40」这种再正常不过的摆法会被报「落在世界之外」。

### 要做的

1. **`auditGameConfig` 的盒子统一由「锚点 + 尺寸」推出来。**
   它已经在读 manifest（`sizeOf`），再用一次 `anchor` **不是新依赖**。
   `inWorld` / `inside` / 台阶高度**全部用同一个盒子**（台阶用盒子的**底边**）。
2. **撤掉票 41 那次「修夹具」。** `packages/contracts/tests/game-config.test.ts` 里
   HUD 面板的 `at.y` 当时被按左上角近似从 `262` 改成了 `230` ——
   锚点语义下 `{x:0,y:1}` + `262` = 底边离地 8px，**262 本来就是对的**。改回去。
   同一份夹具里 `luggage` 的 `at.y = 210`（盒底 210、地面 250）也要重新过一遍。
3. **补反例**：
   - 底边锚点的东西摆在地面线上**不许**被报越界（现在会被报）。
   - 真越界（盒底超过世界底）**必须**被报。
   - ⚠️ 加一条**直接断言锚点语义**的测试。这一条之所以能悄悄错这么久，
     就是因为**没有一条测试问过「盒子是从哪儿算的」**。
4. ⚠️ **schema 一个字都不动**（`.strict()` 照旧）—— 变的只是校验器怎么算盒子，形状没变。

### 不归本票

- **`hud.*` 的屏幕空间边界**（世界宽 1440 vs 视口宽 480）—— 那是另一条，
  已写进[票 33](33-runtime-assembly.md) 的抬头（第五族）。
- **外壳** —— 它已经按锚点语义写好了，本票不必动它。

## Answer

**结论：校验器的盒子现在**只从一处**算出来 —— 由「资源锚点 + 尺寸」推。
票 41 那次「修夹具」撤回了；票 44 的外壳与校验器现在**用同一个公式**。
全套 **318/318** 绿。**决定性的一条**：锚点语义的 last-train config 从 **4 条错误 → 0 条**。

### 1. 改了什么

`auditGameConfig` 里加了 `boxOf(at, size, assetId)` —— **全函数只此一处算盒子**，
三处读法（越界 / 出生点 / 台阶高度）全部走它。之前是三处**各读各的**：

| 用处 | 以前 | 现在 |
|---|---|---|
| 越界检查 | `at` 当**左上角**（`at.x + w > W`） | 盒子的右下角 |
| 出生点卡在 solid 里 | `at` 当**左上角**（注释自称是近似） | 盒子 |
| 台阶高度 | `at.y` 当**底边** | **盒子的底边** |

⚠️ **`anchor` 不是新依赖** —— 这个函数本来就在读 manifest（`sizeOf`），
再多读同一个数组里的一份字段而已。票 41 那句「这一层不该依赖它」的理由站不住：
它**已经**在依赖 manifest 了，而少了锚点根本算不出盒子。

### 2. 撤回票 41 的「修夹具」

`base()` 里 HUD 面板的 `at.y` 从 `230` 改回 **`262`** —— 锚点语义下
（锚点 `{x:0,y:1}`、高 32）盒子是 `230..262`，**底边离世界底 8px，本来就是对的**。
票 41 那次是**修错了地方**：盒子算错，不是夹具写错。

连带承认第二处：「出生点卡在 solid 里」那条反例也写在左上角语义下
—— `(510,220)` 落在 `(500,210) 40×40` 这个**根本不存在的**盒子里。
已改成落在真正的盒子 `(480,170) 40×40` 内。

### 3. 新增三条测试（票 48 §3）

- **站在地面线上的东西不许被判越界** —— 以前必挂（`250 + 40 = 290 > 270`，凭空多一个 `h`）
- **真越界必须被报** —— 盒底 280 > 世界底 270
- ⭐ **锚点决定盒子从哪边长** —— 同一个 `at.x`，`y = 262` 合法、`y = 271` 越界。
  **这一条是锚点语义的守门人**：这个 bug 能悄悄活这么久，正是因为
  **没有一条测试问过「盒子是从哪儿算的」**。

### 4. 验证

- `packages/contracts`：**24 条**全绿（21 + 3 新增）
- 全套 **318 / 318** 绿 · `pnpm check` 绿
- 外壳的冒烟**复跑仍全绿**（本票没动外壳，但校验器与外壳共用同一个公式，值得确认没连带）
- ⭐ **锚点语义的 last-train config：4 条错误 → 0 条** ——
  「能过校验」与「渲染出来是对的」**从此不再互斥**。这正是[票 33](33-runtime-assembly.md) 被挡住的那一条。

### 5. 一条**没做**的（有意）

越界检查**仍然只看远端边**（`x + w > W` / `y + h > H`），**没有**加 `x < 0` / `y < 0`。

理由：那是**一条新检查**，不是「把盒子算对」——把它混进来，等于在一张
「修参考点」的票里悄悄改变谁能过审。要不要加、加了会不会误伤
（比如故意探出左边的装饰物）是**另一个决定**。

⚠️ 但要知道它在：锚点语义下，一个 `at.x = 0`、锚点 `{x:.5}` 的东西，
盒子会伸到 `x = -20` 而**不会被报**。已写进[票 33](33-runtime-assembly.md) 的抬头
（它管装配期那一族校验）。

### 6. 解锁

⭐ **票 33 由此解锁** —— 它是通往产物 B 的最后一段路。
