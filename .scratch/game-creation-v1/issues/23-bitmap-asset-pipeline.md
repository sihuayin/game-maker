### 必须回答的问题

1. **⚠️ 帧一致性：GPT 那张基准图的 trick 是「一张图含全部帧，再按网格切」。**
   我们没测过 wan 能否产出**对齐的网格 sheet**（4 方向 × 8 帧 = 32 格）。
   这是位图路线的生死问题：如果切出来帧与帧错位/尺寸不一，动画就废了。
   要实测：① 让 wan 直接画 N×M 网格 sheet；② 若不行，逐帧生成 + 按 alpha 包围盒
   自动对齐裁切；③ 再不行，只生成单帧静态 + 用 drawlist 做位移假动画。
   三条路的产物都要渲染出来人眼判。
2. **分工边界**：哪些 Asset 走位图、哪些走 drawlist？
   初步提案：**角色/敌人/NPC 走位图**（玩家盯得最多、需要手绘质感）；
   **平台/砖块/拾取物/招牌走 drawlist**（可平铺、可校验、可廉价 repair）。
   边界判据是什么？「需要有机形状或手绘质感」？还是「数量少且重要」？
   这个判据要写成规则，不能每次人肉决定。
3. **`AssetSpec` / `ArtifactRef` 怎么区分两种 Asset？**
   `ArtifactRef.type` 现在是 `z.enum([...,"asset",...])`，没有子类型。
   提案：加 `kind: "bitmap" | "drawlist"`，或靠 `path` 后缀（`.png` vs `.json`）推断。
   **靠后缀推断是隐式契约，会漂移** —— 倾向显式字段，但要改契约。
4. **位图的版本化与 repair**：文档第 21 节的版本化在位图下依然成立
   （`player/v1.png`, `v2.png`）。但 **repair 的语义变了**：
   drawlist 的 repair 是改一个数字；位图的 repair 是**重新生成**（抽奖）
   或**图生图编辑**（wan 支持 image 输入，可能可以做局部修改 —— 未测）。
   票 16 的 RepairAction 需要新增位图策略（`BITMAP_REGENERATION` /
   `BITMAP_IMG2IMG_EDIT`），且 **Stalled 检测在抽奖式 repair 下更重要了**。
5. **像素网格后处理**：生图产出 1024×1024，但游戏要 32px 网格的清晰像素。
   谁负责降采样/量化？要不要「量化到 StyleSpec.palette + 最近邻缩放到目标尺寸」
   的后处理步骤？这一步做不好，游戏里 sprite 会发糊 ——
   而「发糊」恰恰会毁掉像素风的全部价值。
6. **成本与配额**：wan2.7-image-pro 走的是千问 Token Plan。
   一次 run 要多少张图（角色 6 帧 sheet ×1 + 敌人 ×N + …）？
   Token Plan 的**图像配额**是否与聊天共享？用超了会怎样？
   （票 19 的成本核算要并入这一项。）

### 1. 🔴 原型推翻了一个隐含假设：模型给的图**没有像素网格**

素材是 `fixtures/import/wan-player-1024.png`（1024×1024，模型按参考图风格条件生成）。
把它当「像素画」去重采样之前，先量了一下 —— 结果它不是：

| 测量 | 结果 | 含义 |
|---|---|---|
| 边缘位置对 k 取模的集中度 | k=2: **0.500**（均匀是 0.500）· k=16: **0.064**（均匀是 0.063） | **没有任何周期**，网格不存在 |
| 相邻像素平均色差 | **15.07** | 纯像素画的整数边界应接近 0 |
| 前景颜色数 | **61152** | 抗锯齿/重采样过的连续图 |
| 背景四角色 | **4 种不同颜色**（有渐变与噪点） | 不是平色，抠背景**只能按容差**，判等会留下大半背景 |

**所以「像素风」是风格，不是事实。** 这条通道做的不是「重采样回原网格」（没有那个网格），
是**重建**一个网格 —— 像素化，不是缩放。目标 25×48 对应 **16.9 倍**降采样。

这条事实决定了整条管线的形状，也解释了为什么票面第 ⑤ 问不能靠「选个插值算法」回答。

### 2. 裁决与落地

| 决策 | 裁决 | 落地 |
|---|---|---|
| 降采样 | **面积平均（alpha 加权）→ alpha 阈值 → 量化** | `downscaleArea()` / `thresholdAlpha()` |
| 颜色 | **量化到世界色板**（`paletteBinding: "quantized"`） | 复用票 21 的 `quantizeToPalette()` |
| 导入形态 | **单张独立 PNG**（+ 管线容差抠背景）**与 一张 sheet + 网格描述** | `keyBackground()` / `sliceGrid()` |
| 组合入口 | —— | `importBitmap()`（顺序写死，见下） |

**为什么是面积平均而不是另外两个**（原型出的实物对比在
[`../experiments/bitmap-import-draft/`](../experiments/bitmap-import-draft/)）：

| | 效果 | 颜色数（不量化时） |
|---|---|---|
| 最近邻抽样 | 保住眼睛与帽子纹理，但边缘偏噪 | 651 |
| **面积平均** ✅ | 眼睛在（偏软），最稳 | 771 |
| 色板投票 | 网格最干净，**眼睛被投没了** —— 小于一格的细节直接消失 | 9 |

面积平均是三种里唯一**不靠运气**的：最近邻的好坏取决于恰好采到哪个源像素，
换个目标尺寸结果就变。色板投票构造上保证 ∈ 色板、网格最干净，但代价明确得可怕 ——
它会静默丢掉所有小于一格的细节。

**「必须量化」的直接论据就是上表最后一列**：1200 个格子、651~771 种颜色，几乎每格一色。
那不是像素画，是照片。

**顺序不能反**：`importBitmap` 写死「先降采样再量化」。反过来的话，被量化掉的颜色在降采样时
还会参与平均 —— 等于用一堆已经丢掉的信息去决定每一格的颜色。有一条测试专门守着两种顺序结果不同。

### 3. 切片：只在图真有网格时成立

`sliceGrid()` 支持列数/行数/格尺寸/偏移/格间距，行优先返回。

⚠️ 但它的输入只能是**人给的 sheet**（Aseprite 排的、或别的工具导出的），
**不能是模型的产出** —— §1 已经证明模型产出没有网格。这条边界写进了函数的文档注释里，
免得下一个人拿它去切一张抗锯齿图然后困惑。

### 5. 一条诚实的记录：原型自己也踩了坑

第一版对比图把半透明像素的 alpha 原样写进联系表 PNG，看图器把它合成到**白底**上 ——
于是面积平均那一列看起来像套了一圈白边，我差点当成策略的缺陷去否决它。
修法是按 alpha-over 合成到联系图底色。

**半透明像素的渲染结果取决于谁合成它** —— 这正是像素风资源必须 alpha 二值化的原因，
现在有一条测试守着「导入结果里不存在半透明像素」。
