# 35. 位图从哪来：生图能力的合规使用边界

> **本票由[票 34](34-wan-quota-facts.md) 的调研结果直接催生**（2026-09-24）。
> 票 34 查明两件事，其中第二件是产品级问题：
> ① 千问 Token Plan 配额与聊天**共享同一个 Credits 池**，现已耗尽，复位 2026-10-15；
> ② 官方条款**明确禁止**把 Token Plan 的 key 用于「自动化脚本、自定义应用程序后端
> 或任何非交互式批量调用场景」，违者可能封订阅 / 封 key。
>
> 本图的 R3 写着「交付态 = 引擎中立的位图」，票 23 关心「位图的帧一致性」——
> 但**没人问过位图从哪来**。在 R3 之前「从 wan 生成」是默认答案，
> 现在这个默认答案既**当前跑不通**（配额）也**不合规**（条款）。必须重新回答。

## Question

1. **位图的四种可能来源，选哪个（或哪几个）**：
   - **(a) 人导入**：需要手绘质感的 PNG 由**人在合规的交互式工具里**产出
     （⚠️ 条款**明确允许** Claude Code / Cursor 这类「编程工具和智能体工具」中的交互式使用 ——
     这条恰好是我们的主场景），文件放进项目的 `inputs/`，**管线只读不调 API**。
   - **(b) 管线调用商用生图 API**：换一家没有此类限制的服务（需付费 / 新凭据；
     票 01 查过 MiniMax 余额为零、Google/OpenAI 无 key）。
   - **(c) 不做位图原生资源**：创作态统一为 drawlist，交付态 PNG **全部**由
     [票 21](21-drawlist-renderer.md) 的光栅化器产出。管线零 API 调用，绝对合规。
   - **(d) 照旧用 Token Plan**：**违反条款**，有封号风险。列出来只为显式排除。

2. **「交互式」的边界在哪**。条款允许 Claude Code 里的交互式使用 ——
   那么「agent 在 Claude Code 会话里，人点了确认，调一次生图」算不算交互式？
   「CLI 里跑 `game-maker assets gen --bitmap`」明显不算。
   **这条边界直接决定产物 A 的自动化程度上限**，要给出可操作的判据，
   而不是「尽量交互式」这种没法执行的说法。

3. **`inputs/` 是不是一个正式概念**。若选 (a)，产品 A 就有了第二类输入：
   除了「参考图 + 需求」，还有「人放进来的位图素材」。
   它怎么进清单、怎么与 StyleSpec 对齐（人工图的颜色可能不在色板里 ——
   那 R2 留下的「颜色 ∈ 色板」构造恒真性质对它**不成立**）、
   交付时怎么标注来源。

4. **对 R3 的影响**。R3 说「交付态 = 位图」，这条**本身仍然成立**
   （drawlist 光栅化也是位图）。但「**位图原生创作态**」这一半是否还保留？
   若不保留，R3 就退化成单层（drawlist 创作 → PNG 交付），
   架构显著简化；若保留，票 23 的帧一致性问题才继续存在。

5. **对票 23 / 票 22 的影响**，本票要一并交代清楚（它们都卡在这上面）。

## Answer

**两条决策，均由人类在 2026-09-24 的 grilling 中选定。**

### 决策一：位图原生创作态 = **(c) + (a) 组合**

- **(c) drawlist 是唯一的自动生成路径。** 产物 A 的管线**永不调用任何生图 API** ——
  绝对合规，且今天就能开工。
- **(a) 位图作为「人工导入通道」。** 需要手绘质感的 PNG 由**人在合规的交互式工具里**
  产出（条款明确允许 Claude Code / Cursor 这类「编程工具和智能体工具」中的交互式使用，
  那恰好是本项目的主场景），文件放进项目的 `inputs/`，**管线只读不调**。
- ❌ 排除 **(b)** 换商用生图 API：需要付费与新凭据（票 01 已查 MiniMax 余额为零、
  Google/OpenAI 无 key），且现在没有付费意愿。
- ❌ 排除 **(d)** 照旧用 Token Plan：违反条款，有封号风险。

**代价，明确接受**：放弃「管线全自动产出有手绘质感的角色」。
**换来**：一个今天就能开工、将来也不怕封号的产物 A。

**对 R3 的影响**：R3 的「交付态 = 位图」**原样成立** —— 而且现在更彻底：
交付态 PNG **全部**由[票 21](21-drawlist-renderer.md) 的光栅化器产出（含导入位图，
它们只是「创作态即终点格式」的特例）。「位图原生创作态」这一半**保留但降格**：
它是一条**输入通道**，不是一条**生产线**。

**推到下游的账**：
- [票 23](23-bitmap-asset-pipeline.md) 的问题 1（帧一致性 / 网格切分）与问题 2（分工边界）
  **性质变了** —— 不再是「wan 能不能画对齐的网格 sheet」，而是「**人放进来的 sheet 怎么切、怎么对齐**」。
  问题 5（像素网格量化）**原样保留**，且对导入位图更刚需（人给的图未必是目标色板）。
- [票 26](26-animation-representation.md)：帧的来源这一问基本被回答（drawlist 序列为主干，
  导入 sheet 为补充），可以据此往下走。
- **`inputs/` 升为正式概念** —— 产物 A 有了第二类输入，「参考图 + 需求」之外还有「人放进来的素材」。
  它怎么进清单、怎么与 StyleSpec 对齐、交付时怎么标注来源，**未决**，
  转入[票 24](24-asset-pack-contract.md) 的 manifest 契约。
  ⚠️ 特别地：R2 留下的「颜色 ∈ 色板」**构造恒真**性质对导入位图**不成立**
  （人给的图颜色不受控）—— 这是它进入管线时唯一必须额外处理的地方。

### 决策二：参考图 → StyleSpec = **人机协作的一次交互**

人在 Claude Code 会话里让模型看图、产出 StyleSpec JSON、存成文件，**管线只消费文件**。

- **合法**：条款点名的允许场景就是「编程工具和智能体工具中的交互式使用」。
- **几乎免费**：不需要任何管线化的 API 调用。
- **与 R7 同构**：R7 已定「资源清单两条路都开（人给 / 推导）」，
  现在把同一条哲学推广到 StyleSpec —— 产物 A 的入口从「一条命令全自动」
  变成「**一条命令 + 一次人工提取**」。
- 具体的操作流程（用哪张图、prompt 长什么样、产物存哪）归[票 15](15-stylespec-fixture.md)。

**⚠️ 顺带记一条未探的路**：CC Switch 里还挂着 `dragoncode.codes`（票 01 记「未测」）
与 Claude Official / Google Official 三个 provider，后两者当时是空配置。
**没有探** —— 人类判断不值得把本会话自己的凭据挪去跑管线（大概率是另一重条款问题）。
若将来自动化程度成了瓶颈，这里有一条可以回头的路。
