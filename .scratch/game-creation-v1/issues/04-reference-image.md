## Question

仓库里一张图片都没有，而 Q7 决定了「人类未提供 → 程序化造一张」。
造这张图不是随手画个占位符 —— 它是整条链路的**输入端**，
造得太弱会让后面所有 QA 都失去意义。

要造出的图必须同时能考验 StyleSpec 的这几个维度（文档第 12 节）：

- **Palette**：色板要够鲜明、够有限（cozy 风：暖绿 / 奶油 / 棕），
  这样票 12 的「颜色 ∈ palette」静态校验才有意义
- **Shape language**：圆润 / 柔和，要有可辨识的形状特征，
  不能全是矩形（否则「形状语言」这一维无法被区分）
- **Camera / Composition**：top-down，构图要有明确的空间层次
- **Lighting / Material**：手绘感、无强对比光影
- **Character style**：至少一个角色，可爱比例

**关键设计约束**：图里应该**故意不包含** cow / tractor / barn / fishing rod
这类后续会被生成的资源 —— 因为文档第 13 节的
**Novel Asset Style Consistency** 恰恰要求「参考图里没有的东西也必须属于
同一个视觉世界」。如果参考图里什么都画全了，这个最重要的维度就永远测不到。

需要决定：

1. 用什么造？（Node + Canvas / 手写 SVG / HTML + Playwright 截图）
2. 造几张？Q1 说的是「一张**或者多张**图片」—— 多图输入会不会改变
   StyleSpec 提取的语义（多图是取交集还是并集？冲突怎么办）？
   这个要不要现在就支持，还是先做单图？
3. 图放哪、叫什么、多大分辨率？（Q9 决定了 `demo/projects/<id>/inputs/`）
4. 要不要同时造一张**反例图**（比如赛博朋克霓虹风），
   用来验证 StyleSpec 提取不是永远返回同一套 cozy 结果？

调用 `prototype` skill 造出实物，然后让人类 react。
产出物链接到本票，不要贴进正文。

## Answer

### 0. 人类拍板的两件事

| | 决定 |
|---|---|
| 构图 | **C · 分层剖面**（天空 / 候车室内景 / 站台 三条横向带，各带一套光照）——三选一 |
| 题材 | **就用「黄昏的山间列车小站」** |

理由记在 provenance 里：C 是三种构图里**信息量最大的那张** —— 一张图里三种光照，
而且它明确交代了「**同一个世界里的不同空间**」，这正是 Destination 验收第 2 条要考验的东西。

### 1. 四个问题

**① 用什么造？** Node + **仓库自己的 `RasterImage`/`encodePNG`**（`packages/assets`），
50 行自写绘图原语（`draw.mjs`）。零第三方依赖、与管线**同一个 PNG 编码器**、不需要浏览器。
票面列的三个选项（Node+Canvas / 手写 SVG / HTML+Playwright 截图）**都没用上** ——
前两个要多一个依赖，第三个要多一个浏览器。

**② 造几张？** **单图。**[票 15](15-stylespec-fixture.md) 已实测：多图既不是取交集也不是取并集，
是**重合成**（两张图一起喂，出来的色板与两边交集都是 0，`constraints` 里还会出现自相矛盾的话）。
本票不再探多图。

**③ 图放哪、叫什么、多大？**

- 路径 `fixtures/reference/halt-dusk.png` —— 与旧的 `test.png` 并列，**不覆盖它**
  （`experiments/` 里还有引用）。provenance 用兄弟文件，不塞进 PNG。
- 尺寸 **480×270 原生**。实测（`probe_scale.mjs`）：原生与 **960×540 最近邻 2×** 的提取结果
  **没有实质差别**（都读出 "flat shading / no anti-aliasing / pixel grid / limited palette"）
  ⇒ 取原生：保住精确像素网格、文件最小、**每个像素都能由仓库自己的解码器验回色板**。

**④ 要不要反例图？** **不需要持久的反例图。** 票 15 已用一张一次性霓虹图证明
prompt 没被写死（与参考图输出零重合）。票 04 若再造一张持久的，是在重复一个已经被回答的问题。

### 2. 🔴 本票最大的产出：**上游重编码图片 ⇒ 精确读色不可能**

票面要求这张图「要能**真正考验** StyleSpec 提取（色板…都得有话说）」。
于是色板**刻意做小**：18 色，而且**每个像素都恰好是其中之一**。结果：

| 变体 | 图上真实色数 | 模型报的色数 | **精确命中** | 报出的色覆盖了多少像素 |
|---|---|---|---|---|
| A | 16 | 8 | **0** | **0.0%** |
| B | 16 | 9 | **0** | **0.0%** |
| C | 16 | 8 | **0** | **0.0%** |

决定性测试（`probe_reencode.mjs`）—— 送一张 **64×64 纯单色**图，问它是什么颜色：

```
  送 #4a6076  →  答 #5f6a76   ΔRGB=23.3
  送 #d9a441  →  答 #d2a53c   ΔRGB= 8.7
  送 #6b4a33  →  答 #8e7c68   ΔRGB=80.8
  送 #e6e2d6  →  答 #f2efe9   ΔRGB=26.0
  送 #2e3b4e  →  答 #595d66   ΔRGB=59.8
```

**五次零精确。** 纯色图都读不准 ⇒ **与图的色数、质量、格式无关**，是上游在模型看到之前
就把图转过一道（暗色被整体抬亮，像色彩空间/伽马转换）。

**这推翻了票 15 的一个推论。** 票 15 说「参考图有 122,240 色 ⇒ 没有精确色板可提取」，
读起来像是**那张图**的问题。现在知道：**换一张干净的图也一样。**
「提取精确色板」不是**有风险**，是**不可能**。

→ 已写进地图的环境事实段。**直接后果：别再拿「色板准不准」评价一张参考图的好坏。**
`palette` 永远是近似，而契约本来就只要求「颜色 ∈ 色板」（相对于 StyleSpec），
从不要求色板等于参考图。
