# 32. 固定 runtime 外壳的形态与验收

Type: grilling
Status: open
Blocked by: 09, 31
Map: ../map.md

> R8：demo = **固定 runtime + 数据**，AI 一笔代码都不写。
> 这个外壳**永不改变**，是所有 demo 唯一的代码。本票定它是什么、边界在哪、
> 以及「它一定跑得起来」这件事怎么被守住。

> 🔴 **2026-09-25（[票 18](18-artifact-ref-consistency.md)）—— 一条来自版本化的约束。**
> 站点产出在 `out/<gameId>/site/v<N>/`，**`N` 是站点自己的计数器，不跟资源包版本走**。
> 理由正是本票：**外壳还在写、会变，而包不变** —— 换了外壳就要出新站点，
> 那时若站点编号跟着包走，新站点就无处安放，只能覆盖，直接破掉「绝不覆盖」。
> ⇒ **「外壳版本」这件事被站点版本号隐式承载了。** 若你认为外壳本身也需要一个
> 显式的版本标识（写进站点产物里、可被读出来），那是本票该定的 —— 现在没有。

## Question

1. **外壳的成分清单**：按 Q15 的精神，属于「手写固定」的有 ——
   Phaser 主 scene、游戏循环、输入处理、碰撞、资源加载、相机、
   以及「读 game-config 并按其装配世界」的那段胶水。
   **逐项列出来，并判每项是不是真的能固定**：有没有哪一项是
   「看起来能固定、实际每换一个游戏就得改」的？
   （候选嫌疑犯：相机跟随策略、输入映射、UI 布局。若某项真固定不了，
   它就得变成 game-config 里的**数据** —— 那正是 R8 的边界所在。）
2. **`docs/文档.md` 第 6 节目录结构 / 第 55 节 Phase Interfaces 里，
   哪些属于外壳、哪些属于管线**？现有 `demo/src/runtime/orchestrator.ts`
   是「编排器」，R2 之后它编排的东西没了 —— 它变成什么？
3. **「一定跑得起来」怎么被结构性保证**：
   - 外壳自己跑一个**内置的空场景**（零数据或最小 fixture 数据）能不能起来？——
     这是最有价值的性质：**数据全错也不会白屏**。
   - 数据错了怎么办：报错、跳过该实体、还是渲染占位符？三种的用户体验差很远。
   - 这条性质要不要有一个**测试**守着（外壳 + fixture 数据 = 启动成功）？
     这不属于 R2 砍掉的 QA，属于**外壳自身的单元测试**。
4. **视觉风格从哪来**：外壳是固定的，但每个 demo 的 UI 外观不同 ——
   UI 资源（R4）与 game-config 怎么让外壳长出不同的界面？
   （候选：外壳只提供布局容器，样式全部来自资源包里的 UI 资源 + game-config 的摆放。）
5. **分辨率与缩放**：固定外壳意味着固定的画布策略（像素风用 `Phaser.Scale.NEAREST`、
   整数倍缩放）。这是外壳的常量还是 game-config 的字段？

## 产出要求

调用 `grilling` skill。产出**外壳成分清单（逐项判「真能固定 / 必须变成数据」）+
空场景最小数据集的草案**。
若第 3 条需要实物，调用 `prototype` skill 写一个最小 Phaser 外壳 + 一个故意的坏数据，
看它到底怎么失败。
