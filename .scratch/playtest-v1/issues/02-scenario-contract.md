## Question

裁定「试玩场景」是什么、长什么样、绑什么版本（`docs/v7.4/试玩.md` 范围内第 1 条 + 完成条件的「固定场景」）。至少定：

1. **场景本体**：一个试玩场景 = 什么？（a）一份**数据契约**（声明式：初始态 + 动作序列 + 断言，落 JSON/TS 文件，
   harness 读它跑）vs（b）一段**代码**（TS 函数，像现在 `runPlayable`/`runHazard`）vs（c）两者分层（契约描述
   「做什么」、代码实现「怎么驱动」）。现 smoke 场景是写死函数 —— 要不要改成数据驱动？
2. **动作语义**：动作用什么表达 —— 屏幕坐标（键/位移）还是**游戏语义**（「走到 pickup X」「在 gate 前跳」）？
   对应「已出局」的 `Semantic Test Action`，捡回后定义到多细。
3. **断言语义**：一个场景怎么算「通过」—— 断言哪些可观测量（collected 达 N / won=true / 某事件发生 / 无 console.error）？
   断言失败 = 场景失败，如何与归因（票 04）接口。
4. **版本绑定**：「版本绑定」绑谁 —— 场景 ↔ 游戏（pack/config/site 哪个版本）？还是场景契约自身有版本号
   （`playtest-scenario/v1`）？绑定错了怎么拒（像 `assertPublishableQa` 装配期拒绝，还是运行期报 mismatch）？
5. **场景集**：首版要哪几个固定场景（沿用 smoke 的 playable + hazard-reset + 负例，还是重定义）？
   场景怎么跟「回归基线」（票 05）挂钩。

HITL：用户逐字裁定，不替用户答。

## Answer（裁定 · 2026-10-27 用户逐字）

**总约束**：场景契约声明的是**可验证的玩法意图**，不是对某一版游戏内部实现的脚本化描述。这把票 02 和前三项
核心裁定接起来：单一 harness、外部观测优先、试玩结果可复现。

### 已收：Q1 场景本体 = (c) 声明式数据 + 薄解释器

职责边界：

- **场景契约**：定义初始条件、语义动作、前置条件、断言、终止条件、时限。
- **解释器**：读取状态、选择动作执行策略、采集证据、评估断言、生成结果。
- **观测适配层**：把现有 `READ_STATE` 转成统一观测，**不伪装成完整 Runtime Event Log**。
- **报告层**：记录场景版本、实际产物身份、动作轨迹、观测证据、最终判定。

**防退化**：虽然场景改成 JSON，但解释器仍通过 `scenarioId === "collect-and-win"` 分支硬编码整段流程——这只是把
函数名搬进数据文件。解释器可拥有少量通用控制逻辑，但**具体场景的玩法目标和动作序列必须来自契约数据**。

### 已收：Q2 动作抽象 = (b) 语义动作作为公共接口（捡回 Semantic Test Action）

动作语言例：`move_to`（移动到指定语义目标）· `jump_over`（跨越指定危险区域）· `wait_until`（等待可观测条件成立）·
`assert_state`（验证目标状态）· `reach_goal`（到达关卡目标）。

**重要限制**：语义动作不意味着游戏一定提供目标的稳定 ID，也不意味着 harness 能完美规划路径。动作执行允许的结果：
已完成+证据 / 执行失败+证据 / 目标无法定位 / 所需观测不可用 / 超时或无法判定。→ **具体枚举及其与五态结果模型的映射，
留给票 04**。

**动作轨迹必须记录实际执行的操作**（`move_to` 采用了哪些按键、持续多久、在哪些观测后调整策略），否则语义动作易读
却无法重放/比较回归。

**两种重放（不能承诺相同确定性）**：① **语义重跑** = 重执行相同场景契约，允许解释器据新观测调整操作，验证行为是否
仍成立；② **操作轨迹重放** = 重放之前记录的实际按键及时序，辅助定位具体故障。

### 已收：Q3 版本绑定 = (a)+(d)，强化拒绝规则

场景格式版本 + 目标产物版本是**两个独立维度**，都需显式记录：

| 维度 | 职责 | 规则 |
|---|---|---|
| 场景格式版本 | 解释器如何解析契约 | 未支持的格式版本必须拒绝 |
| 目标 site 版本 | 指定实际验证的游戏产物 | 版本不匹配必须拒绝执行 |
| pack 身份 | 确认游戏资源包 | 与目标 site 实际消费的 pack 一致 |
| config 身份 | 确认运行配置 | 与目标 site 实际使用的 config 一致 |
| shell 版本 | 记录运行时兼容信息 | 作兼容性证据；是否硬拒绝由兼容规则决定 |

**为什么主绑 site**：试玩对象是可运行的游戏交付物——相同 pack 不保证 config/页面相同，相同 shell 不保证逻辑/关卡
相同。故：场景声明目标 site 版本 → 加载时验证实际 site 身份 → 从 site 已有元数据解析 pack/config 依赖身份 → 报告记录
**实际运行的完整产物身份**（不复制场景文件里的预期值）→ 依赖不一致 / 身份缺失 / 版本无法解析时**拒绝执行**
（默认拒绝，不降级为警告后继续跑）。

**注**：site 版本号只能证明目录指向，不能单独证明内容未被原地修改；现有产物纪律若已保证目录不可覆盖则沿用，
否则考虑内容摘要作身份补充——不必为这张票立即引入新机制。

### 已收：断言模型（票 03 落地后裁定 · 2026-10-27 用户逐字）

**断言声明形状**：受约束的结构化匹配器 + `onInsufficient` 固定 `"unknown"` 不可配。

```ts
type Assertion = {
  id: string;
  requires: Observable[];     // 票 03 的 11 类闭事件 + 状态快照字段
  expect: Matcher;            // 受约束的结构化匹配器（非任意布尔表达式）
  within: Duration;           // 诊断性窗口
  onInsufficient: "unknown";  // 写死，作者无权改判 pass/fail
}
```

`expect` **不用任意布尔表达式语言**（会重新引入「声明漂亮、解释器判不了」）；`onInsufficient` **不可配**，
作者无权把「没证据」改判成 pass/fail。

**断言类型（闭集三类）**：`state`（某时刻状态谓词，如 `collected==4`）· `event`（闭事件发生/计数，如 `pickup` 4 次）·
`invariant`（窗口内恒成立，如 `hits==0`）。`wait_until` / `reach_goal` 是**动作**不是断言；`until` 是超时包装不是第四类。
加第四类必须说出对应的 03 可判性能力。

**三值求值（证据门控 + 否定可判）**：
- `pass` = 窗口内观测到条件满足，且 `requires` 观测量连续可读。
- `fail` = **双重门槛**：① 证据充分（轮询连续），**且** ② 断言的**否定条件在契约规定的窗口内确实可判**。
- `unknown` = 证据不足 **或** 否定条件在本窗口内不可判。
- **关键限定（用户逐字）**：「即使轮询一直正常，也不能把『没看到事件』一概判成失败。」`fail` **不是 absence 的默认归属**——
  absence 只有在窗口是**诊断性截止期**时才是 fail，否则 unknown。
- 落地取向：`within` 必须是诊断性窗口；机械可判的（如 hazard 断言 vs `hazards[].periodMs`，窗口短于一个周期则
  「无命中」不可判）在加载/装配期校验；机械不可判的是**契约作者显式义务**，不许运行时偷偷补判。

**场景聚合**：`fail > unknown > pass`——任一断言 `fail` → 场景 `fail`；否则任一 `unknown` → 场景 `unknown`
（不许读成 pass）；全 `pass` → 场景 `pass`。场景整体时限到期但未完成核心循环 → **场景级 `unknown`**（五态归票 04）。

### 已收：场景集（2026-10-27 用户逐字）

**三个独立维度（用户关键修正）**：

> 场景预期结果、实际试玩结果、基线资格是三个独立维度。不能因为场景被设计为「游戏失败」，就把每次运行都预先判为
> `GAMEPLAY_FAILURE`；也不能因为场景确定性强，就保证它一定适合做黄金基线。

- **场景预期结果** = 场景**设计意图**（声明的 `expectedOutcome`），只用于校验 harness 是否按设计工作，**绝不预填实际结果**。
- **实际试玩结果** = 每次运行从证据**独立归因**（票 04），与 `expectedOutcome` 无关。
- **基线资格** = 场景声明的 `baselineEligible`，**独立论证**，不由确定性自动推出（票 05 消费）。

**首版五场景集（一态一个，最小）**：

| 场景 | 层 | 预期结果（设计意图） | 基线资格 |
|---|---|---|---|
| `success-basic` | 游戏场景 | 成功 | 候选（须独立论证） |
| `failure-missing-pickup` | 游戏场景 | 游戏失败 | 候选（须独立论证） |
| `limitation-wide-patrol` | 游戏场景 | 代理限制 | 否（非确定性） |
| `env-no-chrome` | harness 条件 | 环境故障 | 否 |
| `timeout-hang` | harness 条件 | 超时 | 否 |

- 游戏失败先只做 **pickup 缺失**（复用现有负例、确定性最强）；地板开洞进 Not yet specified。
- 环境故障先只做 **Chrome 缺失**（最简注入）；站点加载失败进 Not yet specified。
- `baselineEligible` 在表里只是**候选**，最终资格由票 05 按独立论证裁定。

**现有 smoke 场景分层保留（Q6）**：`playable` → `success-basic`（复用）· `hazard-reset` → `invariant` 场景（进五态集）·
`hazard-legacy` + `gate`/`pickup`/`input` 三个负例 → **harness 自测**，单独保留、**不进五态场景集**
（它们测「探针能不能抓到坏」，混进来会让失败归因失真）。

**基线挂钩（Q7）**：场景声明 `baselineEligible`；票 05 据此决定存不存、比不比，但不假设「确定性 ⇒ 可基线」。

### 接口（给票 04 / 05）

- **票 04**：实际五态必须从证据独立归因，**不得用场景的 `expectedOutcome` 预填**；`expectedOutcome` 只用于校验 harness。
- **票 05**：`baselineEligible` 是场景独立声明的维度，**不由确定性保证**；票 05 尊重声明，不自行假设。
- **动作执行结果 ↔ 五态结果映射** → 票 04。
