## Answer（裁定 · 2026-10-27 用户逐字）

**总原则**：观测是「结构化证据」，不是「完整 Runtime Event Log」；断言级三值不得越权替代试玩级五态归因。
v1 只读外部（状态差）+ harness 侧错误捕获，**零会话内打点**。

### Q1 — 事件 vs 状态：边-快照二分 + 闭事件集 ✓

**事件 = 离散状态跃迁（边）**；**状态快照 = 连续量 + 几何**。事件集是 harness 只认的**闭集（11 类）**：

`scene-ready` · `spawn` · `pickup` · `win` · `chest-open` · `danger-hit` · `danger-erupt` · `land` · `jump` · `reset` · `runtime-error`

断言（`wait_until` / `assert_state`）只能引用闭集内的可观测量。状态快照：`x/y/vx/vy/scrollX`（连续）+
`solids / gate / 实体坐标`（几何）。外壳无 `.emit()` 事件源，闭集全部由状态差 + harness 错误捕获推导。

### Q2 — 三值判定 + UNKNOWN：pass / fail / unknown，unknown 一等 ✓

- `pass` = 证据充分且满足；`fail` = 证据充分且不满足；`unknown` = **结构性不可判**（缺少能下结论的证据，不是碰巧没看到）。
- `unknown` **不是** `fail` 的兜底，是「无法下结论」的正式名字（对齐 [[结构性不可判]] 与交付层 `incomplete`）。
- 具体哪些情况强制 `unknown` 由 Q6 表逐条钉死。
- ⚠️ **断言级三值 ≠ 试玩级五态**：五态（成功/游戏失败/环境故障/代理限制/超时）是票 04 的事；断言级不能越权替代五态归因。

### Q3 — 观测产物形状：`events.jsonl` + `trace` + `result.json` 摘要 ✓

- `events.jsonl`（append-only，一行一事件）承载**事件流**。
- `trace` 承载**状态快照**（沿用现有）。
- `result.json` **退成摘要**（ok / 三值判定 / 证据引用），**不再塞原始轨迹**。

### Q4 — 会话内打点范围：v1 零打点，机制保留 ✓

- **v1 不注入会话内打点。** 11 类事件继续状态差推导；`runtime-error` 用 harness 捕获的错误。
- 事件记录注明 `source`：轮询推的用 `poll`；**错误事件用符合其真实来源的标记，不为统一而伪造为 `poll`**。
- 同一轮询间隔内多次变化 / 计数器被清零 / 瞬时事件无法还原 → 按证据粒度返回 `unknown`。
- **将来重新开启打点的条件**：出现一条当前确实无法判定、且业务上必须判定的断言，**并且**钩子可靠性经过验证。
  这不是否定打点，而是把它变成由真实证据缺口驱动的后续需求。

### Q5 — `events.jsonl` 字段集 + 约束 ✓

v1 基线（与提案一致）：

```json
{"v":1,"seq":12,"t":3450,"frame":207,"type":"pickup","actor":"pickup[2]","params":{"collected":3,"expected":4},"source":"poll"}
```

字段职责：`v` 观测产物格式版本（独立于场景格式版本）· `seq` 保证日志记录**全序** · `t` 相对单调时间 ·
`frame` 尽力获取的辅助信息 · `type` 属于闭事件集 · `actor` 引用相关实体 · `params` 承载事件数据 · `source` 追溯证据来源。

补充约束（用户逐字）：

1. **`source` 必须表达实际来源。** v1 至少 `poll`；将来启用会话内打点再扩展 `tap`；harness 捕获的错误若不来自轮询，
   用与其**真实来源**对应的值，不能混入 `poll`。
2. **`actor` 不是天然稳定的跨版本 ID。** `pickup[2]` 只能在**明确的实体排序与作用域规则**下解释；无法可靠定位实体时
   用 `null`，**不允许猜测**。
3. **`params` 按事件类型定义 schema**；不许任意字段混入后被下游解释器当成可靠证据。
4. **`frame: null` 合法**，且**不得用它代替 `seq` 的排序功能**。

### Q6 — 闭事件集可判性表（计数级可判、帧级可能未知）✓

| 事件 | v1 可判范围 | 必须 `unknown` 的典型情况 |
|---|---|---|
| `scene-ready` | 首次成功读取并确认场景可用 | 读取链路异常导致无法确认场景状态 |
| `spawn` | 首次观测到玩家落地等约定的稳定初始状态 | `onFloor` 缺失，或无法区分初始状态与后续落地 |
| `pickup` | 从 `collected` 或 `pickups[].active` 变化推断收集 | 同一轮询间隔内多次拾取，无法还原次数、顺序或时序 |
| `win` | `won` 状态发生变化 | `won` 不可读，或无法确认状态变化的有效性 |
| `chest-open` | `chests[].opened` 状态变化 | 字段缺失，或无法确定对应宝箱身份 |
| `danger-hit` | `hits` 计数增量 | 无法还原确切命中帧，或命中计数被 reset 清零 |
| `danger-erupt` | `dangers[].state` 发生可识别变化 | `state` 缺失，或状态变化不能唯一映射到 eruption |
| `land` | `onFloor` false→true | 中间跃迁被漏采，或前后状态不足以确定发生了落地 |
| `jump` | `onFloor` true→false，且符合约定的起跳推断条件 | 同一轮询间隔内连续起跳、落地，无法还原次数 |
| `reset` | 位置瞬移并伴随约定状态归零 | reset 与正常移动或其他状态跃迁混淆 |
| `runtime-error` | harness **实际捕获到**的 console/exceptions 错误 | 不把未捕获到错误解释为运行时绝无错误 |

**两处重要修正（用户逐字）**：

1. **`scene-ready` 永不 ready 不应直接成为断言 `fail`。** 在契约约定的启动期限内仍未 ready，只能确定「启动条件未满足」。
   启动日志或其他证据足以证明环境故障，才可归为环境故障；原因无法判定，则由**票 04** 决定对应的试玩结果。
   断言级三值不能越权替代试玩级五态归因。
2. **`spawn` / `jump` / `land` 需要明确推断规则。** 首次读到 `onFloor=true` 支持「玩家处于地面状态」，但不能在所有情况下
   证明**刚刚发生了 `spawn`**；`onFloor` true→false 支持起跳推断，但**不必然证明玩家执行了主动跳跃**（也可能是跌落或其他
   状态变化）。事件名可保留，但**载荷和证据必须明确表达这是状态差推断，而不是直接观察到的游戏内部事件**。

### 对票 02 的接口

本票产出「可观测量全集 + 三值可判性表」。票 02 断言模型必须：

- 每条断言声明**所需观测量**（只能来自 Q1 闭集 + 状态快照）、**判定条件**、**超时条件**、
  **证据不足时如何返回 `unknown`**。
- 每条场景断言都落到 Q6 表的具体能力，**不依赖尚不存在的 Runtime 事件源**。
