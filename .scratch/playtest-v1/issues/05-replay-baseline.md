## Question

裁定「可重放测试与回归基线」（范围内第 4 条）。至少定：

1. **「可重放」的层级**：重放什么 ——（a）**输入级**（记录按键/时序，原样重放）vs（b）**动作级**（记录语义动作序列，
   重放时按当前状态重新决策）vs（c）**证据级**（重跑同一场景，比较产出证据是否一致）。哪种是「可复现试玩报告」想要的？
2. **确定性**：同一场景两次跑，什么**必须**一致（判定一致？轨迹一致？事件序列一致？），什么**允许**抖动（物理帧时序、
   截图字节）？重放如何保证可复现（固定种子 / 固定输入脚本 / 固定时序）？
3. **回归基线**：基线是什么（某版本场景的**黄金产物**——判定 + 事件序列 + 证据指纹）？存哪（`out/` / 本 effort 目录 /
   入库 `fixtures/`？）、怎么绑版本（场景 + pack/site 版本）、回归怎么比（精确 diff / 容忍阈）？基线从哪来
   （真实产物第一次跑存为基线，还是手写）？
4. **回归失败语义**：比基线差了算什么 —— 判据（阻断）还是观察（只报）？会不会引入新质量门禁（对照
   [[观察 / 判据]]边界，别擅自加判据）？

## Answer（裁定 · 2026-10-27 用户逐字）

**总原则**：**重跑语义，比较判定；记录输入用于诊断，不拿不稳定的物理轨迹充当回归真相。**

### Q1 — 三层分工 ✓

| 层次 | 职责 | 参与回归 pass/fail |
|---|---|---|
| **语义重跑** | 重执行同一场景契约，解释器据新观测重新决策 | **是**，提供回归输入 |
| **操作轨迹重放** | 记录并尽力重放实际按键及时序，辅助定位故障 | **否**，仅作诊断 |
| **证据级比较** | 比较新运行与已登记基线的规范化证据 | **是**，形成回归比较结果 |

三条锁定要求：

1. **语义重跑复现的是契约执行与判定，不是逐帧运动轨迹**：同场景 + 同版本绑定 + 同归因规则 ⇒ 判定结果确定；
   真实物理轨迹不要求完全一致。
2. **操作轨迹必须成为真实产物**：新增 `input.jsonl`，记录实际发出的输入（`type` / `key` / `code` / 相对时间 `t` /
   序号 / 必要动作来源）；具体 schema 归实现票。**不得把状态快照 `trace` 误称输入轨迹。**
3. **操作轨迹重放不得成为回归通过依据**：可用于重现故障、缩小范围；Arcade 可变步长物理不保证跨机器复现运动结果。

### Q2 — 确定性契约：判定确定性 ✓

**必须一致**（同场景版本 + 同实际产物身份 + 同 harness/interpreter 版本 + 同判定规则下）：

- 最终 `PlaytestOutcome`；
- 每条断言的三值结果 `pass / fail / unknown`；
- 离散终态（`collected` / `won` / `hits` / 宝箱开启 / pickup 生效集合）；
- **基线明确覆盖且证据充分**的规范化事件计数。

**收紧（用户逐字）**：不是所有观测事件计数都天然必须一致。事件计数只有**观测语义足够可靠、场景明确声明受比较、
证据充分**时才能作基线判据；否则标为不可比较或不符合基线资格——**不得为通过比较补造事件**。

**允许抖动**：帧时序与轮询时间戳 · 实体 `x/y/vx/vy` 数值 · 同一轮询窗口内无法确定先后的事件 ·
截图字节与 `frame` 编号 · 不影响判定的其他运行时细节。这些差异**不能直接触发回归失败**；
尤其不得由轮询结果推断未经观察的事件顺序。

**保证手段**：

1. 动作节奏按**观测步 / 逻辑步骤**推进，避免墙钟抖动影响决策；
2. 固定轮询间隔与场景时限，**实际采用值写入报告**；
3. 固定 Chrome flags / viewport / DSF / 渲染路径，**实际值写入报告**；
4. 把影响决策的 `Date.now()` 改为步骤计数或受控逻辑计时（尤其 stuck 检测、jump cooldown）。

**实现边界（用户逐字）**：改 `Date.now()` **不等于物理模拟已确定**——只消除代理决策对墙钟的直接依赖，
不消除可变步长物理差异。基线比较必须继续依赖判定级证据与显式声明的规范化字段。

**v1 不引入随机种子**：当前运行时无随机源；将来内容真正引入 RNG 时再单独评估种子与随机状态的版本绑定。

**对 `baselineEligible` 的约束**：

- 只有能**稳定产生可比较规范化判定证据**的场景才有资格建基线；
- `UNKNOWN`、结构性不可判断言、无法稳定观测的事件**不得**被强行转成稳定基线值；
- `baselineEligible: true` 仅表示**允许申请**建基线，不表示基线已存在，也不代表每个字段都适合逐值比较。

### Q3 — 基线本体、资格、晋升与存放 ✓

**(a) 身份与内容**：一份**自足** JSON，含 `baselineId` / `identity` / `coverage` / `expected` / `source`。

- **新增 `baselineFormatVersion`**（用户补充）：与 `scenario.formatVersion` 是两个独立维度；
  格式升级时旧基线**不得**按新格式静默解释。
- `identity` 任一必需字段不匹配 ⇒ `not-comparable`，不是 `changed` 也不是 `match`。
- `coverage` 是**唯一比较范围**；未声明字段只观察、不比较。
- `expected` 保存晋升时接受的规范化值；**比较器不回读原始运行拼凑基线**。
- `UNKNOWN` 断言、证据不足字段、不稳定事件类型**不得**进覆盖。
- 基线身份必须绑定**实际产物身份 + 判定规则版本**，不能仅凭 `packId` 或场景名认定同一基线适用。

**(b) 资格与晋升**：

- `baselineEligible: true` 仅代表申请资格；
- 新建基线要求：① 至少**连续两次干净运行**，规范化投影完全一致；② 人工显式晋升；③ 填写覆盖理由与审计信息。
- **「两次干净运行」定义（用户补充）**：两次运行使用**相同身份绑定、相同场景、相同判定规则**，且均**没有**
  影响比较的 `UNKNOWN`、证据断档或未归因运行错误。否则两次表面一致可能只是「两次都没观察到问题」。
- **允许记录非 `SUCCESS` 的已接受行为**（如 `failure-missing-pickup` 的 `GAMEPLAY_FAILURE`）——
  基线记录的是经过明确接受的行为，不是自动认可游戏质量。
- **普通试玩、发现变化、CI 检测差异，均不得自动新建或覆盖基线**；重定基线必须显式、留痕、经入库 diff 审计。

**(c) 存放位置**：`fixtures/playtest-baselines/<baselineId>/`，与动画基线入库方式一致。

**批准的工作树纪律加性例外（用户逐字）**：

> 允许新增 `fixtures/playtest-baselines/` 及其基线文件；**不得修改、删除或重写既有 fixture**。

不另建顶层 `baselines/`，也不把长期基线放进 `.scratch/`。

### Q4 — 回归语义：纯观察，不增加第二套判据 ✓

比较器返回三值：

| 结果 | 含义 | 对交付状态的影响 |
|---|---|---|
| `match` | 身份匹配，全部覆盖字段可比较且一致 | **无** |
| `changed` | 身份匹配，至少一个覆盖字段有差异 | **无** |
| `not-comparable` | 身份不匹配或覆盖证据不足 | **无** |

- `changed` 必须附结构化 diff（至少字段路径、基线值、本次值）；
- `not-comparable` 必须说明原因，**不能被 CLI / 报告 / 消费者当作 `match`**；
- **基线差异不改变** `PlaytestOutcome`、断言三值、`DeliveryCheckStatus`、`DeliveryVerdict`；
- 报告与 CLI 用「**与基线不同**」等观察性措辞，**不把 `changed` 称作「回归失败」**。

**「足以判定回归失败」的唯一来源**：票 02 的场景契约断言 + 票 04 的证据归因。
若某个变化必须阻止交付，应写成明确的场景契约断言并说明「为什么它不是有意设计变化」，
**不得**偷偷把基线快照升级成第二套判据。

**不稳定覆盖字段**：干净运行中发现不稳定 ⇒ ① 明确告警；② 降级为仅观察，或把基线标记为需重新审核；
③ **不得**自动放宽阈值、伪造证据或覆盖旧基线。覆盖范围的修订必须显式并留审计记录。

### 实施范围（用户 2026-10-27 授权）

票 05 裁定已足以启动 Harness 实现，分三层：

1. **可复现判定基础**：语义重跑、输入轨迹记录、规范化证据投影、确定性归因；
2. **基线机制**：身份校验、显式覆盖、三值比较、人工晋升、审计记录；
3. **交付接入**：仅展示基线比较结果，**不改变票 04 的交付判定**。

实现仍须遵守票 04 硬约束：`UNKNOWN` 不升 `pass`、代理限制不升 `pass`、必需场景未执行不升 `pass`。
**基线比较器不得成为绕过契约验收的第二条通道。**
