# 05. 失败时报的「已经花掉的」是**下界** —— 在飞的那几笔既没落账、也没落盘

> **由 [`跑一次完整生图包走通 site`](04-image-pack-e2e-through-site.md) 的那两次真跑兑现出来的。**

## Question

```
✗ OpenAI 形态生图失败（3 次内）：Unexpected end of JSON input
（连「已经花掉的（N 次调用 · M 次往返）」那一行都没有）
```

**没有那一行本身就是结论**：它只在账非空时打印 ⇒ **账上一笔都没有**。
而那一跑**确实花了钱**（3 次尝试都发出去了）。

机制（读代码就成立）：`opts.ledger?.push(…)` 在**调用回来之后**（`pack.ts:383`），
而失败时 `ops.ts` 读的是**那一刻**的 `ledger.length`；并发是 3 ⇒
**还在飞的那几笔既没落账、也没落盘**（落盘也一样：原图是跟着回来才写的）。

⇒ 与仓库那条纪律同族：「重试烧掉的额度要能单独看见，**否则失败的归因是错的**」
（`CONTEXT.md` 的「调用 / 往返」）。只是这次丢的是**在飞的**，而不是重试的。

要答的：

1. **账该记「已发出」还是「已回来」？** 现在记的是后者，所以一次失败报出来的数是**下界**，
   极端情况下是 **0**（2026-09-30 真发生过）。
   - **(a) 改成「已发出」**：调用处先记一笔再 await。⚠️ 代价：`ledger.json` 的语义变了
     （**包里的账**应当只记成功的调用 ——「这一包花了多少」与「这一跑花了多少」是两回事）。
   - **(b) 两笔账分开**：包内 `ledger.json` 照旧只记回来的；**异常上**那份改成「发出即记」。
   - **(c) 不改机制，把话说清**：在 CLI 那一行上写明「（**下界** —— 在飞的还没回来）」。
2. **失败时要不要等在飞的收尾？** 等 ⇒ 账更准、失败现场更全（多几张原图）；不等 ⇒ 更快。
   ⚠️ 而那正是「保住创作态」的收益大小 —— 票 01 只保住了**已回来**的那些。
3. **判据是什么？**「一次失败之后，报出来的数与真实发出的笔数是否相等」—— 可断言（用一个
   一半调用抛错的桩生成器：发出的 N 笔里，账上应当恰好 N 笔）。
