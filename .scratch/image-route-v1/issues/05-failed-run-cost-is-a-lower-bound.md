# 05. 失败时报的「已经花掉的」是**下界** —— 在飞的那几笔既没落账、也没落盘

Type: grilling
Status: resolved
Owner: amber（2026-09-30 认领）
Blocked by: —
Map: ../map.md
> **由 [`跑一次完整生图包走通 site`](04-image-pack-e2e-through-site.md) 的那两次真跑兑现出来的。**

## Question

```
✗ OpenAI 形态生图失败（3 次内）：Unexpected end of JSON input
（连「已经花掉的（N 次调用 · M 次往返）」那一行都没有）
```

**没有那一行本身就是结论**：它只在账非空时打印 ⇒ **账上一笔都没有**。
而那一跑**确实花了钱**（3 次尝试都发出去了）。

机制（读代码就成立）：`opts.ledger?.push(…)` 在**调用回来之后**（`pack.ts:383`），
而失败时 `ops.ts` 读的是**那一刻**的 `ledger.length`；并发是 3 ⇒
**还在飞的那几笔既没落账、也没落盘**（落盘也一样：原图是跟着回来才写的）。

⇒ 与仓库那条纪律同族：「重试烧掉的额度要能单独看见，**否则失败的归因是错的**」
（`CONTEXT.md` 的「调用 / 往返」）。只是这次丢的是**在飞的**，而不是重试的。

要答的：

1. **账该记「已发出」还是「已回来」？** 现在记的是后者，所以一次失败报出来的数是**下界**，
   极端情况下是 **0**（2026-09-30 真发生过）。
   - **(a) 改成「已发出」**：调用处先记一笔再 await。⚠️ 代价：`ledger.json` 的语义变了
     （**包里的账**应当只记成功的调用 ——「这一包花了多少」与「这一跑花了多少」是两回事）。
   - **(b) 两笔账分开**：包内 `ledger.json` 照旧只记回来的；**异常上**那份改成「发出即记」。
   - **(c) 不改机制，把话说清**：在 CLI 那一行上写明「（**下界** —— 在飞的还没回来）」。
2. **失败时要不要等在飞的收尾？** 等 ⇒ 账更准、失败现场更全（多几张原图）；不等 ⇒ 更快。
   ⚠️ 而那正是「保住创作态」的收益大小 —— 票 01 只保住了**已回来**的那些。
3. **判据是什么？**「一次失败之后，报出来的数与真实发出的笔数是否相等」—— 可断言（用一个
   一半调用抛错的桩生成器：发出的 N 笔里，账上应当恰好 N 笔）。

## Answer

**✅ 2026-09-30 已决议：两笔账分开 + 失败时等「在飞的」收尾。**

### 先记三条事实（它们决定了怎么做）

- 账**只记「回来的」**：`pack.ts:383` 是调用回来之后才 push。
- `LedgerCall` 里 **`ms` 与 `attempts` 必填** ⇒ 「已发出但没回来」那一笔**今天表达不出来**。
  ⚠️ 而仓库自己的纪律**禁止用占位值糊过去**：`model` 那条写着「拿不到就缺席，**不许编一个**」，
  用量那条写着「没给就缺席 —— **不填 0 冒充「测到了 0」**」（票 19 Q4）。
- 账同时喂**两个不同的问题**：包里的 `ledger.json`（**这一包**花了多少）·
  异常上那份（**这一跑**花了多少）—— 今天它们**共用同一份**。
- 「等」的上界是现成的：生图每笔按协议有 240–300s 超时；并发 3 ⇒ 最多 2 笔在飞。

### 两条决议

| # | 决定 | 依据 |
|---|---|---|
| Q1 | **(b) 两笔账分开**：包内 `ledger.json` 照旧只记**回来的**；**异常上**那份改成**发出即记** | 「这一包花了多少」与「这一跑花了多少」**本来就是两个问题**，今天共用一份把它们混成了一个。⚠️ (a) 会让包里的账列着**对产出毫无贡献**的调用；(c) 承认了数不准但**没修归因** —— 而那正是票 46 要的 |
| Q2 | **(b) 等**：换成 `allSettled` 语义 —— 第一条 rejection 之后**不再立刻抛**，先等在飞的收尾 | 那几笔**已经付过钱**；不等就是把「已经买的图」扔掉。⚠️ 而票 01 整张票就是为的**不再扔这种东西** ⇒ 这一条让那个功能的收益直接变大 |
| Q3 | **判据**：一次失败之后，**报出来的笔数 === 真实发出的笔数** | 可断言：造一个「一半调用抛错」的桩生成器 ⇒ 发出的 N 笔，账上恰好 N 笔 |

### Q1 的连带：一次 **schema 加法**（不是编值）

「发出即记」那一笔**还没有 `ms`**，而 `ms` 今天必填。两种如实做法：

- **`ms` 变可选**，**缺席 = 那笔还没回来** —— 与「拿不到就缺席」那条**同一条纪律** ✓（**推荐**）；
- 或加一个 `outcome: "sent" | "returned"`。

⚠️ **不许**写成 `ms: 0` —— 那是「测到了 0」的冒充，票 19 明确否过。
`attempts: 1` 对「已发出」是**真值**（确实发了一趟），照写 ✓。

⚠️ 连带一处**读**的地方：`summarizeCalls` 求和 `ms` 时要跳过缺席的（否则会 NaN）。

### Q2 的连带：等的上界**用现成的**

⚠️ 不新拍一个「等 30s」的数 —— **调用超时本来就是那个上界**（240–300s）。
再发明一个只会让「等多久」变成两处各说各的。
代价写清楚：一次失败**晚最多 ~4 分钟**才报出来 —— 而失败本身已经花了十几分钟，那不是新成本。

### ⚠️ 2026-09-30 实现时：一处与决议的字面不同 + 一个被审查抓出来的真缺陷

**① 「两笔账分开」落成了「一个数组、两个读的时刻」。**

决议的字面是**两笔账**；实现是一份数组 —— 因为两个问题**本来就是同一个事实的两面**：
「这一跑花了多少」在**失败那一刻**读（有些还没回来 ⇒ `ms` 缺席），
「这一包花了多少」在**成功那一刻**写（走得到那一行就说明**每一条都被补过**）。

⚠️ 而这一点**起初只是碰巧成立**（审查的规格轴点名的：包内那份「只含回来的」是**控制流**给的，
不是**构造**给的）。现在改成构造保证：**每一条「已发出」都记在闸门里面**
（没被放行的一分钱没花、也就不记），而记下的每一条都在同一个 unit 里被 `Object.assign` 补成事实。
⇒ 能走到写包那一行，就说明每一条都被补过。

**② ⚠️ 审查抓到一处**多报**：闸门拒掉的排队调用也被记进了账。**

第一版把 push 放在**闸门外** —— 而那道闸会**拒掉还没发出去的**排队调用（票 47「失败即止」）。
实测：**4 个资源、并发 1、第一个就挂 ⇒ 上游只收到 1 笔，账上却写了 4 笔**，
直接违反本票 Q3 的判据（报出来的 === 真实发出的）。
⇒ 改成**记在闸门里面**，并补了一条用例钉住它（把 push 挪回去那条用例就红 —— 变异验过）。
