## 总边界

**Destination**：完成 Level Playability V1 的当前能力审计、确定性判据规格、历史语料重判、合成负例矩阵、最小实施方案与独立审批包；不修改生产代码，停在实施审批门前。

**成功标准**：

1. 三个维度有统一且精确的判定框架。
2. 每个确定性 error 都有可复现的证明和定位。
3. 历史语料没有无法解释的新增误伤。
4. 合成负例能稳定触发预期判据。
5. Agent 失败、超时和环境失败不会被误判成关卡不可玩。
6. 实施方案明确修改面、测试、回退和契约审批点。
7. 全程零付费。

**停止线**：如果某项判据只能依靠模型判断、主观难度评价或 Agent 试玩成功率，就不进入确定性 error；保留为观察项或标记为证据不足。

### Q1 — 目的地形态

选择 (a)。

Destination 是：

> Level Playability V1 审计规格与审批包完成，停在实施审批门前。

交付至少包括：

- 当前源码能力与缺口审计；
- 「不可玩 / 证据不足 / 未发现确定性问题」的判定定义；
- 机制组合、空间布局、可通行性的原子判据；
- 每条判据的精确算法、输入、输出和失败定位；
- 历史语料重判结果；
- 合成负例测试矩阵；
- 最小实施方案、修改面、测试计划和回退策略；
- 独立实施 effort 的票据与审批问题。

不在本图修改生产代码。后续实施另起 effort，沿用 B/D Audit → P1 的两段式治理方式。

### Q2 — 三个维度

选择 (a)，但机制组合严格限制为现有 10 条机制的组合约束。

三个维度共用一个终点：对生成的横版关卡给出确定性可解释的判定。

1. 机制组合：例如 hazard / 巡逻与跳跃跨度、安全窗口与危险区、拾取物是否被现有机制封死。
2. 空间布局：地形、落脚点、沟壑、台阶、目标和关键实体之间的空间关系。
3. 关卡可通行性：玩家能否沿着实际可用路线到达必须到达的位置，并完成关卡要求。

不新增机制、不改变 Runtime 行为、不把「设计不够有趣」纳入不可玩判定。

### Q3 — 目标格式

选择 (a)：仅横版 `game-config/v1`。

塔防 `td-config/v1` 不进入本轮范围。现有塔防 path 由 arena 派生，当前没有足够证据支持把它纳入同一套可通行性审计。

未来若发现塔防独立的路径或空间失败，再单独立项；不能为了追求格式统一而扩大本轮范围。

### Q4 — 可通行性与可达性

选择 (a)：可通行性包含可达性，但二者不是同义词。

建议在规格中明确三层：

| 层次 | 要回答的问题 | 示例 |
| --- | --- | --- |
| 空间可达性 | 目标是否存在几何上的可达路径？ | 拾取物是否被地形完全隔断 |
| 机制可通行性 | 路径在现有机制约束下是否实际可走？ | 巡逻危险区是否封死唯一通路 |
| 关卡完成性 | 必须完成的目标是否能在关卡规则下完成？ | 必需物品是否可取得、终点是否可到达 |

沿用仓库既有的严格门槛：

- 必须精确可算；
- 必须能证明错误不是设计意图；
- 只有可证明不可玩，才进入确定性 error；
- 难度、节奏、路线优劣和玩家体验仍然是观察项；
- 试玩结果只能作为证据，不能单独成为不可玩判据。

尤其要保留三种不同结果：

- `PROVEN_UNPLAYABLE`：确定性证明不可玩。
- `INSUFFICIENT_EVIDENCE`：当前算法无法证明可玩或不可玩。
- `NO_PROVEN_BLOCKER`：没有发现确定性阻断。

`NO_PROVEN_BLOCKER` 不等于保证玩家一定能通关。

此外，Agent 的 `AGENT_LIMITATION`、`TIMEOUT`、`ENVIRONMENT_FAILURE` 不得自动转成 `PROVEN_UNPLAYABLE`。即使 Agent 多次失败，也必须有独立、确定性的关卡证据才能判定不可玩。

### Q5 — 允许改动面

选择 (a)。

允许进入未来实施方案的内容：

- contracts 包内审计纯函数；
- 编译提示词；
- 确定性测试；
- fixtures；
- 必要的内部诊断与定位信息。

明确排除：

- Runtime 修改；
- 新增 EntityKind、Motion 或机制；
- 斜坡等新碰撞能力；
- 未经审批的 contracts schema/API 形状变更；
- CLI/MCP 对外接口扩展。

特别说明：本图可以提出 contracts 审计函数的修改方案，但任何契约形状变化都必须单列说明必要性、替代方案、影响面和不做后果，等待独立审批。

### Q6 — 种子失败语料与验收对象

选择 (a)。

两类证据承担不同职责：

**历史语料：证明不误伤。**

- 134 对 config；
- 77 关设计；
- FPVS-V1；
- last-train 夹具；
- 现有 `out/**`、`fixtures/**`、`.scratch/**` 中相关语料。

必须记录语料范围、重判结果和新增 error 数量，不能只抽样展示成功案例。

**合成负例：证明判据会响。**

针对以下场景制作最小 fixture：

- 沟壑造成必经路线中断；
- 台阶或落脚点使跳跃无法完成；
- 巡逻 hazard 封死唯一通路；
- 危险区不存在可通过的安全窗口；
- 必需拾取物被地形或机制封死；
- 目标位置无法到达。

每个负例都要有明确的预期结果、失败原因和定位信息。

合成负例必须同时配套合法边界 fixture，避免只证明「错误能被捕获」，却没有证明正常关卡不会被误拒。

## 两个特别钉死的边界

1. **不能把「试玩未成功」等同于「关卡不可玩」。** `AGENT_LIMITATION` / `TIMEOUT` / `ENVIRONMENT_FAILURE` 不得自动转成 `PROVEN_UNPLAYABLE`；即使 Agent 多次失败，也必须有独立、确定性的关卡证据才能判定不可玩。
2. **允许研究和提出审计纯函数，不代表自动批准契约形状变更。** 任何 contracts schema/API 形状变化都必须单列说明必要性、替代方案、影响面和不做后果，等待独立审批。
