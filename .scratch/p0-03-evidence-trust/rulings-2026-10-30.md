## 四、一个必须提前锁定的技术原则

不能把“摘要文件和 Manifest 同在 PR 可修改目录”称为可信锚点。

可信锚点必须从受保护分支或受保护配置中取得，并且 CI 校验逻辑也必须有可信来源。

否则攻击者可以同时修改：

- `expected-hashes.json`
- 摘要文件
- 验收脚本
- workflow

最终仍然让检查返回成功。

因此，后续实施要验证的不只是哈希，而是整个信任链：

`受保护的 main → 可信验收逻辑 → 可信 Manifest 摘要 → Manifest → 223 个冻结证据文件`

### 二、Q6 是本轮最关键的安全裁定

这里需要把“只读 PR 文件”和“执行 PR 代码”严格分开。

建议固定成以下执行模型：

```
受保护的 base
  ├── workflow
  ├── verify-delivery CLI
  ├── evidence-acceptance 脚本
  ├── Manifest
  └── Manifest SHA-256
         │
         ▼
    可信验收执行环境
         │
         ├── 读取 PR head 的证据文件
         ├── 比较 PR Manifest 与 base Manifest
         ├── 用 base Manifest 验证 PR 证据
         └── 输出正式验收报告
```

禁止事项：

1. 不 checkout 后执行 PR head 的 workflow、脚本、CLI 或构建产物。
2. 不从 PR head 读取验收规则、摘要或期望值。
3. 不把 PR 文件路径拼接成可执行命令或 shell 片段。
4. 不向该 workflow 提供 secrets。
5. 不授予写权限；`GITHUB_TOKEN` 只读。
6. 不允许 PR 修改 Manifest 后，再用修改后的 Manifest 验证自身。

尤其要注意：`pull_request_target` 的风险不只在显式执行脚本。任何来自 PR 的文件名、路径、内容和元数据都应视为不可信输入。读取文件时必须限制在预定证据根目录，防止路径穿越、符号链接逃逸及意外读取仓库外内容。

另外，PR Manifest 与 base Manifest 的逐字节比较是必要的，但不是唯一校验：必须继续用 base Manifest 的期望哈希验证 PR head 的证据内容。否则只证明清单没变，并没有证明交付证据没变。

### 三、Q7、Q8：基线更新也纳入信任链

批准 Manifest 与摘要分开存储，但二者都必须从 base 读取。

更新流程固定为：

```
专用基线更新 PR
  ├── expected-hashes.json
  ├── expected-hashes.sha256
  └── MANIFEST-UPDATES.md（只追加）
         │
         ▼
CI 校验
  ├── 摘要与 Manifest 完全匹配
  ├── 更新记录最后一条 new SHA 匹配当前 Manifest
  └── CODEOWNERS 审批 + required checks
```

这里有一个重要限定：

更新日志不是密码学意义上的不可篡改日志。 它仍然受 Git 历史、受保护分支和审查流程保障。不能因为 CI 验证了最后一条记录，就宣称更新历史不可伪造。

还应在实现规格中定义 SHA 的编码口径：对 Manifest 原始文件字节计算 SHA-256，不对解析后的 JSON 对象重新序列化后计算；摘要文件格式固定，避免换行符、编码或文件名歧义。

### 四、Q9–Q13：门禁、证据与正式报告

单人仓库保护： DoD 不再写成“任何人都不能直接推送”，而改为：

> 直接推送对非管理员受限；仓库 owner 保留 documented break-glass 例外，每次绕过必须可追溯。外部 PR 受 required status checks 和适用的 CODEOWNERS 审批约束。

需要注意 GitHub 规则的实际语义：管理员绕过能力取决于最终采用的 ruleset / branch protection 配置，不能只写在文档里。设置完成后必须实测。

四项 Required checks： 名称必须稳定且唯一，避免同名 job 或矩阵任务造成 GitHub required check 绑定歧义。`test:evidence` 单独 job，并且不能被普通测试 job 的成功结果替代。

Sparse checkout： 253 MiB 是目标路径集合的估算，不是已验证的构建可行性。先跑真实 install、build、四项检查；若 pnpm workspace 或构建依赖导致失败，退回全量 checkout，记录实际耗时和体积，不把 sparse 本身设为验收门槛。

Optional logs： 报告必须区分：

- `required-missing = 0`：通过的必要条件；
- `optional-missing`：逐项列出；
- optional 文件存在但哈希不匹配：仍按既有校验器规则处理，不能把 optional 等同于“任意内容都可接受”。

正式报告： 同意扩展 `verify-delivery`，但要保持兼容性：

- 不传 `--expected-manifest-sha` 时，旧调用和旧报告消费者继续有效。
- 传入时，`trust.anchor` 必须明确表达 base/PR 清单比较、摘要验证、锚点来源和最终结果。
- 锚点验证失败必须使正式验收失败，不能只记 warning。
- `trust.anchor` 不得由 PR 输入内容直接决定；可信期望值由 base 侧执行逻辑提供。

### 二、Q14：基线更新与普通 PR 彻底分离

这是最终轮最重要的安全裁定。

普通 PR 的 evidence job 必须始终遵守：

```
PR Manifest == base Manifest
PR SHA-256   == base SHA-256
```

然后：

```
base Manifest
     │
     ▼
验证 PR head 的 151 个 required 证据文件
     │
     ▼
required evidence check
```

普通 PR 无论作者是谁，都不能通过修改 Manifest、摘要和更新日志来改变自己的验收标准。

基线更新采用独立的 owner 通道：

1. 创建专用基线更新 PR。
2. 修改 Manifest、摘要和追加更新记录。
3. 普通 evidence job 按预期失败，不允许切换到 PR 自验模式。
4. owner 审阅新旧基线差异及更新原因。
5. 通过受信任的 `workflow_dispatch` 验证新基线，或由 owner 执行明确记录的 break-glass 操作。
6. 合并后，新 base 才成为普通 PR 的可信基线。

重要补充： `workflow_dispatch` 必须从受保护的 base/ref 运行可信 workflow，并明确指定待验证的候选提交。不能因为它是手动触发，就直接执行候选 PR 中的 workflow 或验收脚本。

基线更新成功也不意味着普通 PR 门禁允许豁免。两种流程必须在报告中明确区分。

### 六、Q18：新增架构 ADR

文件：

`docs/adr/0001-evidence-trust-boundary.md`

只记录架构决策，不扩展成实施说明书。

建议内容：

1. Context：PR 作者可以修改 PR 中的任意文件，包括 workflow、CLI、验收脚本和 Manifest。
2. Threat model：防御普通 PR 作者；假设 base、GitHub 仓库保护设置和可信 CI 执行环境未被攻陷。

6. Consequences：基线更新需要 owner 专用流程；管理员仍是信任边界的一部分。
