## 2. 裁定要点（gist，非逐字）

- **第一轮预算：未授权**；P0-02 付费执行继续阻塞。
- `22 次调用`只是冻结 run 的参考量，不是新设计的硬上限，也不能直接代表货币成本。
- provider 计划沿用冻结 run；执行前确认可用性，但**不读取/输出/记录密钥内容**；无法确认则执行票阻塞。
- 允许管线默认重采样；每次付费调用前检查剩余预算；无法保证下一次不超限就停；无手工重试。
- 当前不批准付费生图；只有预算授权后才能另行批准。
- 第二次完整运行须另行 HITL 批准；只换输入、不改代码、不拼接两次运行。

## 3. 下一张预算授权票必须提供

1. 可核实的**货币上限**（金额/币种）；
2. **调用成本估算**（文本 token 单价 + 生图单次单价；按冻结 run 的实际用量）；
3. **超限前停止机制**（provider 硬限额或 effort 侧 watcher；不改生产代码）；
4. provider 可用性确认方式（不读取密钥内容）；
5. 明确批准/不批准付费生图，以及第二次运行规则。

## 5. 预算授权 v2（Q1–Q6）

**用户逐字：**

> 本轮预算裁定的原则是：先核实实际计价端点，再批准明确的美元上限，并且必须有能阻止超支的硬护栏。 估算价格、调用次数和运行结束后才写入的 ledger，都不能单独保证实际支出不超限。
>
> 目前我不能仅凭现有描述确认 `baseUrl` 的主机名、实际计价档或 provider 是否支持可验证的硬限额，因此不会把这些未知条件当成已经满足。
>
> - Q1：c — 先核实主机名再定。当前不能确认仓库实际 `baseUrl`，因此暂不声称它是官方 Gemini API。官方 Gemini API 的主机名通常是 `generativelanguage.googleapis.com`；这只是核验标准，不是对当前配置的确认。官方价格须按实际模型和计价档核对。
> - Q2：a — 选择 $6.00 USD 作为单次完整 A 运行的预算目标上限，覆盖管线内部默认重采样；第二次完整运行另行批准。但这只是拟定的授权额度，尚未生效，且必须先确认实际 provider 和护栏能否支持该限制。
> - Q3：c — 在硬限额能力未经验证前，不授权付费执行。官方 Gemini API 文档说明，项目级 spend cap 存在约 10 分钟的计费处理延迟，可能发生超额；Prepay 余额归零也可能因处理延迟而超支。因此，不能把它们直接当作严格的单次运行 $6 硬停止保证。
> - Q4：b — 暂不批准付费生图。只有 Q1 的端点和计价档得到核实、Q3 的超限风险得到可接受的控制，并重新确认预算授权后，才能执行 `build`。
> - Q5：a — 执行前明确移除 `ANTHROPIC_BASE_URL` 与 `ANTHROPIC_AUTH_TOKEN` 对本次执行环境的影响，并验证实际使用的是冻结 run 对应的 Gemini 文本路径。不得输出或记录密钥内容。若无法确认 provider 路由，停止执行。
> - Q6：a — 首次运行仅允许管线内部默认重采样；第二次完整运行必须另行取得 HITL 批准，只能更换输入，不改生产代码，也不拼接两次运行的证据。
>
> 预算票结论：预算目标已选定为 $6.00 USD，但付费执行仍未获授权。
>
> 下一步只做零付费核验：确认 `baseUrl` 主机名、实际文本与生图模型、计价档、provider 路由，以及可用的支出限制。若无法建立足以满足本票要求的超限护栏，就保持阻塞，不运行付费命令。
