## 0 · 结论

当前效果差得远，**不是票 107 的 DNA 没写对，也不是模型画不出来**，而是四层输入在**共同把画面压向扁平极简**：

1. **风格参考图**本身就是扁平像素图（`run/v1/reference.png`）；
2. `analyze-reference` 忠实地从它提取出一份**禁止描边、禁止渐变、无光照、方块人**的 StyleSpec；
3. 世界色板只有 **9 色**，而交付时玩家被 **`paletteBinding: "quantized"`** 吸到那 9 色上（实测玩家帧恰好 9 个不透明色）；
4. 票 107 只改了 DNA（角色描述），**参考图与 StyleSpec 一个字没动** ⇒ 新 DNA 只能画出「更精细的方块人」。

⇒ **只换模型、只改 DNA、只重跑，不会接近图 43。** 必须同时替换：参考图、StyleSpec（含色板）、DNA、配方/提示词，并把 6 个 drawlist 资源的处理方式纳入范围。

## 1 · 证据

### 1.1 当前 StyleSpec 是「扁平」的硬约束

`run/v1/stylespec.json` 逐字：

| 字段 | 当前值 |
| --- | --- |
| `characterStyle` | 方块人 · 色块服装 · 抽象五官 |
| `material` | 平涂纯色 · 哑光无反射 · 像素硬边 |
| `lighting` | 均匀无方向光 · 无投影 |
| `constraints` | **禁止渐变与描边** · 禁止有机曲线 · 强调色仅用于发光/可交互物 |
| `palette` | **9 个颜色**（`#5a3a22` `#7a4a28` `#2f3a45` `#f0b53c` `#1f2733` `#232c3a` `#4a4f57` `#8c8f95` `#e8c9a0`） |

### 1.2 9 色是硬天花板（本地复算，零上游）

把图 43 的主角区分别量化到 9 / 24 / 48 / 96 色（`assets/quantization-compare.png`）：

- **9 色**：皮肤、衣褶、明暗全部并成色块 —— 与当前游戏里的玩家同源；
- **24 色**：基本保住明暗与轮廓；
- **48 色**：与原图几乎无差；
- **96 色**：无差。

玩家帧实测：`72×108`、**恰好 9 个不透明色**、`paletteBinding: "quantized"`。

⇒ 目标风格至少需要 **24–48 色**；最终从参考图做中位切分得到 **29 个有效色**（见 `assets/palette-candidate-29.json`，背景/网格色已剔除）。9 色不是「够不够细」的问题，是**数学上装不下**。

### 1.3 参考图与当前风格同源

当前 `reference.png` 是一张扁平极简像素图；`analyze-reference` 提取出上面的 StyleSpec 并没有错。**错的是参考图选错了。**

### 1.4 分辨率不是瓶颈

玩家画布 `72×108`；图 43 的角色约 `40×70`。`assets/player-target-vs-current.png` 把参考角色按最近邻缩到 `72×108`，仍能清楚看到 1px 描边、三级明暗与装备细节。⇒ **画布够用，缺的是色板、描边许可与参考图。**

### 4.3 CharacterDNA

- 玩家：保留「拾荒者」身份还是改用图 43 的「女性幸存者」——**待裁**。若保留身份，建议保留包袱/短檐帽/护目镜三个识别点，但按新风格写成可见布褶、磨损与三级明暗。
- 敌人：图 43 提供两类现成方向（Zombie Nurse / Rusted Scavenger）；当前敌人是「深色方柱」，需要重写成有装备、有明暗的实体。
- DNA 的 `palette:N` 会因色板扩张而**全部重排**；必须随新 StyleSpec 重新生成，不能手改下标。

### 4.4 配方与提示词

- 动作数：当前玩家 `idle×2 / run×4 / jump×2`。图 43 有 `idle/run/jump/fall/attack/damage/death`。**是否扩展动作是玩法决策**；本阶段建议至少保持现有三态，先验证风格。
- 多帧图每帧可用的像素变少：动作数越多，单帧细节越薄。建议先保持 8 帧总量，风格稳定后再加。
- 提示词里的「方块」「纯色块」「抽象五官」等词必须全部清掉，换成 §2 的词汇。
- 反向提示词里的 `human figure` / `character` / `hands` 与动画方向冲突（v2 已知雾），本阶段应一并在新提示词里处理。

### 4.5 道具/UI：这是整包迁移里最大的一处路线变更

当前 10 个资源里 **6 个是 drawlist**（平涂矩形/椭圆），它们**结构上不可能**达到图 43 的细节：

| 资源 | 当前路线 | 建议 |
| --- | --- | --- |
| `scrap-resource` | drawlist | 改为 image（或导入裁切） |
| `hazard-spike-rubble` | drawlist | 改为 image |
| `prop-street-lamp` | drawlist | 改为 image |
| `prop-bench` | drawlist | 改为 image |
| `ui-scrap-counter` | drawlist（96×32 面板） | image 按精确尺寸生成；注意非九宫格 UI 不缩放 |
| `ui-scrap-icon` | drawlist（16×16） | image |

三条路：

1. **image 生成**：+6 次生图，风格统一；推荐。
2. **drawlist 加细节**：不花钱，但要在代码里堆大量矩形，仍没有 3–4 级明暗与描边，达不到目标。
3. **从图 43 直接裁切导入**：最像、零生图，但 create 链今天**不支持 `existingAssets` 输入**（v3 明确留后续）；只能在单跑 `pack`/手写 fixture 里用，等于绕开主链。

⚠️ UI 面板若要九宫格拉伸，今天只有 drawlist 的 nine-slice 支；生成的图片是固定尺寸。本游戏的 HUD 面板是固定尺寸，所以 image 可行；若以后要缩放，需要另立票。

## 7 · 风险

1. **模型能力**：`gemini-2.5-flash-image` 可能输出偏绘画感、抗锯齿或高分辨率糊化；C 阶段就是为此设的闸。
2. **下采样**：从生成大图到 `72×108` 必须最近邻 + 色板量化；若当前 `raster` 走双线性，会把 1px 描边抹掉。C 阶段要专门量。
3. **参考图泄漏**：目录网格、标签、资源排布可能被学走；正式参考图要清理。
4. **一致性**：17 张图逐张生成，风格靠参考图 + StyleSpec 维系；需要 D 阶段逐张并排检查，不能只看一张。
5. **色板扩张的连锁**：DNA 的 `palette:N`、VWS 六桶、drawlist 颜色都引用同一份有序色板；扩张后必须整体重生成，手改下标会错位。
6. **权利**：图 43 若是外部作品，需确认可商用/可改编；本报告只把它当风格样本，未直接复制进交付包。
7. **范围蔓延**：attack/damage/death 会牵扯玩法（武器、伤害、死亡）；本阶段建议只做风格，不扩玩法。
