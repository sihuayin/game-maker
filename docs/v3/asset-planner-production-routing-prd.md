## 1. 背景与问题

当前目标流水线为：

`GameDesignSpec + VisualWorldSpec → Asset planning / AssetRecipe → AssetPack → GameConfig → Demo Site`

资源包与可运行游戏是两个独立交付物。本阶段只改造资源规划及其与 `pack` 的衔接，不重写整条游戏创建流水线。

目前资源生产策略容易出现的问题：

1. 资源清单没有充分区分不同资源的生产需求，复杂角色、敌人和高辨识度道具可能被分配到不适合的生产方式。
2. 资源规划更像是列出“需要哪些图片”，没有明确表达资源的复杂度、用途、约束和生产方式。
3. 生产路线的选择缺少明确、可测试的决策规则，容易过度依赖单一默认值或自由文本提示。
4. 后续 `pack` 阶段难以解释某项资源为什么采用该生产方式，也难以判断当前产物是否符合该资源的预期。
5. 只检查文件存在、格式或 Schema，无法判断规划是否合理；但本阶段也不应试图一次性解决完整视觉 QA。

本阶段的目标不是直接保证所有生成图片都达到最终美术质量，而是先让系统**稳定地决定“要生产什么、用什么方式生产、依据是什么、结果如何追溯”**。

## 2. 产品目标

### 2.1 必须实现

- 使用 `GameDesignSpec` 与 `VisualWorldSpec` 作为 Asset Planner 的主要输入。
- 由明确的 Planner（现有 `planAssets` + 确定性 `resolveRoute` 层）收敛资源推导与路线决策职责；`deriveRecipe` 已在 v2 并入 `planAssets`（v2 票 12），不得恢复或维护两套相互竞争的规划逻辑。
- 对每项资源生成明确的生产路线。
- 当前合法的 `source.kind` 仅为：
  - `image`
  - `drawlist`
  - `import`
- 保留现有 AssetSpec / AssetRecipe / AssetPack 的概念边界和对外交付契约；不得因为本阶段重构而无必要地改变 CLI、MCP、Recipe Schema 或 Pack 目录结构。
- 让路线决策可确定、可解释、可测试。
- 将规划结果和生产结果关联起来，便于定位某项资源的路线、输入、输出和失败原因。
- 对缺少必要信息、无法满足约束或无合法路线的资源，明确拒绝或报错；不得静默地降级成任意路线。
- 为后续资源视觉 QA 留出清晰接口，但本阶段不实现自动修复或自动重生成循环。

### 2.2 不在本阶段实现

- 不重写 `raster.ts` 或整个图像生成子系统。
- 不改变现有 `AssetPack` 目录布局。
- 不增加新的 `source.kind`；尤其不新增 `derived`。派生/变体操作若需要，作为现有路线的内部处理或后续独立设计，不属于本阶段的新资源来源类型。
- 不把碰撞体加入资源清单；碰撞体继续由 terrain / 游戏配置相关结构负责。
- 不把 VisualWorldSpec 直接塞入图像生成请求；VWS 接入 image generation 的改动属于独立任务。本阶段 Planner 可以读取 VWS 并据此规划资源，但不得擅自改变图像生成接口。
- 不构建跨游戏共享视觉记忆、跨项目迁移或跨游戏资源知识复用。
- 不实现自动重试、自动修复、自动重生成循环。
- 不引入单一综合 QA 分数，也不把观察值包装成质量结论。
- 不改变塔防旧链或其他 RuntimeProfile 的既有分派行为。
- 不改动 `compile-runtime` 对 `GameConfig` 的唯一写入职责。

## 3. 用户与使用场景

### 3.1 主要用户

- 使用参考图与游戏需求生成可玩 2D 游戏的开发者。
- 调用 CLI / MCP 运行资源规划与打包流程的自动化 Agent。
- 需要检查资源生成失败原因、控制成本并复现问题的开发者。

### 3.2 核心场景

用户提供：

- 一张废土科幻像素风格参考图；
- 一份横版闯关游戏需求；
- 对玩家、敌人、平台、道具和机关的玩法要求。

系统应自动形成合理的资源清单，并按资源类型与约束决定生产方式，例如：

- 玩家角色、复杂敌人、复杂机械：通常优先考虑 `image`。
- 简单 UI、几何符号、规则明确的简易图形：可以使用 `drawlist`。
- 用户已提供的图片或必须原样使用的既有素材：使用 `import`。
- 模块化地形应根据其真实生产约束选择路线；若要求无缝拼接，不得仅因为“它是地形”就默认选某一路线。

上述只是决策方向，不是无条件硬编码的资源类型映射。最终选择必须考虑资源的实际约束、输入是否存在、现有生产能力和项目风格要求。

## 4. 设计原则

1. **Planner 负责规划，Pack 负责执行。** 不允许 `pack` 再隐式重做一套路线决策。
2. **类型是依据之一，不是唯一依据。** 路线选择需要综合资源语义、复杂度、生产约束、来源材料和现有能力。
3. **显式优于猜测。** 规划结果必须包含可检查的路线和决策理由；必要条件缺失时应拒绝，而不是静默猜测。
4. **确定性优先。** 对相同的规范化输入和相同的 Planner 版本，确定性规则应给出相同结果。若有模型参与语义规划，必须把模型建议与确定性约束校验分离。
5. **不破坏既有契约。** 本阶段以内部实现为主，尽量维持已有调用方式、Schema 和输出布局。
6. **质量判断与客观观察分离。** 例如图片宽高比是可记录的观察值；是否阻断要由该资源的约束决定。
7. **不制造虚假的质量保证。** 本阶段只验证路线决策和生产衔接，不声称已经解决视觉一致性或动画质量。
8. **不增加跨游戏状态。** 所有规划上下文只属于当前游戏项目。

## 5. 功能需求

### FR-1：Asset Planner 输入

Planner 至少接收：

- `GameDesignSpec`
- `VisualWorldSpec`
- 当前版本的资源相关约束与能力信息
- 必要时已有 `AssetSpec` 或等价的资源需求输入（遵循仓库现有类型与边界）

Planner 必须从游戏设计中识别资源的实际用途，例如玩家、敌人、道具、交互对象、地形模块、背景、前景装饰和 UI。不得假设每个游戏固定包含同一组资源类别或固定数量的背景层。

`styleRef` 继续指向提取出的 `StyleSpec`，不得在本阶段更改其语义。

### FR-2：逐资源生产路线

每项资源都必须被分配且只分配一种合法来源类型：

- `image`
- `drawlist`
- `import`

路线选择至少应考虑：

- 资源类别与语义复杂度；
- 需要表达的视觉细节；
- 是否要求精确几何、可拼接边缘或规则化形状；
- 是否已有可复用的输入文件；
- 透明背景、独立对象、动画帧或其他导出约束；
- 当前项目允许使用的生产能力；
- 该资源对游戏可运行性的必要程度。

Planner 必须记录简洁的 `decisionReason` 或仓库现有等价字段。若当前 Schema 没有合适字段，先评估能否使用内部规划结果或现有 metadata 表达；未经必要性论证，不要为了记录理由而扩大公共 Schema。

### FR-3：路线决策规则

应将路线选择逻辑实现为可单元测试的独立函数或模块，不要将全部规则埋在长 Prompt 中。

规则建议：

- 有明确的“必须原样使用既有素材”要求且素材可访问时，优先 `import`。
- 对复杂、具有辨识度且需要丰富材质的原创美术，通常优先 `image`。
- 对简单、规则明确、可由有限绘制指令可靠表达的资源，可以选择 `drawlist`。
- 当资源约束与路线能力冲突时，拒绝该规划或要求上游补充信息，不得静默降级。
- 对存在多种可行路线的资源，按固定优先级与明确规则决策；不能依赖数组顺序、随机数或不稳定的模型措辞。
- 模型可以提出候选分类，但最终结果必须经过确定性校验。

具体类别映射应由现有生产能力与实际代码确定，并以测试锁定。不得未经测试就宣称所有角色必然适用某一种生成模式。

### FR-4：Planner 输出

输出必须符合现有资源规划/Recipe 的契约，并至少能明确表达：

- 稳定的资源 ID；
- 资源用途/类别；
- 资源描述与必要的视觉约束；
- 合法的 `source.kind`；
- 路线选择依据（使用现有字段或内部规划结构）；
- 生产所需输入与依赖（仅限当前 Schema 已支持或本阶段必要的最小扩展）；
- 后续 `pack` 能执行该路线所需的参数。

Planner 输出不得把碰撞体作为资源条目生成；碰撞体继续属于 terrain / 游戏配置领域。

### FR-5：Pack 执行规划结果

`pack` 必须以 Planner/Recipe 的路线为准执行生产：

- `image` 走现有图像生成路径；
- `drawlist` 走现有确定性绘制路径；
- `import` 走现有导入路径。

`pack` 不应根据资源名称、描述文本或文件后缀重新推断生产路线。若路线缺失或非法，应给出明确错误。

本阶段只调整必要的衔接逻辑，不重写 `raster.ts`、图像模型客户端或整套 Pack 目录结构。

### FR-6：执行记录与失败可追溯性

每项资源的执行结果应能关联回其规划结果，至少能查明：

- 资源 ID；
- 选定的 `source.kind`；
- 使用的输入/依赖（若有）；
- 成功或失败状态；
- 失败阶段与可读错误原因；
- 实际产物位置（成功时）。

优先复用仓库现有日志、错误和账本机制。不得重复引入一套相互矛盾的成本账本或执行状态系统。失败记录不得把“未发送请求”误报为已花费模型成本；遵循仓库既有失败账本约束。

### FR-7：验证行为

验证分为两类：

**A. 硬性判据（可阻断）**
- `source.kind` 必须是合法枚举值；
- 必填字段与依赖必须存在；
- `import` 的必要输入必须可解析/可访问；
- Recipe 结构必须符合现有 Schema；
- 资源路线必须能被 `pack` 执行；
- 规划结果不得生成不合法或重复的资源 ID。

**B. 观察信息（默认不单独阻断）**
- 图像实际宽高比；
- 输出尺寸与预期尺寸的差异；
- 其他可供后续 QA 使用的资源属性。

观察值与阻断判据必须分开表示。对于上游 `image` 生成的实际宽高比，按现有约束作为观察信息，不要擅自改成阻断条件；`import` 与 Recipe 自身声明的比例约束继续遵守现有阻断规则。

本阶段不计算综合 QA 分数，不引入自动修复或自动重生成。

## 6. 关键数据流

```text
GameDesignSpec + VisualWorldSpec
                |
                v
          Asset Planner
                |
                v
       AssetSpec / AssetRecipe
       - stable resource ID
       - source.kind
       - constraints
       - decision reason
                |
                v
               pack
        /        |        \
    image     drawlist    import
      |           |          |
      +-----------+----------+
                  |
                  v
              AssetPack
                  |
                  v
       existing verification flow
```

说明：

- 上图表达逻辑关系，不要求新增 package。
- `source.kind` 只有 `image`、`drawlist`、`import` 三种。
- 不新增 `derived` 路线。
- AssetPack 的输出目录与现有契约保持不变。

## 7. 错误处理

- **输入缺失**：指出缺少哪个字段或依赖，不生成猜测性资源路线。
- **没有合法路线**：返回可定位的规划错误，包含资源 ID 和失败原因。
- **路线不支持**：在规划阶段拒绝，不能等到 Pack 执行中才因不支持而失败。
- **Recipe 非法**：在执行前校验并报错。
- **某项资源生产失败**：保留现有错误语义与执行记录，不自动进入重试/修复循环。
- **部分资源成功**：遵循现有 Pack 的原子性与失败目录策略，不改变版本号消耗、临时目录或失败产物规则。
- **旧 Recipe 兼容**：先审计当前已存在的 Recipe 格式与调用方。任何兼容逻辑都必须有明确边界和测试；不得静默把非法路线映射成 `drawlist`。

## 8. CLI / MCP 与兼容性要求

- 现有 CLI 命令名称与主要参数保持不变。
- 现有 MCP 工具名称与主要输入输出保持不变。
- Recipe Schema 不做无必要的破坏性变更。
- AssetPack 目录结构、版本目录与原子发布语义保持不变。
- 不改动 `compile-runtime` 对 `GameConfig` 的唯一写入职责。
- 不影响塔防旧链及其他 RuntimeProfile 的既有分派。
- 如果实现发现无法在现有 Schema 内表达必要信息，必须先提交最小变更理由、兼容策略和测试计划，不可顺手重设计整套契约。

## 9. 测试要求

### 9.1 单元测试

至少覆盖：

1. 复杂玩家角色在约束允许时选择 `image`。
2. 简单、规则明确的 UI/符号在约束允许时可选择 `drawlist`。
3. 已有且要求原样使用的素材选择 `import`。
4. 同一规范化输入重复运行，路线决策稳定一致。
5. 无合法路线时明确失败，不静默降级。
6. 非法 `source.kind` 在进入生产前被拒绝。
7. `pack` 按 Recipe 中的路线执行，而非按资源名称重新猜测。
8. `import` 输入缺失或不可访问时返回可定位错误。
9. 规划不会生成碰撞体资源条目。
10. 旧有有效 Recipe、CLI、MCP 与 AssetPack 交付测试继续通过。

### 9.2 集成测试

使用固定的废土横版游戏输入，至少检查：

- 玩家角色、敌人、道具、平台和 UI 被拆分成合理的资源条目；
- 各资源条目获得合法生产路线；
- `pack` 能按规划执行三种路线；
- 成功产物可被现有 verify / 后续 GameConfig 流程读取；
- 失败时可从错误信息定位到具体资源和生产阶段；
- 现有 Pack 目录与发布语义未发生变化。

### 9.3 回归测试

- 运行 assets package 现有测试。
- 运行涉及 CLI / MCP 的相关测试。
- 运行 `scripts/check-deps.mjs`。
- 运行仓库规定的类型检查、lint 和完整测试命令。
- 检查塔防 RuntimeProfile 和既有资源生成路径没有被意外改动。

实际命令应以仓库当前 `package.json` 和 CI 定义为准，不要在 PRD 中臆造命令。

## 11. 实施拆分建议

### Task 1：现状审计与边界确认

- 查明 `planAssets`（历史名 `deriveRecipe`）、AssetSpec、AssetRecipe、`pack` 三种路线的真实调用关系。
- 查明当前 Schema 中路线、资源 ID、约束、导入路径和错误信息的表达方式。
- 列出必须保持兼容的 CLI / MCP 调用方与测试。
- 输出简短审计记录，不在本任务中顺手重构无关模块。

### Task 2：实现 Asset Planner

- 引入清晰的 Planner 输入、输出和路线选择函数。
- 将路线决策规则从长 Prompt 中移出，形成可测试逻辑。
- 如仍需模型协助理解资源语义，模型只负责提出候选；确定性规则负责合法性与最终约束校验。
- 确认 `planAssets` 是唯一写入侧（`deriveRecipe` 已并入），把路线决策收敛到确定性 resolver。

### Task 3：接入 Pack

- `pack` 消费 Planner 生成的 Recipe。
- 明确分派到 `image`、`drawlist`、`import` 现有生产实现。
- 为非法路线与缺失依赖添加清晰错误。
- 不改变 Pack 目录、原子发布和版本分配语义。

### Task 4：测试与基准

- 添加路线决策单元测试。
- 添加废土横版固定输入的集成测试。
- 运行相关回归测试。
- 记录基线结果：路线分布、成功/失败情况和失败原因；这些是观察数据，不是综合质量分数。
