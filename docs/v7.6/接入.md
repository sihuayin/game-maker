# P0-04：双基线 CI 接入需求文档

- **项目**：game-maker V2
- **阶段**：P0 可信交付体系扩展
- **优先级**：P0
- **类型**：工程基础设施 / CI / 交付完整性
- **预算**：零付费
- **状态**：待实施
- **前置阶段**：P0-02 第二套交付基线冻结；P0-03 可信证据 CI 已通过真实 GitHub PR 验收

---

## 1. 背景与问题

### 1.1 已有成果

目前仓库已经形成两套正式交付基线。

**基线 A：FPVS-V1**

- 来源：P0-03 可信证据 CI 验收。
- 交付清单：223 files。
- Required：151 files。
- Optional：72 files。
- Records：13。
- 已完成真实 GitHub PR 红绿验证。
- 已建立 Base-only trusted evidence、SHA-256 独立信任锚、负向测试 N01–N17、四项 required checks、ruleset 和 owner 专用基线更新通道。

**基线 B：P0-02 Second Demo V2**

- 来源：P0-02 第二套交付基线冻结。
- 冻结快照：112 files。
- 正式清单：`manifest/final-manifest.json`。
- 交付清单：231 files。
- Required：137 files。
- Optional：94 files。
- Records：6。
- `verify-delivery` 已通过。
- `pnpm test`：155 files / 2279 tests 通过。
- `pnpm typecheck` 通过。
- 零付费调用。

### 1.2 当前断点

P0-03 已建立的可信 CI 目前只覆盖 FPVS-V1 原始基线及其 evidence-integrity manifest。

P0-02 新清单及其冻结交付路径尚未完整纳入：

- `.github/workflows/evidence.yml`
- `.github/workflows/baseline-update.yml`

因此，目前 CI 能证明第一套基线的交付完整性，却不能对第二套基线提供同等级别的可信验收。

### 1.3 本阶段目标

实施 P0-04，将 P0-02 第二套正式交付基线接入 P0-03 已验证的可信 CI 体系。

最终要求：

1. 两套基线均可独立验证。
2. 两套基线拥有各自独立的 Manifest 和 SHA-256 信任锚。
3. 普通 PR 无法同时篡改交付文件和对应信任锚来绕过检查。
4. 基线更新只能通过受控的 owner 专用通道。
5. 通过真实 GitHub PR 完成双基线红绿验证。
6. 原有 FPVS-V1 验收行为不回退。

## 3. 核心设计原则

### 3.1 两套基线必须独立

| 属性 | 基线 A | 基线 B |
|---|---|---|
| 名称 | FPVS-V1 | P0-02 Second Demo V2 |
| 清单 | 原 FPVS-V1 Manifest | `manifest/final-manifest.json` |
| 文件数 | 223 | 231 |
| Required | 151 | 137 |
| Optional | 72 | 94 |
| Records | 13 | 6 |
| 信任锚 | 独立维护 | 独立维护 |
| 更新通道 | 原有 owner 通道 | 扩展后的受控通道 |

不得通过拼接、覆盖或重新解释两个 Manifest 的方式实现双基线。

每套基线必须能够单独完成：

- Manifest 定位。
- SHA-256 信任锚读取。
- 文件完整性验证。
- Required 文件检查。
- Optional 文件状态报告。
- 失败定位与诊断。

### 3.2 信任根不能由普通 PR 自证

普通 PR 中的交付文件、Manifest 和信任锚都属于待验证数据，不能直接作为自身可信依据。

必须延续 P0-03 已验证的信任模型：

- 从可信 Base 获取验收依据。
- 从 PR Head 获取待验证内容。
- 明确验证 Base SHA 和 Head SHA。
- 对 Head SHA 进行回验。
- 不允许 PR 修改自己的验收规则后再通过验收。

新增第二套基线时，不得削弱原有 Base-only trusted evidence 机制。

### 3.3 冻结对象不可变

P0-04 是 CI 接入，不是重新制作交付物。

必须保证：

- FPVS-V1 原始 223 文件零变化。
- P0-02 冻结的 112 文件快照零变化。
- P0-02 正式交付清单不被重新生成或重写。
- 不发生版本目录覆盖。
- 不发生历史交付文件删除或替换。
- 不改变现有交付内容的 SHA-256。

如果审计发现冻结对象本身存在问题，应停止接入并单独报告，不得在 P0-04 中顺手修复冻结内容。

## 4. 功能需求

### P0-04-01：第二套基线只读审计

**目标：** 在接入 CI 前，确认 P0-02 基线的身份、路径、数量和冻结状态。

#### 输入

- P0-02 冻结快照。
- `manifest/final-manifest.json`。
- P0-02 最终报告。
- P0-03 现有可信 CI 配置及信任锚。

#### 检查内容

1. 确认 Manifest 文件存在且格式有效。
2. 确认 231 个交付文件的清单统计。
3. 确认 Required 为 137。
4. 确认 Optional 为 94。
5. 确认 Records 为 6。
6. 核实 112 文件冻结快照与正式交付基线之间的身份关系。
7. 核实所有 Manifest 路径均处于预期范围。
8. 检查路径穿越、重复路径、大小写冲突和符号链接风险。
9. 检查文件是否存在、是否与冻结 SHA-256 一致。
10. 核实原 FPVS-V1 基线没有发生变化。

#### 输出

形成独立审计报告，至少包含：

- 基线身份。
- Manifest 路径。
- 文件数量统计。
- Required / Optional 统计。
- 冻结快照关联关系。
- SHA-256 验证结果。
- 路径安全检查结果。
- 与基线 A 的隔离情况。
- PASS / FAIL 结论。

#### 验收标准

- 所有统计与正式冻结记录一致。
- 不修改任何冻结文件。
- 不重新生成正式 Manifest。
- 任一身份或哈希不一致均判定 FAIL。
- 未通过审计不得进入后续接入。

### P0-04-02：第二套基线独立信任锚

**目标：** 为 P0-02 基线建立独立、可审计的 SHA-256 信任锚。

#### 要求

1. 为 P0-02 建立独立信任锚文件或独立记录。
2. 信任锚必须绑定明确的基线身份。
3. 信任锚必须绑定正式 Manifest 的 SHA-256。
4. 不得复用或覆盖 FPVS-V1 的信任锚。
5. 两套信任锚的更新必须分别可追溯。
6. 普通 PR 不得自行更新可信 Base 中的信任锚。
7. 信任锚应具备严格格式校验，拒绝缺失字段、重复字段和不合法摘要。

#### 推荐逻辑关系

```text
Trusted Base
  ├── Baseline A
  │     ├── Manifest A
  │     └── SHA-256 Anchor A
  │
  └── Baseline B
        ├── Manifest B
        └── SHA-256 Anchor B
```

两套基线的信任关系独立，不允许 Anchor A 指向 Manifest B，反之亦然。

#### 验收标准

- 两套基线具有独立信任锚。
- 分别篡改任一 Manifest 均能被发现。
- 仅修改 PR 中的 Manifest 和 Anchor，不能使验收通过。
- 原基线信任锚及其验证行为保持不变。

---

### P0-04-03：Evidence CI 双基线验收

**目标：** 将第二套基线纳入现有 Evidence CI，确保每个相关 PR 同时接受两套基线的独立检查。

#### 涉及文件

重点审计和修改：

- `.github/workflows/evidence.yml`
- 现有 Evidence CI 辅助脚本。
- 双基线 Manifest 与信任锚定位逻辑。
- 必要的测试和文档。

#### 检查流程

```text
PR Event
   |
   v
读取可信 Base
   |
   +---- 验证 Base SHA
   |
   v
读取 PR Head
   |
   +---- 验证 Head SHA
   |
   v
加载可信基线配置
   |
   +-----------------------+
   |                       |
   v                       v
Baseline A              Baseline B
   |                       |
Manifest A              Manifest B
   |                       |
Anchor A                Anchor B
   |                       |
文件完整性验证           文件完整性验证
   |                       |
Required 检查            Required 检查
Optional 报告            Optional 报告
   |                       |
   +-----------+-----------+
               |
               v
       双基线汇总结果
               |
               v
         Required Check
```

#### 行为要求

1. 保留原有 FPVS-V1 检查逻辑。
2. 新增 P0-02 基线独立检查。
3. 两套基线分别输出检查结果。
4. 任一基线 Required 文件缺失或哈希错误，整体检查失败。
5. 任一基线的信任锚异常，整体检查失败。
6. 两套基线不得相互覆盖检查结果。
7. 不允许基线 A PASS 掩盖基线 B FAIL。
8. PR 修改验收脚本、信任锚或配置时，必须沿用 P0-03 的可信 Base 执行策略。
9. Sparse checkout 必须包含第二套基线的 Manifest、信任锚及其验证所需的冻结交付路径。
10. 不得因新增基线而使原有 PR check 失效或降低原有保护等级。

#### Optional 文件处理

Optional 文件必须逐条报告：

- 存在且哈希正确。
- 缺失。
- 存在但哈希不一致。

Optional 缺失本身不应导致 Required 检查失败，但不得静默忽略。

不得将 94 个 Optional 文件自动提升为 Required。

#### 验收标准

- 正常 PR：两套基线均 PASS。
- 基线 A Required 文件被篡改：整体 FAIL。
- 基线 B Required 文件被篡改：整体 FAIL。
- 基线 B Manifest 被篡改：整体 FAIL。
- 基线 B 信任锚被篡改：整体 FAIL。
- Optional 缺失：整体 Required 检查仍可 PASS，但必须报告缺失项。
- 原 FPVS-V1 相关检查行为与 P0-03 保持一致。

### P0-04-04：Baseline Update 双基线更新通道

**目标：** 扩展现有 owner 专用基线更新机制，使两套基线都可以在受控条件下更新，同时避免普通 PR 获得信任根修改能力。

#### 涉及文件

- `.github/workflows/baseline-update.yml`
- 现有基线更新辅助脚本。
- 双基线信任锚配置。
- 更新权限和操作说明。

#### 要求

1. 保留原有 FPVS-V1 更新通道。
2. 新增 P0-02 基线的独立更新目标。
3. 更新目标必须显式指定，不允许默认同时更新两套基线。
4. 更新操作必须具有 owner 专用权限约束。
5. 更新前检查目标基线身份。
6. 更新前检查当前 Manifest 与当前信任锚是否一致。
7. 更新后重新计算目标 Manifest SHA-256。
8. 仅更新目标基线对应的信任锚。
9. 生成更新记录，包含操作者、目标基线、旧摘要、新摘要、提交 SHA 和时间。
10. 更新失败不得留下半更新状态。
11. 不允许普通 PR 通过修改 workflow 参数或脚本绕过权限限制。

#### 隔离要求

```text
Update Baseline A
  -> Manifest A
  -> Anchor A

Update Baseline B
  -> Manifest B
  -> Anchor B
```

更新 A 不得改变 B；更新 B 不得改变 A。

#### 验收标准

- 无权限用户不能执行基线更新。
- 更新 A 不改变 B 的 Manifest 和 Anchor。
- 更新 B 不改变 A 的 Manifest 和 Anchor。
- 未指定目标时拒绝执行。
- 目标身份不匹配时拒绝执行。
- 更新失败时不产生部分写入。
- 更新成功后 Evidence CI 可以验证新基线。

### P0-04-05：真实 GitHub PR 双基线红绿验收

**目标：** 使用真实 GitHub PR 证明双基线 CI 的保护机制有效，而不仅仅依赖本地单元测试。

#### 正向验收

创建正常 PR：

- 不修改任何冻结交付文件。
- 不修改信任锚。
- 不修改可信验收规则。
- 双基线检查均通过。
- 所有原 required checks 正常通过。
- 合并保护正常工作。

#### 负向验收 A：篡改 FPVS-V1

创建测试 PR：

- 修改基线 A 的一个 Required 文件。
- 不修改可信 Base 中的信任锚。
- 预期基线 A 检查失败。
- 预期整体双基线检查失败。
- 证明基线 B PASS 不会掩盖基线 A FAIL。

#### 负向验收 B：篡改 P0-02

创建测试 PR：

- 修改基线 B 的一个 Required 文件。
- 不修改可信 Base 中的信任锚。
- 预期基线 B 检查失败。
- 预期整体双基线检查失败。
- 证明基线 A PASS 不会掩盖基线 B FAIL。

#### 负向验收 C：同时篡改 Manifest 与 Anchor

创建测试 PR：

- 同时修改基线 B 的 Manifest 和 PR 中的 Anchor。
- 不具备 owner 专用更新权限。
- 预期检查仍使用可信 Base 中的信任锚。
- 预期验收失败。

#### 负向验收 D：篡改验收规则

创建测试 PR：

- 修改 Evidence workflow 或相关校验脚本。
- 尝试让 PR 使用自身修改后的校验规则。
- 预期仍由可信 Base 中的规则执行。
- 预期不能绕过 required check。

#### 验收标准

至少完成：

- 1 个双基线正常 PR。
- 1 个基线 A 篡改 PR。
- 1 个基线 B 篡改 PR。
- 1 个 Manifest + Anchor 联合篡改 PR。
- 1 个验收规则篡改 PR。

每个 PR 都必须保留：

- PR URL。
- Base SHA。
- Head SHA。
- Workflow Run URL。
- Required Checks 结果。
- 关键日志或失败诊断。
- 最终结论。

不得仅凭本地模拟或测试脚本结果宣称真实 GitHub 验收通过。

## 5. 安全与兼容性约束

### 5.1 信任边界

- Base 是可信验收依据。
- Head 是待验证对象。
- PR Head 不得决定自己的信任根。
- PR Head 不得决定自己的 required check 规则。
- 所有关键 SHA 必须进行显式回验。
- Fork PR 与同仓库 PR 必须保持一致的保护效果。

### 5.2 文件范围

Sparse checkout 必须覆盖：

- 原 FPVS-V1 Manifest。
- 原 FPVS-V1 信任锚。
- P0-02 `manifest/final-manifest.json`。
- P0-02 独立信任锚。
- 两套基线需要验证的交付文件。
- 必要的校验脚本和可信配置。

不得通过只检出 Manifest 而遗漏实际交付文件的方式制造虚假 PASS。

### 5.3 兼容性

- 不删除原有 required checks。
- 不降低原有 ruleset 保护。
- 不改变 P0-03 的 Base-only 信任模型。
- 不改变原 FPVS-V1 的验收口径。
- 不改变 P0-02 的冻结清单。
- 不允许两套基线共享可变状态。

### 5.4 预算

本阶段必须满足：

- 零付费 API。
- 零生图调用。
- 零模型调用。
- 不增加生产环境支出。
- 不以预算未授权为理由执行第二个 Demo 的付费生成。

P0-04 只有在以下条件全部满足时才能判定 PASS。

| 编号 | 验收条件 | 结果要求 |
|---|---|---|
| AC-01 | 基线 A 冻结文件完整性 | PASS |
| AC-02 | 基线 B 冻结文件完整性 | PASS |
| AC-03 | 两套 Manifest 独立 | PASS |
| AC-04 | 两套 SHA-256 信任锚独立 | PASS |
| AC-05 | Base-only trusted evidence 保持 | PASS |
| AC-06 | 双基线 Evidence CI | PASS |
| AC-07 | 双基线 Baseline Update 隔离 | PASS |
| AC-08 | 基线 A 篡改负向 PR | FAIL 被正确拦截 |
| AC-09 | 基线 B 篡改负向 PR | FAIL 被正确拦截 |
| AC-10 | Manifest + Anchor 联合篡改 | FAIL 被正确拦截 |
| AC-11 | 验收规则篡改 | FAIL 被正确拦截 |
| AC-12 | 正常双基线 PR | PASS |
| AC-13 | 原有 required checks 和 ruleset | 无回退 |
| AC-14 | Optional 文件状态 | 逐项报告 |
| AC-15 | 冻结文件与历史记录 | 零修改 |
| AC-16 | 付费与生图调用 | 零调用 |

任何一项安全相关验收失败，均不得以其他项目通过抵消。

## 9. 完成定义

P0-04 的完成，不是简单地让 workflow 多检查一个 JSON 文件。

真正的完成定义是：
