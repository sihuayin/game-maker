# Evidence Integrity V1：交付证据完整性与可复核验收

> 文档类型：PRD / 工程需求  
> 优先级：P0  
> 状态：待实施  
> 适用项目：`sihuayin/game-maker` V2  
> 基线：FPVS-V1 Final Acceptance，main `5f29592e04c0fa6cb63d41ae72df20adb4368dd4`  
> 核心目标：将目前依赖 effort 脚本完成的证据核验，提升为可重复执行、可发现篡改、可重新计算最终结论的正式验收能力。

---

## 1. 背景与问题

FPVS-V1 已经完成一次真实 Demo 的最终验收：

- 两次真实浏览器试玩均为 `SUCCESS`。
- 两次试玩均达到游戏目标：`won=true`、收集 6 个目标物、开启 2 个宝箱。
- 两次试玩均为 0 次 reset、0 次 hazard-hit、0 次 runtime-error。
- 继承证据核验为 27/27，视觉补审通过，§5.5 检查为 8/8 MET。
- 自动化回归全部通过。
- 当前交付结论为 `pass`。

但目前，部分关键证据的完整性仍依赖 effort 脚本进行核对，而正式验收路径没有完整承担这些检查。

主要缺口：

1. **证据哈希未在正式验收路径重新计算。** 证据文件可能在初次核验后被修改，而产品验收读取路径未必能够发现。
2. **证据与交付身份的关联需要正式校验。** 文件存在并不代表文件属于当前 Demo、当前验收轮次或当前被审查对象。
3. **最终结论需要从当前证据重新计算。** 不能因为历史报告写着 `pass`，就直接继承为当前 `pass`。
4. **缺少系统性的反例测试。** 需要证明缺失、篡改、错配和不一致证据确实会影响验收结论。
5. **人工审核记录与机器验证边界必须保持清晰。** 自动化可以验证审核记录的完整性和关联性，但不能伪造或替代人工视觉审核。

因此，本需求不是增加更多试玩能力，而是为现有验收建立一条正式的证据完整性与结论重算路径。

## 2. 目标与非目标

### 2.1 目标

- 将关键证据的完整性核验纳入正式验收流程。
- 对纳入核验范围的证据文件重新计算 SHA-256，并与可信的预期值比较。
- 检查证据路径、文件存在性、身份关联、记录一致性和引用完整性。
- 从当前有效证据重新计算最终验收结论。
- 对篡改、缺失、错配和内部矛盾给出确定、可定位的失败原因。
- 保留已有交付格式、历史证据和已通过 Demo，不要求重新生成资源或重新运行付费流程。
- 通过负向测试证明验收不会在证据失效时继续输出 `pass`。

### 2.2 非目标

本版本不负责：

- 生成新游戏、关卡、资源或运行时代码。
- 提高生图质量或调整 Prompt。
- 引入第二个真实 Demo。
- 完成纵向巡逻、定时喷发等机制的完整真实端到端验证。
- 引入新的人工审核工作流、截图系统或视觉评分系统。
- 将人工审核记录自动转换为机器验证成功。
- 重构整个 QA、Playtest 或 Delivery 架构。
- 修改已有验收阈值来让历史证据通过。
- 引入付费模型调用、新的付费 E2E 或新依赖。
- 扩展为跨游戏共享知识或跨项目迁移机制。

## 3. 核心设计原则

### 3.1 当前证据优先于历史结论

历史 `pass` 仅是历史结果，不是当前结论的充分依据。

正式验收必须基于当前交付身份、当前引用的证据及重新计算的校验结果，得出本次结论。

### 3.2 完整性校验不等于证据真实性

SHA-256 可以发现文件相对可信预期值的变化，但不能独立证明：

- 文件内容真实反映了实际发生的事件。
- 截图确实来自指定 Demo。
- 人工审核判断正确。
- 初始哈希清单本身没有被一起篡改。

因此，V1 必须同时校验文件哈希、身份关联和记录一致性。对于哈希预期值的可信来源及清单自身的保护，应在实施前明确；不得把同一目录中可被同时修改的文件与哈希清单视为独立信任根。

### 3.3 不因证据缺失而推定成功

缺失、不可读取、无法关联或无法验证的必需证据，不得被默认为有效。

具体状态应映射为现有验收体系支持的失败、阻断或未完成状态，不得新造状态后绕过现有结论逻辑。

### 3.4 保留自动与人工审核边界

- 机器可以验证审核记录是否存在、格式是否有效、subject 是否匹配、审核项目是否齐全。
- 机器不能据此推断人工视觉判断一定正确。
- 原有人工审核结果必须继续由已有审核流程提供。
- 不允许通过 `visualReview`、`knownLimitations` 或其他旁路字段，将缺失的必需试玩证据改写成成功。

### 3.5 不破坏既有交付

本版本应尽可能采用增量式实现：

- 不新增 `GameCreationState`。
- 不引入跨游戏共享状态。
- 不修改现有 `delivery.playtest` schema，除非后续经过明确批准。
- 不改变 `delivery.checks.playable-smoke` 的既有兼容语义。
- 不覆盖历史 `run/vN`、`pack/site/vN` 或已提交的验收证据。
- 不因验证失败而自动修复或重写原始证据。

## 4. 用户与使用场景

主要用户是维护 `game-maker` 的开发者和执行 FPVS 验收的人。

### 场景 A：重复执行验收

开发者对同一份交付重复运行正式验收，得到一致的证据校验结果和最终结论，不依赖人工记忆或一次性脚本输出。

### 场景 B：发现证据被篡改

一份已通过验收的截图、试玩报告或其他必需证据在之后被修改。再次验收时，系统重新计算哈希并报告差异，不再直接继承旧 `pass`。

### 场景 C：发现证据错配

证据文件存在，但其 Demo 身份、试玩 attempt、审核 subject 或报告引用与当前交付不一致。验收必须发现错配。

### 场景 D：重算最终结论

历史聚合报告声明 `pass`，但当前证据已经缺失或校验失败。系统应根据当前有效检查重新计算结论，并指出历史声明与当前结果不一致。

### 场景 E：证明校验器有效

通过故意破坏测试副本中的证据，证明校验器能检测到预期问题，同时不会修改真实交付和历史记录。

## 5. 功能需求

### EI-01：建立正式证据清单

系统必须识别本次验收需要核验的证据及其关联关系。

证据范围以当前 FPVS-V1 已有正式验收链和 `07-verify-inherited.mjs` 所核验的内容为基线，至少覆盖：

- `artifacts/identity.json` 及其与当前交付的关联。
- FA-04 视觉审核、截图和审核材料的 subject 关联。
- FA-04 纳入核验范围的全部材料文件及 SHA-256。
- 视觉材料的数量、去重结果和文件引用关系。
- site-integrity 所需文件。
- FA-05 evidence、consistency 检查及 `qa-report` 哈希关联。
- FA-06 回归结果。
- 两份真实 Playtest attempt 的身份、结果、停止原因和站点未修改证据。
- Playtest 结果与交付摘要之间的一致性。
- site 与 pack 受保护文件的前后哈希一致性。
- FA-09 视觉补审记录、subject 及必需审核项。
- FA-04 历史审核记录的不可变性要求。

清单必须有明确的必需项与可选项定义。不能因为某个文件存在，就自动把它认定为必需证据；也不能因为某个必需文件缺失，就从清单中静默删除该项。

### EI-02：重新计算文件哈希

对清单中所有必需且可哈希的文件，正式验收必须：

1. 解析证据引用。
2. 确认路径位于允许的交付范围。
3. 检查文件存在并可读取。
4. 读取文件实际字节。
5. 重新计算 SHA-256。
6. 与可信的预期哈希比较。
7. 记录校验结果及可定位的错误原因。

至少需要区分：

- `missing`：文件不存在。
- `unreadable`：文件无法读取。
- `hash-mismatch`：实际哈希与预期值不一致。
- `path-invalid`：路径不符合允许的路径规则。
- `reference-invalid`：引用无法解析。
- `verified`：校验通过。

以上是校验结果的语义分类，不要求全部新增为对外合同枚举；应优先复用现有诊断格式。

路径校验必须防止通过 `..`、绝对路径、符号链接或其他路径解析行为逃逸出允许的交付根目录。具体策略应与现有 Runtime 的跨平台文件系统约束保持一致。

### EI-03：校验交付身份

系统必须检查证据与当前交付身份之间的关系。

至少检查：

- identity 文件是否有效。
- 证据引用的身份是否与当前交付一致。
- Playtest attempt 是否属于指定的交付版本。
- 人工审核记录的 subject 是否匹配当前审核对象。
- 审核材料是否属于该审核记录声明的材料集合。
- 报告引用是否指向当前实际存在的报告，而非其他版本或历史目录。

若身份信息缺失或互相矛盾，不得仅凭文件哈希正确而判定证据有效。

### EI-04：校验记录内部一致性

系统必须检查关键报告之间的可验证关系。

至少覆盖：

- `qa-report` 与其引用证据的关联。
- FA-05 evidence 与 consistency 记录之间的既有约束。
- Playtest 报告与 `delivery.playtest` 摘要的一致性。
- 两次真实 Playtest 的 attempt 身份、结果及停止原因。
- 声明的视觉审核项目与实际审核记录之间的对应关系。
- 受保护的 site 与 pack 文件是否发生变化。
- 交付中声明的最终结论是否与本次重新计算的结论一致。

不要求 V1 重构所有报告 schema。应先梳理已有数据关系，尽量在现有 contracts 和纯函数边界内完成校验。

### EI-05：重新计算最终验收结论

正式验收必须基于当前证据重新计算最终结论，而不是直接信任历史 `verdict`。

要求：

1. 对当前必需检查重新执行可执行的校验。
2. 汇总证据完整性、身份关联和报告一致性结果。
3. 调用现有结论计算规则或对其进行最小、明确的增量扩展。
4. 比较本次计算结果与交付中声明的结果。
5. 在结果中明确区分“声明值”和“本次重算值”。
6. 如果两者不一致，提供可定位的原因。
7. 任何必需证据失效都不能被旧 `pass` 覆盖。

结论优先级、`pass` / `fail` / `blocked` / `incomplete` 等既有状态的语义应沿用当前正式规则，不得为本功能另建一套相互冲突的结论体系。

如果现有规则无法确定某种新校验失败应映射到哪个状态，必须在实施前裁定；不得默认映射为 `pass`。

### EI-06：提供可重复执行的正式入口

证据完整性检查必须可以通过仓库正式验收流程重复执行，而不只是由一次性 effort 脚本完成。

正式入口应：

- 使用当前指定的交付作为输入。
- 复用现有路径、报告和结论计算能力。
- 对同一份未变化的交付给出一致的结果。
- 失败时输出机器可读、可定位的诊断。
- 不要求开发者手工编辑中间 JSON。
- 不需要付费模型调用。
- 不自动修改原始交付或历史证据。

入口名称、CLI 参数和报告结构应在代码审查阶段根据当前 CLI 约定确定；本 PRD 不预先要求新增命令或新增合同字段。

### EI-07：保持原始证据只读

校验器必须只读访问待验收的原始证据。

允许写入的内容仅限于现有正式流程已授权的验收输出位置；若需要新增输出文件，必须先确认不会覆盖历史报告或破坏原有目录约定。

校验失败时：

- 不删除文件。
- 不重写证据。
- 不修正哈希清单以迁就当前文件。
- 不重新生成资源。
- 不修改 `pack/site`。
- 不重跑付费生图或模型流程。
- 不吞掉错误后继续使用旧结论。

## 6. 非功能需求

### NFR-01：确定性

相同输入字节、相同清单和相同校验规则应产生相同的证据校验结果与最终结论。

### NFR-02：可诊断性

每个失败项应能定位到具体证据、引用关系或一致性规则。不得只返回笼统的 `verification failed`。

### NFR-03：最小变更

优先增量扩展现有 QA / acceptance 实现，不重建交付系统。

### NFR-04：跨平台路径安全

路径处理必须兼顾仓库支持的平台，并避免证据引用逃逸出允许目录。

### NFR-05：无付费成本

测试和验收均不得触发付费模型或生图调用。

### NFR-06：历史可追溯

历史证据和历史结论保持原样。新的验收结果应能被识别为新的验证运行，而不是覆盖旧记录。

## 7. 验收标准

### AC-01：现有基线可通过

对 FPVS-V1 已通过的冻结 Demo 执行正式证据完整性验收，在原始证据没有变化的情况下：

- 必需证据均被识别。
- 哈希核验通过。
- 身份及引用关系通过。
- 既有人工审核记录被正确读取。
- Playtest 报告与交付摘要一致。
- 最终结论与当前有效证据一致。

注意：这是基线兼容性要求，不代表允许忽略真实存在的历史限制或未验证项。

### AC-02：篡改必需文件会被发现

在隔离的测试副本中修改任意一份必需证据文件，保持预期哈希不变，再运行正式验收：

- 检测到哈希不匹配。
- 报告具体文件和错误类别。
- 不继续沿用原先的 `pass` 作为当前有效结论。
- 不修改原始清单或修复测试文件。

### AC-03：缺失证据会被发现

在测试副本中移除一份必需证据：

- 检测到缺失。
- 不把该项从必需清单中静默删除。
- 最终结论按既有规则重新计算。
- 输出可定位的诊断。

### AC-04：身份错配会被发现

构造哈希正确但身份不匹配的测试证据：

- 文件哈希可通过。
- 身份关联校验失败。
- 该证据不能被当作当前交付的有效证据。

### AC-05：报告矛盾会被发现

构造以下至少一种测试情形：

- `delivery.playtest` 摘要与实际报告不一致。
- 报告声明的 attempt 与当前交付不匹配。
- 人工审核 subject 与审核材料不匹配。
- 声明的最终 `verdict` 与重新计算结果不一致。

正式验收必须发现相应矛盾。

### AC-06：路径逃逸会被拒绝

构造越界路径、`..` 路径和适用平台上的符号链接逃逸案例：

- 校验器拒绝越界引用。
- 不读取允许目录外的文件作为有效证据。
- 返回明确诊断。

### AC-07：历史与交付不被修改

执行成功及失败两种验证流程后：

- 原始证据文件未发生变化。
- 历史验收记录未被覆盖。
- 受保护的 site 与 pack 文件保持原样。
- 不生成新的资源版本。
- 不产生付费调用。

### AC-08：回归全部通过

至少通过仓库现有相关检查：

- `pnpm test`
- `pnpm typecheck`
- `pnpm test:playtest`
- `pnpm test:acceptance`

如果当前仓库命令发生变化，以实施时仓库的正式脚本为准，并在验收记录中明确列出实际执行的命令及结果。

## 8. 测试设计

所有破坏性测试必须在隔离的临时目录或测试 fixture 中执行，禁止直接破坏已通过验收的真实 Demo。

| 测试类别 | 测试操作 | 预期结果 |
|---|---|---|
| 正常路径 | 使用完整、未变化的证据 | 校验通过，重算结论 |
| 内容篡改 | 修改证据字节但保留预期哈希 | `hash-mismatch` |
| 文件缺失 | 删除必需证据 | `missing` |
| 文件不可读 | 模拟读取失败 | 明确诊断，不默认成功 |
| 身份错配 | 替换为另一交付的证据 | 身份校验失败 |
| 引用错配 | 报告引用错误 attempt | 引用或一致性校验失败 |
| 审核错配 | subject 与材料集合不一致 | 审核关联失败 |
| 结论过期 | 声明 `pass`，当前必需证据已失效 | 重算结果不再继承旧 `pass` |
| 路径逃逸 | 引用交付根目录外的文件 | 路径校验失败 |
| 重复执行 | 对相同输入运行两次 | 结果一致 |
| 只读性 | 对比执行前后的原始文件哈希 | 原始文件不变 |

### 测试注意事项

- 必须验证校验器本身，而不仅是测试 fixtures 的构造结果。
- 不得仅以 `07-verify-inherited.mjs` 的成功退出作为新功能通过的证据。
- effort 脚本可以保留为独立交叉验证工具，但正式验收应拥有自己的正式执行路径。
- 如果正式入口内部复用了该脚本的实现，应避免循环调用、重复信任历史输出或把脚本的旧结论当作独立证据。

## 9. 实施计划

### Phase 0：只读审计

梳理当前仓库实现，明确：

- `07-verify-inherited.mjs` 实际检查的全部证据及其来源。
- 正式验收当前读取哪些文件、哪些报告、哪些哈希。
- 最终结论的计算入口及优先级规则。
- 当前文件系统路径解析和原子写入约定。
- 已有纯函数、contracts、CLI 和 QA 的职责边界。
- 哈希清单的生成方式及其可信来源。

输出：差距清单、证据依赖图、最小改动方案。

### Phase 1：实现正式校验能力

优先实现：

1. 证据清单与必需项检查。
2. SHA-256 重新计算。
3. 路径与文件存在性检查。
4. 交付身份关联检查。
5. 关键报告一致性检查。
6. 与现有结论计算规则集成。

优先复用已有 schema 和纯函数，不在本阶段扩展无关合同。

### Phase 2：负向测试

补齐篡改、缺失、身份错配、报告矛盾、路径逃逸和结论过期测试。

所有测试使用隔离副本，验证失败诊断及原始证据只读性。

### Phase 3：基线验收与回归

在不改变真实 Demo 的前提下：

1. 对冻结的 FPVS-V1 交付运行正式验收。
2. 与已有 effort 核验结果交叉比较。
3. 解释任何差异，不允许为了匹配旧结果而跳过校验。
4. 运行全部相关回归。
5. 形成新的验收记录，不覆盖历史记录。

## 10. 交付物

- 正式证据完整性校验实现。
- 与现有验收结论计算路径的集成。
- 必需证据、身份和一致性规则的测试。
- 篡改与路径安全的负向测试。
- 基线 Demo 的正式重验结果。
- 实施差异和已知限制说明。

除非审计发现确实无法在现有接口内表达必要结果，否则不新增对外 schema 字段、CLI 参数或依赖。

## 11. 风险与限制

### R1：哈希清单与证据一起被篡改

如果证据和预期哈希位于同一个可同时修改的信任边界内，重新计算哈希无法发现二者同步篡改。

应在 Phase 0 明确预期哈希的可信来源。V1 至少保证与可信预期值进行比较；不能宣称实现了超出实际信任边界的防篡改能力。

### R2：证据完整不等于游戏质量合格

哈希、身份和引用关系通过，只说明证据在约定范围内完整且关联一致，不代表游戏玩法、视觉质量或用户体验自动合格。实际质量仍由既有 Playtest 和人工审核规则决定。

### R3：单 Demo 覆盖有限

本版本以当前已验收 Demo 为兼容性基线。校验器的通用性由确定性测试和负向测试验证；第二个真实 Demo 的泛化验证留待后续阶段。

### R4：历史证据可能存在已知限制

现有历史限制必须继续披露。不能因为新增完整性校验通过，就将未完成的五态 E2E、机制覆盖或视觉审核范围扩大解释为已完成。

## 12. 完成定义

只有同时满足以下条件，Evidence Integrity V1 才能宣告完成：

- [ ] 正式验收入口会重新计算所有范围内必需证据的哈希。
- [ ] 证据缺失、篡改和不可读取均可被发现。
- [ ] 身份、引用及关键报告的一致性得到正式校验。
- [ ] 最终结论从当前有效检查重新计算，而非直接继承历史声明。
- [ ] 声明结论与重算结论的差异可被定位。
- [ ] 负向测试覆盖篡改、缺失、错配、路径逃逸和结论过期。
- [ ] 测试证明原始证据、历史记录和受保护交付未被修改。
- [ ] 当前冻结 Demo 通过正式基线重验，或对任何差异作出明确、可审计的解释。
- [ ] `pnpm test`、`pnpm typecheck`、`pnpm test:playtest`、`pnpm test:acceptance` 全部通过。
- [ ] 不新增付费调用、不覆盖历史版本、不降低验收阈值。

**最终原则：旧的 `pass` 是历史事实；只有当前证据完整性校验通过、必要检查有效且结论重新计算一致，才可以把 `pass` 作为本次正式验收结论。**

### A2. 三条实施约束

1. **通用入口不等于虚构产品证据。** CLI 接受显式交付根目录，但必须区分：当前目录下实际存在、可验证的证据；需要通过明确参数或配置提供的外部继承证据；当前交付模型尚未支持的证据类型。不得假定 `out/<gameId>/run/vN` 已经包含 `.scratch/fpvs-v1-final` 中的所有继承证据，也不得为了通用化而修改现有 `delivery` schema。冻结基线所需的工作区和继承证据，应通过明确的输入契约纳入验收。
2. **期望哈希清单必须先冻结，再开始负向测试。** 只读审计 → 从已确认的冻结基线生成清单 → 审查清单内容并随 git 提交固定 → 正式校验器只读取清单、绝不自动更新 → 在隔离副本中篡改证据并确认校验失败。清单与证据自述哈希之间的交叉核验只作为额外一致性检查，不宣称它比独立信任锚提供更强的防篡改能力。
3. **保留 `07-verify-inherited.mjs` 的独立性。** 它继续作为独立的交叉验证工具；正式校验器不得仅调用它并继承退出码，负向测试不得只验证 07 自身；两套结果应可比较、差异可解释。

### A3. 期望哈希清单（Q6 / Q9 / Q12）

清单包含：

- `format`：清单格式版本。
- `roots`：交付根（快照 / 工作区）与继承证据根的**封闭**标识符映射。
- `subject`：`packId`、`packVersion`、`siteVersion`、`shellVersion`、`manifestChecksum`、`configChecksum`。
- `files[]`：`root` + `path` + `role` + `required` + `sha256`。
- `records[]`：需要进一步解析和验证的报告及记录（qa-report、review-record、capture、materials、supplement、两份 attempt、evidence.json、consistency.json、regression.json）。

三条规则：

- 清单未列出的普通额外文件不因此报错。
- 被引用但未列入清单的文件报 `reference-invalid`。
- `required: false` 项缺失不阻断；文件存在时仍校验其哈希与可解析性（如适用）。

`roots` 的路径解析规则必须确定且安全；`files[].root` / `records[].root` 只能引用 `roots` 中已登记的标识符，记录不得自行声明新 root。

### A4. 状态映射（Q7）

| 情况 | 结果 |
|---|---|
| 哈希不符、路径越界、引用无效、身份不符、报告矛盾 | `fail` |
| 声明 verdict 与重算 verdict 不一致 | `fail` |
| 必需文件缺失或不可读 | `blocked` |
| 必需身份字段缺失 | `blocked` |
| 清单无法读取或不符合 schema | `EXIT.invalid(4)`，不产出正式验收报告 |
| 所有必需检查有效且通过 | `pass` |

最终状态由既有 `deriveDeliveryVerdict` 规则统一计算（`fail > blocked > incomplete > pass`），不在校验器内复制另一套优先级。某项 `blocked` 时，校验器仍应尽可能检查其他独立、可执行的项目；清单本身无效属于输入无法建立，直接拒绝执行。

### A5. 六项检查的重算定义（Q13）

| 检查项 | 正式校验器的职责 |
|---|---|
| `asset-pack` | 调用 `verifyPack` 重算包内校验结果及 `manifestChecksum`。 |
| `config` | 比较 `game-config.json` 的实际哈希与清单 / 身份声明中的预期值。 |
| `qa` | 从当前 `qa-report` 调用 `qaVerdict(report)` 重新导出结论。 |
| `site` | 校验站点四文件、`site.json` 引用、配置哈希和 `site-integrity` 记录。 |
| `playable-smoke` | 从 `result.json` 使用 `playtestSummaryOf` 与 `mapPlaytest` 重导出结果。 |
| `visual-review` | 验证审核记录完整性、subject、审核项完整性，以及与 `delivery.visualReview` 的一致性；不重新判定人工视觉结论。 |

报告必须并列展示 `declared[]` 与 `recomputed[]` 并保留差异诊断。边界：本功能重新计算的是已有证据能够支持的检查结果，不重新构建游戏、不重新执行 QA、不重新启动浏览器试玩，也不把人工审核转换成机器判断。

### A6. 正式入口、报告与退出码（Q4 / Q8 / Q11）

- **入口**：`game-maker verify-delivery --manifest <file> [--out <dir>] [--json]`。CLI 只认 `--manifest`，不猜、不扫描、不假定 `out/<gameId>/run/vN` 里有继承证据。
- **只读约束**：`--out` 位于任何声明 root 内 ⇒ `usage(2)`，且不得开始写入。路径比较在规范化与符号链接处理后执行。
- **报告**：pipeline 内本地 zod schema `delivery-verification/v1`；`report.json` + `report.md` 描述同一次运行；目录原子分配（`mkdirSync`，已存在则分配新目录），绝不覆盖历史；中途失败不得留下看似完整的结果。
- **报告内容**：输入清单及其 SHA-256、清单声明的 `subject`、声明 verdict 与重算 verdict、逐文件的预期哈希 / 实际哈希 / 校验结果、身份 / 引用 / 一致性逐项诊断、最终状态、退出码、信任边界说明、已知限制与本次实际检查范围。
- **退出码**：重算结论 `pass → 0`；`fail | blocked | incomplete → 1`；用法错 `→ 2`；清单 / 交付读不出或不过 schema `→ 4`。
- **`pnpm test:evidence`**：构建所需 CLI → 使用固定清单运行正式 CLI → 校验退出码与报告存在且结构合法 → 确认本次重算结论与预期基线一致 → 保留本次报告、不覆盖历史。不并入普通测试套件；必须在票面记录真实耗时与证据读取规模。

### A7. 路径安全（Q14）与三方哈希核验（Q15）

- **路径**：root 与目标文件均解析 `realpath`，验证真实路径包含关系；包含性判断基于规范化后的路径组件，不用字符串前缀（否则 `/allowed-other` 会被误认为 `/allowed` 的子目录）。`..` 越界、绝对路径越界、指向 root 外部的符号链接、悬空符号链接均拒绝；root 内部且目标仍在允许范围内的符号链接允许。
- **三方哈希**：对 `evidence.json.files[]`、`materials.json` 以及适用时的 `identity.json`：(1) 从 git 固定的清单读取期望哈希；(2) 从证据记录解析自述哈希；(3) 从实际文件字节重新计算 SHA-256；(4) 比较三方并输出具体差异。应当一致的值发生矛盾记 `fail`。该能力只用于发现内部不一致，不提供更强的独立防篡改保证：若清单与证据自述哈希一起被修改并提交，git 提交历史与审查流程才是当前信任边界。

### A8. 只读性、负向测试与历史证据保护（Q1 / Q10 / 执行边界）

- 只在 `main` 上增量实现；不覆盖历史验收证据；不改冻结 Demo 的 `pack/site`、Runtime、配置或资源。
- 校验器只读访问待验收证据；失败时只报告，不删除、不重写证据、不修正哈希清单、不重新生成资源、不修改 `pack/site`、不跑付费流程。
- 负向测试使用 `mkdtemp` 合成小型 fixture（3–5 文件 + 迷你清单），覆盖篡改、缺失、不可读、身份错配、引用错配、审核 subject 错配、结论过期，以及 A7 的五类路径情形；测试执行前后校验 fixture 全量哈希一致。不得直接破坏已通过验收的真实 Demo。
- 真实基线重验使用冻结 FPVS-V1 的完整证据单独执行，运行前后比较受保护文件快照；不为每个负向场景复制约 200 MB 的真实证据。
- 不增加 MCP 镜像、不扩展无关 contracts、不修改 `delivery` / `qa-report` schema；结论规则统一，不得因无法判定而默认 `pass`；历史限制继续如实披露。

### A9. Phase 0 前置条件

先只读审计并确认现有记录的实际 schema（FA-04 `review-record` / `capture` / `materials`、FA-05 `evidence` / `consistency` / `qa-report#delivery`、FA-06 `regression`、两份 Playtest `result`、FA-09 `supplement` 的身份字段与来源），再生成并审查 git 固定的期望清单。若现有记录与 A3 的身份契约不一致，应如实报告差异并决定如何纳入清单；不得为了让基线通过而修改历史记录或放宽身份规则。

### A10. 执行顺序

1. Phase 0 只读审计：确认真实记录 schema、证据依赖和可信哈希来源。
2. 清单冻结：生成并审查 git 固定的期望哈希清单。
3. 正式实现：`packages/pipeline` 核验逻辑、`verify-delivery --manifest <file> [--out <dir>]` CLI、本地报告 schema。
4. 负向测试：覆盖文件篡改、缺失、身份错配、报告矛盾、路径逃逸和符号链接。
5. 冻结基线重验：执行 `pnpm test:evidence`，产出新报告并确认原始证据未被修改。
6. DoD 收口：完成 §12 的全部验收条件。

**最终验收原则不变**：只有当前证据完整性校验通过、六项检查从有效证据重算成功、声明与重算结论一致，才能认定本次结果为 `pass`。
