# P0-01 · 生成管线只读能力审计 PRD

- **项目**：`sihuayin/game-maker`
- **目标分支**：`main`
- **需求编号**：P0-01
- **优先级**：P0
- **交付类型**：独立、可合并的文档交付
- **前置条件**：FPVS-V1 Final Acceptance、Evidence Integrity V1 已有交付记录
- **后续依赖**：FPVS-V2 独立 Demo 生成与真实验收
- **版本**：v1.0

---

## 1. 背景

`game-maker` 已具备从游戏输入到资源、运行配置、可玩 Demo、Playtest 和交付证据校验的现有管线。

但在启动下一阶段独立 Demo 验收之前，需要先明确：

1. 哪些能力已有生产代码实现？
2. 哪些能力仅由单元测试或 fixture 证明？
3. 哪些能力已通过真实端到端运行验证？
4. 哪些能力虽然存在，但尚未证明能够支持新的游戏意图？
5. 如果生成第二个 Demo，最可能遇到哪些阻塞？

如果没有这份审计，开发容易重复实现已有能力、把模拟测试误认为真实能力，或在缺乏证据时提前扩大架构。

因此，本需求只做一次**可追溯、可复核、零生产代码变更的能力审计**。

## 2. 目标

对 `main` 分支当前实际代码进行只读审计，输出一份能够支持后续开发决策的能力矩阵与缺口报告。

审计必须区分以下四种证据状态：

| 状态 | 含义 |
|---|---|
| `IMPLEMENTED` | 已找到生产代码实现，但不代表端到端能力已经得到验证。 |
| `TESTED` | 有自动化测试证据，但测试范围和真实性需要单独说明。 |
| `E2E_VERIFIED` | 有可追溯的真实端到端运行证据，能够证明对应能力在实际运行链路中有效。 |
| `UNKNOWN` | 现有代码或证据不足以得出可靠结论。 |

另设 `BLOCKED` 表示审计本身因权限、证据不可读取或环境限制而无法完成某项检查。

**状态不得互相替代。** 例如，存在实现不能自动升级为 `E2E_VERIFIED`；fixture 测试通过也不能直接证明真实浏览器中的玩法有效。

## 3. 范围

### 3.1 本期必须审计

1. 输入与游戏意图解析。
2. 风格与视觉世界描述。
3. 游戏设计与机制表达。
4. 资源规划、生成、打包及验证。
5. 关卡配置与运行时编译。
6. Demo 启动、玩家控制及目标达成。
7. Playtest 的执行、观测、结果分类与报告写回。
8. 人工视觉确认及其与最终判定的关系。
9. `verify-delivery` 与证据完整性验证。
10. 版本隔离、历史交付保护及相关测试约束。

具体模块名以当前仓库实际结构为准，不得因为本需求预先列出了模块，就假定对应能力一定存在。

### 3.2 本期明确不做

- 不修改生产代码、公共契约或运行时。
- 不新增 CLI、MCP 接口或依赖。
- 不修改测试逻辑以使检查通过。
- 不执行模型生图或付费端到端生成。
- 不启动第二个 Demo 的正式生成。
- 不修改历史 run、pack、delivery 或验收报告。
- 不新增机制注册表、自动修复或进化能力。
- 不把跨游戏知识共享、迁移或多游戏运行时纳入范围。

## 4. 审计基准与证据来源

审计以执行时确定的 `main` 分支提交为基准。

### 4.1 必须记录的基准信息

- 仓库地址。
- 分支名称。
- 完整 Git commit SHA。
- 审计时间。
- 工作区状态（如有本地副本）。
- 实际读取的关键目录、文档与测试范围。
- 无法读取或无法核实的内容。

不得只写“最新 main”，必须记录可复核的具体提交 SHA。

### 4.2 证据来源优先级

按以下顺序收集证据：

1. 当前生产代码与契约定义。
2. 当前自动化测试及其实际断言。
3. 当前可追溯的真实运行报告、Playtest 报告和交付产物。
4. 历史 PRD、设计文档与验收说明。

设计文档只能说明预期行为，不能单独证明功能已经实现。

历史验收报告必须与对应提交、Demo 身份和交付版本关联。无法核实关联关系的记录只能作为参考，不得作为当前能力的确定性证明。

## 5. 审计任务

### P0-01A：冻结审计基准

**要求**

- 确定 `main` 的审计提交。
- 记录关键目录与包结构。
- 明确审计期间不修改生产代码。
- 列出本次读取的文件和证据来源。

**验收标准**

- [ ] 审计报告记录完整 commit SHA。
- [ ] 能够复核实际审计的代码范围。
- [ ] 没有为完成审计而修改生产实现。
- [ ] 无法读取的证据明确标记，而非推测补齐。

### P0-01B：绘制真实生成管线

**要求**

从真实入口追踪当前代码的实际调用关系，至少覆盖：

`输入 → 设计与意图 → 资源规划与生成 → AssetPack → GameConfig → Runtime → Playtest → 交付验证`

如果实际管线存在分支、条件路径或不同入口，应如实记录，不得为了图示整齐而虚构单一线性流程。

每个阶段必须标明：

- 入口与关键实现文件。
- 输入与输出契约。
- 实际调用的下游模块。
- 失败处理与产物位置。
- 对应自动化测试。
- 已有真实运行证据。
- 未覆盖的路径。

**验收标准**

- [ ] 每个关键阶段都能追溯到实际代码。
- [ ] 明确区分真实调用链与文档中的预期流程。
- [ ] 明确标记仅存在于 fixture 或测试替身中的路径。
- [ ] 没有将目录存在误判为功能完整。

### P0-01C：建立能力矩阵

对第 3.1 节的各个能力域逐项审计。

能力矩阵至少包含：

| 字段 | 要求 |
|---|---|
| `capability` | 能力名称 |
| `implementation` | 生产实现位置或 `UNKNOWN` |
| `contract` | 输入、输出契约位置或不适用原因 |
| `tests` | 测试文件及其验证范围 |
| `real_evidence` | 真实运行证据及其关联身份，或明确缺失 |
| `status` | `IMPLEMENTED` / `TESTED` / `E2E_VERIFIED` / `UNKNOWN` / `BLOCKED` |
| `limitations` | 已知限制、未覆盖场景及证据边界 |
| `next_action` | 无需行动、补证据、继续审计或建议另立需求 |

**状态判定规则**

- `IMPLEMENTED`：能够定位到实际生产实现。
- `TESTED`：存在可核实的测试断言，但没有充分的真实端到端证据。
- `E2E_VERIFIED`：存在可追溯的真实端到端证据，覆盖本条能力声明所描述的场景。
- `UNKNOWN`：缺少足够证据。
- `BLOCKED`：由于审计限制，无法完成核实。

如果一项能力既有实现又有测试，但没有真实端到端证据，主状态应为 `TESTED`，并在实现字段中保留实现事实。不得把多个不同维度压缩成一个容易误读的“已完成”。

**验收标准**

- [ ] 所有规定的能力域都有审计结果。
- [ ] 每条确定性结论都可追溯到代码或证据。
- [ ] 测试替身与生产实现清晰区分。
- [ ] 没有证据的能力标为 `UNKNOWN` 或 `BLOCKED`。
- [ ] 没有将单一成功样本扩大解释为普遍支持能力。

### P0-01D：审计机制与真实可观测性

**要求**

针对游戏机制，核实以下链路是否真实存在：

`机制声明 → 配置表达 → Runtime 实现 → 实际触发 → 状态或事件观测 → Playtest 判定`

审计只关注当前代码能够支持和验证的机制，不在本期增加新机制。

对每项机制记录：

- 机制名称与设计要求。
- 配置表达方式。
- 实际运行时实现。
- 触发条件。
- 可观测状态或事件。
- Playtest 如何验证成功与失败。
- 是否只有 fixture 测试。
- 是否已有真实运行证据。

特别关注：某项机制即使可以在配置中声明，如果没有真实运行时实现、可观测结果或有效判定，也不能视为已具备端到端支持。

**验收标准**

- [ ] 每项已审计机制都能追溯到配置、运行时和验证路径，或明确指出缺口。
- [ ] 明确区分机制实现与机制验收。
- [ ] 不将状态字段存在等同于机制真实发生。
- [ ] 不将执行器无法完成动作误判为机制成功。
- [ ] 未经真实验证的机制明确标注证据不足。

### P0-01E：审计 Playtest、人工视觉与证据完整性

**要求**

只读核实以下事项：

1. Playtest 是否执行真实浏览器操作。
2. 关键游戏状态如何采集，瞬时事件是否可能遗漏。
3. 结果分类是否区分玩法失败、环境故障、执行器限制、超时和未知结果。
4. Playtest 报告如何关联 Demo 身份及版本。
5. 人工视觉确认是否有独立记录，是否与当前交付身份匹配。
6. `verify-delivery` 实际验证哪些证据、身份、路径和判定关系。
7. 缺失证据或身份不一致时是否会拒绝通过。
8. 现有测试覆盖哪些负向场景。

不得重新实现这些功能，也不得仅依据命令名称或测试数量推断其正确性。

**验收标准**

- [ ] 每项结论对应实际实现或测试断言。
- [ ] 明确区分证据存在、证据有效和证据真实性。
- [ ] 明确人工视觉确认在最终判定中的作用。
- [ ] 明确哪些风险已验证，哪些仅在文档中声明。
- [ ] 不修改既有 Playtest 或 Evidence Integrity 契约。

### P0-01F：确定第二个 Demo 的最小可行候选

**要求**

依据审计结果提出一个推荐候选，不执行正式生成。

候选优先考虑与废土寻宝 Demo 有实质差异的玩法，例如俯视角探索解谜；但最终推荐必须以当前运行时和真实机制支持度为依据。

候选评估至少包括：

- 与原 Demo 的玩法差异。
- 所需机制及其真实支持证据。
- 所需资源与关卡要求。
- 当前管线的缺口。
- 预计需要的代码变更。
- 是否需要新增契约、CLI、MCP 或依赖。
- 免费验证的可行性。
- 主要失败风险。

不得仅凭 `compile-td-game` 等实现入口存在，就认定对应类型已经支持端到端生成。

**验收标准**

- [ ] 只推荐一个优先候选。
- [ ] 每项必要机制均有明确支持依据或明确标记为缺口。
- [ ] 能够说明为什么该候选适合验证当前管线。
- [ ] 如果没有合理的低成本候选，明确提出阻塞与所需决策。
- [ ] 不在本任务中启动正式生成或修改生产代码。

### P0-01G：形成开发决策报告

**要求**

基于前述证据，将发现的问题分为：

1. 已具备，无需改动。
2. 已实现，但需要补充真实验收证据。
3. 生产实现存在明确缺口。
4. 机制存在但不可有效观测或判定。
5. 证据、身份或版本管理存在缺口。
6. 证据不足，暂不能判断。

每个缺口必须包含：

- 观察到的事实。
- 对应证据。
- 影响的验收目标。
- 最小建议动作。
- 是否需要独立审批。
- 是否阻塞第二个 Demo。
- 建议优先级及理由。

最后只提出一个下一步优先事项，并说明选择依据。

**验收标准**

- [ ] 结论与能力矩阵一致。
- [ ] 每个 P0 建议都能追溯到明确缺口。
- [ ] 不因“看起来值得做”就新增没有证据支撑的需求。
- [ ] 明确指出第二个 Demo 是否可以进入实施。
- [ ] 若不可进入，给出最小阻塞解除方案。

## 7. 变更与安全约束

本期必须遵守：

- 不修改生产代码。
- 不修改公共契约、CLI 或 MCP 行为。
- 不增加依赖。
- 不进行付费模型调用。
- 不执行会覆盖历史产物的操作。
- 不修改既有测试来改变验收结果。
- 不把历史报告复制成新 Demo 的证据。
- 不把未经核实的推断写成事实。

建议只提交本期新增或明确允许修改的审计文档。若仓库在审计过程中出现与需求无关的变更，应保持原状并在报告中说明，不得顺手清理或重构。

## 9. 完成定义

P0-01 的成功标准不是证明所有功能都已经完善，而是让下一阶段开发决策变得可靠。

完成后，开发者必须能够回答：

1. 当前管线真实支持什么？
2. 哪些能力只有局部测试或 fixture 证据？
3. 哪些机制尚未得到真实运行验证？
4. 第二个 Demo 最可能在哪些地方失败？
5. 下一项最值得实施的工程需求是什么？
6. 为什么该需求优先于其他候选？

**最终决策规则：先审计，再实施。**

如果报告证明现有管线已足以支持独立 Demo，则进入 P0-02；如果存在明确阻塞，则只针对证据充分的最小缺口另立需求，并在必要时审批后实施。

本期不以代码改动量、测试数量或报告篇幅作为成功指标，而以结论的可追溯性、范围纪律和后续决策价值作为唯一核心标准。
