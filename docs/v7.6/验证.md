# FPVS-V1 Final Acceptance — P0：通用试玩策略收敛与真实证据闭环

- **类型**：P0 验收与执行能力改进
- **项目**：`sihuayin/game-maker`
- **阶段**：FPVS-V1 Final Acceptance
- **优先级**：P0
- **状态**：需求待实施
- **核心原则**：证据驱动、失败诚实、范围受控、不强制通过

## 1. 背景

FPVS-V1 的目标是：

> 用现有管线，从风格图与游戏意图生成一个完整、可启动、可操作、能完成目标的真实 Demo。

当前项目已经具备从游戏意图和风格输入，到资源包、游戏配置、Runtime 编译和静态 Demo 交付的主要能力。现阶段的主要瓶颈已经不只是资源生成或管线执行，而是如何证明最终交付物确实可玩、符合目标，并达到可接受的视觉质量。

根据当前开发记录，自动试玩存在以下问题：

1. `delivery.playtest` 只有在自动试玩结果为 `SUCCESS` 时才通过。
2. FA-01B 的 gate-stop 问题已经修复。
3. 危险躲避仍然是当前主要阻塞项。
4. 自动试玩曾推进到 `x=813` 后发生 24 次重置，说明执行器在危险区域无法有效调整策略。
5. 即使最终无法自动完成游戏，也必须保留真实执行证据，并诚实报告未完成的原因。

本需求不预设 Demo 必须通过验收。目标是提升执行器的通用性、形成可信的证据链，并据此判断 Demo 是否达标。

> 实施前必须以当前 `main` 分支源代码、测试和实际运行结果重新核实上述状态。本节是问题基线，不代替最新代码审计。

## 2. 目标与非目标

### 2.1 目标

- 改进通用试玩执行策略，使执行器能够根据实际游戏状态处理危险、跳跃、等待和移动。
- 将试玩过程、运行身份、关键状态变化和最终结果形成可追溯证据。
- 明确区分游戏失败、环境失败、执行器能力不足、超时和未知结果。
- 在自动试玩未能完成时，允许收集独立的人工浏览器试玩证据，但不得将人工试玩伪装为自动试玩成功。
- 建立机器可测量、人工可确认的视觉验收流程。
- 让最终报告能够回答：**这个确定版本的 Demo 是否有足够证据证明达标？**

### 2.2 非目标

本阶段不包含：

- 重写游戏 Runtime 或重构整条生成管线。
- 为单个 Demo 编写硬编码的通关脚本。
- 修改游戏生成协议或新增不必要的契约字段。
- 通过放宽判据、忽略危险碰撞或人工覆盖结果来提高通过率。
- 将人工试玩结果转换为自动试玩 `SUCCESS`。
- 大规模修改上游模型、资源生成策略或游戏设计流程。
- 建设通用自动修复、自动进化或跨游戏知识系统。
- 引入付费模型调用作为本阶段的必要条件。

## 3. 核心验收原则

### 3.1 自动执行与人工审核分离

自动试玩、视觉机器检查、视觉人工审核是三种不同的证据来源，不得相互冒充。

| 证据来源 | 可以证明 | 不可以单独证明 |
|---|---|---|
| 自动试玩 | 在指定执行条件下观察到的真实游戏行为 | 全部视觉质量、所有玩法均正确 |
| 视觉机器检查 | 可量化的资源、尺寸、覆盖率等指标 | 风格是否协调、画面是否具有良好可读性 |
| 视觉人工审核 | 人工对指定版本的视觉质量作出的判断 | 自动试玩已经成功 |
| 构建和静态验证 | 产物可构建、结构或资源检查通过 | 游戏可以实际完成目标 |

### 3.2 失败必须可解释

执行器遇到障碍时，必须尽可能输出可验证的执行记录与终止原因。不得通过忽略失败、修改游戏目标或把未知结果映射为成功来满足验收。

### 3.3 版本身份不可漂移

试玩证据必须对应确定的 Demo、配置和资源版本。执行期间如发现证据所对应的交付物身份发生变化，必须拒绝将该证据写回当前交付结果。

### 3.4 有限迭代

试玩策略改进采用有限轮次验证。默认最多进行 3 轮有记录的策略迭代；达到上限仍不能通过时，输出当前证据和未解决问题，不无限重试。

## 4. 范围与工作包

本需求分为四个工作包，按依赖顺序实施。

- **P0-1：通用试玩策略收敛**
- **P0-2：真实试玩证据闭环**
- **P0-3：视觉人工确认**
- **P0-4：最终验收聚合**

其中 P0-1 是当前首要阻塞项。P0-2 是结果可信度的基础；P0-3、P0-4 在前两项具备可用结果后完成。

## 5. P0-1：通用试玩策略收敛

### 5.1 问题定义

当前执行器可能在危险区域重复采取相同动作，导致玩家反复重置，却没有形成有效的避险策略。

本工作包的目标不是针对某个坐标写通关脚本，而是让执行器根据可观察的游戏状态，动态决定继续移动、跳跃、等待或停止。

### 5.2 输入状态

优先复用现有 Playtest 状态观测和事件，不新增重复的数据通道。

至少关注：

- 玩家位置：`x`、`y`
- 玩家速度：`vx`、`vy`
- 是否落地：`onFloor`
- 是否受到阻挡：`blockedRight`
- 危险对象的位置、范围及可观测状态
- 危险对象的运动阶段或状态变化（如果现有观测能够提供）
- 当前场景与玩家是否已经完成初始化
- 收集物是否仍然有效、是否已收集
- 是否胜利、是否重置
- 最近一段时间的位置进展和动作结果

对于不可观测的信息，不得假设其存在。若当前观测无法可靠判断危险状态，应采取有限的保守策略，并允许结果落入 `UNKNOWN` 或 `AGENT_LIMITATION`。

### 5.3 决策策略

#### A. 危险区域处理

- 识别危险对象与玩家的相对位置和可观测范围。
- 根据危险状态和运动阶段选择移动、跳跃、等待或停止推进。
- 如果危险可能正在攻击、扩张或处于不适合穿越的阶段，不应机械地持续向右移动。
- 在没有可靠证据证明安全前，不得仅凭一次位置观测就认定可以通过。
- 危险消失、攻击结束或场景状态发生变化后，重新评估下一步动作。

#### B. 跳跃与落地

- 仅在适合的游戏状态下执行跳跃。
- 根据 `onFloor`、垂直速度和位置变化判断跳跃是否实际发生。
- 未观察到预期状态变化时，不得无限重复同一跳跃动作。
- 对连续跳跃、空中移动和落地失败设置有限的尝试次数。

#### C. 等待与释放移动

- 允许在必要时暂时停止推进。
- 等待必须有明确的结束条件或最大持续时间。
- 等待期间持续观察玩家、危险对象和场景状态。
- 不允许将无限等待当作规避失败的策略。

#### D. 收集物目标选择

- 避免仅因存在 `pickupAbove` 之类的空间关系，就盲目追逐高处收集物。
- 只有在目标可达性具有足够证据时，才将其作为当前行动目标。
- 优先完成安全、可达且与必需目标有关的行动。
- 如果当前观测不足以判断目标可达性，允许跳过非必需目标或报告能力不足，不得破坏必需目标的验收要求。

#### E. 无进展与重复重置

- 记录连续动作后的实际位置进展。
- 当位置、游戏状态和目标状态长期没有有效变化时，判定为无进展。
- 检测重复重置和重复动作循环。
- 达到有限阈值后，停止当前尝试并输出原因、最后观测和执行轨迹。
- 不得通过无限增加重置次数来提高偶然成功的概率。

### 5.4 失败归因

执行器必须区分：

- 游戏确实无法完成目标或发生游戏规则失败。
- 浏览器、运行环境或游戏启动失败。
- 执行器缺少足够能力或信息完成当前动作。
- 超时。
- 证据不足，无法判断。

不得将所有失败统一解释为游戏缺陷，也不得将所有执行器失败都归咎于环境。

### 5.5 验收标准

- [ ] 危险区域中不再无条件持续向右推进。
- [ ] 执行器能在必要时选择等待，并在条件变化后重新评估。
- [ ] 跳跃动作有实际状态变化作为证据，而非仅记录已发送输入。
- [ ] 对 `pickupAbove` 等目标关系不会盲目追逐，且不绕过必需目标。
- [ ] 连续无进展和重复重置能够触发有限终止。
- [ ] 终止原因、最后状态和动作轨迹可追溯。
- [ ] 现有确定性场景测试仍然通过。
- [ ] 不需要修改游戏生成协议、游戏配置契约或 Runtime 才能实现策略改进。

### 5.6 验证方式

使用同一个固定 Demo 和相同运行条件，对改进前后的执行结果进行比较。

重点记录：

- 是否成功进入游戏场景。
- 最远有效推进距离。
- 必需收集物完成情况。
- 危险碰撞和重置次数。
- 是否完成游戏目标。
- 执行耗时与动作次数。
- 最终结果分类。

不得只根据单次偶然成功认定策略已经收敛。应保留失败样本，并检查策略是否对不同状态变化作出了合理响应。

## 6. P0-2：真实试玩证据闭环

### 6.1 目标

每次试玩都应形成能够独立检查的证据记录，使最终报告能够说明执行了什么、观察到了什么、如何得出结果。

### 6.2 命令与目录约束

保留现有交付检查键：

`delivery.checks.playable-smoke`

提供独立试玩入口：

`game-maker playtest <run>`

继续使用版本化试玩目录：

`run/v<N>/playtest/v<K>/`

一次试玩至少产生：

- `result.json`：机器可读的最终结果。
- 现有实现支持的执行轨迹或状态观测记录。
- 必要的错误记录。

具体文件名称和 schema 应以当前仓库契约为准。本需求不要求重复创建已有能力，也不预设必须新增报告字段。

### 6.3 证据内容

在现有数据模型允许的范围内，记录：

- 运行身份与被测试的 Demo 版本。
- 执行是否真正开始。
- 场景初始化是否完成。
- 关键状态观测。
- 输入动作及其后续可观察结果。
- 收集物状态变化。
- 危险碰撞、重置和胜利事件。
- 执行结束原因。
- 结果分类和必要的诊断信息。

对瞬时事件或采样间隙中无法可靠观察到的变化，必须标记为未知或证据不足，不得凭空补全。

### 6.4 结果分类

采用现有 Playtest 结果模型：

| 结果 | 含义 | 验收处理 |
|---|---|---|
| `SUCCESS` | 真实执行且有证据证明必需目标完成 | 可进入后续验收 |
| `GAMEPLAY_FAILURE` | 有证据证明发生游戏玩法失败 | 不通过 |
| `ENVIRONMENT_FAILURE` | 环境导致测试无法有效执行 | 阻塞，不能判游戏通过 |
| `AGENT_LIMITATION` | 执行器能力不足，无法完成有效判断或动作 | 不完整 |
| `TIMEOUT` | 在规定时间内未得到完成证据 | 不完整或按现有聚合规则处理 |
| `UNKNOWN` | 证据不足以确定结果 | 不完整 |

执行状态与结果分类应保持区分：测试可能未执行，也可能已执行但未能完成。

只有在真实执行、场景初始化及必需目标完成均有充分证据时，才能产生 `SUCCESS`。

### 6.5 结果写回

- 使用现有纯函数边界处理试玩结果映射。
- 保留现有 `delivery.playtest` 摘要及 `playable-smoke` 兼容性。
- 写回必须核对被测试的 Demo 身份。
- 身份漂移时拒绝写回，并记录错误。
- 采用现有原子写入机制，避免半写入状态。
- 旧报告缺少新增的可选摘要时，继续遵循既有兼容规则。
- 不得因报告文件存在、命令退出码为 0 或浏览器启动成功就直接判定游戏通过。

### 6.6 验收标准

- [ ] 每次执行均可定位到对应的版本化试玩目录。
- [ ] 可以区分未执行、已执行但未完成和成功完成。
- [ ] 关键结果能追溯到真实观测。
- [ ] 环境失败、执行器能力不足和游戏失败能够区分。
- [ ] 身份漂移时拒绝将证据写回错误的 Demo。
- [ ] 结果写回失败不会留下伪造的成功状态。
- [ ] 原有 `delivery.checks.playable-smoke` 消费方不因本需求发生不必要的 schema 破坏。
- [ ] 不自动创建基准，不覆盖既有版本目录。

## 7. P0-3：视觉人工确认

### 7.1 目标

确认最终 Demo 的实际视觉表现是否符合输入风格与游戏意图。

视觉确认针对最终交付物，而不是单独评价一张生成图片或某个资源包。

### 7.2 机器检查

优先复用已有 `verify`、`inspect`、资源审计和 QA 能力，检查：

- 资源是否缺失或无法加载。
- 背景层是否覆盖所需世界范围。
- 角色、场景、收集物和危险对象是否存在。
- 资源尺寸、透明区域和动画帧等已有可量化指标。
- 是否出现明显的资源重复、裁切、错位或布局异常。
- 运行页面是否有可观察的渲染错误。

机器检查不能代替人工视觉审核。

### 7.3 人工审核项目

审核人员查看固定版本的真实 Demo，并对以下方面作出判断：

1. **风格一致性**：角色、背景、道具是否符合输入风格。
2. **角色辨识度**：玩家是否容易从背景中识别。
3. **场景完整性**：背景、地形、平台和交互对象是否完整。
4. **画面可读性**：危险、收集物、出口和目标是否容易辨认。
5. **动画表现**：关键动作是否存在明显冻结、错帧或不自然表现。
6. **玩法与视觉对应关系**：可见对象是否与其实际功能一致。
7. **整体完成度**：是否达到可展示、可试玩 Demo 的基本质量。

审核应允许记录具体问题，不应强制所有项目都给出正面结论。

### 7.4 审核证据

人工审核记录至少应能确定：

- 被审核的 Demo 身份。
- 审核时间与审核者。
- 审核结论。
- 发现的问题及其严重程度。
- 必要的截图、说明或其他可追溯依据。

优先使用仓库现有的 QA 报告或人工审核机制。如果当前契约没有适合存放这些记录的地方，先形成独立审核材料，不要未经批准就扩展核心契约。

### 7.5 验收标准

- [ ] 人工审核针对确定版本的最终 Demo。
- [ ] 审核结果可追溯到具体版本。
- [ ] 可以明确记录通过、不通过或证据不足。
- [ ] 视觉审核不能覆盖自动试玩失败。
- [ ] 自动试玩成功也不能自动视为视觉审核通过。
- [ ] 机器可测量指标和人工判断明确分离。

## 8. P0-4：最终验收聚合

### 8.1 最终结论

最终验收至少需要汇总以下维度：

- 交付物身份是否固定且可追溯。
- 构建与静态验证是否通过。
- 真实自动试玩是否提供有效证据。
- 必需游戏目标是否完成。
- 视觉机器检查是否通过。
- 视觉人工审核是否完成并达到要求。

### 8.2 结论规则

| 条件 | 最终处理 |
|---|---|
| 证据证明必需玩法失败 | 不通过 |
| 自动试玩因环境问题无法有效执行 | 阻塞，不能宣称达标 |
| 执行器无法完成测试或证据不足 | 不完整 |
| 自动试玩成功，但视觉人工审核不通过 | 不通过 |
| 自动试玩成功，但必需视觉审核尚未完成 | 不完整 |
| 所有必需条件均通过且证据对应同一 Demo | 可判定达标 |
| 证据来自不同版本或身份无法确认 | 不可比较或不完整 |

最终聚合应复用现有契约中的结果优先级，不得在新代码中另建一套相互矛盾的状态模型。

### 8.3 基准比较

- 基准差异默认只提供观察信息。
- `changed` 不自动等同于 regression 或交付失败。
- 基准身份不匹配时，结果应标记为不可比较。
- 不自动创建新基准来掩盖当前失败。
- 不因新版本指标更好就自动覆盖旧版本的审核记录。

### 8.4 验收标准

- [ ] 最终报告能够说明 Demo 是否达标以及原因。
- [ ] 每个结论均可追溯到对应证据。
- [ ] 自动试玩和视觉审核结果相互独立。
- [ ] 环境阻塞和证据不足不会被误判为成功。
- [ ] 最终结论不依赖人工修改中间 JSON。
- [ ] 不通过放宽规则、忽略失败或改写结果来追求通过率。

## 9. 测试计划

### 9.1 自动化测试

复用现有 Playtest 测试场景，至少覆盖：

- `success-basic`
- `failure-missing-pickup`
- `limitation-wide-patrol`
- `env-no-chrome`
- `timeout-hang`

针对通用策略补充危险处理和重复重置测试，优先采用确定性 fixture，避免依赖真实模型调用或不可控随机场景。

### 9.2 回归测试

- 原有 CLI、MCP 和交付报告测试继续通过。
- `delivery.checks.playable-smoke` 保持兼容。
- 身份漂移、原子写入和报告映射测试继续通过。
- 既有资源验证、Runtime 编译与站点构建能力不回退。
- 不引入不必要的新增依赖。

### 9.3 真实 Demo 验证

在固定 Demo 上进行有限轮次的真实浏览器试玩，保留每轮完整结果。

重点确认：

- 危险区域是否仍然导致反复重置。
- 玩家是否能够继续推进。
- 必需目标是否实际完成。
- 成功或失败是否由真实观测支持。
- 人工浏览器试玩能否提供清晰、独立的视觉审核材料。

如果仍未完成游戏目标，必须保留失败证据，并说明阻塞点，不得通过修改验收规则宣告通过。

## 10. 实施顺序与交付物

| 阶段 | 工作内容 | 交付物 | 完成条件 |
|---|---|---|---|
| P0-1 | 通用试玩策略收敛 | 策略实现、确定性测试、前后对比 | 重复无进展可被识别，动作决策可解释 |
| P0-2 | 真实证据闭环 | 试玩报告、轨迹、身份校验与写回测试 | 结果可追溯且不发生错误写回 |
| P0-3 | 视觉人工确认 | 审核清单、审核记录、必要截图 | 固定版本获得明确的人工结论 |
| P0-4 | 最终验收聚合 | 最终验收报告与回归测试 | 能诚实给出达标、不通过或不完整结论 |

推荐执行顺序：先解决 P0-1，再确认 P0-2 的证据链可靠，随后完成 P0-3 和 P0-4。

如果实施过程中发现当前证据模型无法表达某个必要状态，应先说明缺口、提供最小方案并获得批准，不得为了赶进度直接修改核心契约。

## 11. 范围与成本约束

- 默认不使用付费模型调用。
- 不引入 `game-maker.local.json`。
- 不覆盖既有 `run/v<N>` 或 `pack/site/v<N>` 版本目录。
- 新增试玩产物必须遵循现有版本化与原子写入规则。
- 不修改未经批准的 contracts、CLI、MCP 或新增依赖。
- 策略迭代默认最多 3 轮；达到上限后输出证据与剩余问题。
- 自动试玩和人工审核均须保留可追溯记录。
- 如果当前环境不能完成真实浏览器测试，必须标记阻塞原因，不得用模拟结果替代真实执行结果。

## 12. 最终完成定义（Definition of Done）

只有同时满足以下条件，本需求才算完成：

- [ ] 自动试玩策略具有有限、可解释的危险处理和无进展终止机制。
- [ ] 真实试玩证据能够关联到确定版本的 Demo。
- [ ] 结果分类和写回符合现有 Playtest 契约。
- [ ] 关键测试和回归测试通过。
- [ ] 已对目标 Demo 进行真实试玩，且结果如实记录。
- [ ] 已对同一版本 Demo 完成视觉人工确认，或明确记录尚未完成及其原因。
- [ ] 最终验收报告给出有证据支持的结论。
- [ ] 未通过伪造成功、忽略失败、放宽门禁或人工覆盖结果来完成验收。

**本需求允许最终结论为不通过或不完整。**

本阶段真正的交付不是一个必然通过的 Demo，而是一套能够证明 Demo 是否达标、解释未达标原因，并让后续修复有据可依的验收闭环。
