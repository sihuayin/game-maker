# P0-03 PRD：交付证据可信性与 CI 自动验收

> 项目：`sihuayin/game-maker` V2  
> 优先级：P0  
> 类型：工程质量 / 交付可信性  
> 建议阶段：P0-03  
> 状态：待增量审计与实施裁定  
> 目标：让每一次交付验收都能基于可信证据、可复现地重新计算结论，并由 CI 自动执行。

---

## 1. 背景

### 1.1 当前系统能力

截至当前 `main`，仓库已经具备一部分正式证据完整性能力：

| 能力 | 当前状态 |
|---|---|
| `build-evidence-manifest` | 已实现 |
| `delivery-evidence-manifest/v1` | 已实现 |
| `verify-delivery` | 已实现 |
| SHA-256 文件校验 | 已实现 |
| 文件缺失、不可读、哈希不匹配诊断 | 已实现 |
| 路径越界和符号链接检查 | 已实现 |
| 交付身份检查 | 已实现 |
| 报告一致性检查 | 已实现 |
| 声明结论与重算结论比较 | 已实现 |
| `pnpm test:evidence` | 已接入正式验收 |
| 每次运行独立保存验收记录 | 已实现 |
| CI 自动执行与 PR 门禁 | 待核实 |
| Manifest 独立可信锚点 | 需要增量审计 |
| 系统性负向测试 | 需要增量审计 |
| 冻结 Demo 正式基线复核 | 需要确认当前结果 |

相关实现：

- `packages/pipeline/src/evidence-manifest.ts`
- `packages/pipeline/src/evidence-integrity.ts`
- `scripts/evidence-acceptance.mjs`
- `packages/cli`
- `package.json`

现有 `pnpm test:evidence` 已经执行正式 `verify-delivery`，并检查：

- CLI 退出码；
- 报告格式；
- 验收状态；
- 重算 verdict；
- 声明 verdict 与重算 verdict 的一致性；
- 六项检查的声明值与重算值是否一致。

因此，本阶段不应重新实现上述能力。

### 1.2 当前真正需要解决的问题

现有证据验证能够证明：

> 当前文件与 Manifest 声明的预期哈希是否一致。

但这并不自动证明：

> Manifest 本身来自可信来源，且未被同时篡改。

例如：

1. 原始截图哈希为 A。
2. Manifest 记录截图哈希 A。
3. 有人修改截图，得到文件 B。
4. 同时修改 Manifest，将预期哈希也改成 B。
5. 再次执行校验。

如果 Manifest 没有独立可信锚点，哈希比较仍可能通过。

另外，正式验收虽然已有脚本入口，但还需要确保：

- 反例能够证明校验器真的有效；
- PR 不能绕过正式证据验收；
- CI 不会将缺少基线证据的情况误判为成功；
- 失败结果可以定位具体证据和规则；
- 人工视觉审核仍由人工完成，不被机器伪造或替代。

### 1.3 核心目标

本阶段只解决三个问题：

1. **可信**：知道验收所使用的 Manifest 是否来自可信基线。
2. **有效**：证明校验器能识别篡改、缺失、错配和路径攻击。
3. **自动**：让正式证据验收进入 CI，阻断不符合要求的变更。

## 2. 目标与非目标

### 2.1 目标

- 明确 Manifest 的可信来源和信任边界。
- 确保验收基线不能通过修改待验收文件及 Manifest 同时绕过。
- 对现有校验器增加系统性负向测试。
- 将 `pnpm test:evidence` 纳入适当的 CI 工作流。
- 保证 CI 失败不会被历史 `pass` 或缺失证据覆盖。
- 保持原始交付、历史报告和证据文件只读。
- 保留人工视觉审核的 HITL 边界。
- 全流程零付费、零生图、零生产修改。

### 2.2 非目标

本阶段不负责：

- 第二个独立 Demo 的完整生成。
- 重新生成已有资源或配置。
- 扩展游戏机制。
- 扩展新的游戏类型。
- 修改 Playtest v2 的结果模型。
- 重构 QA 或 Delivery 架构。
- 修改已有验收阈值。
- 通过人工补录将未完成的证据改成 PASS。
- 引入付费模型调用。
- 建立跨游戏共享知识系统。
- 将人工视觉审核自动化。

# 5. P0-03-01：Manifest 可信锚点与信任边界

## 5.1 目标

明确并实现 Manifest 的可信来源。

要求系统不仅能验证：

`actual file hash == manifest expected hash`

还必须能够验证：

`manifest == trusted baseline`

不能将 Manifest 和待验收证据放在同一可同时修改的信任边界中，然后宣称已经实现防篡改。

## 5.2 第一步：只读审计

必须先检查：

1. `build-evidence-manifest` 的生成方式。
2. `verify-delivery` 的 Manifest 读取方式。
3. Manifest 当前存储位置。
4. Manifest 是否进入 Git 版本控制。
5. Manifest 是否可能被 CI job 或 PR 修改。
6. `test:evidence` 是否校验 Manifest 自身的哈希。
7. 是否存在已冻结的外部基线哈希。
8. Manifest 更新是否具有明确的人工授权流程。

输出：

- Manifest 生成流程图；
- Manifest 存储与信任边界图；
- 当前可信根缺口；
- 最小改动建议。

## 5.3 可信锚点设计

候选方案：

**方案 A：Git 版本控制锚定**

将冻结 Manifest 纳入受保护的版本控制路径。

CI 使用受保护分支上的基线版本进行校验，而不是直接信任 PR 修改后的 Manifest。

优点：

- 不需要新服务；
- 无付费成本；
- 可追溯；
- 适合单仓库单 Demo 的当前阶段。

限制：

- 如果攻击者能够修改基线文件并绕过分支保护，仍然可能同时修改证据和预期值。

**方案 B：独立基线摘要**

在 Manifest 之外保存其 SHA-256 摘要。

摘要必须来自独立可信位置，例如受保护分支上的固定文件或 CI 受保护配置。

优点：

- 可以检测 Manifest 自身被修改；
- 实现简单；
- 无需重建 Manifest 格式。

限制：

- 摘要与 Manifest 如果仍可被同一 PR 同时修改，就没有独立信任价值。

**方案 C：签名基线**

对 Manifest 进行签名，验收时使用可信公钥验证签名。

优点：

- 信任边界更清晰；
- 可以扩展到外部交付验证。

限制：

- 引入密钥管理；
- 增加实现与运维复杂度；
- 当前阶段未必值得。

## 5.4 本票建议

优先选择 A + B：

- 冻结 Manifest 进入受保护的版本控制基线；
- 在独立受保护位置保存 Manifest 摘要；
- CI 使用可信基线进行校验；
- Manifest 更新必须经过明确审核；
- 不允许 CI 自动更新预期哈希。

是否需要 C，应由 Phase 0 审计决定，不作为默认要求。

## 5.5 验收标准

- [ ] 明确 Manifest 的可信来源。
- [ ] 明确信任边界和攻击者能够修改的内容。
- [ ] Manifest 自身存在独立可信校验。
- [ ] 修改 Manifest 但不修改可信锚点时，验收失败。
- [ ] 修改证据和 Manifest，但不修改可信锚点时，验收失败。
- [ ] 正常冻结基线可以通过。
- [ ] Manifest 更新不会自动覆盖旧基线。
- [ ] 不新增付费服务。
- [ ] 不修改真实 Demo 的交付内容。

# 6. P0-03-02：证据完整性负向测试

## 6.1 目标

证明现有 `verify-delivery` 不只是能通过正常样本，还能可靠拒绝失效证据。

本票不重新实现校验器，重点是建立攻击性测试矩阵。

## 6.2 测试原则

所有测试：

- 使用临时目录或隔离 fixture；
- 复制测试所需的最小证据；
- 不直接修改冻结 Demo；
- 不使用真实生产交付目录；
- 不调用外部模型；
- 不产生付费请求；
- 不依赖人工修改 JSON 才能完成。

## 6.3 测试矩阵

| ID | 测试场景 | 操作 | 预期结果 |
|---|---|---|---|
| N01 | 正常基线 | 使用未变化的证据 | PASS |
| N02 | 文件内容篡改 | 修改截图字节 | hash-mismatch |
| N03 | Playtest 篡改 | 修改 Playtest 报告 | hash-mismatch |
| N04 | 文件删除 | 删除必需证据 | missing |
| N05 | 文件不可读 | 模拟读取失败 | unreadable |
| N06 | Manifest 篡改 | 修改 Manifest 中的预期哈希 | 可信锚点校验失败 |
| N07 | 双重篡改 | 同时修改证据和 Manifest | 可信锚点校验失败 |
| N08 | 身份错配 | 替换为其他交付的证据 | identity mismatch |
| N09 | Playtest 摘要错配 | 修改摘要或 attempt 关联 | consistency fail |
| N10 | 人工审核错配 | 修改 subject 或材料关联 | consistency fail |
| N11 | 结论过期 | 历史声明 PASS，当前证据失效 | 不得继续 PASS |
| N12 | 路径逃逸 | `../` 越界引用 | path-invalid |
| N13 | 绝对路径 | 使用绝对路径引用 | path-invalid |
| N14 | 符号链接逃逸 | 链接指向允许目录外 | path-invalid |
| N15 | Manifest 重复记录 | 重复文件或记录 | schema/validation failure |
| N16 | 重复运行 | 同一未变化输入运行两次 | 结果一致 |
| N17 | 原始证据只读 | 执行成功及失败验收 | 原始文件哈希不变 |

注意：

现有 schema 可能已经拒绝部分非法 Manifest。对于这类情况，测试应验证实际正式入口是否拒绝输入，而不是为了凑齐测试数量增加重复校验代码。

## 6.4 结果要求

每个失败测试至少验证：

- 退出码；
- 报告状态；
- 失败分类；
- 失败文件或记录定位；
- 历史 verdict 是否失效；
- 原始文件是否保持不变。

不能只断言：

`expect(exitCode).toBe(1)`

还必须验证失败原因确实符合预期。

## 6.5 验收标准

- [ ] N01-N17 有明确测试结果。
- [ ] 所有破坏性测试均在隔离副本中运行。
- [ ] 篡改测试可以识别实际哈希差异。
- [ ] 双重篡改测试可以识别 Manifest 不可信。
- [ ] 缺失证据不能被静默删除出必需清单。
- [ ] 路径逃逸无法读取目录外文件。
- [ ] 历史 PASS 不能覆盖当前失败。
- [ ] 失败诊断能够定位具体证据。
- [ ] 原始交付不发生变化。
- [ ] 不产生付费调用。

# 7. P0-03-03：CI 正式验收门禁

## 7.1 目标

将正式证据验收纳入 GitHub Actions。

CI 不仅运行普通单元测试，还必须验证交付证据完整性。

## 7.2 Phase 0：审计现有 CI

先检查：

- `.github/workflows` 是否存在；
- 当前 workflow 触发条件；
- PR 是否执行 `pnpm check`；
- PR 是否执行 `pnpm test`；
- 是否执行 `pnpm typecheck`；
- 是否执行 `pnpm test:evidence`；
- 当前 CI 是否能够访问冻结 Manifest；
- CI 是否能够访问完整证据文件；
- Manifest 可信锚点是否受到 PR 修改隔离。

本票不得在没有检查现有 workflow 的情况下直接新增重复工作流。

## 7.3 CI 工作流要求

在现有工作流上增量扩展，目标检查集合：

```bash
pnpm check
pnpm test
pnpm typecheck
pnpm test:evidence
```

其中：

- `pnpm check`：依赖、链接和构建检查；
- `pnpm test`：单元与集成测试；
- `pnpm typecheck`：类型检查；
- `pnpm test:evidence`：正式交付证据验收。

注意：

`pnpm test:evidence` 是正式证据验收，不应简单塞进每个单元测试运行中。

如果 CI 运行时间或证据文件体积较大，可以拆分 job，但 PR 合并门禁必须等待正式证据 job 成功。

## 7.4 PR 安全要求

必须防止以下情况：

1. PR 修改 Manifest 预期哈希，同时修改证据。
2. PR 删除冻结基线文件。
3. PR 修改 `test:evidence` 脚本使其跳过正式校验。
4. PR 修改 CI workflow，使证据检查不再执行。
5. CI 因证据缺失而跳过检查，却仍返回成功。
6. CI 使用 PR 自己生成的 Manifest 作为可信预期值。

冻结基线和验收脚本的可信来源必须独立于待验收的 PR 变更。

对于受保护基线的更新，必须通过明确的人工审核流程。

## 7.5 CI 输出要求

每次 CI 失败，应提供：

- 失败 job；
- 失败命令；
- Manifest 版本或摘要；
- Verification Report；
- 失败文件路径；
- 失败规则；
- 声明 verdict；
- 重算 verdict。

可以使用 GitHub Actions Artifact 保存报告。

不得将敏感密钥或环境变量写入报告。

## 7.6 验收标准

- [ ] PR 会触发正式证据验收。
- [ ] 正式证据验收失败会阻断合并。
- [ ] 缺少冻结基线时不能跳过检查并 PASS。
- [ ] PR 无法通过同步修改 Manifest 和证据绕过校验。
- [ ] CI 不自动更新 Manifest。
- [ ] CI 失败时有可定位诊断。
- [ ] 历史报告不被覆盖。
- [ ] CI 不调用付费模型。
- [ ] 现有 workflow 不重复、不冲突。

# 8. P0-03-04：冻结 Demo 基线复核与收口

## 8.1 目标

在前面三票完成后，对已经冻结的 FPVS-V1 Demo 执行一次正式证据复核。

本票不是重新生成 Demo，也不是重新跑付费 E2E。

它只验证：

> 当前冻结交付是否仍然具有完整、可信、身份一致的验收证据。

## 8.2 执行要求

1. 确定冻结 Demo 的身份。
2. 确定 Manifest 可信锚点。
3. 确认所有必需证据仍然存在。
4. 执行正式 `verify-delivery`。
5. 执行 `pnpm test:evidence`。
6. 与历史正式验收结果交叉比较。
7. 检查人工视觉审核记录及 subject。
8. 检查两次真实 Playtest 报告与交付摘要的一致性。
9. 确认 site/pack 没有被意外修改。
10. 保存本次复核报告。

## 8.3 人工审核边界

机器只负责检查：

- 人工审核记录是否存在；
- 格式是否有效；
- subject 是否匹配；
- 必需审核项目是否齐全；
- 审核材料引用是否完整；
- 审核记录是否被修改。

机器不能自行判断：

- 游戏画面是否美观；
- 美术是否符合风格；
- 动画是否自然；
- 游戏体验是否优秀。

以上仍然需要人工确认。

如果原始视觉审核记录已经失效或 subject 不匹配，应要求重新人工审核，不能通过自动修复记录来获得 PASS。

## 8.4 验收标准

- [ ] 冻结 Demo 身份明确。
- [ ] Manifest 可信锚点通过。
- [ ] 必需证据完整。
- [ ] 文件哈希全部符合预期。
- [ ] 身份关联通过。
- [ ] Playtest 证据一致性通过。
- [ ] 人工审核记录有效。
- [ ] 正式验收结论由当前证据重算。
- [ ] 与历史结果的差异有明确解释。
- [ ] 原始交付未被修改。
- [ ] 新复核报告独立保存。

如果存在真实未完成项，最终结果应如实保留 `incomplete`、`blocked` 或 `fail`，不能为了完成 P0-03 而强行得到 PASS。

# 9. 全局验收标准

P0-03 完成必须同时满足：

| 编号 | 验收项目 | 要求 |
|---|---|---|
| AC-01 | Manifest 可信来源 | 明确且可验证 |
| AC-02 | Manifest 防篡改 | 双重篡改无法绕过 |
| AC-03 | 文件完整性 | 必需文件重新计算 SHA-256 |
| AC-04 | 身份一致性 | 证据与当前交付身份匹配 |
| AC-05 | 报告一致性 | Playtest、QA、审核记录关系正确 |
| AC-06 | 负向测试 | 篡改、缺失、错配、越界全部覆盖 |
| AC-07 | 历史结论失效 | 旧 PASS 不能覆盖当前失败 |
| AC-08 | CI 门禁 | PR 自动执行且失败阻断合并 |
| AC-09 | 只读性 | 原始交付和历史证据不被修改 |
| AC-10 | 人工审核边界 | 自动化不替代视觉人工确认 |
| AC-11 | 零付费 | 不产生模型或生图请求 |
| AC-12 | 可追溯性 | 每次验收有独立报告 |

# 10. 实施顺序与提交边界

建议按以下顺序实施：

## 第一阶段：P0-03-01

只读审计 Manifest 信任边界。

交付：

- 可信根审计报告；
- Manifest 更新策略；
- 最小实现方案；
- 信任边界裁定。

在可信来源没有明确之前，不进入 CI 门禁实施。

## 第二阶段：P0-03-02

针对现有 `verify-delivery` 补齐负向测试。

交付：

- 负向测试矩阵；
- 测试 fixtures；
- 测试报告；
- 已知缺陷列表。

如果测试发现校验器缺陷，修复应限定在现有职责边界内。

## 第三阶段：P0-03-03

将正式验收接入 CI。

交付：

- workflow 增量修改；
- PR 门禁；
- 报告留存；
- CI 失败诊断。

## 第四阶段：P0-03-04

执行冻结 Demo 正式复核。

交付：

- 正式复核报告；
- 历史结果差异说明；
- 人工视觉审核确认；
- P0-03 最终验收裁定。

# 12. 风险

### R1：Manifest 与证据同时被修改

这是本阶段最重要的风险。

如果没有独立可信锚点，SHA-256 只能证明文件与当前 Manifest 一致，不能证明 Manifest 本身可信。

### R2：CI 使用 PR 自己提供的基线

如果 CI 直接信任 PR 中修改后的 Manifest，就可能失去校验意义。

必须让可信基线独立于待验收变更。

### R3：负向测试只验证退出码

只验证非零退出码不足以证明检测正确。

必须检查具体诊断、失败路径和最终 verdict。

### R4：自动化替代人工审核

机器发现审核记录存在，不代表审核结论真实或正确。

必须保持人工审核责任边界。

### R5：把基线通过当成泛化能力

当前只有一个冻结 Demo。

本阶段通过只能证明证据系统在当前基线及测试范围内可靠，不代表已经证明第二个独立 Demo 可以完整生成。

P0-03 只有在以下条件全部满足时才可关闭：

# 14. 最终产品价值

P0-03 不会直接增加游戏生成能力，也不会让 AI 生成更好的美术资源。

它解决的是更基础的问题：

**当 game-maker 声称已经生成并交付一个可玩的 Demo 时，我们是否有足够可信的证据证明这个结论？**

这项能力完成后，game-maker 才能逐步建立：

- 可复现的交付验收；
- 可追溯的质量结论；
- 可自动执行的工程门禁；
- 可供后续多个 Demo 使用的可信验收基础。

它是从“能够生成游戏”走向“能够证明交付质量”的关键工程阶段。
