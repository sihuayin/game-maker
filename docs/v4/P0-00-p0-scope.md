## 1. P0 的定义与非目标

### 1.1 P0 的目标

让「风格图 + 游戏意图 → 资源完整、风格匹配、可玩的 Demo」这条路**可被真实验收**，
并且**不能在没有做到时错误地宣告成功**。

P0 完成后，应能回答：

1. 资源是否完整（设计要的实体是否都有对应资源）？
2. 包是否完整（文件、checksum、真实尺寸/帧数是否对得上）？
3. 游戏是否真的能启动、移动、拾取、胜利（不是只看静态可达性）？
4. QA 是否真的跑满 6 条判据，且任何发布路径都不能绕过？
5. 明显坏的像素是否会被判失败（而不是只作观察）？
6. 运行时是否有已知的假胜利 / 软锁（`objective.gate`、危险物重置）？
7. 是否有一条从输入到可玩 Demo 的真实单跑记录（或明确记录阻塞）？

### 1.2 P0 的非目标（明确不做）

- 不重写流水线 / Pack / `raster.ts` / 图像客户端。
- 不新增 `source.kind`（尤其 `derived`）；不新增资源生产路线。
- 不做自动修复 / 自动重生成 / 无限重试。
- 不做跨游戏资源复用 / 跨项目迁移。
- 不实现多关、完整胜负原语、HP/失败态、通用 `motion`。
- 不打通 `import` 三入口、不做六类语义路由。
- 不新建自动参考图风格相似度（P1）。
- 不引入完整 Playwright 套件 / CI 重构（P1/P2）。
- 不做 CLI/MCP 全等价（TD/review/并发参数 P2）。
- 不修改 `game-maker.local.json`。
- 不改变既有失败账本、版本目录、原子发布语义。
- 不把 Phase 1 Tier 2/3 的动画验收工作混入 P0。
- 不在本审计内提交 / 推送。

## 3. P0 工作包详表

### P0-01 运行时胜利判定与危险物软锁

**为什么是 P0**：`objective.gate` 不被消费会导致**任何 goal 都能提前胜利**（假成功）；
危险物重置导致**掉穿地面、不可恢复**（直接破坏可玩性）。两项都直接命中 Q1 的 P0 定义。

**覆盖**：`CAP-SPEC-01`（W2-G01）、`CAP-RUNTIME-01`（W6-G1）。

**建议范围**：

- `packages/demo/src/shell/scene.ts`：胜利绑定只认 `GameConfig.objective.gate` 指向的实体；
  其他 `kind:"goal"` 实体不再绑 `tryWin()`；`hitHazard()` 重置时同步物理体
  （位置、速度、`body.reset()` / 等价手段），并保证重置点在可站立位置。
- `packages/demo/tests/`：新增两 goal 的胜利判定测试；危险物重置的回归测试。
- 若 Phaser body 行为只能在实际浏览器中验证，由 P0-03 的 smoke 覆盖；P0-01 仍需一条
  纯逻辑或外壳级测试钉住「只有 gate 能赢」。

**明确不改**：

- 不新增 `GameConfig` 字段；不实现 HP / 失败态 / 多关；不改变 `entities[].kind` 枚举。
- 不改变 `objective.kind`（仍是单值 `collect-then-reach`）。
- 不改变危险物运动轨迹（`advanceHazards` 语义不变）。

**测试**：

1. 两个 `goal` 的 config：捡齐 pickup 后碰非 gate goal ⇒ `won=false`；碰 gate ⇒ `won=true`。
2. 单个 goal 且就是 gate 的旧 config：行为不变。
3. 复现 W6 的「从木箱顶起跳 → 空中撞 hazard → 重置」序列：重置后玩家不在地面以下，
   可继续移动并完成核心循环；重复重置不累积下沉。
4. 负例：把 gate 指向不存在的 id ⇒ 上游校验仍然拒绝（既有 `auditReferences` 行为不变）。

**验收条件**：

- `CAP-SPEC-01`：两个 goal 的测试在旧代码上失败、新代码通过。
- `CAP-RUNTIME-01`：复现序列不再掉穿；有自动化测试（或 P0-03 smoke 的对应用例）。
- `pnpm test` / `pnpm typecheck` 全绿；不新增付费调用。

**风险 / 回滚**：

- 现有 config 若依赖「多个 goal 都能赢」，行为会变；契约本身以 `objective.gate` 为准，
  这是修正假胜利。回滚只需还原 `scene.ts` 的胜利绑定与 `hitHazard`。
- 软锁修复若只改位置不改物理体，可能仍复现；验收必须用 W6 复现序列，不接受「看起来好了」。

### P0-02 发布闸门统一

**为什么是 P0**：`site` / `assemble_site` 可绕过 QA；`checked=5/6` 的 `incomplete` 不阻断。
这会让「QA 通过」变成不可信结论，直接命中「可能导致错误地宣告成功」。

**覆盖**：`CAP-QA-01`（W4-1）、`CAP-QA-08`（W4-8 / W6-G3）。

**建议范围**：

- QA：补齐 `layer-coverage` 判据（归入合适的族，或在 `assemble.ts` 中真正运行），
  干净包 `checked=6`；`qaVerdict` 语义与 `QA_JUDGEMENTS` 对齐。
- 发布闸门：`create --yes` / `build` / `site` / MCP `assemble_site` 都必须验证**当前包**的 QA；
  `error` 与 `incomplete` 均拒绝发布；`warning` 不阻断。
- 判定「当前包」：QA 报告必须与本次要发布的 pack id + version 对应；过期/缺失报告拒绝。
- `site` / `assemble_site` 如何拿到报告：优先复用 `run/v<N>/qa-report.json` 或让发布路径就地跑 QA。
  **若需要新增 CLI flag / MCP 参数 / 契约字段，必须在施工票中逐项列出并单独获批**，不得静默加参数。
- MCP `create_game`：补 QA 失败路径测试（`isError`、`_exitCode=4`、站点不产、报告在盘）。

**明确不改**：

- 不新增 QA judgement 的语义（`layer-coverage` 已是既有 `QA_JUDGEMENTS` 之一）。
- 不改变 `qa-report/v1` 的既有字段语义；如需新增字段，单独报批。
- 不改变 `warning` 的「不阻断」语义。
- 不改变失败账本 / 版本目录 / 原子发布规则。

**测试**：

1. `checked=6`：干净包（v7 + baseline 或 fixture）所有 6 条真跑；`layer-coverage` 正负例。
2. 发布路径：缺 QA ⇒ 拒；QA error ⇒ 拒；`incomplete` ⇒ 拒；全绿 ⇒ 产站点。
3. CLI `create --yes` / `build` / `site` 与 MCP `create_game` / `assemble_site` 各至少一条覆盖。
4. QA 报告属于旧 pack version ⇒ 拒。
5. 负例：故意删掉 `layer-coverage` 的 runner，测试必须红（防止「假 6/6」）。

**验收条件**：

- 任何发布路径都不能在缺 QA / error / incomplete 时产出 `site/v<N>`。
- 干净包 `checked=6`；`qaVerdict` 不再是恒 `incomplete`。
- MCP QA 失败路径有测试。
- `pnpm test` / `pnpm typecheck` 全绿；不新增付费调用。

**风险 / 回滚**：

- 现有「先 build 失败、再手工 site」的工作流会被拒绝；这是有意的。错误信息必须说清缺什么报告。
- 若无 run 目录的 `site` 被要求提供 QA，可能改变 CLI 使用方式；施工票必须先给出兼容方案，
  并把它列为需要批准的 CLI/契约变更。
- `layer-coverage` 的判据可能与 `compileRuntime` 的 `auditLayerCoverage` 重复；
  必须复用同一判据，不得出现两个事实源。

### P0-03 可玩性 headless smoke

**为什么是 P0**：现有 QA 不启动游戏；归档单跑出现「QA 全绿 + 站点存在但不可玩」。
没有启动 + 输入 + 胜利的自动验证，P0 就无法证明「可玩」。

**覆盖**：`CAP-QA-07`（W4-7 / W5 类别 8 / W6-G2/A6）。

**建议范围**：

- 新增一个**最小** headless 浏览器 smoke，优先复用 W6 的 CDP 脚本思路（系统 Chrome + CDP），
  避免新增 Playwright/Puppeteer 依赖；若必须新增依赖，施工票单独报批。
- 流程：启动本地静态服务 → 打开站点 → 注入**状态感知**的移动/跳跃（读 x/y/onFloor/blockedRight/
  collected，而不是写死时序）→ 断言至少一个 pickup 被收集 → 到达 gate → `won=true`。
- 用 fixture pack + config（优先 v7 + 已验收 config）离线运行；零付费。
- 负例：故意把 `objective.gate` 指错 / 拿掉一个 pickup / 破坏输入 → smoke 必须红。
- 建议命令：`pnpm test:playable`（或等价）作为 P0 验收命令；是否纳入默认 `pnpm test` 由施工票决定，
  但 P0 完成判据必须执行它。浏览器不可用时**失败并记录**，不得静默跳过成绿。

**明确不改**：

- 不做视觉质量 / 风格相似度判断；不做全机制 / 难度 / 多关覆盖。
- 不引入 CI 重构；不要求所有环境都装浏览器。
- 不改变站点运行时行为（这一包只加验收）。

**测试 / 验收条件**：

- 正常 fixture：启动、移动、跳跃、至少 1 个 pickup、到达 gate、`won=true`；exit 0。
- 负例：gate 指错 / pickup 缺失 / 输入被破坏 ⇒ 非 0，并指出失败阶段。
- 运行记录包含：命令、Chrome 版本、站点目录、截图/轨迹路径、耗时；零付费。
- 与 P0-01 的软锁复现共用同一驱动或至少同一状态读取方式。

**风险 / 回滚**：

- CDP 脚本对时序敏感；必须用状态反馈，不接受固定 `sleep` 时序。
- 系统 Chrome 版本差异可能导致选择器/启动参数失效；记录版本，失败时给出可操作错误。
- 若环境无 Chrome，P0 验收记为「未完成」而不是「通过」。

### P0-04 资产完整性链

**为什么是 P0**：设计要的实体可能没有对应资源；包内文件可能损坏；空色板直到 pack 才拒（钱已花）。
三项都直接对应「资源完整」与「假成功」。

**覆盖**：`CAP-SPEC-12`（W2-G12）、`CAP-ASSET-06`（W4-6）、`CAP-SPEC-17`（W2-G17）。

**建议范围**：

1. **design→recipe 覆盖闸**：对 `GameDesignSpec` 的 `enemies` / `npcs` / `interactables` / `resources`
   每个 id，要求 recipe 有对应资产（`characterId` / 资产 id / 明确的豁免规则）。
   豁免必须显式、可测试，不得用「模型说不需要」当豁免。
2. **`verifyPack` 入链**：`runBuild` 在 `packAssets` 成功后、`compileRuntime` / QA / site 之前调用
   `verifyPack`；失败 ⇒ `invalid`，不产 config / QA / site。
3. **空色板前移**：VWS 产出后、`analyzeIntent` / `compileDesign` / `compileCharacterDna` /
   `planAssets` 等下游付费调用之前拒绝空色板；单独 `planAssets` 在入口也拒绝。
   注意：不能要求「在产出色板的那一发之前」拒绝——色板本身就是那一发的产物。

**明确不改**：

- 不新增 `source.kind`；不改变 `resolveRoute` 规则矩阵。
- 不改变 Pack 目录结构 / manifest 语义 / 版本分配。
- 不实现 `import` 三入口。
- 不改变 QA 的既有引用族判据（覆盖闸是新判据，不是替代）。

**测试**：

1. 设计里有一个敌人，recipe 缺它 ⇒ 规划期拒绝（或 `runBuild` 在 config 前拒绝）；负例明确。
2. 豁免规则：显式豁免的 id 不报；未豁免的缺 id 必报。
3. 篡改包内一个文件（checksum 不符）⇒ `runBuild` 在 config / QA / site 前 `invalid`；
   CLI 退 4；站点不产；原包保留。
4. 空色板 VWS ⇒ 在 `analyzeIntent` 之前拒绝；fake upstream 调用计数为 0（下游）；
   `planAssets` 单独入口同样拒绝。
5. 正例：v7 + 已验收 config / design 不被新闸误伤。

**验收条件**：

- 三类失败都在正确的阶段失败，且不产生下游产物。
- 新闸有正例 + 负例；`pnpm test` / `pnpm typecheck` 全绿。
- 不改变既有 pack / manifest 的契约；若需新增错误码，只新增 finding code，不改已有。

**风险 / 回滚**：

- 覆盖闸可能误伤合法设计（例如场景装饰不需要独立资源）；用显式豁免清单 + fixture 控制，
  不接受「一律放过」。
- `verifyPack` 入链会增加构建时间；必须只做一次，不重复全量 checksum。
- 空色板前移可能导致「模型偶尔给空色板」的 run 更早失败；这是有意的（省下游钱）。

### P0-05 像素完整性阈值

**为什么是 P0**：`inspect` 已读真实像素，但 +52.4% 长宽比差、41 个色板外像素仍 exit 0。
这属于「明显坏的像素仍被宣告成功」。

**覆盖**：`CAP-QA-02`（W4-2 / W4-4 的像素部分 / W6-G4 的像素部分）。

**建议范围**：

  背景层覆盖率（以实际 available 的指标为准）；阈值集中在一处，文档化。
- **先测量再定阈值**：对 v7、last-train、counter-siege 等既有包跑一次免费 `inspect`，
  记录分布；阈值必须能解释为什么选它，不能拍脑袋。若某指标误报风险高，P0 可以只选低风险指标，
  其余继续作 observation 并写清。
- 判据产 `error` 时阻断发布；产 observation 的部分不改。
- 频段/阈值/误报边界写入文档和测试。

**明确不改**：

- 不做参考图 vs 交付图的风格相似度（P1 `CAP-QA-03`）。
- 不调用付费视觉模型 / `review`。
- 不改变 `inspectPack` 的「只读、免费」性质；不改变其输出契约（若需新增字段，单独报批）。
- 不自动修复 / 不自动重生成。

**测试**：

1. 用已知坏统计的 fixture（例如长宽比严重漂移 / 大量色板外像素）⇒ QA `error`，发布被拒。
2. 已接受包（v7 或团队认可的 baseline）⇒ 在阈值内通过；阈值数字有记录。
3. 阈值边界：刚好在阈值内 / 外各一条。
4. 观察字段仍出现在报告 `observations`，且不影响未阈值化的指标。

**验收条件**：

- 至少一条像素完整性判据能真实阻断；有正例 / 负例 / 边界测试。
- 阈值来源（测量包、样本数、选择理由）写在文档里。
- 不产生付费调用；`pnpm test` / `pnpm typecheck` 全绿。

**风险 / 回滚**：

- 阈值过紧会误伤正常动画帧间差异；必须用既有包测量，并在施工票里报告误报率。
- 阈值过松会漏掉明显坏图；P0 至少要覆盖已观测到的真实坏例（+52.4%、41 像素）。
- 回滚：把判据降回 observation 需单独说明，不能静默调阈值。

### P0-06 静默降级与入口错误语义

**为什么是 P0**：`frames` 被静默折叠成 `image` 违反「不得静默降级」；
MCP 对同一输入的错误码 / 绝对路径行为与 CLI 不一致，属于入口级真实缺陷。

**覆盖**：`CAP-ASSET-01`（W3-F1）、`CAP-ENTRY-01`（W1-1）、`CAP-ENTRY-02`（W1-2）；
MCP QA 失败测试（`CAP-QA-08` 的一部分）。

**建议范围**：

1. **`frames` 不再静默折叠**：推荐最小修法是 `planAssets` 对 `frames` 候选明确 `invalid`
   （消息说明「请改用 image 或逐帧模式」），并让 sidecar 记录模型真实候选。
   若选择参数化保留 `frames`，必须同时改 prompt / tool schema / resolver / sidecar，
   工作量更大；P0 默认采用「明确失败」。
2. **MCP 错误翻译**：复用 CLI 的 `asCommandError` 语义（或抽到共享层），使设计拒绝 / 契约错误 /
   HTTP / timeout 的 `_exitCode` 与 CLI 一致（4 / 3）。
3. **MCP `stylePath` 相对化**：与 CLI `styleRefOf` 同一规则；绝对路径不再被 `StyleReferencePath` 拒。
4. **MCP QA 失败测试**：`isError`、`_exitCode=4`、站点不产、报告在盘。

**明确不改**：

- 不新增 `source.kind`；不新增 route；不把 `frames` 变成第四条 route。
- 不做 TD / review / 并发参数等价（P2）。
- 不改变 CLI 的退出码语义。
- 不改变 MCP 工具面（除必要的错误语义修复）。

**测试**：

1. 模型给 `frames` 候选 ⇒ `planAssets` 明确失败（推荐）且不落 sidecar；或参数化保留时有测试。
2. 非法 kind / 候选 import / 能力缺失的既有失败行为不变。
3. MCP 设计拒绝 ⇒ `_exitCode=4`；HTTP 失败 ⇒ 3；usage ⇒ 2。
4. MCP 绝对路径 `stylePath` ⇒ 成功（与 CLI 同输入）。
5. MCP `create_game` QA 硬失败 ⇒ `isError`、4、无站点、报告在盘。

**验收条件**：

- 不再存在「模型给 `frames`、系统静默改 `image`」的路径。
- MCP 与 CLI 在错误码 / 绝对路径上一致；测试覆盖。
- `pnpm test` / `pnpm typecheck` 全绿；不新增付费调用。

**风险 / 回滚**：

- 明确拒绝 `frames` 可能让部分模型输出失败；消息必须给出可操作替代，且这是有意的（不静默降级）。
- 抽取错误翻译层可能触及 CLI/MCP 共享代码；不改变已有形状的行为，测试先钉住。
- `stylePath` 相对化要避免改变 CLI 既有行为；以 CLI 为基准。

## 4. 依赖与推荐顺序

```text
阶段 A（可并行，先做便宜的闸）
├─ P0-04 资产完整性（覆盖闸 / verifyPack 入链 / 空色板前移）
├─ P0-06 静默降级与入口错误语义
└─ P0-05 像素阈值（先测量，后定阈值）
        │
阶段 B
└─ P0-01 运行时胜利与软锁
        │
阶段 C
├─ P0-02 发布闸门统一（依赖 P0-04 / P0-05）
└─ P0-03 可玩 smoke（依赖 P0-01；最终绿灯依赖 P0-02）
        │
阶段 D（另立票）
└─ P0-FINAL 一次性付费 E2E（依赖 P0-01…P0-06 全部完成）
```

推荐理由：

1. **先做 P0-04 / P0-06**：防止「资源不完整 / 静默降级」进入后续验证，且成本低。
2. **P0-05 先测量**：阈值没有基线就会变成拍脑袋；测量本身免费。
3. **P0-01 是运行时正确性**：P0-03 的 smoke 需要正确的赢/软锁语义才能稳定。
4. **P0-02 最后接闸**：等 6/6 判据、像素阈值、verifyPack 都就位，闸门才有意义。
5. **P0-03 与 P0-02 可并行**：smoke 可以先在 fixture 上跑，最终验收等闸门统一。
6. **P0-FINAL 永远最后**：否则付费跑的是旧缺陷现场，信息量低。
