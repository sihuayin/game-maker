# P0-00：game-maker 能力差距审计与后续改造依据

- **项目**：`sihuayin/game-maker`
- **文档类型**：源码审计任务 / 后续 P0 需求拆分依据
- **状态**：待按当前目标分支复核并验收
- **优先级**：P0（先审计、后实现）
- **目标**：建立有文件路径、代码证据、测试依据和真实产物证据的能力差距清单，用于决定后续需求的新增、修改与复用。
- **核心原则**：P0-00 是审计与裁定任务，不是借机重写流水线；未被源码和测试证实的结论必须标记为“待验证”。

---

## 1. 为什么需要 P0-00

仓库已有流水线能力与 Demo，并不等于它能根据参考图和游戏意图，稳定生成风格一致、资源完整且真正可玩的游戏。必须用当前源码、测试和真实产物验证以下风险：

1. 资源生产决策可能过度集中在 `deriveRecipe`，或将资源默认分配到 `source.kind="drawlist"`。
2. 复杂角色、敌人、环境与高辨识度道具未必适合统一使用 drawlist；系统需要按资源特征选择合法生产路线。
3. 视觉世界规范、游戏意图、游戏设计、角色 DNA、资源配方、资源包、游戏配置之间的字段传递和语义映射需要逐项核实。
4. 现有 QA 可能主要覆盖 Schema、文件存在性或静态结构，尚不能据此证明视觉风格相似、资源适配和实际玩法成立。
5. 资源包成功与可运行游戏成功是不同交付结果，必须分开验收。
6. 测试通过只能证明测试覆盖范围内的行为，不能代替真实生成产物的验收。

本任务必须输出可供后续工程直接执行的证据表，而非仅写“系统缺少视觉 QA”这类无法落地的判断。

## 2. 审计范围

审计当前仓库中从输入到 Demo 的主链：

```text
Style Image + Game Intent
          |
          v
VisualWorldSpec + GameIntentSpec
          |
          v
      GameDesignSpec
          |
          v
 Character DNA / Asset Planning
          |
          v
      AssetRecipe
          |
          v
       AssetPack
          |
          v
       GameConfig
          |
          v
     Playable Demo
          |
          v
 Existing QA / Real-artifact validation
```

该图是审计地图，不代表所有步骤已经按此顺序实现。审计人必须记录实际入口、调用顺序、条件分支和产物路径。

### 纳入范围

- 输入契约和规格生成：`VisualWorldSpec`、`GameIntentSpec`、`GameDesignSpec`。
- 角色视觉约束与资源规划：`CharacterDNA`、`AssetSpec`、`AssetRecipe`、资源生产路线。
- 资源生成与打包：`pack`、`AssetPack`、资源路径、动画帧与元数据。
- 游戏配置生成与 Demo 构建：`GameConfig`、运行时接线、可玩入口。
- QA：Intent、Design、Asset、Visual、Gameplay 等现有检查的判据与阻断边界。
- CLI、MCP、RuntimeProfile 的入口一致性和兼容性。
- 失败路径、错误语义、成本账本和产物发布行为（只核查与本链路相关的既有契约）。
- 单元测试、集成测试、fixture、真实运行产物。

### 不在本任务内

- 不直接实现后续 P0 需求中的功能。
- 不在证据不足时重写所有 Schema 或包边界。
- 不新增 `source.kind="derived"` 等未经现有契约批准的资源路线。
- 不新增自动修复、自动重生成或无限重试循环。
- 不改写既有失败账本、版本目录、临时目录和原子发布规则。
- 不把跨游戏知识复用、跨项目迁移纳入本轮目标。
- 不以“增加更多 LLM Prompt”替代对数据契约、决策逻辑和验收机制的审计。

## 3. 已知假设与必须核实的风险

下表中的初步判断来自此前的项目分析线索，不得在没有当前分支证据的情况下当作最终事实。

| 编号 | 初步判断 | 必须核实的证据 | 判定方式 |
|---|---|---|---|
| A-01 | `deriveRecipe` 可能将资源默认分配为 `drawlist` | 函数实现、所有调用方、默认值分支、相关测试 | 给出路径、行号、最小复现输入及输出 Recipe |
| A-02 | 资源生产路线不能充分区分复杂角色、敌人、环境与道具 | 资源类型/复杂度字段、路线决策逻辑、提示词与执行分支 | 用代表性资源验证规划是否产生合理且合法的路线 |
| A-03 | VWS/Intent/Design 的字段可能在下游未被实际消费 | 生产者、契约、消费者、调用链、测试断言 | 对关键字段建立 producer → transform → consumer 映射 |
| A-04 | QA 偏结构检查，不能证明视觉与玩法质量 | QA 实现、finding 生成器、阻断规则、CLI/MCP 汇总 | 区分硬性阻断、观察信息和完全未检查的维度 |
| A-05 | 视觉 QA 或试玩结果未必能阻断发布 | 发布入口、QA 调用时序、失败时退出码与目录状态 | 用失败样例证明发布是否被正确阻断 |
| A-06 | 文档可能领先或落后于实现 | 文档要求与源码、测试逐项对照 | 标注 implemented / partial / absent / unknown |
| A-07 | 资源包与可玩游戏可能被混为一个验收结果 | CLI/MCP 交付路径、pack 与 runtime 的独立状态 | 分别验证 AssetPack、GameConfig、Demo 是否成功 |
| A-08 | fixture 可能只验证理想输入，未覆盖语义错误与负例 | 测试数据和断言 | 列出缺失的正例、负例和边界样例 |

## 4. 必须产出的审计证据表

每个能力点必须填写一行。不得只写结论而没有证据。

| 字段 | 要求 |
|---|---|
| ID | 唯一编号，例如 `CAP-ASSET-01` |
| 能力 / 需求 | 用可验证的行为描述，不使用“更智能”“更高质量”等空泛措辞 |
| 当前状态 | `implemented` / `partial` / `absent` / `unknown` |
| 源码证据 | 精确文件路径、符号名；核验后附行号 |
| 调用链 | 谁创建数据、谁转换数据、谁消费数据 |
| 测试证据 | 测试文件、用例名称、断言内容；没有测试须明确写明 |
| 真实产物证据 | 对应 run/pack/site 目录、验证命令与观察结果；未执行标记 `not run` |
| 缺口 | 当前实现与目标行为之间的具体差异 |
| 影响 | 对资源质量、玩法、稳定性、兼容性或成本的影响 |
| 建议归属 | 后续 P0 需求、复用现有能力、补测试或暂缓 |
| 验收条件 | 可由测试或人工操作明确判定通过/失败 |

状态定义：

- `implemented`：源码存在，调用链已接通，测试覆盖关键行为，且所需产物证据成立。
- `partial`：有部分实现，但调用链、边界、测试或真实产物至少一项不完整。
- `absent`：已检查相关入口和调用链，确认没有实现该能力。
- `unknown`：尚未完成足够核查；不得将其写成 absent。

## 5. 审计工作包

### W1：确认真实入口与主调用链

**目标**：明确用户从 CLI/MCP 进入后，实际运行了哪些模块，以及每个阶段写出了什么产物。

必须记录：

- CLI 命令与参数入口。
- MCP 工具入口及其与 CLI/核心函数的复用关系。
- RuntimeProfile 的分派位置及旧链兼容边界。
- 各阶段的输入类型、输出类型、文件落盘位置。
- 失败时的退出码、错误包装和产物清理策略。

**输出**：主链调用图、阶段/产物表、入口差异表。

**验收**：另一位开发者仅根据文档即可找到真实入口、跟踪一次构建，并定位各阶段产物。

### W2：核对规格字段是否被消费

至少核查：

- `VisualWorldSpec` 的调色板、视觉风格、世界约束、参考图和绘制规则。
- `GameIntentSpec` 的实体、机制、核心循环、玩家目标与约束。
- `GameDesignSpec` 的机制、关卡、实体、反馈与可执行设计。
- `CharacterDNA` 的视觉约束、色板引用和角色一致性字段。
- `AssetRecipe` 的资源 ID、生产路线、输入、约束和执行信息。
- `GameConfig` 中资源、动画、控制、碰撞、关卡和玩法配置。

对每个关键字段回答：

1. 谁生成它？
2. 谁验证它？
3. 谁读取它？
4. 读取后改变了什么实际行为？
5. 是否有测试证明该行为，而不只是断言字段存在？
6. 是否有真实产物可以观察其效果？

**验收**：关键字段不存在未解释的“有定义、无消费者”或“测试只检查非空”问题；所有例外均登记为缺口。

### W3：审计资源生产路线

重点核查 `deriveRecipe`（若仍存在）、Asset Planner/资源规划逻辑和 `pack` 执行器。

当前路线契约必须以仓库实际 Schema 为准。此前方案中的合法路线为 `image`、`drawlist`、`import`，必须确认当前分支是否仍采用该枚举，不得未经核验就新增路线。

至少选取以下资源类别构造审计样例：

| 样例 | 关注点 |
|---|---|
| 主角角色与移动动画 | 外观辨识度、帧一致性、透明背景、动画完整性 |
| 敌人 / NPC | 与世界风格一致、不同实体可区分 |
| 大型环境物件 | 轮廓和细节是否适合所选路线 |
| 高频小型道具 | 批量生产、尺寸一致、可读性 |
| HUD / UI | 锚点、布局、可读性及屏幕适配 |
| 已有外部资源 | `import` 路径、合法性和约束检查 |

每个样例必须记录：输入规格、规划输出、`source.kind`、选择理由、执行结果、产物位置、测试覆盖与失败表现。

**验收**：路线选择由可测试规则决定；不合法或缺少必要输入时明确失败，不得静默降级为任意默认路线。

### W4：审计 QA 的真实判定能力

建立 QA 能力矩阵，至少区分：

| 维度 | 必须回答的问题 |
|---|---|
| Contract / Schema | 是否只验证结构，还是也验证跨字段业务约束？ |
| Intent QA | 是否能发现实体/机制缺失及近似替代？判据是什么？ |
| Design QA | 是否能验证设计对意图的覆盖，而非只检查文本相似？ |
| Asset QA | 是否验证文件、帧、尺寸、引用与资源清单的一致性？ |
| Visual QA | 是否实际比较生成结果与参考风格？比较对象、阈值和误报边界是什么？ |
| Gameplay QA | 是否真实启动游戏并执行输入？是否验证目标、失败、胜利与关卡可达？ |
| Integration QA | 是否验证资源被 GameConfig 正确引用并进入最终 Demo？ |
| Publish Gate | 哪些 finding 会阻断成功退出或正式发布？ |

对每个 QA 族必须列出入口和实现文件、finding 生成条件、severity/blocking 规则、CLI 与 MCP 是否一致、正例和负例测试、尚未覆盖的维度。

**边界**：不得将“存在 Visual QA 模块”直接等同于“视觉一致性已经被验证”；必须证明它读取了正确输入与真实产物，并且结果影响验收。

### W5：检查测试与 fixture 的代表性

测试清单至少覆盖：

- 合法输入成功路径。
- 缺失字段与非法枚举。
- 资源路线选择与不支持路线。
- 上游模型输出结构合法但语义错误。
- 参考图没有出现、但游戏需求要求生成的新实体。
- 资源文件存在但内容/尺寸/帧数不符合预期。
- 资源包成功但游戏构建失败。
- 游戏可以启动但关键机制不可执行。
- QA 发现阻断问题时，发布不会被误报成功。
- CLI/MCP 对同一输入的关键行为一致。
- 失败不消耗版本号，临时目录与失败产物遵循既有契约。

每项测试标注 `existing` / `missing` / `needs strengthening`，并给出测试路径和用例名（如已确认）。

### W6：真实产物验证

至少运行一条端到端样例。

**输入**：一张明确的风格参考图 + 一段具体的 2D 游戏意图。

**样例目标**：产出具有统一视觉风格的可玩 2D Demo，例如废土探索/寻宝题材。该题材仅作为测试样例，不构成产品范围限制。

必须保留：

- 输入图片与需求文本。
- 关键中间规格。
- AssetRecipe。
- AssetPack。
- GameConfig。
- Demo/site 产物。
- 验证命令、运行环境和退出码。
- 关键资源截图或图像对照。
- 玩法操作记录及实际结果。
- 所有失败、重试和成本账本信息（遵守现有账本契约）。

至少人工检查：

1. 主角是否清晰可辨、动画帧是否一致。
2. 资源是否与参考图的色彩、轮廓、细节密度和材质表达相符。
3. 参考图未出现的新实体是否仍属于同一视觉世界。
4. 资源是否完整、正确引用且进入游戏场景。
5. 玩家是否可以移动、与目标交互，并完成一段核心循环。
6. QA 的通过/失败结果是否与实际观察一致。

**验收**：没有真实运行记录时，不得宣称端到端能力已经验收；失败样例也必须保存并登记，不能只保留成功 Demo。

## 6. 对后续 P0 需求的分流规则

P0-00 不应预先假定每个缺口都需要新模块。每条建议必须选择一类：

1. **复用**：已有实现满足需求，只需接线或补调用。
2. **修正**：已有实现存在明确错误或不完整行为。
3. **新增**：仓库不存在所需能力，且有证据证明必须新增。
4. **补测**：实现已存在，但没有足够测试证明行为。
5. **补文档**：实现和测试已成立，只有说明缺失或过时。
6. **暂缓**：不属于当前最短交付路径，或证据不足。

对每个缺口提供需求 ID、来源证据、推荐动作与理由、预计修改范围、明确不应修改的范围、依赖关系、测试计划、验收条件和风险/回滚方式（若涉及对外契约）。

### 推荐优先级判定

- **P0**：直接阻断“风格图 + 游戏意图 → 资源完整、风格匹配、可玩的 Demo”，或可能导致错误地宣告成功。
- **P1**：显著影响质量、可诊断性或维护成本，但存在可接受的临时人工步骤。
- **P2**：优化项，不影响当前最小端到端验收。

## 7. 候选改进方向（不是最终裁定）

以下方向值得优先验证，但最终范围必须由证据表决定。

### Candidate A：Asset Planner / 资源生产路线决策

候选需求：以 `GameDesignSpec` 和 `VisualWorldSpec` 为主要输入，为每项资源明确生产路线、约束和决策理由；由 `pack` 执行规划结果。

边界：

- 只允许当前契约支持的路线（此前方案为 `image`、`drawlist`、`import`，须以源码复核为准）。
- 不新增 `derived` 路线。
- 不重写整个 Pack、图像客户端或 `raster.ts`。
- 不无必要地改变 CLI、MCP、Recipe Schema、AssetPack 目录结构。
- 不引入自动修复/重生成循环。
- 保留现有失败账本、成本归因、版本目录和原子发布语义。
- 规划决策必须有单元测试，真实执行结果必须可追溯到对应规划。

### Candidate B：规格字段消费与链路闭合

核实 VWS、Intent、Design、Character DNA 中的关键字段是否影响实际资源与玩法产出。缺字段消费者时，优先确定是接线、修正还是补充契约，避免先重构全链。

### Candidate C：真实视觉与玩法验收

核实现有 QA 能否读取实际生成资源与 Demo，是否具有明确的阻断边界。优先形成可重复的端到端基准和真实产物记录，再决定视觉相似度、自动试玩或后续修复机制的实施顺序。

## 8. 最终交付物

P0-00 完成时必须提交：

1. `P0-00-capability-gap-audit.md`：完整能力差距证据表。
2. `P0-00-call-graph.md`：真实调用链与产物路径。
3. `P0-00-test-matrix.md`：现有测试、缺失测试与 fixture 覆盖矩阵。
4. `P0-00-e2e-evidence.md`：真实运行命令、产物路径、结果与截图/对照材料索引。
5. `P0-00-p0-scope.md`：后续 P0 需求的分流与范围裁定。

如果仓库已有相同用途的文档，应更新或合并既有文件，不要无理由重复创建多份事实来源。

## 9. 完成定义（Definition of Done）

- [ ] 主链入口、调用关系、阶段输入输出已核实。
- [ ] 关键字段均有生产者、消费者与测试证据；未闭合项明确列出。
- [ ] 资源生产路线已通过源码、测试和代表性输入核实。
- [ ] QA 能力矩阵明确区分静态检查、真实视觉检查、真实玩法检查和发布阻断。
- [ ] 测试矩阵覆盖关键正例、负例、边界与失败路径。
- [ ] 至少一条端到端真实运行有完整记录；若因环境或凭证无法运行，须明确记录阻塞原因，且不得冒称 E2E 已通过。
- [ ] 每条差距都有源码路径、测试依据或明确的证据缺失说明。
- [ ] 每条差距均已分流为复用、修正、新增、补测、补文档或暂缓。
- [ ] 后续 P0 需求的范围、依赖和验收条件可直接交给编码代理执行。
- [ ] 未在审计过程中顺手引入未经批准的 Schema、CLI/MCP、Pack 或运行时契约变更。

## 10. 给编码代理的执行指令

先审计，后提案，不要直接实现。

1. 检查当前工作树和分支，确认代码版本；不要假定旧报告对应当前 HEAD。
2. 对主链入口、核心函数和 QA 逐一检索，输出精确路径、符号名与行号。
3. 运行相关现有测试，记录命令、退出码和失败摘要；不得将未运行测试写成通过。
4. 对每个结论区分 `源码已证实`、`测试已证实`、`真实产物已证实`、`推断/待验证`。
5. 建立能力差距表，并将每条建议映射到后续 P0 需求或明确标记为范围外。
6. 如果真实 E2E 因凭证、外部服务或环境无法运行，记录阻塞点和最小补充条件，不得伪造产物证据。
7. 最后只提交审计文档与需求分流建议；未经批准不修改实现代码。

## 附录 A：审计结论的证据强度

- **E0 — 推测**：基于印象或旧讨论，没有当前源码证据。
- **E1 — 源码证据**：找到实现或缺失入口，但未证明实际行为。
- **E2 — 测试证据**：有测试覆盖且断言与目标行为直接相关。
- **E3 — 真实产物证据**：真实执行产物与操作结果证明目标行为成立。

涉及“可以生成风格一致的游戏”“玩法可用”“QA 能阻断错误产物”等核心能力的结论，原则上需要 E3。E0/E1 不得写成已验收。

## 附录 B：本轮审计最重要的判断

P0-00 的成功标准不是发现尽可能多的问题，而是把每个重要判断转化为可追溯证据，并让后续需求不重复造轮子、不破坏现有契约、不把“流程跑通”误判为“产品目标达成”。
