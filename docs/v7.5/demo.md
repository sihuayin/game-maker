# FPVS-V1 Final Acceptance
## 真实 Demo 最终验收闭环需求文档

- **文档类型**：PRD / AI 编码实施需求
- **项目**：`sihuayin/game-maker`
- **目标分支**：`main`
- **需求阶段**：FPVS-V1 最终验收
- **优先级**：P0
- **前置阶段**：FPVS-V1-P0、FPVS-V1-P1、Playtest V1
- **核心目标**：补齐真实试玩证据、完成视觉人工确认，并据此判定 Demo 是否达到 FPVS-V1 验收标准。

---

## 1. 背景与问题

### 1.1 项目目标

FPVS-V1（First Playable Vertical Slice V1）的目标是：

> 输入一张风格参考图和游戏意图，通过现有流水线，生成一个完整、可启动、可操作、能够完成目标的真实 2D 废土寻宝 Demo。

目标链路如下：

`风格图 + 游戏意图 → 设计 → 资源 → GameConfig → 可运行游戏 → 玩家操作 → 完成游戏目标 → 验收报告`

此前已建设生成流水线、运行配置、QA 和 Playtest V1。Playtest V1 提供固定场景、运行时状态观测、失败归因、回归基线和交付报告集成等能力。

但**基础设施测试通过，不代表生成的 Demo 已经完成验收**。

### 1.2 当前已知状态

根据现有项目记录：

- Playtest V1 的 01–10 相关工作已收口。
- 全仓测试、类型检查及 Playtest 专项测试已有通过记录。
- 真实生成流水线已成功创建 Demo，曾有一轮真实产物的 Create QA 通过。
- 旧自动玩家的试玩结果为 3/4，主要限制是自动玩家未能稳定处理宽范围巡逻的危险物。该现象目前不能直接判定为游戏本身不可玩。
- P0-06 的风格参考图与实际游戏资源人工对照尚未完成。
- 现有历史 QA 报告仍然可读，但不能把历史结果自动升级成新验收结论。

以上状态是本需求的起点，不是最终验收结论。实施时必须重新核对当前代码、真实产物及报告，不能只依据历史摘要宣告通过。

### 1.3 本阶段需要解决的问题

1. 是否有证据证明指定版本的 Demo 可以正常启动？
2. 是否有证据证明玩家能够执行必要操作，并通过真实操作完成目标？
3. 自动试玩未完成时，能否区分游戏缺陷、自动玩家能力限制、环境故障和证据不足？
4. 实际生成的资源是否符合输入风格参考图和游戏意图？
5. 能否将上述证据汇总为一个可追溯、可复核的最终验收结论？

- 不将未知、缺失或无法复核的证据视为通过。
- 不默认新增契约字段、CLI/MCP 命令或第三方依赖。

- 不把历史 `playable-smoke` 数据改写为新的 Playtest V1 结果。

## 3. 需求原则

### 3.1 真实产物优先

验收对象必须是本轮实际生成、可运行的 Demo，而不是仅由 fixture、mock 或单元测试构造的理想状态。

Fixture 和离线测试仍然用于验证判定逻辑，但不能替代真实产物验收。

### 3.2 证据优先于状态标签

每个验收结论必须能追溯到对应证据。不能仅凭 `QA pass`、测试全绿、进程启动成功或单个截图认定整体达标。

### 3.3 自动化能力不等于游戏能力

自动玩家无法完成操作时，必须先判断失败归属。自动玩家的能力限制不能直接证明游戏不可玩；同样，不能仅以“可能是自动玩家的问题”为理由忽略真实游戏缺陷。

### 3.4 不确定性必须保留

缺失证据、观测失败、版本不匹配和无法分类的问题必须保留为未完成或阻塞状态。不得通过默认值、宽松回退或吞掉错误来得到通过结论。

### 3.5 不重复建设

优先复用现有 Playtest V1、QA、交付报告、审核结果和版本身份能力。只有在确认现有能力无法表达验收所需信息后，才提出最小必要变更，并先获得审批。

## 4. 功能需求

### FR-01：固定验收对象与版本身份

**目标：确保所有验收证据指向同一个真实 Demo。**

#### 要求

1. 选定本轮验收使用的真实运行产物。
2. 记录现有系统能够提供的以下身份信息：
   - run 标识及版本；
   - site / pack 标识及版本；
   - GameConfig 对应版本或可验证身份；
   - 试玩报告与 QA 报告的位置及版本；
   - 本轮验收的参考图和游戏意图来源。
3. 验证试玩所运行的 site、pack、config 与验收目标一致。
4. 对无法确认身份或发现版本不匹配的证据，不得用于证明该 Demo 达标。
5. 保留历史产物，不覆盖原版本；如需重新生成，应遵守既有版本分配和原子提交规则。

#### 验收标准

- 所有用于最终结论的关键证据均能追溯到明确的验收对象。
- 不存在把旧报告、新 site 或其他版本的 config 混合起来验收的情况。
- 身份无法确认时，结果为未完成或阻塞，而不是通过。

---

### FR-02：补齐真实试玩证据

**目标：证明生成的 Demo 不只是能够构建，而是能够通过实际操作完成核心游戏流程。**

优先复用现有 Playtest V1 harness、固定场景、状态观测和语义动作，不另建一套试玩系统。

#### 必须覆盖的验收维度

| 验收维度 | 需要证明的内容 | 证据要求 |
|---|---|---|
| 启动 | 指定 Demo 能正常加载并进入可玩状态 | 启动结果及对应版本身份 |
| 玩家移动 | 玩家能够执行必要的水平移动 | 实际运行时状态变化或等效可复核证据 |
| 跳跃与落地 | 玩家能够执行必要的跳跃、落地操作 | 动作结果及相关状态证据 |
| 收集物 | 玩家能够触发收集并观察到结果 | 收集前后状态或事件证据 |
| 宝箱 | 玩家能够触发设计规定的宝箱行为 | 触发条件及实际结果证据 |
| 危险物 | 危险接触或躲避行为符合设计预期 | 接触、重置或成功躲避的证据 |
| 游戏目标 | 玩家能够通过真实操作完成目标 | 目标达成状态及操作过程证据 |

说明：

- 上表是验收覆盖范围，不代表每项都必须新增一个独立测试文件。
- 优先复用现有固定场景和 probe。
- 宝箱按现有设计采用接触触发的自动开启行为，不额外引入 `input:interact`。
- 危险物的接触、重置及成功躲避必须按现有设计和可观测状态判定。
- 如果现有 Demo 的实际设计与表格某项不一致，应先核实设计契约，不能擅自更改游戏机制来满足测试。

#### 核心要求：真实目标完成

必须至少取得一条能够证明玩家通过实际操作完成游戏目标的证据链。

证据链应包含：

1. 验收对象身份明确；
2. 实际执行了必要的玩家操作；
3. 运行时观测记录了相关状态或事件；
4. 最终目标达成状态得到确认；
5. 试玩结果与对应证据可以相互核对。

仅调用内部完成函数、直接修改内存状态、手工改写 GameConfig 或使用预置的胜利结果，不满足此项要求。

如果自动玩家无法稳定完成目标，可以使用现有能力支持的人工操作或其他可复核方式补充证据。人工操作必须明确标记为人工证据，不得伪装成自动试玩通过。

#### 验收标准

- 核心验收维度均有明确结果。
- 游戏目标完成有真实操作证据，而非仅有内部测试结果。
- 无法执行或观测的项目明确标记为未完成、阻塞或证据不足。
- 不因单次自动试玩超时就直接认定游戏失败。

### FR-03：建立试玩失败归因规则

**目标：避免将不同性质的失败混为一谈。**

试玩未完成或失败时，必须依据现有 Playtest V1 的结果模型和证据进行归因。

| 归因类别 | 典型情况 | 处理方式 |
|---|---|---|
| 游戏缺陷 | 玩家操作已执行，但游戏行为违反设计，或无法完成必要目标 | 记录缺陷及证据，修复后重新验收 |
| 自动玩家能力限制 | 游戏提供了可行操作路径，但当前 agent 无法找到或稳定执行该路径 | 记录限制，不能单凭此项判定游戏不达标 |
| 环境故障 | 浏览器、页面加载、运行环境或观测通道异常 | 修复或排除环境问题后重新取证 |
| 证据不足 | 状态缺失、关键事件未观测到、结果无法复核 | 保持未完成，不得判定通过 |
| 超时或中断 | 试玩在限定时间内没有得到确定结果 | 结合已有证据继续归因；无法归因时保留未完成状态 |

#### 具体规则

1. 不得把 agent limitation 自动映射为 game failure。
2. 不得把环境故障映射为游戏成功或失败。
3. 不得把 timeout 自动视为游戏缺陷。
4. 不得因为没有观察到失败事件，就推断游戏通过。
5. 不得将 unknown、missing evidence 或无法归因的状态升级为 pass。
6. 如果证据已直接显示游戏违反必要行为要求，应记录为游戏缺陷，不能以自动玩家能力限制掩盖。
7. 归因必须保留可复核依据，而不是只记录一个类别标签。

#### 验收标准

现有离线测试应继续覆盖成功、游戏失败、环境故障、agent limitation、timeout 等情况，并验证未知状态不会通过。

如果现有测试未覆盖本需求新增的判定边界，可补充纯离线测试；不得为了完成验收而发起付费调用。

### FR-04：完成 P0-06 风格一致性人工确认

**目标：确认最终生成的游戏资源与输入风格参考图相符，而不只是确认资源文件存在或技术指标合格。**

#### 审核材料

审核者应能够查看并关联以下材料：

1. 原始风格参考图；
2. 实际交付的资源包；
3. 实际运行的 Demo 截图或等效视觉证据；
4. 与当前 Demo 对应的资源及版本身份；
5. 已有 Visual QA 结果和相关问题记录。

应优先使用现有审核和报告能力。不得为了展示方便而替换成另一个版本的截图或资源。

#### 审核内容

| 检查项 | 判断问题 |
|---|---|
| 整体风格 | 游戏画面的整体美术表达是否与参考图一致 |
| 色彩与明暗 | 主色调、对比关系及明暗分布是否存在明显偏差 |
| 角色 | 玩家角色的外观、轮廓和视觉表达是否符合预期 |
| 场景 | 背景、地形及环境元素是否符合参考图风格 |
| 关键物件 | 宝箱、收集物、危险物等关键资源是否符合游戏意图 |
| 实际运行效果 | 资源在游戏中是否出现明显裁切、比例异常、错位或其他影响体验的问题 |

审核不应要求像素级复制参考图。重点是风格与关键视觉意图是否得到实现，以及实际运行画面是否达到可接受水平。

已有自动化指标可作为辅助证据，但不能取代人工对照。

#### 审核结果

必须明确记录审核结果：

- **通过**：风格及关键视觉要求满足预期。
- **不通过**：发现明确的视觉缺陷，或实际资源明显偏离要求。
- **未完成 / 阻塞**：审核材料不完整、版本不匹配或无法作出可靠判断。

每次审核至少应记录：

- 被审核的 Demo 版本；
- 所使用的参考图和实际运行画面；
- 审核结果；
- 主要判断理由；
- 已发现问题及相关证据；
- 审核时间和审核者身份（如现有系统支持）。

如果当前审核结果模型不支持上述信息，先确认能否使用现有备注或报告结构表达。确需扩展契约时，应单独提出变更方案并获得审批。

#### 验收标准

- P0-06 不再处于“尚未审核”的状态。
- 审核结果明确，且绑定实际验收版本。
- 审核结论有足够材料和理由支撑。
- 审核不通过时，最终验收不能判为通过。

### FR-05：生成最终验收结论

**目标：综合试玩、QA、视觉审核和版本身份，得出可追溯的最终结论。**

最终结论应复用现有交付报告及结果模型。不得未经审批新增一套平行的验收状态体系。

#### 判定维度

最终验收至少综合以下维度：

1. 产物身份和版本一致性；
2. 现有构建、配置及 QA 结果；
3. 真实启动与必要玩家操作证据；
4. 真实目标完成证据；
5. 试玩失败归因；
6. P0-06 人工视觉审核；
7. 未解决的阻塞项及证据缺口。

#### 最终状态的语义

下表描述的是验收语义，不要求直接新增同名枚举。如果现有契约已提供对应状态，应复用现有状态。

| 结果语义 | 判定条件 |
|---|---|
| 通过 | 所有强制验收条件均有充分证据，目标完成得到证明，视觉人工审核通过，且不存在未解决的阻塞项 |
| 不通过 | 有明确证据表明强制验收条件未满足，例如游戏缺陷或视觉审核不通过 |
| 阻塞 | 受环境、版本不匹配或其他外部问题影响，当前无法完成必要验证 |
| 未完成 | 必要证据缺失、结果未知或尚未执行完全部验收步骤 |

如现有系统只有部分状态，必须依据其既有契约表达，不得私自创建或改变枚举含义。

#### 判定规则

- 全仓测试通过，不等于最终验收通过。
- Create QA 通过，不等于试玩目标已完成。
- 试玩报告通过，不等于视觉人工审核通过。
- 视觉审核通过，不等于游戏可以正常操作。
- 任一强制条件存在明确失败，整体不得通过。
- 任一强制条件缺少必要证据，整体不得通过。
- agent limitation 可以不直接构成游戏失败，但不能替代目标完成证据。
- 只有全部强制条件满足时，才允许输出最终通过。

#### 验收标准

- 最终结论能够从关联的报告和证据中复核。
- CLI、MCP 和交付报告对同一验收对象给出一致的结果。
- 无法复核的结果不能通过默认值或宽松转换变成通过。

## 5. 建议实施顺序

### 阶段 A：只读审计与验收对象冻结

**目的：先确认已有能力和真实产物，不急于修改代码。**

任务：

1. 检查当前 `main` 的实际 HEAD。
2. 检查 Playtest V1、QA、交付报告及人工审核相关契约。
3. 找出当前真实 Demo 的 run、pack/site、config 和报告位置。
4. 复核历史试玩记录、3/4 自动试玩结果及其归因。
5. 列出已具备、缺失、无法确认的验收证据。
6. 明确当前最小修改清单。

交付物：

- 当前实现能力与需求的差距清单；
- 真实验收对象及版本身份记录；
- 本轮证据缺口清单；
- 必要代码变更及契约审批清单。

完成标准：没有在尚未理解现有契约和真实产物的情况下重复建设功能。

### 阶段 B：补齐真实试玩证据

任务：

1. 复用现有 Playtest V1 harness 执行必要的试玩场景。
2. 检查启动、移动、跳跃、收集、宝箱、危险物和目标完成的证据覆盖。
3. 核对观测结果是否确实来自实际运行中的 Demo。
4. 对自动试玩失败逐项进行归因。
5. 对 agent limitation 或证据不足的项目，使用现有能力补充可复核证据。
6. 修复发现的真实游戏缺陷；如需重新生成产物，遵守版本不可覆盖规则。
7. 保留失败结果和历史证据，不删除不利结果来制造通过。

交付物：

- 对应真实版本的试玩报告；
- 必要的操作及状态证据；
- 失败归因记录；
- 尚未解决的问题清单。

完成标准：能够证明至少一条真实操作路径完成游戏目标，并明确说明其余强制试玩维度的结果。

### 阶段 C：完成视觉人工审核

任务：

1. 整理参考图、实际资源和实际运行画面。
2. 确认所有审核材料与目标 Demo 版本一致。
3. 按 FR-04 检查风格、色彩、角色、场景、关键物件及运行效果。
4. 记录通过、不通过或未完成的审核结论。
5. 如发现问题，明确问题是否影响强制验收条件。

交付物：

- 绑定实际版本的视觉审核结果；
- 审核理由和证据；
- 必要的视觉问题记录。

完成标准：P0-06 得到明确且可复核的审核结论。

### 阶段 D：汇总最终验收

任务：

1. 汇总版本身份、QA、试玩、目标完成和视觉审核结果。
2. 检查所有强制条件是否有充分证据。
3. 依据现有结果模型输出最终结论。
4. 核对 CLI、MCP 和交付报告的一致性。
5. 运行相关测试、类型检查及现有验收命令。
6. 确认本轮没有发生未经授权的契约变更、依赖增加、付费调用或历史产物覆盖。

交付物：

- 最终验收报告；
- 强制条件逐项判定；
- 证据引用和版本身份；
- 未解决问题及最终结论理由；
- 自动化验证结果。

完成标准：任何人都可以根据报告判断 Demo 是否达标，并追溯到支撑结论的证据。

## 6. 测试要求

### 6.1 离线测试

优先使用现有测试框架和 fixture 覆盖以下情形：

- 真实验收所需条件全部满足；
- 目标未完成且存在明确游戏缺陷；
- 自动玩家能力不足，但尚无证据证明游戏不可玩；
- 环境故障导致试玩中断；
- 试玩超时；
- 关键状态或事件缺失；
- site、pack、config 版本不匹配；
- 视觉审核未完成；
- 视觉审核不通过；
- 历史报告仍可读取，但不能自动升级为新验收通过；
- 未知状态不能被映射为通过；
- CLI、MCP 和交付报告对同一结果保持一致。

### 6.2 回归测试

至少执行：

- `pnpm test`
- `pnpm typecheck`
- `pnpm test:playtest`

如实际修改触及其他专项测试，应执行相应的现有命令，包括需要时的 `pnpm test:acceptance`。

以上是建议验证清单，具体执行范围应根据实际改动和当前脚本定义确认。测试命令通过只证明相应自动化检查通过，不替代真实 Demo 验收。

### 6.3 真实验收

必须使用实际生成并可运行的 Demo 验证最终结论。

真实验收不能由以下内容单独替代：

- 单元测试；
- fixture；
- mock 运行时；
- 仅有构建成功的记录；
- 仅有 QA pass 的记录；
- 仅有自动试玩框架自测通过的记录。

## 7. 范围与变更控制

本阶段严格遵守现有项目约束。

### 7.1 允许优先实施

- 补齐现有试玩场景的证据；
- 修复验收过程中发现的确定性缺陷；
- 补充纯离线测试；
- 使用现有报告能力记录人工审核；
- 在不改变契约的前提下，完善结果汇总和证据引用；
- 修正文档中与当前实现不一致的验收说明。

### 7.2 必须先审批

- 新增或改变 contracts 中的 schema、枚举或字段；
- 改变 CLI / MCP 的公开输入输出；
- 新增第三方依赖；
- 改变既有状态的语义；
- 新增付费 E2E 或模型调用；
- 改变版本分配、产物写入或历史数据兼容规则。

### 7.3 禁止事项

- 覆盖 `run/vN` 或 `pack/site/vN`；
- 将失败结果改写为通过；
- 将未知状态默认为成功；
- 为满足自动测试而擅自更改游戏意图或核心机制；
- 以删除测试、缩减覆盖范围或降低阈值的方式获得绿灯；
- 将旧 `playable-smoke` 历史数据伪装成 Playtest V1 新证据；
- 未经授权发起付费调用。

## 9. 最终完成定义

只有同时满足以下条件，FPVS-V1 Final Acceptance 才算完成：

1. **真实可玩性得到证明**：指定版本的 Demo 可以运行，必要玩家操作有证据，至少一条真实操作路径完成了游戏目标。
2. **视觉人工确认完成**：P0-06 已对实际参考图、资源和运行画面进行审核，结果明确且可追溯。
3. **验收结论可信**：最终结论基于真实证据，正确处理游戏缺陷、自动玩家限制、环境故障及证据不足。
4. **报告保持一致**：最终结果与对应的 QA、Playtest 和人工审核证据一致，CLI、MCP 与交付报告没有相互矛盾的结论。
5. **工程约束未被破坏**：不通过降低门槛、篡改历史结果、覆盖产物或未经授权付费来达成验收。

如果 Demo 存在明确缺陷、P0-06 不通过，或必要证据仍然缺失，则不能宣布 FPVS-V1 达标。应保留准确状态、问题和证据，继续修复或补齐验证。

## 10. 本阶段的核心交付物

最终应交付：

- 一份真实验收对象与版本身份记录；
- 一份完整的真实试玩证据及归因报告；
- 一份 P0-06 视觉人工审核记录；
- 一份最终验收报告，包含逐项结论、证据引用、限制和未解决问题；
- 与实际改动匹配的离线测试及回归验证结果。

**最终判断标准不是“流水线是否跑通”，而是“这个指定版本的 Demo 是否已经通过真实证据证明可玩、可完成目标，并符合预期视觉风格”。**
