# Entity Identity V1.1：错误归属拒绝与关卡作用域

> **类型**：Implementation PRD / Contract Hardening  
> **优先级**：P0  
> **目标**：修复 Entity Identity V1 中“引用存在但归属错误仍然通过验真”的缺口，并明确多关卡项目中身份覆盖校验的边界。  
> **实施原则**：先明确身份契约，再修改实现；先通过针对性测试，再执行真实 E2E。  
> **范围限制**：只处理设计实体与运行时实体之间的身份映射，不扩展资源生成策略、视觉质量、玩法机制或跨项目知识复用。

---

## 1. 背景与问题

### 1.1 V1 已确立的契约

V1 已实现以下基础能力：

- `GameConfig.Entity.id`：运行时实体的唯一标识。
- `GameConfig.Entity.sourceIntent`：回指 `GameDesignSpec` 中设计实体的 ID。
- 允许多个运行时实体指向同一个设计实体，即合法的 `1:N` 映射。
- 允许结构性运行时实体没有 `sourceIntent`，例如没有独立设计实体对应项的地面、出口等实体。
- `compileRuntime` 提示模型输出正确的 `sourceIntent`。
- 确定性验真检查设计实体覆盖和悬空引用。
- QA 第 7 项身份比较使用 `sourceIntent`，不再直接使用运行时 `id`。

### 1.2 问题 A：引用存在不代表归属正确

当前身份校验主要检查：

1. 设计实体是否至少被一个运行时实体引用。
2. 非空 `sourceIntent` 是否指向真实存在的设计实体。

这两个条件不足以证明身份映射正确。

例如：

设计规格中存在设计实体 `chest`，表示宝箱；运行时配置中存在 `gate`，其 `kind` 为 `goal`，却声明：

```ts
{
  id: "gate",
  kind: "goal",
  sourceIntent: "chest"
}
```

由于 `chest` 确实存在，且其他设计实体也可能已经满足覆盖要求，当前校验可能不会拒绝该配置。

但这条映射在语义上是错误的：**出口不能仅仅因为宝箱存在，就被认定为宝箱的运行时实现。**

这会造成更隐蔽的问题：身份审计通过、QA 关联成功，但实际生成的游戏已经偏离设计规格。

### 1.3 问题 B：全局设计实体与单关卡配置的作用域不明确

`compileRuntime` 会选择特定的 `levelId`，而现有身份审计接收整个 `GameDesignSpec` 与一个 `GameConfig`。

如果校验对完整设计规格中的所有敌人、NPC、交互物和资源一律要求覆盖，就可能要求某个关卡的配置包含其他关卡才会使用的实体。

反过来，如果为了让单关卡构建通过而直接删除全局覆盖检查，也可能遗漏当前关卡真正需要的设计实体。

因此必须明确：

- 哪些设计实体属于当前关卡的验真范围。
- 哪些实体需要跨关卡全局覆盖。
- 哪些实体只在特定条件下要求出现。
- 结构性运行时实体如何参与身份审计。

不得依赖偶然的配置内容来推断关卡作用域。

## 2. 目标与非目标

### 2.1 本期目标

1. **拒绝错误归属**：`sourceIntent` 指向存在的设计 ID，但运行时实体与设计实体的语义类型不兼容时，必须产生确定性错误。
2. **明确合法映射**：保留合法的 `1:N`，不要求设计实体与运行时实体一一对应。
3. **保留结构性实体**：没有设计实体对应项的结构性运行时实体可以不设置 `sourceIntent`。
4. **明确关卡作用域**：当前关卡的覆盖检查只针对契约规定的当前关卡必需实体。
5. **保持悬空引用检查**：任何非空 `sourceIntent` 都必须指向合法的设计实体。
6. **在昂贵生成前失败**：确定性身份错误应在资源生成、图片生成等下游成本发生之前被拒绝。
7. **使用真实产物验收**：通过针对性单测、集成测试与真实 E2E 证明修复有效。

### 2.2 非目标

本期不处理：

- 基于名称、描述或相似度的模糊身份匹配。
- 自动猜测错误的 `sourceIntent` 并静默修复。
- 重新设计 `GameDesignSpec` 或 `GameConfig` 的整体结构。
- 引入 `SceneLayoutSpec`、视觉布局编译或新的场景系统。
- 改变资源路由、素材提示词、图片生成模型或动画验收阈值。
- 修改成本账本、版本目录、失败运行编号等既有生命周期规则。
- 为通过测试而放宽输入校验或忽略 `empty-input`。
- 跨游戏项目的设计知识复用。

## 3. 核心契约

### 3.1 身份字段语义保持不变

| 字段 | 契约 |
|---|---|
| `Entity.id` | 运行时实体自身的身份标识 |
| `Entity.sourceIntent` | 运行时实体对应的设计实体 ID |
| `sourceIntent` 缺失 | 该运行时实体不声明设计实体归属；仅在契约允许的情况下合法 |
| 多个实体共享 `sourceIntent` | 允许，但每个实体都必须与所引用设计实体的语义兼容 |
| 非空 `sourceIntent` 指向不存在的 ID | 确定性错误 |
| 当前作用域内的必需设计实体没有运行时对应项 | 确定性错误 |

`sourceIntent` 不是名称字段，不是资源文件名，也不是运行时实体 ID 的别名。

### 3.2 必须增加语义兼容性验证

不能只验证：

```ts
designEntityIds.has(entity.sourceIntent)
```

还必须验证：

```ts
isCompatibleIdentity(designEntity, runtimeEntity)
```

上面的函数仅用于说明契约，不要求采用此函数名或接口形态。

实现必须基于仓库中已有的 `GameDesignSpec`、`GameConfig` 类型及明确的实体语义规则，建立确定性的兼容性判断。

**实施要求：**

1. 先审查现有设计实体分类、运行时 `kind` 联合类型及其实际用途。
2. 明确每种运行时实体类型允许指向哪些设计实体类别。
3. 对无法明确证明兼容的映射采取拒绝策略，而不是默认放行。
4. 不得使用实体名称相同、字符串包含关系或 LLM 自我解释作为通过依据。
5. 不得将所有 `interactables` 统一视为可接受任意 `goal`、`chest`、`switch` 等运行时实体的通用类别。
6. 如果现有设计规格缺少表达兼容性所需的信息，应先确定最小契约补充方案，并在实施前说明其影响；不得暗中引入推断规则。

兼容性矩阵应以仓库现有枚举和类型为准，不得凭空扩展实体类型。

### 3.3 结构性实体规则

结构性实体可以没有 `sourceIntent`，例如：

- 没有对应设计实体的地面或碰撞边界。
- 仅由关卡结构产生的出口或终点。
- 其他经现有契约明确允许的运行时辅助实体。

但必须遵守以下规则：

- 没有 `sourceIntent` 的结构性实体，不应被强行归属到一个无关设计实体。
- 一旦提供 `sourceIntent`，该引用必须有效且语义兼容。
- 不得因为实体类型看起来像结构性实体，就忽略其非空但错误的引用。
- 如果设计规格明确要求该实体具有设计身份，则必须按设计实体契约验真，不能再以结构性实体为由豁免。

**重要区别：**“允许没有归属”不等于“允许错误归属”。

### 3.4 合法的 1:N 映射

以下情况应继续合法：

一个设计实体可以对应多个运行时实体，例如同一个设计敌人在运行时拆分为多个实例。

```ts
const config = {
  entities: [
    { id: "enemy-a", kind: "enemy", sourceIntent: "scavenger" },
    { id: "enemy-b", kind: "enemy", sourceIntent: "scavenger" },
  ],
};
```

以上仅为概念示例，实际字段和类型以仓库现有契约为准。

验真要求：

- 每个运行时实体的映射分别通过语义兼容性检查。
- 不要求 `sourceIntent` 唯一。
- 不允许借助多个合法映射掩盖其他设计实体的缺失。
- 不允许一个正确映射为同一设计实体的实例，为另一个错误类型的实体背书。

## 4. 关卡作用域契约

### 4.1 先确定作用域来源

实现前必须沿调用链确认：

1. `compileRuntime` 如何选择 `levelId`。
2. `GameDesignSpec` 如何表示关卡与实体之间的关系。
3. 敌人、NPC、交互物和资源是全局定义、关卡局部定义，还是两者兼有。
4. 当前 `GameConfig` 是否明确记录自己所属的关卡。
5. QA 与身份审计分别使用哪一层级的设计规格。

优先使用已有的显式关卡关联信息。不得通过运行时实体名称、生成结果中是否出现某个实体等偶然特征推导关卡归属。

### 4.2 定义两种不同的覆盖范围

应在契约中区分：

**A. 当前关卡覆盖（Level Coverage）**

当前 `GameConfig` 必须覆盖当前关卡中被明确声明为必需的设计实体。

**B. 全局设计完整性（Global Integrity）**

整个设计规格中的实体定义及其关卡关联必须有效；但这不意味着每个关卡配置都必须包含所有全局设计实体。

全局完整性和单关卡覆盖不得混为一个检查。

### 4.3 关卡级验真规则

当项目包含多个关卡时：

- 当前关卡必需的设计实体未被映射：报错。
- 仅属于其他关卡、且不属于当前关卡必需范围的设计实体未出现在当前配置：不应因此报错。
- 全局设计实体引用无效、关卡关联无效等结构性错误：由明确的全局检查负责。
- 当前配置的实体引用了当前作用域之外的设计实体：必须依据既定的跨关卡引用规则判定，不能无条件通过，也不能未经定义就一律禁止。
- 如果现有规格无法区分全局实体与关卡局部实体，应先补齐最小必要的显式关联契约，再实施覆盖判断。

### 4.4 单关卡项目保持兼容

对于现有单关卡项目：

- 不得因为引入作用域概念而改变合法映射的结果。
- 不得要求用户额外维护重复的关卡身份清单。
- 如果当前设计规格没有显式的关卡级实体关联，必须明确其兼容策略。
- 兼容策略应可预测、可测试，不能用静默忽略错误替代作用域定义。

## 5. 实现要求

### 5.1 身份审计职责

在现有身份审计能力上补齐以下检查：

| 检查项 | 规则 | 失败级别 |
|---|---|---|
| 设计 ID 完整性 | 被引用的设计 ID 必须唯一且有效 | Error |
| 引用有效性 | 非空 `sourceIntent` 必须指向有效设计实体 | Error |
| 语义兼容性 | 运行时实体类型必须与被引用设计实体兼容 | Error |
| 关卡覆盖 | 当前关卡必需的设计实体必须被覆盖 | Error |
| 错误作用域 | 不得把其他关卡的实体错误计入当前关卡覆盖 | 按作用域契约判定 |
| 合法 1:N | 多个兼容运行时实体指向同一设计实体 | 不报错 |
| 无归属结构实体 | 符合豁免条件且没有 `sourceIntent` | 不报错 |

如果仓库已有对应检查，应扩展现有能力，避免重复实现两套相互矛盾的身份校验器。

### 5.2 审计接口

优先保持现有接口的最小改动。

如果关卡作用域无法从现有参数中可靠获取，应显式传入当前关卡标识或已经解析好的作用域信息，例如：

```ts
auditEntityIdentity(design, config, scope)
```

其中 `scope` 仅为示意，最终接口应由现有类型与调用链决定。

要求：

- 作用域信息必须来自确定性的上游数据。
- 不得通过默认选择“第一个关卡”掩盖调用方缺少关卡信息。
- 所有调用点都必须清楚自己执行的是全局完整性审计还是单关卡覆盖审计。
- 对外导出的接口、MCP/CLI 行为和序列化格式如有变更，须评估兼容性并遵守仓库现有变更审批规则。

### 5.3 错误信息

错误应可定位、可操作，至少包含：

- 运行时实体 ID。
- 当前关卡 ID（适用时）。
- `sourceIntent` 的值。
- 实际设计实体类别。
- 运行时实体类别。
- 拒绝原因。

例如：

```text
entity "gate" in level "level-1":
sourceIntent "chest" is incompatible with runtime kind "goal";
the referenced design entity is an interactable chest.
```

以上为示例文案，不要求固定英文或固定字符串。

错误信息不得只返回“身份校验失败”，也不得通过名称相似度给出未经验证的自动修复建议。

### 5.4 验真时机

错误身份映射必须在昂贵的下游资源生成之前被拒绝。

推荐顺序：

1. 读取设计规格及当前关卡信息。
2. 校验设计 ID、关卡关联和身份映射。
3. 对不合法的映射返回确定性错误。
4. 仅在校验通过后进入后续资源规划与生成阶段。

如果当前流水线的架构限制导致无法在 `compileRuntime` 之后、资源生成之前完成某项检查，应在 PR 中说明实际调用顺序，并选择最早可执行的确定性校验点。

不得为了提前失败而重复触发模型调用，也不得把确定性错误交给模型无限重采样。

## 6. 测试需求

### 6.1 单元测试：错误归属

必须新增以下测试：

| 场景 | 预期结果 |
|---|---|
| 运行时 `goal` 指向设计宝箱 `chest` | Error |
| 运行时敌人指向不兼容的设计资源 | Error |
| 运行时实体指向不存在的设计 ID | Error |
| 两个兼容敌人都指向同一个设计敌人 | 通过 |
| 合法结构性实体不提供 `sourceIntent` | 通过 |
| 结构性实体提供错误但真实存在的 `sourceIntent` | Error |
| 当前关卡必需设计实体完全没有运行时映射 | Error |
| 设计 ID 重复导致引用无法唯一解析 | Error |

具体类型组合以仓库实际类型为准；如果某种组合在类型层面不可能构造，测试应通过适当的 fixture 或输入校验边界覆盖，而不是为了测试而放宽生产类型。

### 6.2 单元测试：关卡作用域

必须至少覆盖：

1. 单关卡设计中的合法映射保持通过。
2. 两个关卡分别拥有不同的必需实体。
3. 关卡 A 不包含仅属于关卡 B 的实体时，A 的覆盖检查仍通过。
4. 关卡 A 缺少自身必需实体时，覆盖检查失败。
5. 关卡 B 的实体被错误引用时，按照明确的跨关卡规则拒绝或处理。
6. 全局设计完整性检查仍能发现无效设计 ID 或关卡关联。
7. 缺少必要关卡上下文时，不得静默回退为错误的全局覆盖模式。

### 6.3 集成测试：编译与 QA

必须验证：

- `compileRuntime` 的输出经过确定性身份校验。
- 身份校验失败时，下游资源生成不启动。
- QA 第 7 项继续使用 `sourceIntent` 进行设计与运行时关联。
- QA 不会因为某个 ID 存在，就把语义错误的实体映射当作正确映射。
- 合法 1:N 仍然可以通过 QA。
- 对结构性实体的合法豁免不会导致错误引用被忽略。

测试应检查错误类型、错误定位及下游是否执行；不应只断言返回值非空。

### 6.4 回归测试

必须覆盖 V1 已建立的行为：

- `Entity.id` 仍然表示运行时身份。
- `sourceIntent` 仍然表示设计身份。
- 设计实体覆盖检查仍然有效。
- 悬空引用检查仍然有效。
- 合法 1:N 映射不被误拒。
- 结构性实体可以在符合规则时不带 `sourceIntent`。
- 现有单关卡 fixture 不因新增作用域参数而发生无意破坏。

## 7. 真实 E2E 验收

### 7.1 基线

使用 V1 已有的真实游戏项目和测试素材，保留可复现的运行记录。

重点核实此前观察到的两类问题：

- `gate` / `goal` 错误归属 `chest` 的映射不再通过。
- `plan-assets` 阶段出现的 `empty-input` 不会被身份修复掩盖。

### 7.2 必须执行的验收场景

**E2E-A：错误归属拒绝**

- 使用包含真实设计规格的输入。
- 构造或注入一个引用存在但语义不兼容的身份映射。
- 验证流水线在下游资源生成前失败。
- 验证错误明确指出运行时实体、设计引用及不兼容原因。
- 验证没有为该错误启动后续图片生成等付费步骤。

**E2E-B：合法身份映射通过**

- 使用合法设计规格和运行时配置。
- 验证当前关卡必需实体覆盖完整。
- 验证合法的 1:N 映射可以通过。
- 验证结构性实体不必伪造设计身份。
- 验证 QA 第 7 项使用正确身份关系并通过。

**E2E-C：多关卡作用域**

- 使用至少两个关卡的设计规格。
- 分别编译两个关卡。
- 验证每个关卡只需覆盖其契约规定的必需实体。
- 验证全局设计完整性检查没有被削弱。
- 验证错误的跨关卡引用按既定规则被拒绝。

如果现有真实 E2E fixture 只有一个关卡，应增加最小多关卡 fixture，而不是把单关卡成功当作多关卡验收。

### 7.3 `empty-input` 的独立处理

若 `plan-assets` 再次报错 `empty-input`：

1. 保存完整失败日志与运行目录。
2. 确认输入为空的具体节点、数据来源及失败阶段。
3. 区分身份审计错误与资源规划输入错误。
4. 不得通过跳过身份审计、提供虚假资源或放宽输入校验让流水线继续。
5. 如发现独立缺陷，建立单独问题或后续任务；仅当其确实阻塞本期验收时才纳入修复范围。

### 7.4 成功判据

- 单元测试、集成测试和 E2E 均通过。
- 错误归属场景明确失败。
- 合法映射与合法结构性实体仍然通过。
- 两个关卡的作用域检查结果符合契约。

## 11. 最终裁定原则

本期的核心不是让更多配置通过，而是让**通过的身份关系真正可信**。

身份校验必须回答两个独立的问题：

1. **归属是否正确？** 引用的设计实体不仅存在，而且与运行时实体语义兼容。
2. **覆盖是否合理？** 当前关卡覆盖自己的必需设计实体，而不是被迫覆盖所有关卡的实体。

只有同时满足这两点，`sourceIntent` 才能成为后续 QA、资源映射与游戏验证可信赖的身份契约。

**建议实施顺序：先完成 Phase 0 的契约裁定，再依次实施 Phase 1、Phase 2，最后进行真实 E2E 验收。** 不应先重跑大量完整生成任务，再根据偶然结果反推身份规则。
