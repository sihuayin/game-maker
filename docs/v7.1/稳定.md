# P0 需求：保持 GameDesignSpec 实体 ID 在编译链路中的稳定性

> **项目：** game-maker  
> **优先级：** P0  
> **类型：** 编译链路正确性修复  
> **建议阶段：** VDC E2E 后的第一项改进  
> **状态：** 待实施  
> **核心目标：** 从 GameDesignSpec 到 GameConfig 的编译过程中，保持实体身份稳定，使 VDS 与 GameConfig 能够基于同一个实体 ID 完成 QA 关联。

---

## 1. 背景

game-maker 的目标是根据用户提供的游戏风格图与游戏意图，自动完成：

```text
用户需求
  ↓
Visual World Spec
  ↓
Game Intent Spec
  ↓
GameDesignSpec
  ↓
Asset Recipe
  ↓
资源生成
  ↓
GameConfig
  ↓
游戏构建
  ↓
QA 验收
```

VDC（Visual Design Compiler）作为视觉设计编译链路，能够根据 GameDesignSpec 生成确定性的视觉布局，并输出 VDS、SVG 和 PNG 等产物。

在最近一次真实 E2E 验收中，整个创建流程已经能够执行到 QA 阶段，但 QA 暴露出实体身份不一致的问题：

- GameDesignSpec 中存在明确的实体 ID。
- 编译 GameConfig 时，部分实体 ID 被重新命名。
- VDS 保留原始设计实体 ID。
- QA 根据实体 ID 关联 VDS 与 GameConfig 时，无法找到对应实体。
- 最终出现多个实体关联失败，导致 QA 未通过。

例如，设计阶段的实体 ID 可能是：

```text
chest-ruined-city
enemy-wasteland
scrap-resource
```

而编译后的 GameConfig 中可能变成：

```text
chest-1
enemy-1
pickup-1
pickup-2
```

这不是视觉布局问题，也不是 QA 判据过严，而是编译链路破坏了实体身份。

**实体 ID 是跨阶段关联的稳定契约，不应在编译过程中被无意重写。**

---

## 2. 需求目标

### 2.1 必须实现

1. GameDesignSpec 中的实体 ID 能稳定传递到 GameConfig。
2. VDS 的 `sourceIntent` 与 GameConfig 实体的 `id` 可以通过精确匹配建立关联。
3. 编译过程不得因为实体类别、数组顺序、显示名称或生成顺序而重写原始实体 ID。
4. 如果确实需要运行时 ID，必须与设计实体 ID 明确分离。
5. 对实体 ID 的传递、重复、缺失、重命名等行为建立自动化测试。
6. 修复后，原有 QA 身份关联检查继续保持严格，不通过放宽校验来掩盖编译错误。

### 2.2 预期结果

对于同一份有效 GameDesignSpec：

```text
GameDesignSpec
  ├── entity.id = chest-ruined-city
  ├── entity.id = enemy-wasteland
  └── entity.id = scrap-resource
```

编译结果应满足：

```text
GameConfig
  ├── entity.id = chest-ruined-city
  ├── entity.id = enemy-wasteland
  └── entity.id = scrap-resource
```

VDS 应能够通过：

```text
VDS.sourceIntent === GameConfig.entity.id
```

找到对应实体。

---

## 3. 非目标

本需求不包含以下工作：

- 不扩展 VDC 的布局策略。
- 不从 `world.structure`、`levels.layout` 等自由文本推导实体身份。
- 不修改 GameDesignSpec 的实体分类体系。
- 不要求 VDS 的 `role` 与 GameConfig 的 `kind` 完全一致。
- 不通过模糊匹配、名称匹配或数组位置匹配来补偿 ID 丢失。
- 不引入跨游戏项目的实体 ID 复用机制。
- 不修改资源生成提示词或图像模型选择策略。
- 不增加主观视觉质量评分或新的付费 QA 阶段。

---

## 4. 核心设计原则

### 4.1 设计实体 ID 是身份来源

GameDesignSpec 中的实体 ID 表示设计层实体的稳定身份。

下游阶段可以新增字段、补充运行时信息或生成资源引用，但不得随意改变实体身份。

```text
GameDesignSpec.entity.id
          │
          ├── VDS.sourceIntent
          │
          └── GameConfig.entity.id
```

这三个字段应当指向同一个设计实体。

### 4.2 视觉角色不等于玩法类型

VDS 的 `role` 表示视觉呈现角色，GameConfig 的 `kind` 表示玩法实体类型。

例如：

```text
VDS.role = hazard
GameConfig.kind = hazard
```

二者可能一致，但不能据此建立身份关系。

身份关系必须由 ID 建立：

```text
VDS.sourceIntent = GameConfig.entity.id
```

角色与类型的合理性校验应由独立 QA 规则完成。

### 4.3 不允许通过降低 QA 严格性修复问题

错误方案：

```text
如果找不到精确 ID
  → 尝试按名称匹配
  → 尝试按数组位置匹配
  → 尝试按 role/kind 匹配
```

这会使实体关联产生不确定性，并掩盖真正的编译缺陷。

正确方案：

```text
如果设计实体 ID 在编译过程中丢失
  → 修复编译过程
  → 保留严格身份校验
```

---

## 5. 功能需求

### P0-01：保持设计实体 ID

**需求描述**

检查 GameDesignSpec 到 GameConfig 的编译链路，确保设计实体 ID 被直接传递，不因运行时编译逻辑重新生成。

**要求**

- 设计实体 ID 应作为编译输入的稳定字段。
- 生成 GameConfig 时，优先使用设计实体 ID。
- 禁止根据 `kind`、实体数组序号或默认命名规则覆盖设计实体 ID。
- 不得因多个实体具有相同 `kind` 而发生 ID 冲突。
- 对已有有效实体 ID，不得静默替换。

**验收标准**

- 输入 `chest-ruined-city`，输出仍为 `chest-ruined-city`。
- 输入 `enemy-wasteland`，输出仍为 `enemy-wasteland`。
- 输入 `scrap-resource`，输出仍为 `scrap-resource`。
- 编译结果与输入实体顺序无关。
- 同一输入重复编译，实体 ID 保持一致。

### P0-02：区分设计 ID 与运行时 ID

**需求描述**

如果运行时系统确实需要独立 ID，应明确区分设计实体 ID 与运行时实体 ID。

建议结构：

```ts
interface GameEntity {
  id: string;
  runtimeId?: string;
  kind: EntityKind;
}
```

其中：

- `id`：设计实体身份，跨编译阶段稳定。
- `runtimeId`：可选的运行时身份，仅在确有需要时使用。
- `runtimeId` 不得替代 VDS 与 GameConfig 之间的设计身份关联。

具体字段名应以仓库现有合同为准，不应在没有必要的情况下新增字段。

**验收标准**

- 设计实体 ID 与运行时 ID 的语义明确。
- 运行时 ID 不会覆盖设计实体 ID。
- VDS 关联 QA 继续使用设计实体 ID。

### P0-03：重复 ID 检查

**需求描述**

确保 GameDesignSpec 中的实体 ID 唯一。

如果输入包含重复 ID，应在编译前或合同校验阶段明确失败，不允许静默覆盖或自动改名。

错误信息应包含：

- 重复实体 ID。
- 所属阶段。
- 可定位的实体路径或索引。

示例：

```text
Duplicate entity id: chest-ruined-city
Path: GameDesignSpec.entities[2]
```

**验收标准**

- 有效唯一 ID 输入正常通过。
- 重复 ID 输入明确失败。
- 不发生自动重命名。
- 错误能够定位到具体实体。

### P0-04：缺失 ID 检查

**需求描述**

设计实体缺少 ID 时，不允许编译器静默生成一个与设计实体身份混淆的 ID。

应根据现有合同确定处理方式：

- 如果 ID 是必填字段：在合同校验阶段失败。
- 如果现有设计允许缺省 ID：明确由哪个阶段分配 ID，并保证后续阶段使用同一个 ID。

不允许在 GameDesignSpec、VDS、GameConfig 各自独立生成 ID。

**验收标准**

- 缺失 ID 的处理方式明确且一致。
- 不存在跨阶段独立生成 ID 的情况。
- 错误或生成行为可测试、可复现。

### P0-05：保持 QA 精确身份关联

**需求描述**

保留 VDS 与 GameConfig 的精确 ID 关联检查。

```ts
vdsObject.sourceIntent === gameConfigEntity.id
```

当 VDS 中存在带 `sourceIntent` 的对象，但 GameConfig 中找不到对应实体时，应报告错误。

错误信息应至少包含：

```text
sourceIntent
VDS object
关联失败原因
```

**验收标准**

- ID 精确匹配时通过。
- ID 不匹配时失败。
- 不使用模糊匹配。
- 不使用数组位置匹配。
- 不因 `role` 与 `kind` 不同而直接判定身份不一致。

## 6. 自动化测试要求

### 6.1 单元测试

| 测试场景 | 预期结果 |
|---|---|
| 单个实体 ID 传递 | ID 保持不变 |
| 多个不同 kind 的实体 | 所有 ID 保持不变 |
| 多个相同 kind 的实体 | ID 不冲突、不重写 |
| 改变实体数组顺序 | ID 不变化 |
| 重复编译相同输入 | 输出 ID 一致 |
| 输入重复 ID | 明确失败 |
| 输入缺失 ID | 按合同规定失败或统一分配 |
| VDS 与 GameConfig 精确 ID 匹配 | QA 通过 |
| VDS 与 GameConfig ID 不匹配 | QA 失败 |
| 仅 role 与 kind 不一致 | 不应误判为身份错误 |

### 6.2 集成测试

建立一份包含以下实体的 GameDesignSpec fixture：

```text
player
enemy-wasteland
chest-ruined-city
hazard-spike-rubble
scrap-resource
```

验证：

1. GameDesignSpec 编译为 GameConfig。
2. 所有设计实体 ID 保持不变。
3. VDS 的 `sourceIntent` 与 GameConfig 实体 ID 一一关联。
4. QA 不产生由 ID 重写导致的身份错误。
5. 资源引用和玩法类型仍然有效。
6. 原有构建、版本目录和产物规则不受影响。

### 6.3 E2E 验收

使用真实游戏创建流程执行一次完整 E2E。

验收记录至少包括：

- 输入需求与风格图。
- 使用的命令。
- 退出码。
- run 路径。
- GameDesignSpec 实体 ID 清单。
- VDS `sourceIntent` 清单。
- GameConfig 实体 ID 清单。
- QA 结果。
- 失败账本记录（如果发生付费调用）。

**本需求的 E2E 目标是消除实体 ID 关联错误，不代表整个游戏已经满足所有玩法、资源和视觉质量标准。**

## 7. 实施步骤

### Step 1：定位 ID 重写源头

检查以下阶段：

```text
GameDesignSpec
  ↓
compileRuntime / GameConfig 编译
  ↓
GameConfig entities
```

重点查找：

- 根据 kind 生成 ID 的逻辑。
- 基于数组索引生成 ID 的逻辑。
- 运行时实体映射。
- 实体归一化、重命名或复制逻辑。
- 对 ID 字段进行覆盖的默认值处理。

### Step 2：修复 ID 传递

原则：

```text
已有设计 ID → 原样保留
```

只有当当前合同明确允许缺省 ID 时，才考虑统一的 ID 分配逻辑。

不要在多个编译阶段重复生成 ID。

### Step 3：补充单元测试

先覆盖 ID 稳定性、重复 ID、缺失 ID、实体顺序变化等场景。

### Step 4：补充集成测试

验证 GameDesignSpec、VDS、GameConfig 的 ID 一致性。

### Step 5：执行 E2E

使用当前稳定的游戏创建流程，确认原有身份错误消失，并记录其他剩余 QA 错误。

---

## 8. 完成定义（Definition of Done）

本需求只有同时满足以下条件才算完成：

- [ ] GameDesignSpec 到 GameConfig 的实体 ID 保持稳定。
- [ ] 不存在根据 kind 或数组顺序重写设计 ID 的逻辑。
- [ ] 如有运行时 ID，已与设计 ID 明确区分。
- [ ] 重复 ID 有明确失败行为。
- [ ] 缺失 ID 有明确且一致的处理行为。
- [ ] VDS 与 GameConfig 使用精确 ID 关联。
- [ ] QA 没有通过模糊匹配来掩盖 ID 错误。
- [ ] 单元测试通过。
- [ ] 集成测试通过。
- [ ] 至少一次真实 E2E 验收通过身份关联检查。
- [ ] 不影响现有产物、版本目录和失败账本规则。
- [ ] 文档与实现一致。

---

## 9. 后续优先级

本需求完成后，再进入以下工作：

| 优先级 | 功能 | 原因 |
|---|---|---|
| P0 | 实体 ID 稳定性 | 当前 E2E 暴露的确定性编译问题 |
| P1 | 资源宽高比与动画验收改进 | 解决资源与设计意图不匹配的问题 |
| P2 | SceneLayoutSpec 中间层 | 为复杂布局提供结构化输入，避免解析自由文本 |
| P3 | 主观视觉质量评估 | 在基础编译和资源链路稳定后提升整体品质 |

**本轮不建议同时扩展 VDC 的布局能力。** 先修复实体身份契约，让已有 VDS、GameConfig 和 QA 能够正确协作，再扩大视觉布局表达能力。
