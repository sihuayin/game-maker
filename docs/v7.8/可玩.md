# PRD：Level Playability V1（关卡可玩性验证）

- **项目**：game-maker V2
- **需求编号**：P1-Level-Playability-V1
- **优先级**：P1 / 最高优先级
- **状态**：已批准进入独立实施阶段
- **实施分支**：`p1/level-playability-v1`
- **实施范围**：LP-00 ～ LP-07
- **实施原则**：串行实施、零付费、证据驱动、每票一个 commit
- **强制复核点**：LP-00、LP-02、LP-03

---

## 1. 背景与问题

game-maker 已经具备从游戏意图、关卡配置、资源生成、Demo 构建到 QA、发布和试玩验证的生产链路。

但现有验证仍存在一个重要缺口：

**配置合法、资源完整、机制存在，并不代表生成的关卡真正可玩。**

例如：

1. 玩家出生点被地形包围，无法移动。
2. 宝箱存在，但被墙体封锁，玩家无法接近。
3. 收集物位于不可到达的平台。
4. 危险区域封锁唯一通路，玩家无法通过。
5. 危险区域存在周期变化，但玩家没有任何安全通过窗口。
6. 玩家可以收集全部必需物品，却无法到达终点。
7. 关卡中的对象分别合法，但组合后形成无法通关的布局。

现有 QA 和试玩测试能够发现部分问题，但缺少一个确定性、可重复、可解释的关卡可玩性静态验证层。

因此，需要建设 Level Playability V1。

## 2. 产品目标

建立一套面向当前 Demo Runtime 语义的关卡可玩性分析能力。

输入为现有 GameConfig、关卡空间数据及 Runtime 相关信息。

输出为可解释的可玩性分析结果，识别有确定性证据支持的不可玩问题，并在证据不足时保持谨慎。

### 2.1 核心目标

- 检测玩家出生位置是否被静态几何阻塞。
- 检测必需对象是否存在可达路径。
- 检测地形、平台和障碍物造成的确定性空间阻断。
- 检测危险机制是否封锁必要路径。
- 检测周期性危险是否存在安全通过窗口。
- 检测收集必要物品后是否能够到达终点。
- 将确定性判据接入现有 Pipeline、deterministic QA 和 Publish Gate。
- 建立历史语料及负例回归测试，控制误报。

### 2.2 非目标

本项目不是：

- 新的游戏 Runtime。
- 自动修复关卡布局的系统。
- 通用物理引擎或完整物理模拟器。
- AI 自动试玩系统的替代品。
- 新的游戏机制或 EntityKind。
- 通用多游戏类型关卡求解器。

V1 只解决当前已支持 Demo Runtime 中能够由现有源码语义和几何模型可靠判断的问题。

## 3. 核心设计原则

### 3.1 三态结果模型

所有判据必须采用三态结果，禁止将无法判断的问题直接认定为不可玩。

| 状态 | 含义 | Pipeline 行为 |
|---|---|---|
| `PROVEN_UNPLAYABLE` | 有确定性证据证明关卡不可玩 | 阻断 |
| `INSUFFICIENT_EVIDENCE` | 当前算法或 Runtime 证据不足以判断 | 不阻断 |
| `NO_PROVEN_BLOCKER` | 已执行的判据未发现确定性阻断 | 不阻断 |

重要约束：

`NO_PROVEN_BLOCKER` 不等于已经证明关卡可玩。

它只表示已执行的判据没有找到确定性阻断证据。

### 3.2 证据优先

每个确定性错误都必须能够说明：

- 哪个对象或区域存在问题。
- 使用了哪些几何信息。
- 采用了什么判定规则。
- 为什么该规则足以证明阻断。
- 对应的测试用例是什么。

禁止使用缺乏证据的启发式规则直接阻断关卡。

### 3.3 Runtime 语义优先

所有空间分析必须以 `packages/demo` 中真实 Runtime 实现为准。

不得仅根据配置字段名称、设计文档或假设推断碰撞行为。

Runtime 语义无法确认时，结果必须降级为 `INSUFFICIENT_EVIDENCE`。

## 4. 功能需求

### 4.1 LP-00：Runtime 语义核验

**目标：建立可信的 Runtime 语义证据档案。**

在实现几何判据之前，先从 `packages/demo` 源码核实以下四项语义。

| 编号 | 核验内容 | 必须回答的问题 |
|---|---|---|
| P1 | 资源尺寸、锚点与碰撞几何 | 资源尺寸、锚点如何影响实体实际空间占用？ |
| P2 | EntityKind 与 body | 不同 EntityKind 的 body 是否实际生效？具体规则是什么？ |
| P3 | Chest 交互范围 | 宝箱实际交互范围如何计算？ |
| P4 | 出生点与静态几何 | 出生点与地形重叠时，Runtime 实际如何处理？ |

**交付物：**

- Runtime 源码定位与证据记录。
- P1～P4 的实际语义说明。
- 每项语义对应的源码位置及测试证据。
- 无法确认的语义及其影响范围。
- LP 后续算法可使用的语义边界。

**验收标准：**

1. P1～P4 每项均有源码证据，或明确标记为 `INSUFFICIENT_EVIDENCE`。
2. 不得用推测补齐缺失的 Runtime 语义。
3. 几何算法必须以核验后的语义为基础。
4. 完成后进行第一次强制复核。

**硬性要求：**

如果关键 Runtime 语义缺乏源码证据，相关判据不得输出 `PROVEN_UNPLAYABLE`。

### 4.2 LP-01：基础几何模型

**目标：建立与 Runtime 一致的空间分析基础。**

实现：

1. AABB 碰撞区域模型。
2. 实际几何重叠判定。
3. Solid 静态几何模型。
4. 玩家可行走路径边。
5. 玩家下落路径边。
6. 出生点、地形、实体之间的空间关系。
7. 统一碰撞语义入口。

**核心要求：**

- 使用真实碰撞区域，而不是仅使用图片外接尺寸。
- 处理锚点与碰撞偏移。
- 明确哪些对象属于 Solid。
- 区分可行走、可下落和不可通过的空间关系。
- 不允许不同判据各自实现一套互相矛盾的碰撞规则。

**验收标准：**

- AABB 相交、包含、边界接触等基础用例通过。
- Solid 阻挡用例通过。
- Walk/Fall 可达关系用例通过。
- 与 LP-00 确认的 Runtime 语义一致。
- 不引入未经确认的物理行为。

### 4.3 LP-02：空间可达性分析

**目标：发现对象存在但玩家无法到达的确定性空间问题。**

重点判据：

| 判据 | 检测内容 |
|---|---|
| Spawn in terrain | 出生点与不可穿越地形发生确定性冲突 |
| Chest unreachable | 宝箱无法通过实际交互范围接近 |
| Pickup blocked | 必需拾取物被静态几何阻断 |
| Chest blocked | 宝箱被静态几何阻断 |
| Gate blocked | 必需通行目标被静态几何阻断 |

**分析方法：**

1. 构建玩家空间可达图。
2. 使用实际碰撞尺寸和锚点。
3. 依据 Walk/Fall 关系建立可达边。
4. 以出生点为搜索起点。
5. 判断目标对象是否存在有效可达路径。
6. 对于无法可靠建模的情况，输出 `INSUFFICIENT_EVIDENCE`。

**验收标准：**

- 能够识别确定性不可达的 Chest、Pickup、Gate。
- 能够识别出生点与地形的确定性冲突。
- 合法的复杂布局不能被简单几何启发式误杀。
- 必须包含正例、反例和边界测试。
- 空间判据不能因为算法简化而误判合法关卡。

**强制复核点：**

LP-02 完成后必须进行第二次强制复核。

复核通过后，允许创建 Draft PR。

### 4.4 LP-03：机制可通行性分析

**目标：识别机制组合导致的确定性通路阻断。**

重点判据：

| 判据 | 含义 |
|---|---|
| `PATH_BLOCKED` | 必要路径被危险区域或机制确定性阻断 |
| `PATH_NO_SAFE_WINDOW` | 周期性危险不存在可证明的安全通过窗口 |

**分析范围：**

- 危险区域与必要路径的空间关系。
- 危险区域对可达图的影响。
- 周期性危险的激活周期。
- 玩家通过路径所需的时间条件。
- 是否存在满足 Runtime 语义的安全通过窗口。

**设计原则：**

- 不得将危险区域存在直接等同于不可通行。
- 不得将存在周期性危险直接等同于没有安全窗口。
- 必须基于已核实的机制语义进行判定。
- 对缺乏足够时间或空间证据的情况，返回 `INSUFFICIENT_EVIDENCE`。

**验收标准：**

- 能识别危险区域确定性封锁唯一必要路径的情况。
- 能识别不存在安全窗口的周期性危险情况。
- 合法危险机制不应被错误阻断。
- 所有阻断结果均可解释和复现。

**强制复核点：**

LP-03 完成后必须进行第三次强制复核。

### 4.5 LP-04：关卡完成性分析

**目标：验证收集必要物品后是否仍能到达终点。**

仅验证单个对象可达是不够的。

例如：

玩家能够到达所有拾取物，但收集完成后仍然无法到达终点。

因此需要考虑收集状态。

**分析方法：**

- 在空间可达图上增加收集状态。
- 将必要收集物纳入状态空间。
- 搜索从出生点到终点的合法路径。
- 路径必须满足必要物品收集要求。
- 使用 Mask DP 或等价的状态搜索方法。
- V1 必须将必要收集物数量限制在 `k ≤ 12`。

**验收标准：**

- 能识别所有必要物品可达但最终无法通关的情况。
- 能识别完整收集后存在通关路径的情况。
- 搜索状态和边界条件正确。
- 超出可靠计算范围时返回 `INSUFFICIENT_EVIDENCE`。
- 不允许通过忽略收集状态来宣称关卡可完成。

### 4.6 LP-05：Pipeline 集成

**目标：让可玩性判据成为正式生产流程的一部分。**

实现统一入口：

`auditPlayability`

接入：

1. 现有 Pipeline。
2. deterministic QA。
3. Publish Gate。

**集成规则：**

| 结果 | Pipeline | Publish Gate |
|---|---|---|
| `PROVEN_UNPLAYABLE` | 确定性失败 | 阻断发布 |
| `INSUFFICIENT_EVIDENCE` | 保留诊断 | 不因该结果单独阻断 |
| `NO_PROVEN_BLOCKER` | 继续流程 | 不阻断 |

**重要约束：**

- 不新增 QA 第 8 条。
- 不改变现有 QA 条目数量。
- 不新增 CLI 参数。
- 不新增 MCP 参数。
- 不新增持久化 Playability Schema。
- 不改变 Runtime 行为。
- 不允许 Publish Gate 绕过已有确定性失败。

### 4.7 LP-06：历史语料与负例验收

**目标：证明新判据具有实际价值，同时控制误报。**

必须使用冻结的历史语料和研究阶段的合成矩阵进行回归。

研究阶段已知数据：

| 项目 | 数量 |
|---|---:|
| 历史唯一配对 | 96 |
| 唯一配置 | 20 |
| 合成矩阵 | 39 |
| 确定性不可玩 | 17 |
| 未发现阻断 | 18 |
| 证据不足 | 4 |

已有研究结果：

- 空间判据历史新增误报：0。
- 机制 A 合法设计误伤：0。
- 机制 A 历史语料识别出 3 条真实缺陷。

以上是研究阶段基线，不是实施完成后的自动通过结论。

**验收要求：**

1. 冻结语料全部回归。
2. 39 例矩阵全部执行。
3. 真实缺陷能够被对应判据识别。
4. 合法设计不得出现不可解释的误阻断。
5. 证据不足案例不得被强行归类为不可玩。
6. 对所有新增误报进行根因分析。

**最终原则：**

宁可将无法确定的情况归类为 `INSUFFICIENT_EVIDENCE`，也不能为了提高检测率牺牲确定性判据的可信度。

### 4.8 LP-07：最终收口

**目标：形成可审查、可复现、可回退的完整交付。**

交付内容：

- 完整实现代码。
- 全部自动化测试。
- 历史语料回归报告。
- 39 例矩阵验收报告。
- Runtime 语义证据档案。
- 判据结果及误报分析。
- Pipeline 集成证据。
- 版本与 commit 记录。
- 已知限制和回退说明。

完成后：

- 将 Draft PR 转为正式 PR。
- 提供完整验收结论。
- 不自动合并。
- 不推送 main。

## 5. 技术边界与约束

### 5.1 允许的修改

- `packages/demo` 之外的可玩性分析实现。
- 必要的纯函数、几何算法和图搜索实现。
- 对现有 Pipeline 的加法式集成。
- 测试、历史语料回归和诊断报告。
- 已批准范围内的 C1 加法导出。

### 5.2 明确禁止

| 类别 | 禁止事项 |
|---|---|
| Runtime | 修改 Runtime 游戏行为 |
| Entity | 新增 EntityKind |
| Motion | 新增 Motion |
| Mechanic | 新增游戏机制 |
| Contract | 新增持久化 Playability Schema |
| QA | 新增第 8 条 QA |
| CLI | 新增 CLI 参数 |
| MCP | 新增 MCP 参数 |
| Dependencies | 未经批准新增依赖 |
| Paid API | 调用付费模型、生图或其他付费服务 |
| Workflow | 自动合并 PR 或推送 main |

### 5.3 架构要求

- 尽量采用纯函数实现判据。
- 统一空间几何语义。
- 判据不得直接修改输入配置。
- 不允许将诊断结果伪装成配置修复。
- 结果必须具有确定性和可重复性。
- 现有 `run/vN` 和 `pack/site/vN` 版本化规则保持不变。
- 不得覆盖已有交付产物。

## 6. 实施与代码管理策略

### 6.1 分支

从当前受保护的 `main` 创建：

`p1/level-playability-v1`

不得直接在 main 开发。

### 6.2 Commit 策略

LP-00 至 LP-07 每票一个独立 commit。

要求：

- 每票完成后先执行对应测试。
- commit 内容只包含当前阶段范围。
- 不将未完成工作混入其他阶段。
- 每个 commit 能够独立审查和定位问题。

### 6.3 强制复核

| 阶段 | 复核内容 | 通过后允许 |
|---|---|---|
| LP-00 | Runtime 语义是否有充分源码证据 | 进入几何实现 |
| LP-02 | 空间判据是否可靠、无明显误报 | 创建 Draft PR |
| LP-03 | 机制判据是否符合真实机制语义 | 进入完成性分析 |

复核未通过时，必须暂停后续阶段，先解决问题。

### 6.4 付费策略

全程零付费。

不得：

- 调用付费 LLM。
- 调用付费图像生成 API。
- 以测试名义产生付费请求。
- 擅自扩大 API 预算。

## 7. 全局验收标准

LP-V1 必须同时满足以下条件：

| 编号 | 验收项目 | 通过标准 |
|---|---|---|
| AC-01 | Runtime 语义 | P1～P4 有源码证据或明确降级 |
| AC-02 | 几何模型 | AABB、Solid、Walk/Fall 测试通过 |
| AC-03 | 空间可达性 | 能识别确定性不可达对象 |
| AC-04 | 机制可通行性 | 能识别确定性路径阻断与无安全窗口 |
| AC-05 | 关卡完成性 | 能验证必要收集后到达终点 |
| AC-06 | 三态模型 | 不将证据不足错误判定为不可玩 |
| AC-07 | Pipeline | 确定性不可玩能够阻断发布 |
| AC-08 | 历史回归 | 冻结语料及 39 例矩阵完成验收 |
| AC-09 | 误报控制 | 不存在未解释的新增误阻断 |
| AC-10 | 工程质量 | 构建、类型检查、测试通过 |
| AC-11 | 范围约束 | 无未经批准的 Runtime/Contract/CLI/MCP 扩展 |
| AC-12 | 交付审查 | 正式 PR、完整证据和回退说明齐全 |

**注意：** `NO_PROVEN_BLOCKER` 不是“关卡已被证明可玩”。最终报告必须保留该语义区别。

## 8. 风险与应对

| 风险 | 影响 | 应对策略 |
|---|---|---|
| Runtime 语义不完整 | 几何算法可能误判 | LP-00 先行，证据不足就降级 |
| AABB 模型过于简化 | 合法关卡被阻断 | 统一几何语义，使用反例测试 |
| Walk/Fall 模型不完整 | 路径搜索错误 | 明确算法适用边界 |
| 危险机制时间模型不准确 | 错误判定无安全窗口 | 只使用已确认的机制语义 |
| 状态空间膨胀 | 完成性分析耗时 | V1 限制 `k ≤ 12` |
| 历史语料覆盖不足 | 隐藏误报 | 保留负例和证据不足案例 |
| 判据与发布流程不一致 | 绕过阻断 | LP-05 明确接入 deterministic 和 Publish Gate |

## 10. 产品价值

LP-V1 的核心价值不是让 game-maker 生成更多关卡，而是让系统能够识别自己生成的关卡中，哪些问题有证据证明不可玩，哪些问题暂时无法判断。

完成后，game-maker 将从：

**能够生成游戏内容、检查配置合法性、执行试玩**

进一步提升为：

**能够基于真实 Runtime 语义，对关卡空间、机制通路和最终通关条件进行确定性验证。**

这是提升自动生成游戏交付可信度的关键基础设施。

**最终实施决策：直接从 LP-00 开始，严格按 LP-00～LP-07 串行执行，不重新打开已批准的需求范围。**
