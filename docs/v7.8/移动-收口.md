### §1.4 fixture 边界

1. fixture 新建**只经本包 FIX 单元**（§5.1）授权与生产；其他单元不得新建 fixture。
2. FIX 前置 = 收口包签署 + 可行性评审 PASS；三案例须在 I-05 消费前完成授权、生产、独立复核与签署。

4. FIX 判定 `INFEASIBLE` 或实现失败 ⇒ I-05 与 closure 均为 `INCOMPLETE`，DoD「Pipeline 真实流程验收通过」保持未勾选。

## §3 授权模型

1. 本包由用户签署后建立**逐单元申请依据**；签署不授权任何单元，不授权 fixture 工作，不改变 gate。
2. 每个单元实施前写独立增量授权记录，字段固定：**单元 / 范围 / 允许文件白名单（精确路径或 glob）/ 只读输入 / 证据落点 / 复核报告路径 / STOP / 回滚目标 SHA / 有效期 / 不触碰的 out-of-scope 项 / 用户签署栏**。
3. 「不触碰的 out-of-scope 项」必须从 §1.1 表中逐条引用与该单元相关的行，不得只写「遵守总包范围」；授权人须在签署前看到本单元的禁止动作。
4. 增量授权记录落点：`.scratch/level-playability-v1.1-closure/reports/<UNIT>-incremental-authorization.md`，用户签署后 docs-only PR 合入 `main`；Ledger「增量授权状态」列引用它。
5. 有效期：至该单元 Ledger 行闭合，或用户显式撤回。
6. 每个单元固定九步：①增量授权记录 → ②用户签署 → ③docs-only PR → ④从更新后的 `main` 切实施分支（PU-C5 为 audit 分支）→ ⑤实施 / 测试 / 证据 → ⑥fresh 独立复核逐项 `PASS / FAIL / NOT_RUN` → ⑦用户签署 → ⑧合并 / 归档 → ⑨独立 Ledger 行。
7. 白名单只能由单元 brief 收窄；需要放宽 ⇒ STOP + HITL。
8. Phase-1 / Phase-2 的授权记录已耗尽，收口单元不得引用。
9. 越界检查有两个门：开工前看授权记录是否明确排除相关事项；复核时看实际改动是否遵守授权与白名单。任一门不一致 ⇒ STOP + HITL。

## §5 I-05 · Pipeline 验收 + 最终收口报告

### §5.1 FIX · I-05 真实时序案例 fixture

**性质**：产品相邻（可能新增 `fixtures/**`）的独立授权单元；须有自己的增量授权、白名单、复核、签署与 Ledger 行。

**前置**：收口包签署 + 可行性评审 PASS（现有 pack 能否表达 gate / goal / 单 X 轴 mover；goal 是否落在 x 走廊内；是否需要新 pack 版本）。

**必须交付**：
- **NB witness**：单 X 轴 mover 存在可利用安全窗口 ⇒ `NO_PROVEN_BLOCKER`（窗口连续性 + 玩家通行时间）。
- **PU witness**：正宽度永久封锁门、全周期覆盖、无垂直规避 ⇒ `PROVEN_UNPLAYABLE`；必须挂 PU-C5 条件 5 证据或独立证明。
- **IE 负例**：关键证据不足 ⇒ `INSUFFICIENT_EVIDENCE`，不得提升。
- 每个案例：真实 pack + manifest；至少一条正式流程（`create` / `build` / `publish-gate` / `qa-report`）完整跑通；确定性重复（含两档 lag）；逐项证据 + hash；fresh 独立复核；用户签署。
- 合成 `PU_WORLD`、内存 config、只跑判定核心的单点调用均不算真实案例。

**白名单默认值**：产品代码零改动；新增 `fixtures/**` 须在 FIX 增量授权记录中逐文件列出；不得修改判据 / 算法 / 已签署文档；零付费上游。最终白名单以 FIX 增量授权记录为准。

**证据与复核**：`.scratch/level-playability-v1.1-closure/fixture/{scripts,evidence,reports}`；复核 `FIX-review.md`、签署 `FIX-signature.md`；fresh reviewer 独立复跑三案例与确定性检查。

**判定**：`PASS` = 三案例 + 证据 + 复核 + 签署；`FAIL` = 任一案例不符合预期或流水线回退；`INFEASIBLE` = 可行性评审不通过；`NOT_RUN` = 未执行。`INFEASIBLE` / `FAIL` ⇒ I-05 与 closure `INCOMPLETE`。

**回滚**：新增产品 fixture ⇒ 按 §9 产品相邻单元做 revert drill；仅 audit corpus ⇒ 丢弃分支。

**STOP**：在 I-05 内自建 fixture；用静态层 NB/PU 或合成 `PU_WORLD` 冒充真实案例；为凑案例修改判据 / 算法 / 产品代码；付费上游；把失败改写成 PASS。

## §13 不变量

以下条款为恒真不变量；违反任一条 ⇒ §10 的 STOP。§1 与 §10 只引用本节，不重复定义。

- **gate 状态**：`PUBLIC_NB` / `PUBLIC_PU` 恒为 `BLOCKED`。gate 状态是独立概念（`BLOCKED` / `WIRED` / `ADMITTED` / `OPEN`），不得与内部字段 `publicCapability` 混写。
- **内部字段**：I-02 的 `publicCapability` 恒为 `"BLOCKED"`、`publicResult` 恒为 `null`；适配层只消费，不回写 / 篡改；不新增公共 `publicCapability` 字段。
- **已签署文档不可变**：I-00 / I-02 / I-03（含 §12.2）/ Phase-2 annex 正文不得改写；变更只能以新文档叠加。
- **公共形状与发布行为**：公共 `PlayabilityVerdict` 顶层形状与发布拒稿行为不变。
- **判定口径**：`NOT_RUN` 不得计为 PASS；不得用通过率 / 加权 / 分组替代逐项判定；收口整体结论只有 `PASS` / `FAIL` / `INCOMPLETE` 三态。
- **能力边界**：V1.1 收口完成、DoD 全 PASS、收口声明签署均不等于公共能力开放；任何 gate 开放需独立 effort、独立审查与用户显式授权。
