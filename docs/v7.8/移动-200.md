## 1. 背景与问题

I-01 已建立动态 Hazard 分析所需的可信输入基础：

- Atlas 文件读取、哈希校验、解析使用同一份字节，避免 TOCTOU。
- 逐帧几何验证覆盖 `sourceSize`、`anchor`、`rotated`、`trimmed` 等信息。
- 建立 `16.67ms` 与 `200ms` 双档 lag 编排。
- 两档判定不一致时降级为 `INSUFFICIENT_EVIDENCE`。

但 I-01 尚未实现真正的动态 Hazard 判定算法。当前生产分析器仍是 `stubTemporalAnalyzer`，适用输入只返回 `INSUFFICIENT_EVIDENCE`；时序结果也尚未接入最终 Playability Verdict。

因此，当前系统能验证部分输入证据，却不能可靠回答：

1. 玩家是否能通过等待 Hazard 的安全窗口穿过危险区域？
2. Hazard 是否在整个周期内持续封锁通道？
3. 是否存在通过垂直移动或其他合法空间路径绕过危险区域的可能？
4. 当搜索预算不足、几何证据不完整或不同 lag 档结果冲突时，是否能安全降级？

I-02 的任务是实现这一层算法核心，而不是直接宣称 V1.1 已具备完整生产能力。

## 2. 目标与非目标

### 2.1 目标

I-02 必须交付一个受限、可验证、确定性的单移动 Hazard 连续时间判定核心：

1. 正确计算周期移动 Hazard 与玩家路径之间的连续时间几何关系。
2. 能够构造并验证安全通过 Witness。
3. 只有满足严格条件时，才能证明永久封锁。
4. 对垂直规避可能性进行保守分析，避免把局部封锁误判为全局不可玩。
5. 所有预算超限、证据不足、模型不适用和数值不稳定情况均安全降级。
6. 保留 I-01 的双档 lag 结果一致性要求。

### 2.2 非目标

本阶段明确不做：

- 多个移动 Hazard 的联合时序求解。
- Y 轴移动 Hazard 的正式判定。
- Moving Platform 的运动与承载分析。
- Runtime、CLI、MCP 的功能扩展。
- 新增持久化 Verdict 或修改现有公共 Contract。
- 新增第三方算法依赖。
- 直接接入 Pipeline 并宣称生产验收完成。
- 通过放宽证据标准提高 `PROVEN_UNPLAYABLE` 命中率。

## 3. 支持范围与降级规则

| 场景 | I-02 行为 | 允许的结论 |
|---|---|---|
| 单个 X 轴周期移动 Hazard，几何证据可信 | 执行正式分析 | 三态均可 |
| Y 轴移动 Hazard | 不执行正式判定 | `INSUFFICIENT_EVIDENCE` |
| 多个移动 Hazard | 不执行正式判定 | `INSUFFICIENT_EVIDENCE` |
| Moving Platform | 不支持 | `INSUFFICIENT_EVIDENCE` |
| Atlas 帧几何无法验证 | 拒绝使用相关几何证据 | `INSUFFICIENT_EVIDENCE` |
| 无法验证安全通过路径 | 不得输出安全通过证明 | `INSUFFICIENT_EVIDENCE` |
| 无法排除垂直规避路径 | 不得输出永久封锁证明 | `INSUFFICIENT_EVIDENCE` |
| 搜索预算超限 | 停止搜索并降级 | `INSUFFICIENT_EVIDENCE` |
| 双档 lag 结果不一致 | 按 I-01 规则降级 | `INSUFFICIENT_EVIDENCE` |

三态定义：

- `PROVEN_UNPLAYABLE`：已得到满足证明条件的不可玩证据。
- `NO_PROVEN_BLOCKER`：当前分析未能证明存在阻断，不代表已经证明关卡可玩。
- `INSUFFICIENT_EVIDENCE`：证据不足、模型不适用、搜索未完成或结果不稳定。

**禁止将“没有找到安全路径”直接等同于“证明不可玩”。**

## 4. 功能需求

### I02-01：连续时间求交

**目标：** 建立移动 Hazard 与玩家碰撞体之间可验证的连续时间求交能力。

#### 输入要求

- 单个 X 轴周期移动 Hazard。
- Hazard 的运动区间、速度、周期及相位信息。
- 玩家碰撞体和合法移动范围。
- 已通过 I-01 验证的逐帧几何证据。
- Runtime 所需的碰撞体与边界参数。

#### 功能要求

1. 正确表达 X 轴三角波运动，包括运动方向、折返点和周期边界。
2. 在每个运动区段内进行连续时间分析，不得仅依赖固定帧采样判断碰撞。
3. 在折返点处分段，保证分段前后的时间和位置连续。
4. 对 Hazard 与玩家 AABB 进行一致的求交判断。
5. 明确 AABB 相交语义：严格重叠、边界相切和零面积接触必须有固定且一致的处理规则。
6. 数值容差 `epsilon` 必须集中定义，不得由不同算法各自使用隐式容差。
7. 对周期边界、负时间、浮点误差和临界速度进行测试。
8. 求交结果必须可重复，不得依赖运行时偶然的浮点或迭代顺序。

#### 验收要求

- 能正确处理正向、反向及折返点运动。
- 对周期起点和终点得到一致结果。
- 临界相切场景符合冻结的 AABB 语义。
- 连续时间结果不能被粗粒度采样的漏检替代。
- 同一输入重复运行，结果一致。

### I02-02：安全通过 Witness

**目标：** 当存在等待安全窗口时，构造可验证的玩家通过路径。

#### 功能要求

1. 支持由等待、水平移动和必要的路径段组成的 Witness。
2. 每个路径段必须包含可验证的起止状态和时间区间。
3. 对路径段内的玩家与 Hazard 进行连续时间碰撞检查。
4. 等待阶段也必须参与碰撞检查，不能默认等待是安全的。
5. 路径段连接处必须满足位置、时间和状态连续性。
6. Witness 必须从合法初始状态出发，并到达目标通过区域。
7. 所有路径段通过验证后，才允许将该 Witness 作为安全通过证据。
8. 不能只验证路径终点或采样点。
9. 搜索过程中产生的部分路径、未完成路径和未经验证的候选路径不得提升为正式 Witness。
10. 搜索耗尽预算时，即使已经找到部分候选路径，也必须按完整证明条件处理。

#### 验收要求

- 有安全等待窗口的案例能够构造有效 Witness。
- Hazard 运动期间的碰撞能够被识别。
- 等待期间发生碰撞的路径不能被接受。
- 路径中任意一段验证失败，整个 Witness 失败。
- 不存在已验证 Witness 时，不得据此直接输出 `PROVEN_UNPLAYABLE`。

### I02-03：永久封锁证明

**目标：** 证明单个移动 Hazard 是否在整个周期内持续阻断指定通道。

#### 功能要求

1. 对 Hazard 的完整周期进行分析，而不是只检查某个时刻。
2. 识别 Hazard 在周期内的运动区段、折返点和覆盖范围。
3. 分析 Hazard 与通道之间的持续封锁关系。
4. 证明必须覆盖完整周期，不能由有限采样点推断整个周期。
5. 对门区宽度、玩家宽度和 Hazard 覆盖范围使用统一几何语义。
6. 对正宽度门区使用严格的永久封锁条件；建议采用 `R - L > epsilon` 作为门宽有效性判据，并在实施前与 AABB 语义一起冻结。
7. 若存在任何可能的安全时间窗口，不得输出永久封锁证明。
8. 若周期分析不完整、几何不可信或数值边界无法确定，降级为 `INSUFFICIENT_EVIDENCE`。
9. 永久封锁证明必须与垂直规避分析共同满足不可玩判定条件。

#### 验收要求

- Hazard 完整周期持续覆盖有效门区时，能够形成封锁证据。
- 存在安全窗口时，不能形成永久封锁证据。
- 零宽度、边界相切和 epsilon 临界案例按统一语义处理。
- 周期未完整分析时不得输出永久封锁结论。

### I02-04：垂直规避图割分析

**目标：** 防止系统把水平通道封锁错误地推导为整个关卡不可通过。

#### 功能要求

1. 使用可信的玩家几何、障碍几何和合法移动边界构建规避分析空间。
2. 将已证明持续封锁的门区作为 forbidden region。
3. 分析玩家是否能通过垂直移动或其他合法空间路径绕过该区域。
4. 只有在规避图满足严格不连通条件时，才允许将其作为不可玩证明的一部分。
5. 不得仅凭“常见路线被阻断”或“当前采样路径无法通过”推导全局不可达。
6. 图割分析必须保守处理边界、碰撞体宽高和障碍接触语义。
7. 对 hop 采样进行加倍不变性验证：采样加密后若推翻原有不可玩证明，原证明必须失效并降级。
8. 无法证明垂直规避不存在时，必须返回 `INSUFFICIENT_EVIDENCE`。

#### 验收要求

- 存在合法垂直绕行路线时，不得判定为不可玩。
- 门区封锁且不存在合法垂直规避时，能够形成图割证据。
- 边界路径和碰撞体尺寸变化不能造成未经证明的不可达结论。
- hop 加倍后原有不可玩证明被推翻时，必须阻断该证明。

### I02-05：搜索预算、确定性与降级边界

**目标：** 确保算法在资源受限时仍保持结果可信。

#### 初始预算建议

| 参数 | 建议默认值 | 硬上限 |
|---|---:|---:|
| `maxStates` | 500,000 | 1,000,000 |
| `timeBudgetMs` | 2,000 | 10,000 |

以上是 I-02 的预算设计建议，不是已验收的性能数据。正式实施前应通过基准测试验证，并冻结实际配置及计量口径。

#### 功能要求

1. 状态扩展数量必须可计量、可限制。
2. 墙钟时间必须受限，且超时不能被当作搜索完成。
3. 达到任一预算上限时立即停止相应搜索。
4. 预算超限必须返回 `INSUFFICIENT_EVIDENCE`。
5. 不得将部分搜索结果提升为完整的安全通过或永久封锁证明。
6. 不得通过静默扩大预算、自动重试或切换算法绕过硬上限。
7. 相同输入、相同配置必须产生确定性结果。
8. 搜索顺序、状态去重和边界处理必须避免不稳定的结果差异。
9. 双档 lag 必须分别完成分析；结果不一致时按 I-01 规则降级。
10. 记录足够的内部诊断信息，以便复现预算超限和判定差异，但不新增未经批准的公共持久化字段。

#### 网格约束

对于需要离散化的搜索空间，网格数量必须满足：

`N ≥ 2`

同时受移动速度、周期和水平步长约束：

`N ≤ floor(maxSpeed × periodMs / xStep)`

若参数不满足约束、计算结果无效或搜索规模超出预算，应安全降级，不得静默截断后继续输出确定性结论。

## 5. 总体判定约束

I-02 的算法结果必须遵守以下逻辑：

| 安全通过 Witness | 永久封锁证据 | 垂直规避分析 | 结果约束 |
|---|---|---|---|
| 已验证 | 无 | 不要求 | `NO_PROVEN_BLOCKER` |
| 无 | 已验证 | 证明不存在合法规避 | 可支持 `PROVEN_UNPLAYABLE` |
| 无 | 已验证 | 存在合法规避 | 不得输出 `PROVEN_UNPLAYABLE` |
| 无 | 已验证 | 无法证明规避不存在 | `INSUFFICIENT_EVIDENCE` |
| 无 | 未验证 | 任意 | 不得输出 `PROVEN_UNPLAYABLE` |
| 候选路径或部分搜索结果 | 任意 | 任意 | 不得作为正式证明 |
| 任一必要阶段预算超限 | 任意 | 任意 | `INSUFFICIENT_EVIDENCE` |
| 双档 lag 结论不一致 | 任意 | 任意 | `INSUFFICIENT_EVIDENCE` |

补充约束：

- `NO_PROVEN_BLOCKER` 不是 `PROVEN_PLAYABLE`。
- `PROVEN_UNPLAYABLE` 必须同时具备有效的封锁证据和规避不存在的证据。
- 算法无法覆盖的情况不得通过推测补齐证据。
- 不允许用更宽松的阈值换取更多确定性 Verdict。

## 6. 测试需求

### 6.1 核心场景矩阵

| 编号 | 场景 | 预期结果 |
|---|---|---|
| A | Hazard 周期运动存在安全等待窗口，玩家可以通过 | `NO_PROVEN_BLOCKER` |
| B | Hazard 永久封锁有效门区，且无垂直规避路径 | `PROVEN_UNPLAYABLE` |
| C | 几何、时序或规避证据不足 | `INSUFFICIENT_EVIDENCE` |
| D | Hazard 折返点处发生临界碰撞 | 按连续时间语义正确判定 |
| E | 等待阶段存在碰撞 | Witness 不通过 |
| F | 周期内存在短暂安全窗口 | 不得判定永久封锁 |
| G | 存在垂直规避路径 | 不得判定不可玩 |
| H | 搜索预算超限 | `INSUFFICIENT_EVIDENCE` |
| I | 两档 lag 结果不一致 | `INSUFFICIENT_EVIDENCE` |
| J | 相同输入重复运行 | 结果完全一致 |

### 6.2 数值与边界测试

必须覆盖：

- AABB 严格重叠、边界相切、零面积接触。
- `epsilon` 临界值两侧。
- Hazard 运动方向切换。
- 周期起点、周期终点和折返点。
- 玩家与 Hazard 速度相同或接近。
- 极短安全窗口。
- 极短通道和临界门宽。
- 负时间、无效周期、非有限数值。
- 网格步长不满足约束。
- 状态预算和时间预算刚好达到上限。

### 6.3 证明健全性测试

必须包含以下反例测试：

1. **网格细化反例：** 细化网格后出现原先遗漏的合法路径，必须阻止原有不可玩证明。
2. **Hop 加倍反例：** hop 加倍后推翻原有不可玩证明，必须阻止原有证明继续生效。
3. **部分路径反例：** 搜索中找到未完成路径，不能作为安全通过 Witness。
4. **局部封锁反例：** 水平门区封锁，但玩家可从上方绕行，不能判为不可玩。
5. **采样漏检反例：** 离散采样未发现碰撞，但连续时间区间内发生碰撞，必须识别。

### 6.4 双档 lag 测试

- `16.67ms` 与 `200ms` 两档分别执行完整分析。
- 两档结论一致时，按冻结规则处理。
- 两档结论不一致时，必须降级为 `INSUFFICIENT_EVIDENCE`。
- 不允许只保留较乐观或较确定的一档结果。

| AC-12 | 未越过批准的文件、接口和依赖范围 | 阻断 |
| AC-13 | 核心测试、回归测试和性能证据完整 | 阻断 |

**验收原则：** 任何错误的 `PROVEN_UNPLAYABLE` 都属于严重失败。宁可返回 `INSUFFICIENT_EVIDENCE`，也不能用不完整搜索或未经验证的几何推导确定性不可玩结论。

## 10. 实施拆分与复核点

建议按以下顺序实施，保持每个单元独立提交和可复核：

| 单元 | 内容 | 必须先通过的复核 |
|---|---|---|
| I02-01 | 连续时间求交 | 运动模型、AABB 语义、数值稳定性 |
| I02-02 | 安全通过 Witness | 路径完整性、连续时间安全验证 |
| I02-03 | 永久封锁证明 | 完整周期证明、门宽与边界条件 |
| I02-04 | 垂直规避图割 | 图割健全性、网格细化与 hop 反例 |
| I02-05 | 预算、确定性和集成测试 | 性能上限、降级一致性、最终范围审计 |

建议在 I02-01、I02-02、I02-04 后设置强制复核点。前一单元未通过复核，不得继续扩大后续算法范围。

## 11. 后续阶段边界

I-02 不是 V1.1 的最终交付。后续阶段必须串行推进：

- **I-03：生产接入。** 将已验证的时序分析接入现有 Playability 流程，处理 `moving-hazard-phase` gap、`coverage.temporal` 和顶层 Verdict 聚合，确保时序 IE 不被错误聚合成 `NO_PROVEN_BLOCKER`。
- **I-04：负向与回归验收。** 完成 G-01～G-07、V1 历史回归和既有案例矩阵复跑，重点检查既有 19 个移动 Hazard 关卡是否发生误判 `PROVEN_UNPLAYABLE`。
- **I-05：Pipeline 验收。** 使用真实关卡案例验证三态输出、确定性、性能和构建集成；不能仅依靠人工夹具证明 Pipeline 能力。

I-02 未验收前，不启动 I-03。

## 12. 实施授权建议

本需求文档只定义 I-02 的目标和验收边界，**不构成实施授权**。

正式启动前，应另行提交 I-02 实施授权包，至少明确：

1. 具体文件白名单和允许修改的模块。
2. I02-01～I02-05 的提交拆分。
3. AABB、epsilon、三角波和图割的正式数学语义。
4. 默认预算及硬上限的最终冻结值。

6. 公共接口、依赖和 Runtime 变更的审批边界。

**最终建议：** 先批准 I-02-01 的算法设计与测试夹具准备；在连续时间求交语义和数值稳定性得到独立复核前，不授权完整 I-02 实施。I-02 的核心成功标准不是尽可能多地产生确定性结论，而是在有限支持范围内，确保每一个确定性结论都有完整、可复现且不会被反例推翻的证据。
