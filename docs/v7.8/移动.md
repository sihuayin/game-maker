# Level Playability V1.1 — 单移动 Hazard 正式集成需求文档

- **文档类型：** 独立集成需求（PRD）
- **项目：** Game Maker V2
- **目标版本：** Level Playability V1.1
- **工作项：** Temporal Hazard Integration
- **当前阶段：** 技术可行性已获 GO，正式集成待独立授权
- **依据：** PR #28（Level Playability V1）与 PR #29（V1.1 P0 技术可行性研究）
- **状态：** 待评审，不代表实施获批

---

## 1. 背景与问题定义

### 1.1 当前能力

Level Playability V1 已实现关卡可玩性审计，主要包括：

1. Spatial Reachability：空间可达性。
2. Mechanic Traversability：机制通行性。
3. Level Completion：关卡完成条件。

现有审计基于 Runtime Geometry Profile、实体 AABB、移动图及关卡目标等信息，能够识别一部分由静态几何结构造成的不可达和阻塞问题。

### 1.2 当前缺口

对于 `motion` 类型的 Hazard，V1 当前会将其归入：

`moving-hazard-phase` → `INSUFFICIENT_EVIDENCE`

原因是：

- 静态几何可达不代表实际时间条件下可通行。
- 移动 Hazard 会随时间改变占用区域。
- 玩家到达障碍位置的时刻，可能与 Hazard 的安全窗口有关。
- 如果忽略运动相位，可能错误地把实际可通行的关卡判为不可玩，也可能漏掉真实的永久封锁。

因此，需要增加一个受严格边界约束的时序可达性判定能力。

### 1.3 本次解决的问题

在可信输入和确定性运动模型成立的前提下，判断：

**玩家是否能够利用单个沿 X 轴运动的 Hazard 所提供的时间窗口，通过危险区域并继续到达目标。**

本次不试图解决通用动态障碍物规划问题。

---

## 2. 目标与非目标

### 2.1 目标

- 将 P0 原型验证过的单移动 Hazard 时序判定能力，设计为可正式集成的生产能力。
- 复用 V1 已有的几何和可达性语义，避免建立平行的可玩性判定体系。
- 对安全窗口、永久封锁和证据不足给出正确且可解释的结果。
- 保证输入来源可信、判定过程确定、结果可复现。
- 保持现有三态判定语义及既有静态关卡行为不回退。

### 2.2 非目标

本次不支持：

- 多个同时运动的 Hazard。
- Moving Platform。
- Danger 区域与移动 Hazard 的联合时序分析。
- 玩家跳跃、下落、重力与移动 Hazard 的精确时序耦合。
- 通用连续物理模拟或完整 Runtime 行为仿真。
- 根据设计文本推断未提供的运动规律。
- 新增用户可配置的通用时序规划 DSL。
- 修改游戏 Runtime 的实际运动和碰撞逻辑。
- 将时序判定扩展为完整 QA 第 8 条或新的独立 QA 系统。

## 3. 设计原则

### 3.1 证据优先

没有可信证据，不得输出确定性结论。

### 3.2 保守降级

输入缺失、运动模型不确定、相位不确定或关键假设无法验证时，必须返回 `INSUFFICIENT_EVIDENCE`，不得猜测。

### 3.3 不扩大不可玩结论

只有满足明确、可证明的永久封锁条件，才允许输出 `PROVEN_UNPLAYABLE`。

### 3.4 不改变既有判定语义

继续使用 V1 已有的三态结果：

- `PROVEN_UNPLAYABLE`
- `INSUFFICIENT_EVIDENCE`
- `NO_PROVEN_BLOCKER`

不得新增持久化 verdict 或 `ConfigIssue.code`，除非未来独立评审并授权。

### 3.5 原型与生产实现隔离

P0 原型证明技术路径可行，但不能直接视为生产实现。正式集成必须重新完成契约、测试、回归和构建验收。

## 4. 功能需求

### FR-01：单个 X 轴移动 Hazard

系统应支持一个符合限定运动模型的移动 Hazard：

- 同一关卡分析范围内最多一个移动 Hazard。
- Hazard 仅沿 X 轴运动。
- 运动范围、方向、速度或周期必须来自可信且可验证的输入。
- 运动规律必须能够被确定性地描述。
- 不符合模型的运动行为不得强行纳入分析。

超出模型边界时，应返回 `INSUFFICIENT_EVIDENCE`。

### FR-02：连续时间窗口分析

系统应能够在限定运动模型下分析：

- Hazard 随时间变化的占用区间。
- 玩家抵达危险区域的可能时间。
- Hazard 离开危险区域后形成的安全通行窗口。
- 玩家通过危险区域所需的时间。
- 安全窗口是否足以容纳一次有效通行。

判定应基于连续时间区间，而不是只检查若干离散采样点。

不得将采样点没有碰撞误当成完整的安全性证明。

### FR-03：时序路径验证

系统应验证候选路径是否同时满足：

1. 空间几何可达。
2. 玩家运动能力符合当前 Runtime Geometry Profile。
3. 通过 Hazard 区域时不存在时间上的碰撞。
4. 到达目标的路径仍然有效。

如果候选路径依赖当前模型不支持的跳跃、下落或其他运动机制，则不得将其作为确定性可达证明。

### FR-04：Lag 参数

时序分析必须显式处理 `lagMs`。

- 默认采用 P0 研究所使用的 `lagMs = 200ms` 作为集成评审基准。
- 参数来源和单位必须明确。
- 不得将 lag 隐式写死在多个实现位置。
- 应保留两档敏感性分析，以检查结论对 lag 假设的依赖程度。
- 不得将研究基准直接解释为所有 Runtime 场景的真实输入延迟。

若无法确定适用的 lag 假设，应降级为 `INSUFFICIENT_EVIDENCE`。

### FR-05：永久封锁判定

只有在以下条件全部成立时，才允许输出 `PROVEN_UNPLAYABLE`：

- 存在正宽度的永久封锁区间。
- 玩家无法通过该封锁区间。
- 不存在符合当前模型的其他合法通路。
- 结论不依赖未经证明的调用方声明。
- 相关几何和运动输入均可信。

特别地，不能仅因为某个时刻 Hazard 占据通路，就认定其永久封锁。

### FR-06：安全窗口判定

如果存在经过验证的安全窗口，并且玩家能够在窗口内完成通行，则该 Hazard 不应单独构成不可玩阻塞。

在其余必要证据充分的情况下，允许输出 `NO_PROVEN_BLOCKER`。

该结论仅代表当前分析范围内没有证明出阻塞，不代表对所有 Runtime 行为作出完整保证。

### FR-07：证据不足处理

以下情况必须降级：

- Hazard 的运动周期或相位未知。
- 运动轨迹不符合单 X 轴模型。
- 关键几何数据无法从可信资源中确认。
- 无法确定适用的 `lagMs`。
- 玩家通行时间无法在当前运动模型下可靠计算。
- 存在未建模的垂直运动规避可能。
- 页面暂停、后台计时或其他时间行为可能改变运动相位。
- 关键输入之间存在矛盾。

统一使用 `INSUFFICIENT_EVIDENCE`，并提供可定位的原因。

## 5. 七项生产集成硬门槛

以下门槛是正式实施的必要条件，不得通过降低测试标准或增加调用方声明绕过。

### G-01：Hitbox 来源可信

- Hazard 的实际碰撞几何必须来自真实 Asset Pack 帧和可信 Manifest。
- 必须验证实际 Pack 帧几何与 Manifest 的一致性。
- 不得只信任调用方提供的 hitbox、body 或尺寸声明。
- 无法确认实际几何时，降级为 `INSUFFICIENT_EVIDENCE`。

### G-02：Lag 来源明确

- `lagMs` 必须是显式输入或由明确、可审计的可信配置提供。
- 必须保留两档敏感性分析。
- 不得把研究假设当成已经测得的生产 Runtime 延迟。
- 无法建立有效假设时，降级。

### G-03：时间行为确定

- Hazard 的运动相位和时间模型必须可确定。
- 未知相位、隐藏页面时间行为或无法解释的时间变化，不得参与确定性证明。
- 对页面暂停、后台计时等可能影响相位的行为，应明确支持范围。
- 无法证明时间模型成立时，降级。

### G-04：垂直规避必须有真实证据

- 不得相信调用方提供的 `verticalEvasionImpossible` 布尔标记。
- 必须根据可信几何和当前支持的玩家运动模型，判断是否存在垂直规避路径。
- 不能证明不存在垂直规避时，不得以该假设输出永久封锁结论。
- 需要跳跃、下落或重力精确模拟才能判断的场景，本次不支持。

### G-05：运动模型边界严格

仅支持单个 X 轴移动 Hazard 的受限时序模型。

不支持：

- 多 Hazard 联合运动。
- 移动平台。
- 精确跳跃时序。
- 下落与重力时序。
- 未建模的运动状态转换。

模型外输入必须明确降级，不得静默近似后给出确定性结果。

### G-06：判定语义受限

- 保留 V1 三态语义。
- 只有正宽度永久封锁门可以作为本次新增的确定性不可玩证明。
- 瞬时阻塞、短时间无法通过或暂时没有找到路径，不等于永久不可玩。
- `NO_PROVEN_BLOCKER` 不得被解释为绝对可玩保证。
- `INSUFFICIENT_EVIDENCE` 不得被提升为不可玩或可玩结论。

### G-07：生产集成独立验收

- P0 原型代码不能直接作为生产实现。
- 正式实现必须有独立测试和代码审查。
- 必须执行现有 V1 回归。
- 必须验证构建、打包和现有审计流程。
- 必须证明旧有静态关卡行为不回退。
- 必须保留可审计的输入、结果和证据。

## 6. 输入与输出要求

### 6.1 输入

正式集成设计应明确以下输入类别：

| 输入类别                     | 要求                     |
| ------------------------ | ---------------------- |
| GameConfig               | 使用现有游戏配置及实体定义          |
| AssetPackManifest        | 提供可信资源及帧几何来源           |
| Runtime Geometry Profile | 沿用 V1 的玩家运动和碰撞几何约束     |
| Hazard 运动描述              | 单个 X 轴 Hazard 的确定性运动参数 |
| 时间相位                     | 必须明确且可验证               |
| `lagMs`                  | 显式、可审计                 |
| 分析范围                     | 必须明确空间边界、通路及目标         |

具体字段、类型、可选性和来源验证规则应在 I-00 阶段冻结。

### 6.2 输出

继续沿用 V1 内部审计结果结构，不在本需求阶段预设新增持久化字段。

结果必须能够解释：

- 判定状态。
- 使用的运动模型。
- 关键几何证据。
- 时间窗口或永久封锁证据。
- 使用的 lag 假设。
- 降级原因（若有）。
- 结论所覆盖的范围和限制。

### 6.3 三态语义

| 结果                      | 含义                    |
| ----------------------- | --------------------- |
| `PROVEN_UNPLAYABLE`     | 有充分证据证明存在符合限定条件的永久封锁  |
| `INSUFFICIENT_EVIDENCE` | 证据不足，无法可靠判断           |
| `NO_PROVEN_BLOCKER`     | 在当前支持范围和证据条件下，没有证明出阻塞 |

## 7. 验收案例与测试矩阵

P0 已验证的 A/B/C 三类案例必须成为正式集成的核心验收基线。

| 案例 | 场景                     | 预期结果                    | 核心验证            |
| -- | ---------------------- | ----------------------- | --------------- |
| A  | 单个移动 Hazard 存在可利用的安全窗口 | `NO_PROVEN_BLOCKER`     | 连续时间窗口及玩家通行时间验证 |
| B  | 正宽度永久封锁门               | `PROVEN_UNPLAYABLE`     | 永久封锁条件和不可规避证明   |
| C  | 运动相位或关键时间证据不足          | `INSUFFICIENT_EVIDENCE` | 正确降级，不作猜测       |

### 7.1 必须覆盖的补充测试

**几何与资源来源**

- Manifest 与实际 Pack 几何一致。
- Manifest 与实际 Pack 几何不一致。
- 缺失帧、缺失几何。
- 调用方伪造 hitbox。

**时间模型**

- 不同运动相位。
- 安全窗口足够长。
- 安全窗口短于玩家通行所需时间。
- 时间边界上的碰撞。
- 不同 `lagMs` 档位。
- 未知相位。
- 时间行为不确定。

**规避与路径**

- 水平通路可行。
- 正宽度永久封锁。
- 存在其他合法通路。
- 可能存在垂直规避。
- 必须依赖未支持的跳跃或下落才能通过。

**回归**

- V1 静态 Hazard 行为不变。
- 非移动实体的既有审计行为不变。
- 旧有 `INSUFFICIENT_EVIDENCE` 案例不被错误提升。
- 既有三态语义不变。
- 既有调用方无需因本功能而被迫修改。

## 8. 实施阶段规划

正式实施授权后，按以下阶段串行推进。每阶段完成后提交证据，进入下一阶段前进行复核。

### I-00：集成需求与边界冻结

交付：

- 最终输入和输出契约提案。
- 运动模型定义。
- 时间与 lag 假设。
- 七项硬门槛的验证方案。
- 文件与模块修改白名单。
- 明确的非目标和退出条件。

验收：没有未裁定的核心语义或输入来源问题。

### I-01：可信输入与几何来源

交付：

- Pack 帧几何与 Manifest 一致性验证。
- Hazard 运动输入验证。
- 时间相位与 `lagMs` 来源验证。
- 不可信输入降级测试。

验收：无法通过调用方伪造声明获得确定性结论。

### I-02：时序判定核心

交付：

- 单 X 轴 Hazard 连续时间模型。
- 安全窗口计算。
- 玩家通行时间验证。
- 永久封锁证明。
- 确定性和边界测试。

验收：A/B/C 三类基线均符合预期，且模型外输入正确降级。

### I-03：现有判定体系集成

交付：

- 接入 V1 现有可玩性审计流程。
- 保留现有三态语义。
- 保留原有静态审计行为。
- 形成可追踪的判定证据。

验收：不建立平行审计入口，不改变既有调用方语义。

### I-04：负向与回归验收

交付：

- 七项硬门槛的负向测试。
- 伪造几何、未知相位、错误 lag 等拒绝案例。
- V1 完整回归结果。
- 确定性和重复执行验证。

验收：所有已知风险均有对应测试，且无既有行为回退。

### I-05：Pipeline 验收与最终收口

交付：

- Pipeline 集成验收证据。
- 真实关卡案例。
- 最终测试和构建报告。
- 支持范围、限制和已知问题。
- 最终集成结论。

验收：证明新能力在正式创作与审计流程中有效，同时不扩大其模型承诺。

## 11. 已有技术可行性证据与结论边界

PR #29 的 P0 研究已验证：

- A：安全窗口路径可得到 `NO_PROVEN_BLOCKER`。
- B：正宽度永久封锁可得到 `PROVEN_UNPLAYABLE`。
- C：证据不足可正确降级为 `INSUFFICIENT_EVIDENCE`。
- 原型 12/12 单元测试通过。
- 案例 A 的一次原型运行记录为 4096 visited、12288 edges、7–19ms；该性能数据仅是研究样本，不构成生产性能承诺。

**当前裁定：GO — 技术可行性得到支持，可以规划正式集成。**

该 GO：

- 不代表 V1.1 已具备直接进入 Runtime 或 Pipeline 的条件。
- 不代表正式生产实现已获批准。
- 不代表任何 contracts、CLI、MCP 或新依赖变更已获批准。
- 不替代 I-00 的边界冻结和后续独立实施授权。

## 12. 最终完成定义（Definition of Done）

只有同时满足以下条件，才能宣布单移动 Hazard 正式集成完成：

- [ ] I-00 至 I-05 全部完成并有审查记录。
- [ ] 七项生产集成硬门槛全部通过。
- [ ] A/B/C 核心案例全部通过。
- [ ] 补充正向、负向和边界测试全部通过。
- [ ] V1 既有静态审计回归通过。
- [ ] 未支持模型输入全部正确降级。
- [ ] 结果证据可解释、可复现、可审计。
- [ ] Pipeline 真实流程验收通过。
- [ ] 修改范围与授权记录一致。
- [ ] 最终报告明确支持范围、限制和残余风险。

**完成后的能力声明应限定为：**

> 系统能够在可信输入和确定性运动假设成立的条件下，对单个沿 X 轴运动的 Hazard 进行受限时序可达性分析，并对安全窗口、正宽度永久封锁及证据不足作出符合既有三态语义的判断。

不得宣称已经支持通用动态障碍物可玩性分析。
