# PRD：移动 Hazard 时序分析预研（Temporal Playability P0）

**项目：** `sihuayin/game-maker`  
**阶段：** Level Playability V1.1 — P0  
**性质：** 小范围研究与原型验证  
**目标：** 验证单个移动 Hazard 是否能够进行可信的时序可达性分析。

## 1. 背景

现有 Level Playability V1 已支持：

- 空间可达性分析。
- 静态 Hazard 禁区分析。
- 单个全高 Danger 安全窗口分析。
- 收集目标完成性分析。
- Pipeline 和 Publish Gate 集成。

目前移动 Hazard 已在 Runtime 中实现，但分析器遇到移动 Hazard 时会产生 `moving-hazard-phase` gap，返回 `INSUFFICIENT_EVIDENCE`。

这导致一类实际存在的关卡无法得到更准确的判断：

- Hazard 周期性移动。
- 玩家可以等待安全窗口通过。
- 但分析器无法证明该安全窗口是否存在。

## 2. 本阶段目标

只验证三个问题：

1. Runtime 移动 Hazard 的运动周期、时间相位和碰撞行为能否被准确建模？
2. 能否建立一个针对单个移动 Hazard 的最小时间状态模型？
3. 能否用真实 Runtime 案例证明分析结果正确？

本阶段不追求完整功能交付。

## 3. 工作内容

### P0-01：Runtime 时序语义确认

检查现有 Runtime 实现，重点研究：

- `packages/demo/src/hazard.ts`
- `hazardAnchor`
- `periodMs` 的实际含义。
- Hazard 的起点、终点和往返轨迹。
- 时间如何推进。
- 玩家 reset 后 Hazard 是否继续运动。
- Hazard 位置更新与碰撞检测的先后顺序。

**交付：** 一份简短的 Runtime 时序语义报告，列出已确认事实和未确认事项。

验收：所有用于算法建模的关键假设均有源码或实验依据。

### P0-02：最小时序算法原型

仅支持：

- 一个移动 Hazard。
- 已知运动轨迹和周期。
- 已有 Spatial 分析支持的场景。
- 玩家等待和正常移动。
- 可验证的碰撞体几何。

建立最小时间相位模型，判断玩家是否存在安全通过窗口。

要求：

- 不允许仅凭离散采样没有碰撞就证明安全。
- 无法确认安全时返回 `INSUFFICIENT_EVIDENCE`。
- 搜索超时、状态耗尽不得解释为 `PROVEN_UNPLAYABLE`。
- 不改变现有三态结果语义。

**交付：** 独立算法原型及单元测试，不急于接入 Pipeline。

### P0-03：三个关键案例验证

只做三个核心案例：

| 案例 | 场景 | 预期 |
|---|---|---|
| A | 移动 Hazard 经过通道，玩家可以等待后通过 | 识别安全窗口 |
| B | 移动 Hazard 始终封锁唯一通道 | 只有在证明无安全路径时才判定不可玩 |
| C | 时间相位或碰撞边界无法可靠确定 | `INSUFFICIENT_EVIDENCE` |

至少对 A、B 使用真实 Runtime 进行对照，记录：

- 玩家位置。
- Hazard 位置。
- 时间。
- 碰撞事件。
- 分析器判断。

**交付：** 三个案例的配置、运行记录和判断对照报告。

## 4. 范围限制

本阶段明确不做：

- Moving Platform。
- 多移动 Hazard 联合分析。
- 多 Danger 联合分析。
- Hazard 与目标的复杂组合判定。
- Gameplay QA 改造。
- Pipeline 和 Publish Gate 集成。
- CLI/MCP 参数或公开契约修改。
- Runtime 行为修改。
- 新增第三方依赖。

## 5. 工程约束

- 零付费。
- Runtime 只读。
- 历史 run、pack 和冻结证据只读。
- 不修改现有三态语义。
- 不放宽 LP-02～LP-07 的测试。
- 新实验产物写入独立 scratch/evidence 目录。
- 不推送、不合并、不绕过 PR 审查。

## 6. 验收与后续决策

完成 P0-01～P0-03 后，提交一份简短总结，回答：

1. Runtime 时间语义是否足够明确？
2. 单移动 Hazard 是否能建立可信的时序模型？
3. 是否能正确识别等待后的安全窗口？
4. 是否能证明确定封路，而不是依赖采样猜测？
5. 算法的性能和状态空间是否可控？
6. 是否值得进入正式 Pipeline 集成？

最终结论允许：

- **GO：** 证据充分，可以规划正式集成。
- **CONDITIONAL GO：** 只有部分场景可证明，需要收缩范围。
- **NO-GO：** Runtime 语义或算法模型不足，暂不继续。

## 7. 执行顺序

P0-01 → P0-02 → P0-03。

完成后停止，不自动扩展功能。

**本阶段只授权研究和独立原型，不授权 Runtime、公开契约、CLI、MCP、Pipeline 或 Publish Gate 修改。**
