# 怎么写一份塔防需求

> 这份文件是[td-compile-v1 的票 07](../.scratch/td-compile-v1/issues/07-arena-tile-size.md)
> 的产物。它存在的理由与 [`stylespec-extraction.md`](stylespec-extraction.md) 一模一样：
> **这件事每个世界都要重做一次**，而不能被依赖的东西**必须有承载它的地方**。
>
> ⚠️ 而它更硬的一条理由是**量出来的**：`derive` 与 `compile-td-game` 都**不是玩法感知的** ——
> 它们是「**照需求列资源 / 画关卡**」的机器。**需求没说的，它们只能拿示例填。**

## ⚠️ 先读这一条：需求没说的，模型会拿示例填

两处真跑各量到一次，形状完全一样：

- [票 01](../.scratch/td-compile-v1/issues/01-derive-for-td.md)：需求点名「场地是一格格砖」时，
  `derive` **给出 5 块 15×15 的砖**并真出包；只说「店铺的场地」时，它给一张 **640×360 的三层大背景图**
  —— 而塔防的 `arena` **表达不了**它。⚠️ 那份清单**完全合法**，失败在很远的 `compile-td-game` 才响。
- [票 05](../.scratch/td-compile-v1/issues/05-first-td-prompt.md)：提示词里明明写着「骨架那张地图
  **是行格式的演示，不是一张可以拿来用的地图**……照抄它 = 没有按需求设计这一关」，
  而模型**还是照抄了** —— 因为需求里没有布局，示例是它手上**唯一**的布局信息。
  ⚠️ 它照抄是**理性的**。

⇒ 所以写需求的人有两件事**必须说**，说了它们，后面每一步才有着落。

## 必须说的两件（缺一件就会出问题）

### 一、**场地是一格格砖**，不是一张整幅的画

要点名「走道 / 地面 / 货架 / 墙 / 入口」这几种砖的存在。

⚠️ **为什么这条不能省**：管线里画 480×270 的整幅场景会**退化成一片抖动条纹**
（模型画小物件很稳，画大场景不稳）。场地拆成砖之后，地图还能**在构建期整个校验**
（尺寸、字符、以及「敌人走过的每一格必须是走道砖」）—— 一张大图只能靠人眼。

### 二、**布局画在哪**

至少说清：**入口在哪一端、柜台在哪一端、走道大致怎么折**。

⚠️ **为什么这条不能省**：不说的话，模型会照抄提示词骨架里那张示意地图
（票 05 实测）—— 于是每一关都长成同一关。

## 过程

1. **写一段需求**（自由中文散文即可）。可以照下面那份提示词让模型起草，也可以自己写。
2. **自查那两件**：场地是砖吗？布局说清了吗？
3. **存进 `inputs/<世界名>/PROMPT.md`** —— 与 [`inputs/last-train/PROMPT.md`](../inputs/last-train/PROMPT.md) 同款。
   它同时是 `derive` 的输入（产资源清单）与 `compile-td-game` 的输入（产关卡）。
4. **喂给管线**：

   ```sh
   game-maker derive          --requirement inputs/<名>/PROMPT.md --style fixtures/style-spec.json --out out
   game-maker pack            --recipe out/<recipeId>/recipes/v1.json --out out
   game-maker compile-td-game --requirement inputs/<名>/PROMPT.md --pack out/<recipeId>/pack/v1 --out out
   game-maker site            out/<recipeId>/pack/v1 --config out/<recipeId>/td-configs/v1.json --out out
   ```
   ⚠️ **「这一关通不通」判在 `site`**（那一步需要模拟器）—— `compile-td-game` 只跑得动
   契约三族与屏幕空间那两族。

## 一份可直接复制的提示词

把 `<一句话的想法>` 换成你的，发给模型，它会产出一份**说清那两件**的需求：

```
你在为「图片驱动的游戏创作工具链」写一份**塔防关卡的需求**。
它会被喂给两个下游：一个负责推导资源清单，一个负责产出关卡数据。**两者都不懂玩法** ——
所以需求没说的，它们只能拿示例填，而那样出来的东西看起来很正常、其实是错的。

请根据下面这一句话的想法，写一份中文需求（散文，不要 JSON，不要小标题堆砌）：

<一句话的想法>

**必须写清的两件**（缺一件下游就会走偏）：

1. **场地是一格一格的砖**，不是一张整幅的画。逐一点名有哪几种砖、各自什么颜色什么质感
   （通常五种：地面 / 走道 / 货架 / 墙 / 入口）。
   ⚠️ 一定要说「走道」是敌人走的那一条，而且它**明显区别于地面**。
2. **布局画在哪**：入口在哪一端、要守的东西在哪一端、走道大致怎么折（几个横段、几个竖段）。

**还应当写**（下游要靠它们认东西）：
- 守的东西是什么（形状、颜色、上面摆着什么）；
- 有哪几种机关，各自长什么样（它们是**装在走道边的空位**上的）；
- 有哪几种敌人，各自长什么样、走得快还是慢、经打还是脆；
- 界面上有什么（状态条、按钮、图标）；
- 一句「这一关怎么算赢、会不会死」。

⚠️ **不要写数值**（伤害、血量、造价）—— 那是关卡编译那一步的事，
而它有一份**量出来的**参考刻度（写弱一点比写强一点安全 10 倍）。
```
