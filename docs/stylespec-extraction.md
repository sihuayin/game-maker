# 从参考图产出一份 StyleSpec

> 这份文件是[票 39](../.scratch/game-creation-v1/issues/39-palette-role.md) 的产物。
> 它存在的理由很直白：**这件事每个世界都要重做一次**（[R11](../.scratch/game-creation-v1/map.md)），
> 而在它之前，「该对模型说什么」**只活在一个实验脚本里**
> （`.scratch/game-creation-v1/experiments/stylespec-extraction/prompt.mjs`）——
> 换一张参考图的人没有任何地方可查。被依赖的东西必须有承载它的地方。

## 它是什么

**一次交互，不是一次管线调用。** R11 把它定成「**人在 Claude Code 会话里让模型看图、
产出 StyleSpec JSON、存成文件**」，管线**只消费那个文件**（`derive` 的 `--style`）。

这条分工不是将就：它是[票 35](../.scratch/game-creation-v1/issues/35-bitmap-provenance.md)
查清条款之后**唯一**既合规又能用的路，而且它有一个额外的好处 ——
**那份文件是人过目过的**，管线拿到的是一个已经被人看过的输入。

## ⚠️ 先读这一条：`palette` 是**绘制词汇**，不是画面分布的摘要

这是票 15 量出来、票 39 定死的一件容易搞反的事。

`palette` 的**功能**是给 drawlist 的 `palette:N` 当取值域（硬编码 hex 会被 schema 直接拒）。
它要回答的是「**这个世界里的东西能不能被画出来**」，不是「这张图主要由什么颜色组成」。

两条会把人带偏的事实：

- 参考图**根本没有**「占比」可摘。票 15 量到它有 **122,240 种颜色**，占比最高的色只有 **1.42%**；
  **83% 的像素饱和度 ≤ 25**。按面积分配的九色**必然全灰** ——
  而那套全灰色板**画不出橙色海报、青绿机器外壳、橄榄绿罐子**。
- 票 04 更狠：上游重编码 ⇒ **精确读色不可能**（送纯单色图 5 次零命中）。
  ⇒ 色板**永远是近似**，契约只要求「颜色 ∈ 色板（相对于本 StyleSpec）」，从不要求它等于参考图。

### 所以：**选**色是对的，**排**色是错的

- ✅ **选**：每个色必须**真的出现在这张图里** —— 不要补全、不要凭空发明。
  （票 01 的实测：不加这句会有色板幻觉。）
- ❌ **排**：**不要**按画面占比从高到低排序，也不要拿占比当评价标准。
  那句排序指令与「只列真实存在的颜色」**挨着写在同一段里**，一半可信一半有害 ——
  这就是它一直没被察觉的原因。

### ⚠️ 还有一件事从 `constraints` 里拿掉

**不要写「某色面积 < X%」这类数值上限。** 两个理由：

1. **R2 之后没有任何东西会校验它** —— 那是一句**字符串**，不是一条规则。
2. 更要紧的是：**它把重音色当成污染物**。而按上面的定义，重音色恰恰是色板**必须有**的那部分。

## 过程

1. **准备两份东西**
   - **参考图**（放进 `inputs/` 或 `fixtures/reference/`）
   - **需求文本**（例如 `inputs/last-train/PROMPT.md`）——
     ⚠️ **一定要给**。色板的判据是「能不能画出这个世界里的东西」，
     而**要画的东西有一部分压根不在参考图里**，需求正好点名了它们。
     （Destination 的原话：参考图里没有火车、信号灯、行李、赶末班车的人 —— 但它们必须属于同一个世界。）
     ⚠️ **资源清单给不了** —— `derive` 要用 StyleSpec 当输入，所以提取的时候清单**还不存在**。
2. **在 Claude Code 会话里发一次**（就一次，用下面的提示词全文）
3. **把结果存成文件**：`fixtures/style-spec.<世界名>.json`，
   并在旁边写一份 `<同名>.provenance.json`（见下）
4. **人过目** —— 尤其是 `palette`：**它画得出这个世界里的东西吗？**
   （可以拿 `game-maker inspect <资源包>` 看交付态实际用色，但那是**观察不是判据**）

## 提示词全文（可直接复制）

```
这是一张游戏截图，将作为**风格参考图**。

提取它的**视觉语法**（视觉语法 = 这个世界长什么样、按什么规则长），
**不要描述画面内容**、不要提 UI 文字、不要复述剧情。

palette 的选择标准是**能不能画出这个世界里的东西**，不是它在图上占多大面积：
- 每个色都**必须真的出现在这张图里** —— 不要补全猜测色、不要凭空发明
- ⚠️ **不要**按画面占比从高到低排序。参考图往往 80% 以上是中性色，
  按占比分配的色板会**全是灰的**，而灰的色板画不出招牌、发光屏、机器外壳、罐子这些**必须画得出来**的东西
- 顺序随意。下面还给了这个世界**将来要画什么**，照它挑能画出那些东西的颜色

constraints 只写**生成新资源时必须遵守的规则**，
⚠️ **不要**写「某色面积 < X%」这类数值上限 —— 那类句子会把**重音色当成污染物**，
而这个色板恰恰需要重音色。

严格按以下 JSON 结构输出，只输出 JSON 本体，不要 markdown 围栏、不要解释：

{
  "id": "string（短 slug）",
  "identity": "string[] 3-6 个风格气质词",
  "camera": {"mode":"string","angle":"string"},
  "composition": {"layout":"string","density":"string"},
  "palette": "string[] 6-10 个 #RRGGBB",
  "lighting": {"direction":"string","contrast":"string","ambience":"string"},
  "shapeLanguage": "string[] 形状特征",
  "material": "string[] 材质质感",
  "environment": "string[] 环境元素",
  "characterStyle": "string[] 角色画法",
  "constraints": "string[] 生成新资源时必须遵守的规则",
  "confidence": "number 0-1"
}

# 这个世界将来要画什么
<把需求文本贴在这里>
```

## 产物与 provenance

- 落盘：`fixtures/style-spec.<世界名>.json`
- provenance 放**兄弟文件**，**不塞进 StyleSpec 本体** ——
  塞进去会被 Zod 静默剥掉（`StyleSpecSchema` 是 `.strict()`）。
  照 `fixtures/style-spec.halt-dusk.provenance.json` 那份写：参考图的 sha256、
  用哪个模型、什么时候、**人改过什么**、以及**它的能力边界**。
- ⚠️ 规范化：hex 落盘时统一**小写 `#rrggbb`**（票 24 Q3：原样的大写过不了 schema）。

## ⚠️ 代价：它不可复现

同一张图提两次会得到**不同的色板**。这不是缺陷，是票 15 的结论 ——
**提取是构造，不是测量**。

而喂了需求文本之后，这件事更明显：**同一张图 + 不同的需求 ⇒ 不同的色板**。这是**有意的** ——
色板是**为这个世界挑的**，不是这张图的属性。
