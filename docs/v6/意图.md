# Intent-to-Mechanics Contract
## 游戏意图到可执行玩法机制的闭环需求文档

- 项目：`sihuayin/game-maker`
- 需求类型：P0 功能
- 建议模块：Game Design / Runtime / Gameplay QA / Pipeline
- 状态：待实施
- 文档版本：v1.0

---

## 1. 背景

当前 Game Maker 的核心目标是：

> 用户提供一张风格参考图和游戏意图，系统自动生成符合视觉风格、玩法意图明确、资源完整且可实际游玩的游戏 Demo。

当前流水线大致为：

```text
Style Image + Game Intent
        ↓
VisualWorldSpec + GameIntentSpec
        ↓
GameDesignSpec
        ↓
AssetRecipe
        ↓
Asset Generation
        ↓
AssetPack
        ↓
GameConfig
        ↓
Runtime
        ↓
Visual QA + Gameplay QA + Intent QA
        ↓
Playable Game
```

现阶段系统已经能够对输入进行解析，并在设计、资源和运行时阶段执行多种约束检查。

但近期 P0-FINAL Stage A 重跑暴露出一个真实阻塞：

- `VisualWorldSpec` 阶段通过。
- `GameIntentSpec` 阶段通过。
- `GameDesignSpec` 阶段失败。
- R12 报告 `intent-mechanic-missing`。
- 意图中的 `open-chest`（开启宝箱）和 `avoid-danger`（躲避危险）无法映射到设计层当前封闭的机制集合。

当前已知机制集合包括：

```text
run
jump
gravity
collide-terrain
collect-pickup
moving-platform
hazard-contact
reach-goal
```

系统拒绝生成不满足机制约束的设计是正确行为。问题不是应该放宽检查，而是：

**系统尚未建立一套可扩展、可执行、可验证的意图机制契约。**

---

## 2. 目标

建立 Intent-to-Mechanics Contract，使系统能够将用户的自然语言游戏意图转化为：

1. 明确的玩法机制需求。
2. 可验证的机制契约。
3. 设计层可表达的机制配置。
4. 运行时可执行的机制行为。
5. Gameplay QA 可验证的行为断言。
6. 端到端流水线可追踪的机制满足情况。

本需求的最终目标不是单纯增加两个机制，而是建立机制从意图到可玩游戏的完整闭环。

### 2.1 核心目标

- 解决 `open-chest` 和 `avoid-danger` 的机制缺失问题。
- 避免设计层声明支持某机制，但运行时没有对应行为。
- 避免运行时实现了机制，但 QA 无法证明它满足用户意图。
- 避免通过切换模型、放宽 R12 或跳过 QA 隐藏机制缺失。
- 为后续机制扩展建立统一契约。

### 2.2 非目标

本需求暂不包含：

- 跨游戏项目机制复用。
- 跨项目设计知识迁移。
- 通用游戏编辑器。
- 新增完整游戏类型。
- 大规模重构所有现有机制。
- 以增加模型调用次数代替机制能力建设。
- 为了通过验收而降低已有质量门槛。

---

## 3. 设计原则

### 3.1 机制必须端到端可追踪

每个机制必须具有稳定标识，并能关联：

```text
Intent Requirement
    ↓
Mechanic Contract
    ↓
GameDesignSpec
    ↓
GameConfig
    ↓
Runtime Behavior
    ↓
Gameplay QA Assertion
```

不能仅凭设计文档中出现了机制名称，就认定机制已被实现。

### 3.2 声明支持不等于真正支持

一个机制只有在以下条件同时满足时，才能标记为可用：

- 契约定义完整。
- 设计层能够表达。
- GameConfig 能够配置。
- Runtime 能够执行。
- Gameplay QA 能够验证。
- E2E 能够证明其行为。

### 3.3 保留严格失败语义

当用户要求的机制无法实现时：

- 应明确报告缺失机制。
- 不应静默删除用户意图。
- 不应把机制替换为语义不等价的机制。
- 不应通过跳过检查来继续流水线。
- 不应将模型重试作为机制能力缺失的解决方案。

### 3.4 兼容现有机制

现有机制应通过统一契约注册，而不是被无必要地重写。

## 4. 功能需求

### FR-01：Mechanic Capability Registry

建立统一的机制能力注册表。

每个机制至少需要定义：

| 字段 | 说明 |
|---|---|
| `id` | 稳定机制标识 |
| `version` | 契约版本 |
| `description` | 机制语义 |
| `entities` | 机制涉及的实体 |
| `triggers` | 机制触发条件 |
| `stateChanges` | 机制导致的状态变化 |
| `runtimeSupport` | 对应运行时能力 |
| `configSchema` | 配置结构 |
| `qaProbes` | 对应的 QA 验证项 |
| `status` | 支持状态 |

建议支持状态：

```text
experimental
supported
deprecated
```

只有 `supported` 状态的机制，才能被用于正式 E2E 生成。

机制注册表必须是设计层、运行时和 QA 共享的能力来源，避免各模块维护相互矛盾的机制列表。

### FR-02：Intent Mechanic Extraction

从 `GameIntentSpec` 中提取用户要求的机制。

例如：

```text
玩家在废土中寻找宝藏。
玩家可以打开宝箱获取奖励。
玩家需要躲避危险。
玩家最终到达撤离点。
```

应得到类似的机制需求：

```text
run
collect-pickup
open-chest
avoid-danger
reach-goal
```

提取结果应区分：

- 明确要求的机制。
- 由玩法自然推导的机制。
- 可选机制。

不能将推导机制与用户明确要求的机制混为一谈。

每个机制需求应保留来源信息，例如：

```text
requirementId
mechanicId
sourceText
sourceType
priority
```

其中 `sourceType` 用于区分用户明确要求与系统推导。

### FR-03：Mechanic Contract Validation

设计阶段生成 `GameDesignSpec` 后，应执行机制契约检查。

检查内容包括：

- 用户要求的机制是否存在。
- 机制是否处于 `supported` 状态。
- 设计是否提供必要的实体与参数。
- 机制之间是否存在冲突。
- 机制是否能够映射到运行时。
- 是否存在无法满足的玩法约束。

对于缺失机制，应返回结构化错误。

示例：

```json
{
  "code": "intent-mechanic-missing",
  "mechanicId": "open-chest",
  "requirementId": "intent-03",
  "stage": "design",
  "reason": "No supported design/runtime implementation is registered."
}
```

具体字段应遵循仓库现有错误契约；以上仅为语义示例，不要求直接照搬字段。

### FR-04：设计层机制表达

`GameDesignSpec` 必须能够表达机制所需的玩法信息。

对于 `open-chest`，至少需要表达：

- 宝箱实体。
- 玩家与宝箱的交互范围。
- 交互触发方式。
- 宝箱打开状态。
- 奖励内容。
- 奖励发放条件。
- 是否允许重复打开。

对于 `avoid-danger`，至少需要表达：

- 危险实体或危险区域。
- 危险触发条件。
- 玩家受到的影响。
- 危险行为的时间或空间特征。
- 玩家可采取的规避方式。
- 机制结束或恢复条件。

具体字段和数据结构应由现有 `GameDesignSpec`、`GameConfig` 结构决定，不应在未检查仓库契约的情况下另造一套平行 Schema。

### FR-05：Runtime Mechanic Implementation

Runtime 必须真正执行设计中声明的机制。

#### open-chest

最低行为要求：

1. 玩家能够接近宝箱。
2. 玩家在有效范围内触发交互。
3. 宝箱状态从关闭变为打开。
4. 奖励按照配置发放。
5. 宝箱状态能够被记录。
6. 重复交互不能重复发放一次性奖励。
7. 交互范围外的输入不应打开宝箱。

#### avoid-danger

最低行为要求：

1. 游戏中存在可识别的危险实体或危险区域。
2. 危险能够按照配置触发。
3. 玩家能够通过游戏输入或行为规避危险。
4. 危险触发后产生明确、可观察的结果。
5. 危险状态变化能够被记录。
6. 玩家规避成功与失败能够被 QA 区分。

具体惩罚、移动方式、伤害数值等应由 GameConfig 决定，不在本需求中固定为某一种玩法。

### FR-06：Gameplay QA Mechanic Probes

为每个机制提供可执行的 QA Probe。

QA 不应只检查配置中是否存在机制 ID，而应验证实际行为。

#### open-chest QA

至少验证：

- 宝箱存在。
- 玩家能够接近宝箱。
- 交互能够触发打开状态。
- 奖励被正确发放。
- 奖励不会重复发放。
- 无效距离下交互不生效。

#### avoid-danger QA

至少验证：

- 危险能够触发。
- 危险触发结果符合配置。
- 存在有效规避路径或操作。
- QA 能够区分成功规避与未规避。
- 危险状态不会导致无法恢复的意外卡死，除非设计明确要求该结果。

QA 输出必须关联对应的 `requirementId` 和 `mechanicId`。

### FR-07：Intent Coverage Report

在 Gameplay QA 和 E2E 阶段输出机制覆盖报告。

建议报告结构：

```text
Intent Mechanic Coverage
├── Required Mechanics
│   ├── open-chest
│   ├── avoid-danger
│   └── reach-goal
├── Design Coverage
├── Runtime Coverage
├── QA Coverage
└── Final Result
```

每个机制应有独立结果：

```text
satisfied
missing
unsupported
not-tested
failed
```

不能用总体通过状态掩盖单个必需机制失败。

### FR-08：Pipeline Gate

机制契约应作为正式流水线 Gate。

推荐检查顺序：

```text
Intent Extraction
    ↓
Capability Resolution
    ↓
Design Generation
    ↓
Design Contract Validation
    ↓
Asset Compilation
    ↓
GameConfig Compilation
    ↓
Runtime Execution
    ↓
Mechanic QA
    ↓
Intent Coverage Report
    ↓
E2E Acceptance
```

如果某个用户必需机制没有可用的端到端能力，应在尽可能早的阶段失败，避免继续产生不必要的资源成本。

## 5. 核心数据模型建议

以下为概念模型。正式字段必须与仓库现有契约对齐。

### 5.1 Mechanic Requirement

```ts
type MechanicRequirement = {
  requirementId: string;
  mechanicId: string;
  sourceText: string;
  sourceType: "explicit" | "inferred";
  priority: "required" | "optional";
};
```

### 5.2 Mechanic Capability

```ts
type MechanicCapability = {
  id: string;
  version: string;
  description: string;

  entities: string[];
  triggers: string[];
  stateChanges: string[];

  configSchema: unknown;

  runtimeSupport: {
    status: "experimental" | "supported" | "deprecated";
  };

  qaProbes: string[];
};
```

### 5.3 Mechanic Coverage

```ts
type MechanicCoverage = {
  requirementId: string;
  mechanicId: string;

  design: "satisfied" | "missing" | "failed";
  runtime: "satisfied" | "missing" | "failed";
  qa: "satisfied" | "not-tested" | "failed";

  evidence: string[];
};
```

以上类型仅用于说明概念，不要求直接复制到仓库。实现时应优先复用现有 contracts 包。

## 6. P0 实施范围

### P0-1：机制契约与能力注册表

- 梳理现有机制。
- 建立统一能力注册表。
- 将现有机制迁移到统一注册结构。
- 明确设计层、运行时和 QA 的机制能力边界。
- 保留现有机制的行为与兼容性。

### P0-2：实现 open-chest

- 定义机制契约。
- 设计层能够表达。
- GameConfig 能够配置。
- Runtime 能够执行。
- Gameplay QA 能够验证。
- 加入重复奖励防护。

### P0-3：实现 avoid-danger

- 定义机制契约。
- 设计层能够表达。
- GameConfig 能够配置。
- Runtime 能够执行。
- Gameplay QA 能够验证。
- 支持规避成功与失败的判定。

### P0-4：Intent Coverage Report

- 建立机制覆盖报告。
- 报告关联需求来源。
- 报告区分设计、运行时、QA 三个层次。
- 对必需机制执行严格 Gate。

### P0-5：P0-FINAL E2E 重跑

使用现有废土寻宝风格图和意图进行端到端验收。

不允许手工编辑中间 JSON 来绕过流水线。

## 7. 验收标准

### AC-01：机制能力完整性

每个标记为 `supported` 的机制必须具备：

- 设计表达。
- GameConfig 表达。
- Runtime 实现。
- Gameplay QA Probe。

不满足任一项的机制不能被标记为 `supported`。

### AC-02：open-chest

自动化测试证明：

- 宝箱能够打开。
- 奖励能够正确发放。
- 一次性奖励不会重复发放。
- 无效距离下交互不生效。
- QA 能够输出明确的机制验证结果。

### AC-03：avoid-danger

自动化测试证明：

- 危险能够触发。
- 危险结果符合配置。
- 玩家能够执行有效规避。
- QA 能够判定规避成功与失败。

### AC-04：Intent Coverage

对于每个用户明确要求的机制：

- 必须存在对应的机制需求记录。
- 必须存在对应设计。
- 必须存在运行时实现。
- 必须有 QA 证据。
- 必须进入最终覆盖报告。

### AC-05：失败语义

当机制未实现时：

- 返回明确错误。
- 保留机制 ID 和需求来源。
- 不静默降级。
- 不跳过 Gate。
- 不通过切换模型或放宽验证掩盖问题。

### AC-06：E2E

给定风格图和游戏意图：

```text
Style Image + Intent
        ↓
Design
        ↓
Assets
        ↓
GameConfig
        ↓
Playable Runtime
        ↓
Gameplay QA
        ↓
Intent Coverage Report
```

整个流程必须自动完成。

最终游戏必须满足：

- 玩家能够移动。
- 玩家能够执行意图要求的玩法机制。
- 宝箱能够正确交互并发放奖励。
- 危险机制能够被触发和规避。
- 玩家能够到达目标。
- Gameplay QA 能够提供对应机制的证据。
- 不需要人工修改中间 JSON。

## 8. 测试策略

### 单元测试

- 机制注册表查询。
- 机制状态与版本校验。
- 意图机制提取。
- 机制契约验证。
- 机制覆盖报告生成。

### Runtime 测试

- 宝箱交互范围。
- 宝箱打开状态变化。
- 奖励发放与防重复。
- 危险触发。
- 危险规避。
- 危险状态恢复。

### Gameplay QA 测试

- 每个机制对应的 Probe。
- Probe 结果与运行时状态一致。
- 机制失败能关联原始意图。

### E2E 测试

- 使用现有 P0-FINAL 输入。
- 不人工编辑中间产物。
- 记录各阶段状态。
- 记录机制覆盖报告。
- 记录失败原因与实际成本。

## 10. 风险与约束

### 风险一：注册表与实际运行时能力不一致

应通过测试或构建检查，防止机制被错误标记为 `supported`。

### 风险二：机制契约过度抽象

第一阶段只解决现有机制与两个真实阻塞机制，不应为了未来可能的游戏类型构建过度通用的机制框架。

### 风险三：QA 只检查配置，不检查行为

QA Probe 必须能够观察或控制实际运行时行为，不能仅凭 `GameConfig` 存在对应字段判定成功。

### 风险四：为通过 E2E 而弱化 Gate

本需求要求修复真实能力缺失，不允许通过关闭 R12、减少必需机制或跳过 Gameplay QA 达成通过。

---

## 11. 完成定义（Definition of Done）

本需求完成时：

- [ ] 机制能力注册表已建立。
- [ ] 现有机制已统一注册。
- [ ] `open-chest` 完成端到端实现。
- [ ] `avoid-danger` 完成端到端实现。
- [ ] 两个机制均有自动化 QA Probe。
- [ ] Intent Coverage Report 已输出。
- [ ] Pipeline Gate 已接入。
- [ ] 现有机制测试未发生非预期回归。
- [ ] P0-FINAL E2E 完成重跑。
- [ ] E2E 不需要人工修改中间 JSON。
- [ ] 所有失败均保留可追踪证据。

## 12. 最终判断

当前 Game Maker 的主要问题已经不只是“能否生成游戏资源”，而是：

> 系统能否把用户明确提出的玩法意图，转化为真实运行、可验证、可追踪的游戏行为。

Intent-to-Mechanics Contract 是连接设计、运行时与 Gameplay QA 的关键基础能力。

本需求以 `open-chest` 和 `avoid-danger` 为切入点，建立一套最小但完整的机制闭环，为后续提高游戏意图满足率和 E2E 成功率提供基础。
