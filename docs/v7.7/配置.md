# PRD：Design-to-Config V1
## 游戏设计到可执行配置的语义编译与验证

- **项目**：game-maker V2
- **需求编号**：DTConfig-V1
- **优先级**：P0
- **状态**：待实施裁定
- **类型**：工程能力建设 / 可靠性改进
- **预算要求**：零付费、零模型调用、零生图
- **适用范围**：单个游戏项目的 Design → GameConfig → Runtime 编译链路

---

## 1. 背景与问题

### 1.1 项目现状

game-maker 已经具备从游戏意图到可玩游戏交付的主要工程链路：

1. 输入参考图片和游戏 Intent。
2. 生成游戏设计与机制描述。
3. 生成视觉规范和资源设计。
4. 生产角色、场景、道具及动画资源。
5. 生成游戏配置和关卡配置。
6. 通过 Phaser Runtime 执行游戏。
7. 通过 QA、Playtest 和 Delivery 验证游戏。
8. 通过 Evidence CI 保证验收证据的可信度。

当前系统已经具备较完整的资源生产、机制识别、Runtime 执行和证据验证能力。

但这条链路仍存在一个关键问题：

**上游生成的设计和资源，即使分别符合各自的数据结构，也不代表它们组合后能够形成正确的 Runtime 配置。**

### 1.2 已发生的真实失败

2026-10-23 的 P0-FINAL 真实付费重跑中：

| 阶段 | 结果 |
|---|---|
| Intent 理解 | 成功 |
| 机制映射 | 成功 |
| 资源生成 | 12 次 Gemini 生图全部成功 |
| 资源生成重试 | 0 次 |
| 资源生成费用 | 约 $0.40 |
| compile-runtime | 失败 |
| GameConfig 业务校验 | 5 个硬错误 |

五个错误：

| 编号 | 错误 | 本质问题 |
|---|---|---|
| E01 | `block-1` 引用 `scavenger-hero` | 角色资源被错误用作地形块 |
| E02 | `slope-1` 引用 `scavenger-hero` | 角色资源被错误用作斜坡 |
| E03 | `hud.panel` 引用 `chest` | Sprite 资源被错误用作 UI |
| E04 | `hud.pip` 引用 `resource-item` | 玩法 Sprite 被错误用作 UI |
| E05 | HUD 尺寸为 72×32，但资源实际只有 32×24，且不支持九宫格 | UI 尺寸与资源能力不匹配 |

这次失败说明：

- 资源生成成功，不等于资源可以正确使用。
- JSON 符合 Schema，不等于配置具有正确的游戏语义。
- 机制映射正确，不等于 Runtime 装配正确。
- 上游输出之间缺少足够严格的语义约束。

失败时 config/site 没有落盘，现有失败保护行为符合预期，不应为了修复本问题而改变。

### 1.3 核心问题定义

当前最需要补齐的不是资源生成能力，而是：

**Design、Asset Manifest、Visual Design 和 GameConfig 之间缺少一层可确定性验证的语义编译约束。**

系统需要判断的不只是：

> 这个资源 ID 是否存在？

还需要判断：

> 这个资源是否具有当前槽位要求的语义？它的动画、尺寸和使用方式是否满足 Runtime 的要求？

## 2. 产品目标

### 2.1 核心目标

建设 Design-to-Config V1，使游戏设计和资源能够被可靠地编译为 Runtime 可执行配置。

具体目标：

1. 建立设计对象与资源类型之间的语义约束。
2. 建立 GameConfig 槽位与资源能力之间的兼容性校验。
3. 明确动画资源的引用规则。
4. 验证 UI 资源尺寸及其使用能力。
5. 在配置编译阶段发现并准确定位语义错误。
6. 保证合法配置仍能正常进入 Runtime。
7. 建立历史失败场景的确定性回归测试。

### 2.2 成功标准

完成后，系统应能在进入 Runtime 之前识别：

- 玩家角色不能被用作地形。
- 普通玩法 Sprite 不能被用作 UI。
- 动画资源引用必须明确对应的动画状态。
- UI 尺寸不能超过资源实际支持的能力。
- 资源缺失或类型不兼容不能被静默忽略。
- 配置中的资源引用必须与资源 Manifest 保持一致。

### 2.3 非目标

本版本不解决：

- 自动生成新的游戏机制。
- 重写 Phaser Runtime。
- 重构完整的资源生产流水线。
- 增加新的 Demo 或游戏类型。
- 自动修复所有不合法配置。
- 通过模型重试掩盖配置错误。
- 重新执行付费生图。
- 修改历史冻结 Demo。
- 建立跨游戏的设计复用或知识迁移系统。

## 3. 核心设计原则

### 3.1 Schema 合法不等于语义合法

Schema 负责数据结构约束。

语义校验负责数据之间的业务关系。

两者必须独立存在，不能用扩大 Schema 的方式替代全部业务验证。

### 3.2 以真实 Runtime 能力为准

语义规则必须从现有代码和数据契约中推导，不能凭产品设想直接增加资源类型或槽位类型。

例如，不能在没有审计现有 Runtime 的情况下，直接假定所有项目都支持 `terrain`、`collectible` 或 `interactive-object` 等资源类别。

### 3.3 确定性优先

相同的输入必须产生相同的校验结果。

校验不依赖模型，不依赖随机数，不依赖外部 API。

### 3.4 不静默降级

发生资源类型不匹配、引用缺失、动画状态不明确等问题时，应返回明确错误。

不能自动选择一个看似可用的资源来掩盖错误。

### 3.5 保持现有架构边界

优先在现有 `game-design`、`assets`、`contracts`、`pipeline` 和 `qa` 包中定位职责。

不新增不必要的包，不改变 Runtime 的执行模型。

## 4. 功能需求

### FR-01：设计对象与资源语义校验

系统必须能够判断设计对象所使用的资源是否符合其业务语义。

建议检查以下关系，最终以现有契约和 Runtime 审计结果为准：

| 使用场景 | 必须验证的语义 |
|---|---|
| 玩家 | 资源支持角色或玩家所需表现 |
| 敌人 | 资源支持敌人所需表现 |
| 地形块 | 资源具有地形或对应场景对象能力 |
| 斜坡 | 资源具备对应的地形表现能力 |
| 收集物 | 资源符合收集物使用约束 |
| 宝箱 | 资源符合交互对象使用约束 |
| 危险物 | 资源符合危险对象使用约束 |
| 背景 | 资源符合背景使用约束 |
| HUD | 资源符合 UI 使用约束 |

要求：

1. 校验设计对象与资源的对应关系。
2. 检查资源类型是否兼容。
3. 检查引用资源是否真实存在。
4. 对不兼容情况返回确定性错误。
5. 不允许通过资源 ID 存在性检查替代语义检查。

### FR-02：GameConfig 槽位兼容性校验

系统必须识别 GameConfig 中不同槽位对资源的要求。

至少覆盖：

- 玩家槽位。
- 敌人槽位。
- 地形槽位。
- 斜坡槽位。
- 收集物槽位。
- 交互对象槽位。
- 危险物槽位。
- 背景槽位。
- HUD 面板槽位。
- HUD 图标槽位。

每个槽位需要有明确的资源兼容规则。

要求：

1. 规则来源必须是现有 GameConfig 契约和 Runtime 消费逻辑。
2. 不兼容资源必须被拒绝。
3. 兼容规则必须有正向和负向测试。
4. 不得为通过历史案例而硬编码特定资源 ID。

### FR-03：动画引用完整性

当资源包含多个动画时，GameConfig 必须明确指定需要使用的动画。

例如，一个角色可能同时拥有：

- idle
- run
- jump
- hurt

如果配置引用的是多动画角色资源，但没有明确指定动画状态，则必须根据现有 Runtime 契约判断是否属于错误。

要求：

1. 检查动画引用是否存在。
2. 检查动画名称是否有效。
3. 检查动画引用是否满足 Runtime 的使用要求。
4. 不允许在缺少必要信息时静默使用默认动画。
5. 错误应包含实体 ID、动画字段和资源 ID。

### FR-04：UI 资源能力与尺寸校验

HUD 不能直接使用普通玩法 Sprite 代替 UI 资源。

系统需要校验：

1. HUD 引用资源的类型是否满足 UI 要求。
2. 资源的实际宽高是否满足配置要求。
3. 如果配置使用九宫格，资源是否支持九宫格。
4. 如果配置要求特定尺寸，资源是否具备对应能力。
5. 是否存在尺寸声明与实际资源不一致的情况。

具体尺寸规则必须基于现有 UI Runtime 和资源契约审计确定。

不得直接假定所有 UI 资源都必须与目标显示尺寸完全一致；应区分实际资源尺寸、显示尺寸、缩放能力和九宫格能力。

### FR-05：资源引用完整性

编译时检查：

- 资源 ID 是否存在。
- 引用的资源是否属于当前项目。
- 资源类型是否符合使用位置。
- 动画引用是否存在。
- 资源能力声明是否完整。
- 是否存在无法解析的引用。

不允许缺失资源被自动替换为其他资源。

### FR-06：错误诊断

错误信息必须足够精确，能够直接指导开发者定位问题。

建议统一包含：

| 字段 | 说明 |
|---|---|
| code | 稳定错误代码 |
| entityId | 发生错误的实体 ID |
| field | 出错字段 |
| assetId | 相关资源 ID |
| expected | 预期能力或类型 |
| actual | 实际能力或类型 |
| message | 面向开发者的错误描述 |

示例：

```json
{
  "code": "ASSET_SLOT_TYPE_MISMATCH",
  "entityId": "block-1",
  "field": "asset",
  "assetId": "scavenger-hero",
  "expected": "terrain-compatible",
  "actual": "character",
  "message": "地形对象不能引用角色资源"
}
```

以上错误代码和字段仅作为设计示例，正式名称应在审计现有错误体系后确定。

要求：

1. 错误代码稳定。
2. 错误信息可测试。
3. 同一问题不能因为执行顺序不同而产生不确定结果。
4. 不以模糊的 `invalid config` 代替具体诊断。
5. 不将普通警告升级为硬错误，除非契约明确要求。

### FR-07：编译阶段接入

语义校验必须接入现有 `compile-runtime` 流程。

执行顺序原则：

1. 读取并解析设计和资源数据。
2. 执行现有 Schema 校验。
3. 执行资源引用完整性校验。
4. 执行设计对象与资源语义校验。
5. 执行 GameConfig 槽位兼容性校验。
6. 执行动画和 UI 能力校验。
7. 通过后进入现有 Runtime 编译流程。

具体调用顺序以源码审计结果为准。

要求：

- 语义校验失败时不得产生有效的最终 GameConfig。
- 不改变现有失败现场保留机制。
- 不覆盖历史 run 或 pack。
- 不绕过现有 `auditReferences`。
- 不改变现有 Delivery 的最终验收含义。

## 5. 工程实施范围

### 5.1 第一期：只读源码审计

目标：确认五个历史错误分别由哪个模块产生、在哪个阶段能够被阻止。

必须检查：

- `compile-runtime` 实现及调用链。
- GameConfig Schema。
- Asset Manifest Schema。
- 设计对象和资源的关联模型。
- `auditReferences`。
- Runtime 对资源的实际消费逻辑。
- 动画资源元数据。
- UI 资源元数据及尺寸处理逻辑。

输出：

1. 完整调用链。
2. 五个历史错误的根因。
3. 当前已有校验能力清单。
4. 校验缺口清单。
5. 最小修改模块清单。
6. 测试矩阵。
7. 是否需要扩展现有契约的结论。

本阶段不修改生产代码。

### 5.2 第二期：语义校验实现

根据审计结论实施：

- 资源槽位兼容性校验。
- 动画引用完整性校验。
- UI 资源能力校验。
- 资源引用完整性校验。
- 错误诊断。
- `compile-runtime` 集成。

优先复用现有契约和纯函数边界。

除非审计证明现有契约无法表达必要信息，否则不扩展对外 Schema。

### 5.3 第三期：确定性回归测试

将五个历史错误转化为独立测试。

每个错误都必须：

1. 有最小复现 fixture。
2. 能稳定触发对应错误。
3. 能验证错误代码。
4. 能验证错误定位字段。
5. 能验证不会生成有效配置。

同时增加合法配置回归测试。

### 5.4 第四期：Runtime 装配验证

通过合法 fixture 验证：

1. 配置编译成功。
2. 资源引用完整。
3. Runtime 正常装配。
4. 游戏可以启动。
5. `playable-smoke` 通过。
6. 不影响现有机制和游戏运行。

## 6. 验收标准

### AC-01：历史五个错误全部拦截

| 测试 | 输入 | 预期结果 |
|---|---|---|
| AC-01-1 | 玩家资源被地形块引用 | 明确拒绝 |
| AC-01-2 | 玩家资源被斜坡引用 | 明确拒绝 |
| AC-01-3 | 普通 Sprite 被用作 HUD Panel | 明确拒绝 |
| AC-01-4 | 普通 Sprite 被用作 HUD Icon | 明确拒绝 |
| AC-01-5 | UI 尺寸超出资源能力且不支持九宫格 | 明确拒绝 |

五项均必须通过确定性自动化测试。

### AC-02：合法配置通过

至少包含：

- 合法玩家资源。
- 合法地形资源。
- 合法斜坡资源。
- 合法敌人资源。
- 合法收集物资源。
- 合法交互对象资源。
- 合法 HUD 资源。
- 合法多动画角色引用。

合法配置必须通过 Schema 和语义校验。

### AC-03：错误定位准确

每个负向测试必须能够定位：

- 具体实体。
- 具体字段。
- 具体资源。
- 预期条件。
- 实际条件。

不得只返回全局失败。

### AC-04：引用审计通过

合法配置必须通过现有 `auditReferences`。

语义校验不能替代已有引用审计。

### AC-05：Runtime 装配成功

合法 fixture 必须进入现有 Runtime，并通过：

- Runtime 启动。
- 资源加载。
- 配置装配。
- `playable-smoke`。

### AC-06：历史数据不受影响

必须证明：

- 不修改历史冻结 Demo。
- 不覆盖现有 `run/vN`。
- 不覆盖现有 `pack/site/vN`。
- 不改变版本号分配规则。
- 不改变失败运行保留规则。

### AC-07：零付费验证

本需求的全部自动化测试和 Runtime 验证必须满足：

- 零模型调用。
- 零生图调用。
- 零新增 API 费用。
- 不需要外部服务。

### AC-08：回归通过

至少通过：

- 新增语义校验测试。
- 相关 package 测试。
- 相关 typecheck。
- `pnpm check`。
- `pnpm test`。
- 合法 fixture Runtime 验证。

如果完整仓库测试因历史环境依赖无法运行，必须明确记录缺失项和原因，不得宣称全量通过。

## 8. 技术约束

### 8.1 架构约束

- 维持现有 package 分层。
- 不引入新的 GameCreationState。
- 不引入跨游戏共享设计知识。
- 不重写 Runtime。
- 不改变 MCP 和 CLI 的既有行为。
- 不随意扩展对外契约。
- 不引入新第三方依赖，除非另行审批。

### 8.2 数据约束

- 继续使用现有 Asset Manifest。
- 保留资源 ID 的唯一性和引用关系。
- 不改变资源文件和历史资产。
- 不修改历史冻结证据。
- 不允许校验阶段修改原始设计数据。

### 8.3 运行约束

- Node 22.23.2。
- pnpm 10.7.1。
- 复用现有测试和 Runtime 环境。
- 所有测试使用本地 fixture。
- 不执行付费生成。

### 8.4 版本和目录约束

继续遵循：

- `run/vN` 和 `pack/site/vN` 不覆盖。
- 临时构建目录使用现有 `.building-<pid>-<next N>` 机制。
- 失败运行不消耗正式版本号。
- 不修改既有版本分配和原子提交逻辑。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 现有资源类型无法表达业务语义 | 无法准确判断兼容性 | 先审计，必要时提出最小契约扩展 |
| Runtime 隐含使用默认动画 | 过度严格可能破坏合法配置 | 以真实 Runtime 消费逻辑为准 |
| UI 尺寸规则过于简单 | 错误拒绝可缩放资源 | 区分源尺寸、显示尺寸和九宫格能力 |
| 语义规则硬编码在 Pipeline | 后续难以维护 | 明确纯函数和规则边界 |
| 只针对历史案例修复 | 新错误仍然出现 | 增加通用正反向矩阵测试 |
| 校验与 Runtime 行为不一致 | 出现假通过 | 增加真实 Runtime 装配测试 |

## 10. 明确不做的事情

本版本不应演变为一个大规模重构项目。

禁止借此：

1. 重写 GameConfig。
2. 重写 Asset Manifest。
3. 重构全部资源生成逻辑。
4. 重写 Phaser Runtime。
5. 新增游戏机制。
6. 重新生成 FPVS-V1 Demo。
7. 启动 P0-02 第二个 Demo 的付费生成。
8. 引入自动修复或自动重试系统。
9. 修改 Evidence CI 双基线策略。
10. 将历史验收结果改写为通过。

任何超出本 PRD 的契约扩展、CLI/MCP 行为变化和新增依赖，都需要单独审批。

## 13. 最终验收结论

Design-to-Config V1 的目标不是让编译器接受更多配置，而是让系统能够可靠地区分：

- 结构合法但语义错误的配置。
- 资源存在但使用位置错误的配置。
- 资源合法且能够被 Runtime 正确执行的配置。

**最终成功标准：游戏设计和资源不再只是分别生成成功，而是能够被正确组合成一份经过验证、可由现有 Runtime 执行的 GameConfig。**

本需求完成后，建议下一优先级进入 Level Playability V1，解决机制组合、空间布局和关卡可通行性问题。

game-maker 下一阶段的核心方向是：

**从生成更多游戏内容，转向确保生成的内容能够正确组合成真正可玩的游戏。**
