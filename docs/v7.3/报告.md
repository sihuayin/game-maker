- **基线日期**：2026-10-26

## 1. 背景与问题定义

### 1.1 项目现状

截至基线提交，game-maker 已经具备从游戏创意到可玩网页 Demo 的主要能力。

现有主链路包括：

1. 输入风格参考图与游戏意图。
2. 生成视觉世界描述、游戏意图规格和游戏设计规格。
3. 生成角色设计与资源制作配方。
4. 生成、处理并验证游戏资源。
5. 编译游戏配置。
6. 使用固定 Runtime 构建可运行的网页游戏。
7. 执行 QA 和 headless playable smoke 检查。
8. 输出可通过静态站点托管的游戏产物。

最新提交记录表明，真实 `create → build → QA → site` 链路已通过一次端到端验收，生成了站点产物。

同时，最新提交还包含多项确定性问题修复：

- 背景覆盖率检查与提示词约束。
- 游戏意图到具体机制的拆解。
- 动画精灵表网格推导。
- 敌人资源尺寸约束。
- 自动试玩器对巡逻危险物的时序感知处理。

这些工作说明，项目已经不只是验证单个模块能否运行，而是在逐步解决生成结果是否符合交付要求的问题。

### 1.2 当前核心问题

**生成成功、构建成功、QA 通过和游戏完整合格，是四种不同的状态。**

当前需要进一步明确以下问题：

- 资源包通过结构校验，不代表最终画面与参考风格一致。
- 游戏配置成功编译，不代表真实游戏过程没有玩法问题。
- 自动试玩器未完成关卡，不一定代表游戏本身不可玩。
- 自动试玩器完成关卡，也不代表所有视觉和体验要求都已满足。
- 旧资源包的验收结果，不能被误用于新版本资源包。
- 缺少视觉评审记录时，不能把视觉质量默认视为通过。

如果这些状态没有统一的报告与验收规则，流水线就可能将“成功生成”误认为“已经达到交付标准”。

### 1.3 已知基线问题

#### A. 自动试玩未完全通过

最新提交记录的 headless smoke 结果为 **3/4**。

已知限制是：自动玩家无法跳过一个较宽的移动巡逻敌人，但记录认为真人可以完成该段玩法。

因此，不能直接将其判定为游戏不可玩，也不能将其视为完整试玩通过。应当保留失败步骤和证据，将其标记为“自动试玩未完成，原因待区分”。

#### B. 最终视觉人工对照尚未完成

基线记录中，P0-06 风格人工对照仍待完成。

这意味着，即使资源、配置、QA 和站点构建全部通过，最终视觉风格仍可能处于待确认状态。

#### C. 历史背景覆盖问题已进入修复基线

最新提交已经引入背景覆盖率门禁与相应提示词约束，针对背景层尺寸、视口高度、视差及可平铺要求进行处理。

因此，本需求不应重复实现背景覆盖功能，而应确认现有检查结果能够被纳入统一的验收报告，并在失败时保留可追溯信息。

## 2. 产品目标

### 2.1 核心目标

建立统一的**生成结果交付验收与证据报告**，将现有资源验证、配置校验、QA、运行检查、自动试玩和视觉评审结果汇总为一个可追溯的交付结论。

交付结论必须能够回答：

1. 本次游戏生成是否完整执行？
2. 资源包和游戏配置是否通过确定性校验？
3. 游戏站点是否成功构建？
4. 自动试玩是否完成，失败发生在哪一步？
5. 失败属于游戏缺陷、自动试玩器限制，还是尚未确定？
6. 最终视觉风格是否已经人工确认？
7. 当前版本是否满足正式交付条件？
8. 每一个结论对应哪一版资源、配置和站点产物？

### 2.2 成功标准

- 不需要人工拼接多个日志才能判断一次构建是否合格。
- 不把构建成功直接等同于交付通过。
- 不把自动试玩未完成直接等同于游戏不可玩。
- 不把未进行的视觉评审默认为通过。
- 不允许旧版本报告被错误地用于新版本产物。
- 所有失败都尽可能关联到具体阶段、资源、配置或试玩步骤。
- 验收流程优先复用现有产物，避免为验证而重复付费生图。

### 2.3 非目标

本阶段不负责：

- 重写现有 `create` 生成流水线。
- 新增游戏引擎或重构固定 Runtime。
- 替换现有资源生成路线。
- 引入完整的自动修复、自我进化或自动实验系统。
- 建设跨游戏知识复用、跨项目迁移或共享设计知识系统。
- 为了获得更高验收分数而重复进行付费生成。
- 将所有视觉质量要求强行转换为未经验证的数值阈值。
- 把自动试玩器升级为完整的人类行为模拟器。

## 4. 核心设计原则

### 4.1 不重造已有检查

优先复用现有资源校验、QA、构建和试玩结果。

如果某项能力已经提供结构化结果，应当消费其输出，而不是在新模块中复制一份同样的判断逻辑。

### 4.2 硬失败与未完成必须区分

至少区分以下情况：

- **FAIL**：确定性校验失败，或强制验收条件未满足。
- **INCOMPLETE**：检查没有完成，无法得出结论。
- **BLOCKED**：因前置条件失败而无法继续。
- **PASS**：该检查项已经完成且满足条件。
- **NOT_REQUIRED**：该检查项不适用于当前交付要求。

具体状态名可以与仓库现有枚举保持一致，但语义必须清晰。

不得使用一个简单的 `success: boolean` 覆盖全部状态。

### 4.3 试玩器失败不等于游戏失败

自动试玩失败后，应记录：

- 失败的试玩步骤。
- 最后一个成功步骤。
- 失败时的游戏状态或可用截图。
- 当前失败分类。
- 是否已有证据支持“试玩器能力不足”的判断。

若原因尚不明确，必须保留为未确定状态，不能自动归因于游戏，也不能直接归因于试玩器。

### 4.4 视觉验收独立于结构验收

以下结果不能互相替代：

- 色板合法。
- PNG 文件有效。
- 图集结构正确。
- 资源尺寸合理。
- 最终画面符合参考风格。

本阶段将视觉评审作为独立验收项记录。未经实际评审，不得自动设置为通过。

### 4.5 验收报告必须绑定具体产物

同一游戏项目可能经历多次资源生成、配置修改和站点构建。

报告必须明确对应哪个版本的资源包、配置和站点，不能仅根据项目名称或最近一次成功状态推断当前版本合格。

## 5. 功能需求

### FR-01：统一交付验收报告

**优先级：P0**

系统应当在现有构建和 QA 流程结束后，提供一份统一的交付验收报告。

#### 输入

- 当前构建或创建流程的执行结果。
- 资源包验证结果。
- 游戏配置编译结果。
- QA 结果。
- 站点构建结果。
- 自动试玩结果。
- 视觉评审记录（如果已完成）。

#### 输出

优先复用并扩展现有 `qa-report.json`，避免再创建语义重复的报告系统。

报告至少应能表达：

- 本次执行的标识。
- 资源包、配置与站点产物的版本标识。
- 各检查项的状态。
- 失败或未完成的原因。
- 可用的日志、截图或其他证据引用。
- 最终交付状态。
- 视觉评审状态。

实际字段应根据现有 schema 设计，避免为了满足文档而引入重复字段。

#### 验收标准

- 一次执行能够获得统一报告。
- 报告能够区分确定性失败、检查未完成和通过。
- 缺失的检查结果不会被自动解释为通过。
- 报告生成失败不会被静默忽略。

### FR-02：建立明确的最终交付状态

**优先级：P0**

最终交付状态必须综合强制检查项，而不能只读取某个阶段的成功标志。

建议采用以下语义：

| 最终状态 | 判定条件 |
|---|---|
| `PASS` | 所有强制检查均通过，且要求的视觉评审已通过 |
| `FAIL` | 任一确定性强制检查失败，或已确认存在交付阻断问题 |
| `INCOMPLETE` | 关键检查尚未执行、未完成，或结果不足以作出结论 |
| `BLOCKED` | 必要的前置阶段失败，导致后续检查无法进行 |

如果仓库已有不同的枚举，允许沿用现有命名，但必须保持上述语义。

#### 判定规则

1. 资源包确定性校验失败，最终交付不得通过。
2. 配置编译或强制 QA 失败，最终交付不得通过。
3. 站点未成功构建，最终交付不得通过。
4. 自动试玩未完成时，必须保留未完成状态，不得自动判定完整交付通过。
5. 要求的视觉评审尚未完成时，最终交付不能标记为完整通过。
6. 所有强制条件满足且视觉评审通过后，才能判定完整交付通过。

注意：`INCOMPLETE` 不代表游戏不可玩；`FAIL` 也应尽可能说明是哪个检查项失败。

### FR-03：记录自动试玩结果和证据

**优先级：P0**

系统应将现有 headless playable smoke 结果纳入统一报告。

#### 最低记录要求

- 试玩是否启动。
- 试玩是否完成。
- 计划执行的步骤数与实际完成的步骤数（如果现有工具提供）。
- 最后一个成功步骤。
- 失败步骤。
- 失败原因或分类。
- 可用的截图、日志或状态快照。
- 当前分类是否已经有证据支持。

#### 失败分类

建议支持以下语义分类：

- `GAMEPLAY_FAILURE`：有足够证据确认游戏玩法存在问题。
- `AGENT_LIMITATION`：有足够证据表明自动试玩器能力不足。
- `UNKNOWN`：目前无法可靠区分游戏问题与试玩器问题。
- `NOT_RUN`：试玩未执行。
- `INCOMPLETE`：试玩执行了，但未完成。

实际枚举以代码审计结果为准。

#### 已知场景验收

对于基线提交中的移动巡逻敌人场景：

- 自动玩家无法跳过宽巡逻敌人时，不得直接判定整个游戏不可玩。
- 如果没有充分证据证明是试玩器限制，应标记为原因未确定。
- 保留相关试玩步骤和证据。
- 试玩未完成时，不得将该项记为 `PASS`。

本阶段不要求彻底解决所有自动试玩失败，而是先让失败能够被正确解释和追踪。

### FR-04：视觉评审状态管理

**优先级：P0**

系统应明确记录最终视觉评审是否完成。

#### 状态

至少表达以下三种语义：

- `PENDING`：尚未完成评审。
- `PASS`：评审者确认满足当前视觉验收要求。
- `FAIL`：评审者确认存在不符合要求的问题。

如需记录评审取消、无效结果或重新评审，应在实现阶段根据实际流程补充。

#### 评审关联信息

在现有能力允许的情况下，记录：

- 对应的参考风格图。
- 被评审的资源包版本。
- 被评审的关键资源或最终游戏截图。
- 评审结论。
- 问题说明。
- 评审时间及可识别的评审来源。

不得仅凭 `inspectPack` 通过、色板匹配或图集结构合法，就将视觉评审设为通过。

#### 验收标准

- 新生成的资源包默认没有视觉通过结论。
- 视觉评审通过后，报告能够显示该状态。
- 新资源包生成后，不得继承旧资源包的视觉通过结论。
- 视觉评审不通过时，报告必须能够定位对应版本与问题说明。

### FR-05：报告与产物版本绑定

**优先级：P0**

每份验收报告都必须能够识别其对应的实际产物。

#### 必须关联的对象

1. 本次执行。
2. 资源包。
3. 游戏配置。
4. 站点产物。
5. 自动试玩结果。
6. 视觉评审结果。

优先复用仓库已有的 run ID、版本目录、校验和及资源标识，不新造平行的版本管理体系。

#### 规则

- 新资源包生成后，旧资源包的验收结论不得直接应用于新资源包。
- 配置发生变化后，旧配置的验收结果不得直接代表新配置已通过。
- 站点产物必须能够追溯到实际构建所使用的配置和资源。
- 如果无法确认某项结果属于哪个产物，应将其标记为无法关联，而不是默认有效。

#### 验收标准

- 使用同一个项目连续生成两个资源包时，报告能够区分两者。
- 第二个资源包不能错误继承第一个资源包的视觉通过状态。
- 历史报告仍然保留其原始关联，不因新版本生成而被覆盖或改写。

### FR-06：报告摘要与问题定位

**优先级：P1**

在统一报告的基础上，提供便于开发者阅读的摘要。

摘要应回答：

- 当前是否满足交付条件。
- 哪些强制检查失败。
- 哪些检查未完成。
- 是否存在自动试玩未完成的情况。
- 视觉评审是否完成。
- 最值得优先处理的问题是什么。

#### 输出原则

- 以真实检查结果为依据。
- 优先展示确定性问题。
- 区分错误、警告和待确认事项。
- 不把同一问题在多个阶段产生的重复记录当作多个独立缺陷。
- 保留指向原始日志或证据的引用。

本功能优先使用现有 CLI 和报告展示能力，不要求在本阶段建设新的 Web 管理后台。

## 6. 验收规则矩阵

以下场景是本需求必须覆盖的核心测试。

| 场景 | 资源 / 配置 / QA | 自动试玩 | 视觉评审 | 预期交付状态 |
|---|---|---|---|---|
| A. 全部通过 | 全部通过 | 完成 | 通过 | `PASS` |
| B. 资源校验失败 | 资源校验失败 | 未执行 | 待确认 | `FAIL` |
| C. 配置编译失败 | 配置失败 | 未执行 | 待确认 | `FAIL` |
| D. QA 失败 | 强制 QA 失败 | 任意 | 任意 | `FAIL` |
| E. 站点构建失败 | 前置检查通过，但构建失败 | 未执行或无法执行 | 待确认 | `FAIL` |
| F. 自动试玩未完成 | 其他强制检查通过 | 未完成，原因未知 | 通过 | 不得 `PASS`；按规则标记 `INCOMPLETE` |
| G. 疑似试玩器限制 | 其他强制检查通过 | 未完成，有试玩器限制证据 | 通过 | 不得 `PASS`；保留未完成状态 |
| H. 试玩完成但视觉未评审 | 全部通过 | 完成 | 待确认 | `INCOMPLETE` |
| I. 视觉评审失败 | 全部通过 | 完成 | 不通过 | `FAIL` |
| J. 报告与新产物不匹配 | 新版本产物缺少对应检查结果 | 任意 | 旧版本曾通过 | 不得 `PASS` |
| K. 缺少必要检查结果 | 无法确认强制检查是否通过 | 任意 | 任意 | `INCOMPLETE` 或 `BLOCKED`，不得 `PASS` |
| L. 前置阶段失败 | 前置阶段失败，后续无法执行 | 未执行 | 待确认 | `FAIL` 或 `BLOCKED`，依现有状态语义裁定 |

**重要：** 自动试玩未完成不一定说明游戏不可玩，但在交付策略要求完整试玩的情况下，它仍然不能被当成完整验收通过。后续如果确实需要允许人工豁免，应另行设计显式、可追溯的豁免机制，不在本阶段隐式放行。

---

## 7. 实施方案

### 阶段 A：只读审计现有能力

**目标：** 在修改代码之前，确认现有报告、状态与产物之间的实际关系。

检查范围：

- `qa-report.json` 的 schema 和生成位置。
- `create`、`build`、QA、site 之间的数据传递。
- headless playable smoke 的执行入口与结果结构。
- `inspectPack` 和 `reviewPack` 的实际输出。
- 现有 run/version 目录与资源包标识。
- 失败时报告是否仍然生成。
- 报告是否可能引用旧版本产物。
- 视觉人工评审结果目前是否已有存储机制。

交付物：

1. 现有能力清单。
2. 当前报告结构。
3. 产物版本关联图。
4. 缺失字段和状态语义清单。
5. 最小改动建议。

约束：

- 不进行付费生图。
- 不修改正式产物。
- 不修改版本目录或失败账本。
- 不新增依赖。
- 不修改契约、CLI 或 MCP 的公开接口。

### 阶段 B：补齐报告契约与状态计算

**目标：** 用最小改动建立统一验收语义。

实施内容：

1. 基于现有 `qa-report.json` 扩展必要字段。
2. 为各检查项建立一致的状态映射。
3. 实现最终交付状态的确定性计算。
4. 绑定报告与资源包、配置及站点产物。
5. 接入现有试玩结果。
6. 增加视觉评审状态的记录方式。
7. 为关键状态组合补充自动化测试。

实施原则：

- 不重写已有 QA 规则。
- 不重复实现背景覆盖、图集校验等已有能力。
- 不新增平行的执行状态系统。
- 不因为新增报告而改变既有资源生成行为。
- 对缺少的数据显式标记，不推断为通过。

### 阶段 C：使用已有产物完成验收

**目标：** 验证统一报告是否能正确解释真实生成结果。

使用现有已生成产物进行测试，优先覆盖：

- 最新成功的端到端生成结果。
- 最新的 3/4 headless smoke 结果。
- 资源或配置失败的既有测试夹具。
- 站点构建失败的既有测试夹具。
- 新旧资源包报告关联。
- 视觉评审待确认与通过的状态切换。

随后完成尚未完成的 P0-06 视觉人工对照，确认报告能正确记录该结果。

如果现有产物不包含某类必要证据，应明确记录该缺口。除非没有其他可行验证方式且获得明确批准，否则不应为了补充测试数据直接触发付费生图。

## 8. 测试策略

### 8.1 单元测试

覆盖：

- 各阶段状态到统一状态的映射。
- 最终交付状态计算。
- 缺失检查结果的处理。
- 新版本与旧版本的关联隔离。
- 视觉评审状态更新。
- 自动试玩失败分类。
- 失败、未完成、阻塞和通过之间的区别。

### 8.2 集成测试

验证：

- `create → build → QA → site` 的报告关联。
- 站点构建失败时的报告结果。
- headless smoke 未完成时的状态传递。
- 资源包版本变化后旧报告不会误用于新产物。
- 视觉评审结果能够进入最终报告。
- 报告生成异常不会被静默解释为成功。

### 8.3 回归测试

确保：

- 现有资源生成行为没有发生非预期变化。
- 现有资源包校验仍然有效。
- 背景覆盖率门禁仍然有效。
- 现有动画网格推导和相关验证不受影响。
- 固定 Runtime 与站点构建行为不受影响。
- CLI/MCP 现有接口没有未经批准的破坏性变更。

### 8.4 真实产物验证

至少完成一次不依赖新付费生成的真实产物验收，输出：

- 统一报告。
- 产物版本关联结果。
- 自动试玩结果及证据。
- 视觉评审状态。
- 最终交付结论。

如果只完成了模拟数据测试，不得声称真实端到端交付验收已经完成。

## 9. 非功能要求

### 9.1 可追溯性

报告中的每一个重要结论都应能够追溯到具体检查结果或评审记录。

### 9.2 确定性

对于相同的产物与相同的检查结果，最终状态计算必须一致。

### 9.3 低成本

优先复用已有报告、日志、资源包和站点，不以重复调用付费模型作为常规验收步骤。

### 9.4 版本安全

历史报告不能被新产物覆盖或错误复用。继续遵守仓库现有的版本目录和失败产物保留约定。

### 9.5 最小改动

优先修改现有报告生成、结果聚合和测试逻辑。若确实需要新增契约、CLI/MCP 接口或依赖，应先明确必要性和兼容性，再单独裁定。

## 10. 完成定义（Definition of Done）

只有满足以下条件，才能认为本需求完成：

- [ ] 已完成现有报告、QA、试玩和产物关联机制的只读审计。
- [ ] 已明确最终交付状态及各检查项的状态映射。
- [ ] 已复用或扩展现有 `qa-report.json`。
- [ ] 资源、配置、QA、站点和试玩结果能够进入统一报告。
- [ ] 报告能够区分确定性失败、未完成、阻塞和通过。
- [ ] 自动试玩失败时能够保留步骤和可用证据。
- [ ] 自动试玩器限制不会被自动解释为游戏缺陷，原因未知时也不会被直接认定为试玩器限制。
- [ ] 视觉评审未完成时不会被默认判定为通过。
- [ ] 新版本资源包不会继承旧版本的验收结论。
- [ ] 验收状态矩阵中的核心场景均有自动化测试。
- [ ] 使用已有真实产物完成至少一次端到端报告验证。
- [ ] P0-06 视觉人工对照的结果已完成记录，或明确记录仍未完成及其原因。
- [ ] 全仓测试、相关 typecheck 和回归检查通过。
- [ ] 未发生未经批准的付费生成、公开接口变更或额外依赖引入。

## 11. 后续路线图

本需求完成后，建议按以下顺序推进。

### P1：视觉一致性验收 V1

在交付报告基础上，建立参考风格图、关键资源和最终游戏截图之间的可追溯关系。

优先方向：

- 关键资源的视觉检查证据。
- 最终游戏截图采集。
- 参考图与生成结果的人工对照流程。
- 免费确定性检查与人工/模型辅助评审的职责划分。
- 视觉问题的可定位记录。

不应直接把色板一致性或单一图像相似度当作完整的风格验收结论，也不应在缺乏基线的情况下随意设定分数门槛。

### P2：失败定位与低成本重跑

在已有报告和产物版本关联稳定后，再改进失败定位与局部重跑。

重点包括：

- 识别失败发生在哪个生成或构建阶段。
- 判断哪些中间产物可以安全复用。
- 减少不必要的重复生图和重复构建。
- 继续复用已有失败账本和版本化产物。
- 确保重跑不会覆盖历史证据。

### 暂缓：自动修复与自我进化

在验收标准、失败分类和证据关联尚未稳定之前，不建议优先引入自动修复闭环。

否则系统可能基于错误的失败归因修改资源或玩法，进一步增加调试成本。

---

## 12. 最终决策建议

当前 game-maker 已经具备从游戏意图到可玩站点的主要生成能力，并且最新提交记录了真实端到端 QA 通过的结果。

下一阶段的核心问题不再是简单增加生成模块，而是确保系统能够可靠回答：

**“这一版游戏究竟通过了哪些检查，还有哪些问题未解决，现有证据是否足以支持交付？”**

因此建议：

1. **首先完成 FPVS-V1-P1 交付验收与证据报告。**
2. 随后推进视觉一致性验收 V1。
3. 再改进失败定位和低成本重跑。
4. 在上述基础稳定之后，再评估自动修复是否值得投入。

这条路线复用现有生成、QA、试玩和站点构建能力，优先提高单个游戏项目从创意到交付的可信度，不扩展到跨游戏知识复用或跨项目迁移。
