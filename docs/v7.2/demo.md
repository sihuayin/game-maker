# FPVS-V1-P0：First Playable Vertical Slice

## 从风格图与游戏意图到可启动、可操作、可通关的真实 Demo

- **需求编号**：FPVS-V1-P0
- **优先级**：P0
- **目标仓库**：https://github.com/sihuayin/game-maker
- **实施策略**：先审计，后修改；最小增量；复用现有管线
- **验收范围**：一个游戏项目、一个关卡、一个完整游戏目标
- **最终交付**：真实 Demo、可复现的验收步骤、验收结果及已知限制

---

## 1. 需求目标

使用一张风格参考图和一段游戏意图，通过仓库现有创建管线，生成一个完整、可启动、可操作、能够完成目标的 2D 游戏 Demo。

必须形成以下完整链路：

`风格图 + 游戏意图 → 创建管线 → 设计与资产 → GameConfig → 可启动游戏 → 玩家操作 → 目标完成`

本需求不以静态契约通过、资源生成成功、配置生成成功或站点目录存在作为最终完成标准。

**P0 的唯一核心目标：证明现有创建管线能够交付一个真实可玩的游戏，而不是只交付游戏规格和资源文件。**

## 2. 固定验收案例

采用一个固定的 2D 横版废土寻宝案例。

### 2.1 输入

- 一张废土风格参考图。
- 一段明确的游戏意图。
- 现有创建入口支持的参数。

示例意图：

> 创建一款 2D 横版废土寻宝游戏。玩家控制废土探索者在遗迹中移动和跳跃，找到宝箱并完成寻宝目标。最终画面应使用参考图的配色、轮廓、材质和整体美术风格。

具体输入格式与资源生成方式以当前仓库已有实现为准。

### 2.2 预期结果

系统生成一个无需手工修改中间文件即可运行的 Demo，至少包含：

- 玩家角色。
- 可辨认的场景与地形。
- 可操作的玩家控制。
- 一个具有实际运行时行为的交互对象，例如宝箱。
- 一个明确、可达成的游戏目标。
- 可观察的目标完成反馈。

资源必须实际参与游戏运行，而不只是存在于 AssetPack 中。

## 3. P0 功能需求

### P0-01：现有管线审计与缺口定位

**目标：** 确认现有系统已经具备什么，以及完成真实 Demo 还缺少什么。

工作内容：

1. 检查当前创建入口及其实际调用链。
2. 追踪 GameDesignSpec、AssetPack、GameConfig 到运行站点的连接。
3. 检查现有运行时的资源加载、玩家输入、移动、交互和目标完成机制。
4. 检查现有测试及验收能力。
5. 使用固定验收案例，记录哪些环节已通过、哪些环节失败。
6. 为每个失败定位具体代码位置、调用链或可复现现象。

交付物：

- 当前创建与运行链路说明。
- 已有能力与缺失能力清单。
- 固定验收案例。
- 基线测试结果。
- 按优先级排列的最小修改计划。

**验收标准：**

- 缺口基于代码和实际执行结果，而非推测。
- 每项拟修改内容均能对应到明确的缺口。
- 不提前重构没有证据表明存在问题的模块。

### P0-02：通过现有入口生成完整 Demo

**目标：** 让固定验收案例走通现有创建管线。

工作内容：

1. 复用现有游戏意图解析与设计生成流程。
2. 复用现有资产配方、AssetPack 生成及验证流程。
3. 复用现有 GameConfig 编译及创建流程。
4. 补齐创建产物与最终运行站点之间的必要连接。
5. 确保运行时引用的资源与本次创建产物一致。

**验收标准：**

- 使用现有受支持的创建入口。
- 创建流程不依赖手工修改中间 JSON、GameConfig 或 AssetPack。
- 生成的 Demo 具备完整运行所需的产物。
- 不为固定案例编写绕过通用管线的专用快捷路径。
- 创建结果与本次输入和产物可以相互追踪。

### P0-03：游戏能够启动并加载实际内容

**目标：** 确保生成结果不只是合法文件，而是能够运行的游戏。

工作内容：

1. 确保生成站点可以按仓库支持的方式启动。
2. 确保运行时入口正确加载。
3. 确保玩家、场景及交互对象资源正常加载。
4. 处理阻断初始化或游戏运行的错误。

**验收标准：**

- 有明确、可复现的启动方式。
- 游戏页面能够正常呈现实际场景。
- 关键资源能够正确加载。
- 不存在阻断游戏运行的初始化错误。
- 启动失败能够被识别为验收失败，而不是因创建命令成功就被误判为通过。

### P0-04：玩家能够实际操作

**目标：** 让玩家能够在生成的游戏中完成基本操作。

本案例最低要求：

- 左右移动。
- 跳跃。
- 对交互对象执行约定的交互操作。

若现有运行时已经具备相关能力，应优先复用。

**验收标准：**

- 约定输入能够触发玩家行为。
- 玩家位置或状态发生可观察的变化。
- 场景中的基础地形和碰撞行为不会阻断正常操作流程。
- 交互操作能够改变真实游戏状态，而不是仅显示装饰动画。

### P0-05：游戏目标能够通过真实操作完成

**目标：** 证明 Demo 存在完整的游戏玩法闭环。

固定验收流程：

1. 启动游戏。
2. 控制玩家移动和跳跃。
3. 到达宝箱附近。
4. 执行交互操作。
5. 触发目标完成状态。
6. 观察明确的完成反馈。

**验收标准：**

- 游戏初始状态明确。
- 交互条件与目标完成条件明确。
- 按照验收步骤能够完成目标。
- 未满足条件时，不会错误地进入完成状态。
- 完成状态具有可观察的反馈。
- 不通过手工修改运行时状态、配置文件或调用内部测试函数来代替真实玩家操作。

### P0-06：风格资源实际接入与人工确认

**目标：** 确保风格参考图通过现有管线对最终游戏画面产生实际影响。

工作内容：

1. 确认最终游戏实际加载本次生成或选取的资产。
2. 检查玩家、场景和关键交互对象是否具有可辨认的视觉形态。
3. 保存参考图、关键资源和最终游戏画面的证据。
4. 对整体风格进行人工对照审查。
